## Context

1. SAH-78 (Phase 1) built stores, staff mapping and the store guard, products and units, vendors, approval rules (versioned), numbering series with a gapless counter function, reason lists, print-template settings and an approved, unposted opening-stock import (`docs/database/SAH-78-pharmacy-masters.md`, migrations `V2026_12_17_1000` to `1260`).
2. SAH-79 adds every stock movement: posting opening stock, purchase orders, receiving stock with a vendor payable, vendor returns and debit notes, indents with dispatch and receipt, returns to the Central Store and damage reports, transfers, ward consumption, stock audits, stock adjustments, the approvals inbox, the reorder list and reports (BRD I1 to I10, AC-I1 to AC-I8).
3. Fixed rules that must hold in code **and** in the database (BRD section 2, ADR-028 D6 and D7): stock never negative; the ledger cannot be edited; nobody approves their own request; Schedule X needs a pharmacist and a second signature.
4. Built facts that constrain the design:
   - Persistence is Spring JDBC with hand-written SQL (ADR-028 R3-2). No JPA.
   - The platform colleague PIN check (`platform.api.StaffPinPort.checkColleague`) **must be called outside any transaction**; it names one required team role per call and answers `NOT_ELIGIBLE` without comparing or counting when the person does not fit.
   - The store-access denial audit is written after the caller's transaction ends (ADR-028 R5-1). A request never holds two connections.
   - There is no scheduler, no event registry and no new library allowed (phase 1 limits; DEC-072 standing rules).
   - The IPD module has no public reader of admitted patients by ward. `opd.api.CourseAdmissionSource` and `ipd` internal repositories exist, but nothing in `ipd.api` lists a ward's admitted patients.
   - Billing has no supplier, payable or credit-note concept (OQ-79-5 finding).
5. DEC-072 also says: changes to IPD or billing code sit behind a port with a no-op implementation, are listed for the human, and are reviewed by the IPD session before anyone edits them.

## Decisions

### P1 · One contract file, one module, new feature packages

- **`docs/api/pharmacy.yaml` 0.2.0, additive.** Not a second file. Reasons: ADR-028 D1 gives the module one base path `/api/v1/pharmacy` and one contract; the SAH-79 stories' overlap rule says "One `docs/api/pharmacy.yaml` (architect)"; SAH-79 reuses SAH-78 components (problem types, `StoreForbidden`, `IntegrationOff`, `Rate`, `Percent`, product and store ids) that a second file would have to copy or reference across files, which the existing tooling does not do anywhere in Sahaj. The cost is a long file; every new operation carries `x-sub-story` and `x-work-package`, and the tags group it.
- New feature packages inside `com.sahaj.pharmacy` (ADR-028 D1 named `stock`, `purchase`, `indent`): `stock` (batch, balance, ledger, FEFO, expiry, adjustment, opening-stock posting), `approval` (the runtime engine; the rules stay in the SAH-78 package), `purchase` (PO, receipt, payable, debit note), `indent` (indent, dispatch, receipt of a dispatch, return items, shortages), `storeuse` (return to Central Store, damage report, transfer, consumption), `stockaudit`, `report`. `integration` gains the admitted-patients reader (P14).
- Nothing outside `com.sahaj.pharmacy` depends on it (ADR-028 D1 build check (a) stays).

### P2 · Batch identity, expiry and rates

- `pharmacy.batch`: one row per **product, batch number and expiry** (ADR-028 D6), with `mrp numeric(14,4)`, `purchase_rate numeric(14,4)` per issue unit (the latest receipt's, OQ-79-6), `vendor_id` (the vendor of the latest receipt; null for opening stock, OQ-79-11), `first_received_at` (FEFO tie-break), `source` (`OPENING_STOCK` / `GRN` / `FOUND`).
- **Expiry** is a `date`: the last day of the month when typed as month and year (OQ-79-7); the opening-stock file keeps its full date. A batch is usable through `expiry_date` and expired when `expiry_date < today (Asia/Kolkata)`. Screens show "Mar 2028".
- **MRP clash** (BR-10): the same product, batch number and expiry with a different MRP is refused, 409 `batch-mrp-mismatch`, naming the lines; nothing is posted.
- **Case of batch numbers (OQ-79-37, OPEN).** Interim holding: the batch match ignores case and leading or trailing spaces, as the SAH-78-7 import already does (ADR-028 R4-5, built). The table keeps `batch_no` as first received (shown as typed) and a generated `batch_key = upper(btrim(batch_no))`; the unique key is `(tenant_id, unit_id, product_id, batch_key, expiry_date)`. If the pharmacist decides that case matters, a forward migration replaces this unique index by one on `batch_no` (a relaxation: no existing row can violate it) and the matching code compares `batch_no`; no data moves. If the pharmacist confirms the interim, nothing changes. This is a holding, not a business rule; the human is asked in the handoff.
- **Rates.** Every receipt line keeps its own rate, discount, free quantity and GST; the batch shows the latest purchase rate (OQ-79-6). Landed per issue unit = (billed quantity × PTR × (1 − discount %)) ÷ ((received + free) × conversion), held to 4 decimals, without GST. Margin = (MRP − landed) ÷ MRP, one decimal, "—" when there is no rate. Stock value = quantity × the batch's purchase rate, rounded half up to the paisa per batch, then summed (G-13).

### P3 · Stock balance and the append-only ledger

- **States** (BR-4): `AVAILABLE`, `IN_TRANSIT`, `PENDING_RETURN`, `QUARANTINE`. Only `AVAILABLE` and unexpired is usable. No fifth state: a shortage is In transit units with an open `shortage` row (OQ-79-18); held vendor-return units are `PENDING_RETURN` at the Central Store with an open debit-note line (OQ-79-12).
- **`pharmacy.stock_balance`**: one row per `(store, product, batch, state)` with `qty integer` and `check (qty >= 0)`; `product_id` is denormalised from the batch for FEFO and store views. It is a projection of the ledger, changed only by the posting service in the same transaction as its ledger lines. Rows are never deleted; a zero row stays.
- **`pharmacy.stock_ledger`**, append-only, range-partitioned by month on `occurred_at`:
  - columns: `id`, `occurred_at` (server time, never from a client), `movement_id` (groups the lines of one movement; a move between stores or states is exactly two lines with the same `movement_id`), `txn_type` (the list in the contract, `LedgerTransaction`), `doc_type`, `doc_id`, `doc_no` (the reference shown; the admission number for patient-wise consumption, never a name), `doc_line_id`, `store_id`, `state`, `product_id`, `batch_id`, `qty_in`, `qty_out` (exactly one above 0), `balance_after` (of that store, batch and state), `actor_kind` (`USER` / `SYSTEM`), `actor_membership_id` (null for SYSTEM, shown "System"), `second_signer_membership_id` (Schedule X), `approved_by_membership_id` (when an approval led to the line), `reason_key`, `reverses_ledger_id` (no FK: a foreign key to a partitioned table would need the partition key; the service checks it), `admission_id` (patient-wise consumption only; an id, never a name);
  - `GRANT SELECT, INSERT` only to `sahaj_app`; row-level deny triggers on `UPDATE` and `DELETE` on the parent (cloned to every partition); a statement-level deny trigger on `TRUNCATE` on the parent **and on each partition** (statement triggers are not inherited); RLS `ENABLE` + `FORCE` on the parent and each partition; `sahaj_app` gets no grant on partitions directly;
  - corrections are new lines: a reversing or adjustment line with `reverses_ledger_id` (79-5).
- **Reconciliation** (79-4, 79-18): for every store, batch and state, the sum of `qty_in − qty_out` equals `stock_balance.qty`. A QA integration test and the ledger report check it; there is no job.

### P4 · FEFO, expiry quarantine without a job

- **Pick.** Every issue, dispatch, transfer and consumption picks `AVAILABLE` balances of the store and product whose batch is unexpired, ordered by `expiry_date`, then `first_received_at`, then `batch.id`. The user never chooses the batch (BR-7). A quantity larger than the first batch is split across batches, each its own pair of ledger lines. Batch-specific actions (vendor return, adjustment, count, damage report, return to Central Store) name the batch.
- **Preview.** `GET /stores/{storeId}/stock/fefo-pick` answers the batches the server would pick now; the posting picks again under locks, and the result may differ if stock moved in between (the answer of the posting is what happened).
- **Expired stock in a movement.** Inside any movement, after the balance rows are locked (P5), every locked `AVAILABLE` row whose batch has expired is first moved to `QUARANTINE` (ledger `EXPIRY_QUARANTINE`, actor SYSTEM, reason `damage.expired`), then the pick runs. So an expired batch is never picked, even if no screen was read first.
- **Expired stock in a read** (79-3 "the first screen that finds it"). Stock reads of a store (`/stock/overview`, `/stock/batches`, `/stock/products/{id}`, the reports for that store) run in a read-write transaction that first sweeps that store: it selects `AVAILABLE` rows with `qty > 0` and an expired batch `FOR UPDATE SKIP LOCKED`, moves them as above, then reads. `SKIP LOCKED` means a read never waits on a busy row; a skipped row is held by a movement that sweeps it itself. Index for the sweep: `(tenant_id, store_id, state) where qty > 0` on the balance, joined to the batch by `expiry_date`. Cost: a read may write a few ledger lines once per expired batch; nothing writes when nothing has expired.
- An expired batch can never be received into, accepted back into or released to `AVAILABLE` (409 `batch-expired`).

### P5 · Posting: all or nothing, one service, a fixed lock order

- **One posting service** (`stock.StockPosting`) writes every ledger line and balance change. Feature services build a list of moves (`from (store, state)` → `to (store, state)`, batch or FEFO request, quantity, reason) and call it inside their own transaction. All lines of one document action are in one transaction; any refusal rolls everything back (BR-5, BR-6).
- **Lock order** (every transaction that changes stock or decides an approval takes locks in this order, and only the ones it needs):
  1. `store` rows (ascending id): the store whose action it is, and every store whose `has_stock` flips from false to true. The store row lock is always taken **first** (as built after DEC-077; ADR-028 R7-1), so the open-import checks of ADR-028 R5-2 and the ACTIVE re-check of the opening-stock `start`, `submit` and `approve` are ordered against a store switch-off;
  2. the `approval_request` row (`FOR UPDATE`) when an approval decision drives the action;
  3. the document header (`FOR UPDATE`, checked against `version`);
  4. the `document_counter` row, through `pharmacy.next_document_no()`, when a number is taken;
  5. `product` rows whose `has_stock` flips (ascending id). **Amended (code review R3-3, DEC-077 item 1; ADR-028 R7-1, R7-2):** product edits (`pharmacyUpdateOwnProduct`, `pharmacyPutLocalSettings`) lock the product row `FOR UPDATE` **before** their open-import and has-stock checks, and take no store, import or balance lock, so no cycle is added; the opening-stock line write reads every product it matches `FOR SHARE` after the import lock (store, import, products). Until DEC-077 neither lock was built, which left one residual race: a units change or switch-off of a product could commit between a line write's product check and its insert (the FK takes only `FOR KEY SHARE`), so an open file could point at a product whose units had changed. DEC-077 closes it with these two locks and with `submit` flagging a line whose product is no longer ACTIVE;
  6. `batch` rows to create or top up (ascending `product_id`, `batch_key`, `expiry_date`; create with `INSERT … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE`);
  7. `stock_balance` rows: first insert the missing destination rows in the same order with `ON CONFLICT DO NOTHING`, then lock **every** balance row of each involved `(store_id, product_id)` with one `SELECT … ORDER BY store_id, product_id, batch_id, state FOR UPDATE`; FEFO is computed in memory from the locked rows;
  8. inserts: ledger lines, document lines and status, audit.
- **Known residual: a store switch-off racing an approval-driven posting (19 Nov 2026, code review m-7, DEC-082; migration 1740 comment).** Serialised against a switch-off, because they take the store row lock (step 1) first and re-check the store is ACTIVE: opening-stock start, submit and approve; every person-driven posting of a store operation (the store guard reads the store, then the posting locks it). Not serialised: a posting driven by `pharmacyDecideApproval` (a stock adjustment, an audit variance, a damage write-off or send-to-Central-Store) locks the approval request (step 2) and the balances, and the has-stock trigger reads the store from its own snapshot. A switch-off that commits between the decision's read and its commit can therefore leave a store that is no longer ACTIVE holding stock (its `has_stock` true). Nothing is lost or invented: the ledger and balances stay consistent, the stock is visible to the owner, and switching the store back on, or a later fix that takes the store row lock in the decision path, settles it. Accepted as a known limit for Phase 2; the fix (the store row lock `FOR SHARE` first in the decision path, before the request lock, which keeps step 1 before step 2) is a candidate for the run after WP-F.
- Lock waits use the existing lock and statement timeouts; a timeout or a deadlock (SQLSTATE `55P03`, `57014`, `40P01`) answers 503 `database-busy` with nothing saved (DEC-054), and the client retries with the same `clientKey`.
- **Never negative** (BR-6): the service refuses with 409 `insufficient-stock` carrying `available` (and the line) before writing; the `check (qty >= 0)` is the database backstop. Two users taking the last unit: the second waits on the balance lock, then sees the new quantity and gets 409.
- **Idempotency.** Every create and every post carries `clientKey`. A generic `pharmacy.client_request (tenant_id, membership_id, client_key, operation, subject_id)` row is inserted in the same transaction; the same key from the same caller answers the current state of the first result (200, nothing written); another caller 409 `client-key-reused` (existing rule 10). **Concurrent replays (DEC-082, security L15; contract 0.3.4 rule 10):** when the insert finds the key taken (`take` returns false), the service re-reads the row: the same member, operation and subject answers as a replay; another operation or subject 409 `client-key-reused`. The key stays unique per member (no new index). Posts on an existing document also carry `version` (409 `changed` with `current` when old).
- **Opening stock posting** (79-1, OQ-79-30): one transaction for up to 5,000 lines (OQ-79-35). The import row is locked first (it is the document); `opening_stock_import.posted_at` set once, guarded by a check and the import trigger (an APPROVED row may change only `posted_at`, `posted_by` and `version`, once); a second post answers 409 `already-posted` with `postedAt`. Batch creation and balance locking follow steps 6 and 7. Lines expired at posting time go to `QUARANTINE` with reason `damage.expired` (OQ-79-30). A batch MRP clash stops the whole posting with 409 `batch-mrp-mismatch` listing up to 100 row numbers. The statement timeout for this one operation is raised to 60 s (java-developer config, a `SET LOCAL statement_timeout` in that transaction); the page shows "Posting. Do not close this page.".

### P6 · Approval engine runtime (ADR-028 D7 made exact)

**Structures.**
- `pharmacy.approval_request`: `transaction_type` (the nine types of D7; SAH-79 uses seven: `PURCHASE_ORDER`, `GRN_RATE_RISE`, `VENDOR_RETURN`, `INDENT`, `STOCK_TRANSFER`, `WRITE_OFF`, `STOCK_ADJUSTMENT`), `subject_type` (`PURCHASE_ORDER`, `GOODS_RECEIPT`, `DEBIT_NOTE`, `INDENT`, `TRANSFER`, `DAMAGE_REPORT`, `SHORTAGE`, `STOCK_ADJUSTMENT`, `STOCK_AUDIT`), `subject_id`, `subject_no` (the document number when it has one), `rule_store_id` (the store whose HOD is the "store approver", BR-14), `raised_by` (membership id), `raised_at`, `rule_version_id` (the version used, BR-12), `amount_paise` (BR-17), `has_schedule_x`, `has_high_value_item`, `urgent`, `max_rate_rise_percent` (GRN only), `escalate_after_minutes` (resolved at submit: the urgent minutes for an urgent indent, else hours × 60, else null), `current_level` (1 or 2, null when finished), `status` (`PENDING`, `APPROVED`, `REJECTED`, `WITHDRAWN`), `version`. `unique (tenant_id, subject_type, subject_id) where status = 'PENDING'` (one open request per document). Select, insert, update; no delete.
- `pharmacy.approval_request_level`: the copy of the rule kept at submission: `level_no`, `approver_kind` (`STORE_APPROVER` / `OWNER`), `condition_kind`, `amount_paise`, `percent`, `store_types`, `applies` (the condition's result at submit), `rule_text` (the "Rule" column, for example "PO above ₹ 50,000", "Rate up more than 5%", "Sending store HOD", "Schedule X item"). Select and insert only.
- `pharmacy.approval_decision`, **append-only** (select and insert; deny triggers on update, delete, truncate): `request_id`, `level_no`, `decision` (`APPROVED` / `REJECTED`), `decided_by`, `raised_by` (a copy, so the check is row-local), `acting_as` (`HOD`, `DELEGATE`, `OWNER`, `ESCALATED`), `reason_key`, `note` (≤ 300), `decided_at`. Checks and keys: **`check (decided_by <> raised_by)`** (BR-13, the fixed rule in the database); a trigger refuses a row whose `raised_by` differs from the request's; `unique (tenant_id, request_id, level_no)` (one final decision per level; a second decider gets 409 `already-decided`); `unique (tenant_id, request_id, decided_by) where decision = 'APPROVED'` (the same person cannot approve both levels, OQ-79-28); `reason_key not null` when `REJECTED`.
- Withdrawal: cancelling a document that waits (OQ-79-19) sets the request `WITHDRAWN`; no decision row.

**Submit.** The document's service calls `ApprovalEngine.submit(subject)` in the document's transaction. The engine reads the rule set's current version, writes the request and its level copies, evaluates each level's condition once (`ALWAYS`; `ABOVE_AMOUNT`: `amount_paise > amount`; `ABOVE_PERCENT`: GRN rate rise only, `max_rate_rise_percent > percent`, and `SALE_DISCOUNT` in SAH-80; `SCHEDULE_X_ITEM`; `HIGH_VALUE_ITEM`: a line's value above the version's `high_value_threshold_paise`; `URGENT_PRIORITY`; `STORE_TYPE`: the rule store's type is in the list). If no level applies, it writes **no request** (level 0, BR-12; story 79-2 "no inbox item is created") and the document proceeds at once. A rule change later does not touch the copy (BR-12). **No saved rule set (QA D-5, 19 Nov 2026):** the engine evaluates the Standard preset that `GET /approval-rules` serves at `versionNo` 0 (owner levels, condition ALWAYS), never "no levels", so a Store user cannot approve their own purchase order or post their own adjustment before an owner saves rules (N4).

**Amount basis** (BR-17, OQ-79-36): purchase order = its total including GST; every other type = Σ quantity × the batch's purchase rate per issue unit, without GST (for an indent and a transfer, before dispatch, the latest purchase rate of the product at the issuing store's FEFO batches; a product with no rate counts 0); for a GRN rate rise = the value of the lines whose rate rose. Architect reading of "the batches involved"; confirm with the accountant (G-13).

**Rule store** (BR-14): indent → requesting store; transfer → sending store (OQ-79-20a); write-off from a damage report → the reporting store; write-off from a shortage → the store that settles it (the Central Store for an indent, the sending store for a transfer); stock adjustment and audit → the store adjusted or counted; purchase order, rate rise and vendor return → the Central Store.

**Who is the current approver** of a pending request at its `current_level` (worked out on every read and on every decision, never stored per person):
- `STORE_APPROVER`: the rule store's ACTIVE `APPROVER` mapping (`acting_as HOD`), or its CURRENT `DELEGATE` (IST dates, `acting_as DELEGATE`). A member who cannot sign in, or whose mapping needs review, does not count. If neither exists, every owner (`acting_as OWNER`, BR-14 "HOD absent").
- `OWNER`: every owner (`acting_as OWNER`).
- Escalation (BR-16, OQ-79-29): when `now − raised_at` (or the time the request reached level 2) is longer than `escalate_after_minutes`, the item is marked "Escalated" and also shows to the next approver: for a `STORE_APPROVER` level, every owner (`acting_as ESCALATED`); for an `OWNER` level there is no next approver, the mark only. Computed at read time; no job, no notification.
- Excluded always: the raiser (BR-13), and for level 2 whoever approved level 1 (OQ-79-28). If the set is then empty, the item shows "Needs another approver" to the next approver (the owners), and to the raiser on the document; if that set is also empty (a one-owner clinic whose owner raised it), the item waits and the document says "Ask another person to approve this" (OQ-79-28). Nothing is bypassed.

**Decide.** `POST /approvals/{requestId}/decision` (one operation for every type). In one transaction: lock the request (`FOR UPDATE`), check `status = PENDING` and the `level` and `version` sent (else 409 `already-decided` with the current state), check the caller is a current approver (else 403 `self-approval` for the raiser, 404 for anyone who is not an approver, the raiser or an owner), insert the decision, then call the subject's handler (below). Final approval sets `APPROVED` and the handler lets the document proceed (for a stock adjustment, a damage report, a shortage write-off and an audit, the handler **posts** in the same transaction, with the approver recorded on the ledger lines). A rejection sets `REJECTED`; the handler returns the document to its raiser with the reason; no stock moves (except the damage-report outcome of 79-14, released or kept by the HOD's choice). Level 1 approval of a two-level request sets `current_level = 2`.

**Subject handlers.** Each later package registers an internal `ApprovalSubjectHandler` (`subjectType`, `validateDecision`, `onApproved`, `onRejected`, `summary` for the inbox row). The engine and the inbox (WP-D) never change when a package adds a type (story overlap rule). Type-specific decision input travels in the one decision body: `indentLines` (INDENT, story 79-10: approved quantities and remark) and `damageRejectOutcome` (WRITE_OFF from a damage report: `RELEASE_TO_AVAILABLE` or `KEEP_IN_QUARANTINE`); any other type sending them gets 400.

**Inbox.** `GET /approvals/inbox` lists pending requests for which the caller is a current approver (including escalated and "Needs another approver"), across the stores of the unit; sorted urgent first, then escalated, then longest waiting; counts per chip (All, Indents, Purchase, Stock); chips with no built type are not answered. Access: PHARMACY_ACCESS and the caller is an owner, or an ACTIVE `APPROVER`, or a CURRENT `DELEGATE` of at least one store; else 403 `forbidden` (story 79-2). Each row links to the document's review step.

**Opening stock** keeps its own fixed rule ("a different owner approves", ADR-028 D7) and is not an engine request.

### P7 · Schedule X: pharmacist plus a second signature (BR-32, OQ-79-8)

- **Who handles.** A Schedule X line (product schedule `X`) may be received (receipt of a GRN, of a dispatch, of a transfer, acceptance of a return), dispatched, transferred, counted, adjusted, returned, reported damaged, handed to a vendor or consumed only by a caller whose **team role is PHARMACIST** and who is mapped to the store. Never the owner, never Store staff, never a nurse (OQ-79-8: a nurse cannot record Schedule X consumption). Otherwise 403 `schedule-x-pharmacist` "Only a pharmacist can handle Schedule X items, with a second signature." for that line; on receipts the other lines may still be received (79-12).
- **Second signature.** The body carries `secondSigner { membershipId, pin }`. The pin is never stored, logged, audited or echoed (StaffPinPort contract). Because `StaffPinPort.checkColleague` must run **outside any transaction**, the web layer calls `ScheduleXSignature.verify` **before** the posting transaction: first with `requiredRole = PHARMACIST`; if the answer is `NOT_ELIGIBLE` (nothing compared or counted), once more with `OWNER` (OQ-79-8: a pharmacist or an owner may countersign). The outcomes map to the platform's existing problems: `wrong-pin` 403, `pin-locked` 403, `pin-not-set` 409, `rate-limit` 429, `colleague-pin-limit` 429, `pin-unavailable` 503, `pin-check-failed` 503; `NOT_ELIGIBLE` answers 403 `second-signer-invalid` "The second signer must be another active pharmacist or owner." - Database: `check (second_signer_membership_id is null or second_signer_membership_id <> actor_membership_id)` on the ledger and on each document line table that has a signer. ### P10 · Buying: purchase order, receipt, vendor payable, debit note (WP-E)

- **Purchase order** (79-6, OQ-79-31, OQ-79-32): Central Store only (`purchase`). Statuses `DRAFT`, `WAITING_APPROVAL`, `APPROVED`, `REJECTED`, `SENT`, `PARTLY_RECEIVED`, `RECEIVED`, `CLOSED_SHORT`, `CANCELLED`, `DISCARDED`; "Overdue <n> days" is computed (`delivery_expected < today` and goods outstanding, while `SENT` or `PARTLY_RECEIVED`). Lines in purchase units with `rate` per purchase unit (`Rate`, 4 decimals), `gst_rate` copied from the product at submit, `line_amount_paise` = round half up (qty × rate), `gst_paise` per line round half up. A vendor must be ACTIVE, not Blocked, and supply the Central Store at create and at submit (409 `vendor-blocked`, AC-M5). A Blocked vendor's existing sent PO can still be received (OQ-79-9d).
- **Receipt (GRN)** (79-7): statuses `DRAFT`, `WAITING_APPROVAL` (rate rise), `APPROVED` (rate rise approved, ready to post), `POSTED`, `DISCARDED`. Unique `(tenant_id, vendor_id, lower(invoice_no))` among non-discarded receipts → 409 `duplicate-invoice`. Lines: batch (1 to 20), expiry month and year (not past), `qty` received and `billed_qty` (purchase units), `free_qty`, `ptr`, `mrp` (per issue unit), `discount_percent`, `gst_rate` (from the product), `claim_rate_difference`, `short_action` (`BALANCE_TO_COME` / `CLOSE_SHORT`). Invoice total typed; posting refused (400 `invoice-total-mismatch`) when |typed − computed| > 100 paise (OQ-79-9b, a placeholder for the accountant, G-14).
- **Rate rise** (OQ-79-10): reference rate = the PO line rate (against a PO), else the last posted receipt rate of the same product and vendor (per purchase unit, after discount); no reference → no check. The GRN_RATE_RISE rule decides through the engine: no level → no check; `ABOVE_PERCENT` compares the highest line rise (one decimal; 70.00 → 74.30 is +6.1%); `ALWAYS` means any rise. When a level applies, "Post receipt" becomes "Send for approval (rate ↑)": the receipt is `WAITING_APPROVAL`, nothing posted. **Architect reading (A-1):** on final approval the receipt becomes `APPROVED` and the Central Store user then posts it (the poster, not the approver, is the actor on the ledger, and a Schedule X signature belongs to the poster); an `APPROVED` receipt cannot be edited (`pharmacyReopenGoodsReceipt` returns it to draft; the spent approval no longer covers it, so a rate rise needs a new approval at the next post). On rejection it returns to `DRAFT` with the reason.
- **Posting a receipt**: in one transaction: (received + free) × conversion issue units into the Central Store `AVAILABLE` (ledger `GRN`, reference the receipt number), batches created or topped up (MRP clash 409 `batch-mrp-mismatch`), PO lines updated (`received`, `closed_short`), PO status recomputed, the **vendor payable** created, a **draft debit note** prepared for short-billed lines (billed > received) and for ticked rate differences (OQ-79-9a, 9c), the GRN number taken.
- **Vendor payable** (OQ-79-5 option A, G-19): `pharmacy.vendor_payable` (one per posted receipt: vendor, invoice number and date, `amount_paise` = the typed invoice total, `due_date` = invoice date + credit days, `credited_paise`, `status` `OPEN` / `SETTLED_BY_CREDIT`) and `pharmacy.vendor_payable_entry`, append-only (`INVOICE` +, `CREDIT_NOTE` −, with the debit note id). No payment, no ageing, no accounts export; billing is untouched. Shown on the receipt ("Payable · due 16 Dec 2026") and on the debit note tracking. A credit note is applied to the payables of that vendor oldest due first (the debit note's own receipt first when it came from one); a credit above what is open stays as `unapplied_credit_paise` on the debit note (no negative payable). Architect reading; accountant to confirm (G-19).
- **Debit note** (79-8, OQ-79-11, 12, 13): statuses `DRAFT`, `WAITING_APPROVAL`, `REJECTED`, `CREATED` (approved or level 0: units held), `PICKED`, `HANDED_OVER`, `CREDIT_NOTE_RECEIVED` (also "Adjusted in payable"), `CANCELLED`, `DISCARDED`. Line types `STOCK_RETURN` (a batch, its source state `QUARANTINE` or `AVAILABLE`) and `SHORT_SUPPLY` (a receipt line, no stock). Eligibility: Central Store batches with `vendor_id` = the vendor, in Quarantine, or Available with expiry within the vendor's `return_days_before_expiry`; minus quantities on other open debit notes (`DRAFT` excluded, `WAITING_APPROVAL` and later included until handed over or cancelled). Credit = qty × batch purchase rate × credit % (round half up); GST reversal per line at the product's GST % on the credit (round half up). **On approval or at once for level 0** the stock lines move to `PENDING_RETURN` at the Central Store (ledger `VENDOR_RETURN_HOLD`); if the units are gone, 409 `insufficient-stock` and nothing is held (the approver then rejects or the Central Store cancels). "Handed to vendor rep" (representative name 1 to 80; Schedule X signature) posts `VENDOR_RETURN` out of `PENDING_RETURN`. "Credit note received" (number, date, amount) reduces the payable. Cancel before hand-over moves held units back (`VENDOR_RETURN_RELEASE`) to the state they came from, or to `QUARANTINE` when the batch has expired since.

### P12 · Indents, dispatches, returns, shortages, transfers, consumption, audit (WP-F to WP-H)

- **Shared dispatch and receipt.** An indent dispatch and a transfer dispatch are the same record, `pharmacy.dispatch` (`source_type` `INDENT` / `TRANSFER`, from store, to store, reference, `status` `IN_TRANSIT` / `PARTLY_RECEIVED` / `RECEIVED`), with `dispatch_line` per batch. One receipt per dispatch (DEC-063, OQ-79-2), each line received exactly once (Schedule X lines left by a non-pharmacist: open point Q-1, `PARTLY_RECEIVED` until a pharmacist receives them), by `POST /stores/{toStoreId}/dispatches/{id}/receipt`: per line accepted + rejected = dispatched (400 otherwise); accepted `IN_TRANSIT → AVAILABLE`; rejected for a physical reason `IN_TRANSIT → PENDING_RETURN` at the receiving store plus a **return item**; "Short / not received" stays `IN_TRANSIT` with an open **shortage**. An expired batch cannot be accepted (400, reject it as "Near expiry / expired").
- **Return items** (`pharmacy.return_item`): one per rejected dispatch line, return to the Central Store, and damaged stock sent to the Central Store; `from_store` (holding the units as `PENDING_RETURN`), `to_store` (Central Store, or the sending store of a transfer), batch, quantity, reason, status `WAITING`, `DISPUTED`, `ACCEPTED_SALEABLE`, `ACCEPTED_QUARANTINE`; reply notes in `return_item_note`. Acceptance moves `PENDING_RETURN` at `from_store` → `AVAILABLE` or `QUARANTINE` at `to_store` (ledger `RETURN_ACCEPTED`, two lines). Accepting is whole-item (no partial acceptance is in the mockup or the stories).
- **Shortages** (`pharmacy.shortage`): dispatch line, quantity, status `OPEN`, `CLAIM_OPEN`, `WAITING_WRITE_OFF`, `FOUND`, `WRITTEN_OFF`; settled by the Central Store (or the sending store of a transfer). Found: `IN_TRANSIT` at the receiving store → `AVAILABLE` (or `QUARANTINE` if expired) at the settling store (`SHORTAGE_FOUND`). Transit loss: a WRITE_OFF engine request (rule store = the settling store); on approval `IN_TRANSIT` out (`SHORTAGE_WRITE_OFF`, reason "Transit loss"). Claim from carrier: `CLAIM_OPEN`, settled later as found or written off (OQ-79-18, G-17).
- **Indent** statuses: `DRAFT`, `WAITING_APPROVAL` (shown "Waiting for HOD approval" or "Waiting for owner approval" by level), `APPROVED` ("Approved · with Central Store"), `PARTLY_DISPATCHED` ("Approved · back-order open"), `DISPATCHED` ("Dispatched · in transit"), `RECEIVED`, `CLOSED`, `REJECTED`, `CANCELLED`, `DISCARDED`; receipt chips ("· <n> rejected, waiting for CS", "· <n> short, CS investigating") are computed. Lines keep requested, approved (HOD change and remark), dispatched, received, rejected, short, closed balance, replacement product and reason. Replacement (OQ-79-16): an ACTIVE product of the unit with the same normalised salt and the same schedule (400 otherwise); offered by `GET …/replacement-options`.
- **Return to Central Store** (79-14): RET number; `AVAILABLE → PENDING_RETURN` at once (`STORE_RETURN`); a return item to the Central Store. **Damage report**: DMG number; `AVAILABLE → QUARANTINE` at once (`DAMAGE_QUARANTINE`; a Quarantine batch is reported without a move); a WRITE_OFF engine request; on approval `WRITE_OFF` out of `QUARANTINE`, or `QUARANTINE → PENDING_RETURN` plus a return item for "Send to Central Store"; on rejection the HOD's outcome `RELEASE_TO_AVAILABLE` (not if expired, `DAMAGE_RELEASE`) or `KEEP_IN_QUARANTINE`. Level 0 applies the chosen outcome at once.
- **Transfer** (79-15, OQ-79-20): no draft; created and submitted in one step (TRF number); the sending and receiving stores are active stores of the unit, different, and the receiving store is never the Central Store (400). Statuses `WAITING_APPROVAL`, `APPROVED`, `IN_TRANSIT`, `RECEIVED`, `REJECTED`, `CANCELLED`; "Not received · <n> h" computed from the rule's transfer escalation hours (default 24) and shown to both stores' HODs as a mark on the transfer lists of both stores (it is not an approval item). One dispatch of all lines by FEFO (409 `insufficient-stock` if the sending store no longer has enough).
- **Consumption** (79-16): `pharmacy.consumption` (type `GENERAL` / `PATIENT`, purpose, admission id, ordered-by membership id or typed name, `charge_status` `NOT_APPLICABLE` / `CHARGE_PENDING`, optional `stock_audit_line_id`), lines per batch picked by FEFO; ledger `WARD_CONSUMPTION` or `WARD_CONSUMPTION_PATIENT` with `doc_no` = "Ward general" or the admission number. Never edited or deleted. SAH-80 posts every `CHARGE_PENDING` entry through T5 when the human approves it (DEC-072 answer 2).
- **Stock audit** (79-17, OQ-79-26): AUD number at start; one open audit per store (`unique (tenant_id, store_id) where status in ('COUNTING','WAITING_REVIEW','WAITING_APPROVAL')`); lines per batch with Available stock (or chosen products) at start. **Blind count**: the counter's operations (`count-sheet`, `counts`) never answer a system quantity, a difference or a value; the schemas have no such field, and a QA test asserts it. Extended to every stock read for a caller without `reviewCount` by note N3 (DEC-080 L12, contract rule 24). Submit fixes `book_qty` per line (the `AVAILABLE` balance at that moment) and `book_ledger_id` (the last ledger line of that store, batch and state). Review (`reviewCount`) sees system, counted, difference and value. "Stock moved since the count": any ledger line of that store, batch and `AVAILABLE` after `book_ledger_id`, except consumption lines linked to the audit line ("Post as consumption instead", which also lowers the line's book quantity). Approve and post submits a STOCK_ADJUSTMENT engine request (subject `STOCK_AUDIT`, amount = Σ |difference| × rate, raiser = the person who submitted the count) and, when the reviewer is a current level-1 approver, records the reviewer's level-1 approval in the same transaction (one button, as the mockup); approval posts `STOCK_AUDIT_ADJUSTMENT` lines; a decrease above Available at posting refuses that line with 409 `insufficient-stock` and returns it to recount (the request stays decided; the audit then needs another review for the recounted lines). Rejection returns the audit to counting.

### N2 · Note (19 Nov 2026): migration ordering, a lesson from the SAH-78 QA round (programme DEC-061; contract 0.3.1)

A rule for the db-engineer and for every reviewer of a Flyway change in the pharmacy schema (and any other schema).
- **A replaced function takes its final body from the highest version.** When more than one migration runs `create or replace function` on the same function (for example a guard or trigger function), the body that stays in the database is the one in the highest-numbered migration that ran, whatever order the changes were designed in. A later-numbered migration must therefore carry forward every change made by any earlier-numbered one; it never states only its own change. Before writing a replacement, read every earlier migration that touches the function and start from the latest body.
- **A reserved range must lie above the highest applied version.** With `outOfOrder` false (the default), Flyway does not apply a pending migration whose version is below the highest applied one, and validation reports it as resolved but not applied. The SAH-78 hardening range `1270` to `1290` (`V2026_12_17_1270` opening-stock import hardening, `1280` document counter `last_issued_at`, `1290` vendor credit levels) sits below the Phase 2 range `1300` to `1390`, so a database that has already applied `1300` sees `1270` to `1290` as out of order: it must be migrated once with `outOfOrder` (dev only, a human decision) or be recreated (`scripts/setup/create-database.mjs`). New work takes a range above the highest version on `main` and every open branch at the time it starts.
- **This round's fix.** The guard-function correction is migration `1710` (`V2026_12_17_1710__pharmacy_opening_stock_import_guard_merge.sql`, db-engineer), above every applied version; it carries the full function body including the changes of the earlier migrations.
- **Contract 0.3.1 clarification of N1.** `numbersIssued` means a number of the doc type has been issued in the **current financial year**, so it is true exactly when `PUT /document-series/{docType}` answers 409 `series-locked`. This replaces the last sentence of the N1 series-locking item ("keeps its meaning ... ever taken").
- **Consequence.** No boundary, module dependency or tenant rule changes. Reviews of a migration that replaces a function compare its body with the body of the highest earlier version, and check that the new version number is above every applied one.

### N3 · Note (19 Nov 2026): review round 4 decisions that bind Phase 2 (DEC-080; contract 0.3.2)

Recorded here because every SAH-79 package builds on them. Security review round 4 (`docs/reviews/SAH-78-security.md`), findings L11 to L14.
- **L11 · numbering against a series edit (P5 step 4, P9).** `pharmacy.next_document_no()` reads the unit row `FOR SHARE` before it touches `document_counter`; a series save (`PUT /document-series/{docType}`) holds the same unit row `FOR UPDATE`.   | `receiveScheduleX` (`RECEIVE_SCHEDULE_X`) | receiving | `pharmacyPostGoodsReceipt` (goods receipt posting), `pharmacyReceiveDispatch` (receipt of a dispatch, lines not skipped), `pharmacyListSecondSigners` (the signers read, as built) | yes (not for the read) |
  | `handleScheduleX` (checked as `RECEIVE_SCHEDULE_X` until a separate one is needed) | handling | `pharmacyDispatchIndent`, `pharmacyDispatchTransfer` (dispatch); `pharmacyAcceptReturnItem` (accepting a return); `pharmacySettleShortage` (settling a shortage, FOUND); `pharmacyHandOverDebitNote` (the vendor-return hand-over); `pharmacyCreateStockAdjustment`, `pharmacyCreateStoreReturn`, `pharmacyCreateDamageReport`, `pharmacyCreateConsumption`, `pharmacySubmitCount`, `pharmacySubmitVarianceForApproval`; `pharmacySaveCounts` | yes, except `pharmacySaveCounts` |

  The second-signers read is needed by both rows. As built it requires `RECEIVE_SCHEDULE_X`; that is correct while the sets are equal. If the flags ever differ, the read must accept a caller with **either** flag at the store (the contract says so); no code change now.
- **WP-F wording (contract 0.3.5).** A dispatch line's held quantity is the quantity dispatched and in transit (not yet received); back-order is approved minus dispatched so far, kept open by `BACK_ORDER`. A `PARTLY_RECEIVED` dispatch is received again with only the lines not yet received (Q-1 below is closed this way: a non-pharmacist skips the Schedule X lines, a pharmacist receives them later; each line is received exactly once). An indent approval with every approved quantity 0 is refused (400 `indentLines`, "Reject the indent with a reason instead"). `Indent.chips.rejectedWaitingCs` is the rejected quantity still waiting for the Central Store; `shortInvestigating` the shortage not yet settled. `ApprovalSummary` carries `requestVersion` and `levelNo`. `MyStore.issuesFrom` names the issuing store before a draft exists. The expired-batch reason key is the seeded `receipt-reject.near-expiry` (the contract's earlier `near-expiry-expired` was never seeded).

### N5 · Note (20 Nov 2026): review round 6 decisions that bind Phase 2 (DEC-083; contract 0.3.6)

- **Context.** The round 6 security review found that a dispatch can outgrow its receipt (M4), that an approver can raise indent quantities past a value-based level (L20), a field-name slip on the second signer (L21) and a Schedule X write-off without a pharmacist (I23). DEC-083 decided each; the contract text is 0.3.6.
- **M4 · the dispatch matches the receipt cap.** A dispatch is received in one body of at most 400 lines, and every line not yet received must be sent. So the dispatch side is capped too: after the FEFO pick under the locks, more than 400 dispatch lines (one per product and batch) is refused with 400 `lines` "Split this dispatch into smaller ones.", nothing posted. The same rule binds `pharmacyDispatchTransfer` when 79-15 is built. Options: (a) the dispatch cap, chosen: one check, nothing can be stranded in transit; (b) raise the receipt cap and page the receipt in the client: rejected, it makes "each line once" span several requests and widens the receipt race. A Schedule X PIN verified before the refused transaction is spent (it is checked outside the transaction by design, P7); accepted, as for any other refusal after the PIN.
- **L20 · an increase belongs to the last level.** The levels are fixed at submit from the requested value (P6). An approved quantity above the requested one is allowed only at the last level that applies to the request, or to an owner; otherwise 400 `indentLines` "This increase needs the next approver.". Rejected option: working the value out again from the approved quantities and re-routing the request (a level could appear mid-decision; harder to explain on screen).
- **L21.** A `secondSigner` without `membershipId` is field `secondSigner`; the pin format is `secondSigner.pin` (P7 "PIN format first" unchanged otherwise).
- **I23 · a level-0 Schedule X transit loss needs a pharmacist.** `pharmacySettleShortage` TRANSIT_LOSS that the WRITE_OFF rule writes off at once (level 0) on a Schedule X product needs a mapped pharmacist (`handleScheduleX`), else 403 `schedule-x-pharmacist`. No second signature: `SHORTAGE_WRITE_OFF` stays off the P7 list (the units are already lost; nothing is handed over). With a level 1 or 2 rule the approver decides as before.
- **I24, I26 (java and db; no contract change).** A dispatch line is Schedule X when its dispatch copy or the product is Schedule X at receipt time; an adopted product's schedule is read in one order everywhere (the product's own value, then the catalogue's), as the ledger trigger does.
- **Rule 24 and quantity messages.** The over-stock messages of the store return and the damage report carry the stock number ("Enter a whole number from 1 to <n>."); for a caller blind at the store on a product of its open audit they carry none ("This is more than the quantity in stock."), so the blind count cannot be read through a validation message.
- **Consequence.** No boundary, module dependency, tenant rule or table ownership changes; no migration. One new read (`pharmacyListTransferStores`, store names of the caller's own unit, guarded like the transfer create), response members added (`moreWaiting`, `HeldBill.products`, report group `label`) and seven StoreAccess flags made required.

## Consequences

**Positive**
- Every fixed rule has a database backstop: `qty >= 0`, append-only ledger and decisions, `decided_by <> raised_by`, one approval per person per request, second signer ≠ actor.
- One posting service and one lock order: no lost update, no deadlock between pickers; FEFO and expiry are enforced at the only place stock moves.
- The approval engine and inbox are written once (WP-D); later packages register handlers.
- Patient-wise consumption is designed and testable now, and switched on by one adapter after the IPD approval, with no contract change.
- No job, no new library, no new extension, billing untouched.

**Negative / accepted costs**
- Stock reads may write (expiry sweep); they run read-write with SKIP LOCKED.
- Locking every balance row of a (store, product) serialises movements of the same product in the same store (intended: the last unit cannot be taken twice).
- Partitions must be extended by a migration before Apr 2030.
- The contract file grows to about twice its size.
- Several choices (A-1 to A-7, OQ-79-37 interim) are architect readings to confirm; each is reversible without data loss.
