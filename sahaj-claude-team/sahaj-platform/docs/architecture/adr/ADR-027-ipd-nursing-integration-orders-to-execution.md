Reference screen (human-approved design, DEC-055 answer 2): "Nursing workspace · one patient" (`reference/Nursing_workspace_one_patient/Main.dc.html`), only for the parts named in the stories.
Module: ipd (patient data through `patient.api`; team, PIN, audit and entitlement through `platform.api`)
Status: PROPOSED (15 Nov 2026), with `docs/api/ipd.yaml` 0.4.0. Accepted when the human writes `SAH-76 · contract · APPROVED`. `stories` is APPROVED (docs/approvals.md, 15 Nov 2026).
Deciders: Ganesh (human), tech-lead; recorded by solution-architect
Related: ADR-006 (D1 clinical event, D4 admission row lock, D7 templates), ADR-009 (order lifecycle, safety check, catalogue, D10 lock), ADR-010 and ADR-014 (staff PIN, colleague check), ADR-011 (MAR, computed slots, append-only dose), ADR-012 (Medicine round), ADR-013 (card flags), ADR-017 (ward scope guard), DEC-054 (503 database-busy), DEC-055 (programme answers), `docs/requirements/SAH-76.md` (BR-1 to BR-18, OQ-76-1 to OQ-76-29), `docs/stories/SAH-76.md`, the spec sections 2, 5, 6, 7.

## Context

1. Built (SAH-30 to SAH-35, SAH-38): `ipd.medicine_order` (one row per order, statuses PENDING, ACTIVE, REJECTED, STOPPED, one-way transitions under a guard trigger, `version` = row change counter); `ipd.dose_administration` (append-only, unique per order and slot, no undo: ADR-011 D1); slots computed per day from four fixed frequencies by `DoseSlots` (ADR-011 D2) and reused by the Medicine round (ADR-012) and the tab count; `VitalsDue` fixed at 240 minutes; settings in the lazy row `ipd.config`.
2. The approved spec (DEC-055) asks for: dose, route, start, duration, priority, PRN and STAT; change as new versions with past doses kept on their version; hold, resume and stop with reasons; a nurse inbox with acknowledgement; pharmacist query and retrospective review of STAT doses; a medicine scan and a manual override; a 10-second undo and "recorded in error"; ward profiles and settings; audit with before/after and a device label.
3. The requirement's architect checks: (a) stored dose events and a scheduler, or computed slots plus correction records; (b) an order and version model that lab, nursing, monitoring, diet and device orders (A4 to A9) reuse without rework.
4. Phase 1 limits (CLAUDE.md, DEC-055 answer 3): no push, SSE, WebSocket, notifications, devices, documents or analytics; in-app badges and polling only. No new module, library or service may be added without the human.
5. The 503 `database-busy` problem (DEC-054) is built in the platform handler (`Problems.busy`, `Retry-After: 5`, `retryAfterSeconds`) and applies to every operation; ipd.yaml did not list it.

## Decision

### D1 · Order head and versions (reusable for A4 to A9)

- **The head stays `ipd.medicine_order`** (stable id: the EMR, the MAR, the queue, doses and audits all key on it). The head carries what is true for the order as a whole: drug (never changes: a different medicine is a new order), admission, orderer, `client_key`, status, `current_version` (new, 1-based, the number users see as "v2"), `priority` of the current version (copied for the queue indexes), `stopped_*` plus `stop_reason`. The existing `version` column stays the row change counter used by `changeToken` (ADR-009 D8); the two are never mixed. Contract name: `orderVersion` = `current_version`.
- **New `ipd.medicine_order_version`**: one row per version, written in the same transaction as the head change. Columns: order id, `version_no`, `kind` (`SCHEDULED`, `PRN`, `ONCE`), `frequency_key` (SCHEDULED only), `dose_amount`, `dose_unit`, `route_key`, `start_at`, `end_at` (null = until stopped), `indication`, `priority` (`ROUTINE`, `URGENT`, `STAT`), PRN `min_interval_min` and `max_per_24h`, `change_reason` (null on v1), `created_by`, `created_at`, `superseded_at` (set when the next version is made), the verification of this version (`verification` `REQUIRED` or `NOT_REQUIRED`, `verified_by`, `verified_at`). Versions are never updated except two one-way stamps (`superseded_at`, and the verify pair) under a guard trigger.
- **Head status** describes the current version: `PENDING` "Pharmacist check", `QUERIED` "Queried" (new), `ACTIVE`, `ON_HOLD` "On hold" (new), `REJECTED`, `STOPPED`. Transitions (Java `OrderLifecycle`, pure, plus the database guard):

| From | Action | To | Who | Read-only IPD |
|---|---|---|---|---|
| (new) | order, verification required | PENDING | OWNER, DOCTOR | 409 |
| (new) | order, verification not required (ward profile Off) | ACTIVE (version `NOT_REQUIRED`) | OWNER, DOCTOR | 409 |
| PENDING | verify (PIN) | ACTIVE | PHARMACIST, OWNER, not the orderer | 409 |
| PENDING | reject | REJECTED | PHARMACIST, OWNER | allowed |
| PENDING | query | QUERIED | PHARMACIST, OWNER, not the orderer | allowed |
| QUERIED | reply | PENDING | OWNER, DOCTOR | 409 |
| PENDING, QUERIED, ACTIVE | change | PENDING (new version, REQUIRED) or ACTIVE (NOT_REQUIRED) | OWNER, DOCTOR | 409 |
| ACTIVE | hold | ON_HOLD | OWNER, DOCTOR | allowed |
| ON_HOLD | resume | ACTIVE | OWNER, DOCTOR | 409 |
| PENDING, QUERIED, ACTIVE, ON_HOLD | stop (reason) | STOPPED | OWNER, DOCTOR | allowed |

  Change of an ON_HOLD order is refused (409 `order-state`, "Resume this order before changing it."): the story lists change for Active and Pharmacist check only (Q9). A change or stop closes an open query (BR-5). Resume needs no new verification (OQ-76-9).
- **Reuse for A4 to A9:** the cross-order pieces are keyed by `(order_kind, order_id, order_version)` with one typed foreign key column per kind and a check "exactly one set" (today only `medicine_order_id`, kind `MEDICINE`): `ipd.order_notice` (D5) and `ipd.order_hold` (D4). `OrderLifecycle`, `OrderVersionDiff` (the "Changed: old → new" lines) and `OrderNotices` are written over an `OrderRef(kind, id, version)` and know nothing of medicines. A later lab or nursing order adds its own head and version tables (its payload differs) and one nullable FK column on the two shared tables. Rejected alternative: one generic `clinical_order` with a JSON payload (loses database checks on clinical values and means rewriting the built medicine table, its guard trigger and its indexes).
- **Built rows** get a version 1 by the migration (kind SCHEDULED, the built frequency, dose and unit null = "as in the medicine name", route from the drug, `start_at` = `ordered_at`, end null, ROUTINE, verification REQUIRED with the built verified pair). No built behaviour changes for them.
- **The duplicate backstop** (partial unique index on live orders of the same drug) widens to PENDING, QUERIED, ACTIVE, ON_HOLD, and `MedicineSafetyCheck` treats the same four as live (QUERIED and ON_HOLD are still on the chart). OQ-76-1 and OQ-76-2 defaults: allergy and duplicate stay hard stops.

### D2 · Slots stay computed; dose and correction records are stored; no scheduler

**Chosen: computed slots plus append-only records.** The spec's "scheduler materialising DoseEvent rows (rolling 48 h)" is rejected for phase 1:
- every slot state the spec's scheduler stores (`scheduled`, `due`, `overdue`, `cancelled`) is a function of the version, the holds, the stop time, the settings and the clock; storing it means a job that must run on time on every instance, a multi-instance lock (a new library such as ShedLock, or a hand-made advisory-lock job), about 150,000 to 300,000 extra writes a day, and rows that go stale at every change, hold and stop;
- the built `DoseSlots` already gives one answer to the MAR, the tab count, the Medicine round and the dose endpoint (story 76-4 note: "one code path").

`DoseSlots` (pure) is extended to take an **`OrderTimeline`**: the versions of the order (kind, frequency, start, end, superseded_at, verification), its hold intervals, its stop time, the dose records and corrections of the day, the effective windows (D8) and `asOf`. Per order, today's slots are the union over versions of the frequency's times on the IST date of `asOf` with `start_at ≤ slot < min(end_at, superseded_at)`; when two versions give the same instant, the current version's slot is kept and the older one is not shown. ONCE has one slot at the version's creation minute; PRN has none (D7).

**Slot state, first that applies** (replaces the ADR-011 D2 table; the built states keep their texts):

| # | Condition | State | Givable |
|---|---|---|---|
| 1 | a live (uncorrected) dose record for the slot | GIVEN / HELD / REFUSED | no |
| 2 | admission not ADMITTED | NOT_RECORDED | no |
| 3 | order STOPPED and slot ≥ `stopped_at` | STOPPED ("Stopped by Dr X at 2:00 PM") | no |
| 4 | slot of an older version, slot ≥ its `superseded_at` and the current version has no slot at that instant | REPLACED ("Replaced by a change by Dr X at 11:05 AM") | no |
| 5 | slot inside a hold interval (`held_at ≤ slot < resumed_at`, or the hold is open) | ON_HOLD ("On hold by Dr X"); never DUE or LATE, never counted | no |
| 6 | the slot's version is not verified (head PENDING or QUERIED) and the version is not ONCE-STAT | WAITING ("Waiting for pharmacist"; "Queried" for QUERIED) | no |
| 7 | verified version, `slot < verified_at − windowBefore` | BEFORE_START (built rule, window from settings) | no |
| 8 | by the clock with the effective window: more than `windowAfter` whole minutes after → LATE; from `windowBefore` before to `windowAfter` after → DUE; else LATER | LATE / DUE / LATER | DUE, LATE |

- ONCE (STAT): DUE from the slot to `slot + statWindow`, then LATE ("overdue by N min" in the STAT line, "late" on the chip, OQ-76-3), never LATER; givable before verification (D7). The slot belongs to its IST day; a STAT signed just before midnight and not recorded leaves the MAR at midnight (built midnight rule, OQ-35-2; Q10).
- Corrected doses (D3) never decide the state; IN_ERROR records are returned with the slot as struck-through history; UNDO records are not shown on the MAR (they are in the event log and audit).
- The Medicine round (SAH-35), the tab count, the card counts and the dose endpoint all call this one function; `MedicineRoundReader` loads timelines in a fixed number of statements (versions, holds and corrections of the visible admissions: three more set reads, never one per patient).
- **MAR listing** changes: orders PENDING, QUERIED, ACTIVE, ON_HOLD, plus orders STOPPED or REJECTED **on today's IST date** (so the stopped slots and their text show, story 76-4 D1); older stopped orders stay off the MAR as built (Q12).

### D3 · Undo and "recorded in error": appended correction records (reverses ADR-011 D1 "no undo")

The human's approved spec reverses SAH-32 AC9 / OQ-32-5. The history stays append-only:
- **`ipd.dose_correction`** (new, append-only): `dose_id` (unique: one correction per dose), `kind` `UNDO` or `IN_ERROR`, `reason_key` (IN_ERROR only: `NOT_GIVEN_ACTUALLY` "Dose was not actually given", `WRONG_PATIENT` "Documented on the wrong patient", `WRONG_TIME` "Wrong time recorded", `DUPLICATE` "Duplicate entry"), `corrected_by`, `corrected_at` = `clock_timestamp()`, `client_key`. Insert and select only; triggers refuse update, delete, truncate.
- **The dose record** gains `attempt` (1, 2, …) and `supersedes_dose_id`. The built unique `(tenant_id, order_id, slot_at)` is replaced by unique `(tenant_id, order_id, slot_at, attempt)` and unique `(tenant_id, supersedes_dose_id)`; the insert guard requires that attempt n > 1 supersedes the attempt n − 1 of the same slot and that it has a correction. So a slot still has at most one live record, and a new give after an error is a new row linked to the struck-through one.
- **Undo** (`POST /doses/{id}/undo`): GIVEN only (OQ-76-25); the caller is the recorder; the database clock is not after the dose's `undo_until` (stamped at insert as `recorded_at + undo seconds` from the settings in force, so a later settings change never reopens or shortens a past window). Effects: the slot returns to its clock state; the PRN count no longer counts it; open order notices acknowledged by that dose stay acknowledged (an acknowledgement is a read receipt); a review item created by that dose (D6) is closed with outcome `DOSE_UNDONE`. High-alert second nurse is not asked again.
- **Recorded in error** (`POST /doses/{id}/recorded-in-error`): GIVEN only; by the recorder, any NURSE who passes the scope guard for the patient, or OWNER; only while the IST date of the database clock equals the IST date of `slot_at` (409 `error-window-closed`; OQ-76-25, OQ-35-2). Effects as undo, plus the record shows struck through with who, when and why.
- Not given (HELD, REFUSED) records are never corrected here (409 `dose-state`; corrected by a nursing note, OQ-76-25).
- Both actions take the admission row lock (ADR-006 D4) and are idempotent on `clientKey` (same caller, same kind and reason → 200 replay).

### D4 · Change, hold, resume, stop

- **Optimistic version check:** each body carries `orderVersion` (the version the doctor saw). Under the admission row lock: not equal to `current_version` → 409 `order-changed` "This order was changed by someone else. Reload and check the new order." (no clinical values in a problem detail; the client reloads the EMR sheet and shows the current values). First writer wins (story 76-1).
- **Change:** builds version n+1 from the current version and the edited fields (dose, unit, route, frequency or PRN fields, duration or end, indication, priority); `start_at` = the later of the requested start and the change time; `end_at` = start plus duration; the old version gets `superseded_at` = the change time. "Nothing was changed" 400 when every field equals the current version. A change to priority STAT makes a ONCE version. Verification: REQUIRED when the ward profile in force requires it (OQ-76-9 default yes) → head PENDING; else ACTIVE. Notice CHANGED (D5).
- **Hold:** `ipd.order_hold` row (order ref, `held_at`, `held_by`, `hold_reason`, `resumed_at`, `resumed_by`), at most one open hold per order (partial unique). **Resume** closes it. Slots missed during the hold are not created again; held slots are never due or late (OQ-76-27).
- **Stop:** body now required: `orderVersion` and `reason` (4 to 200 characters). Stop of a STOPPED order by the same caller stays a 200 replay (built rule; `orderVersion` and reason not compared).
- Reasons, indication, query and reply are clinical text: stored, shown to clinical roles, never logged, never in audit values, events or problem details (BR-15). Clinical events use fixed templates: "Changed <drug> (v<n>)", "Held <drug>", "Resumed <drug>", "Stopped <drug>" (kinds order, stop, stop, order).

### D5 · Nurse order notices (the inbox) and acknowledgement

- **`ipd.order_notice`** (new): order ref and version, admission, `kind` (`NEW`, `CHANGED`, `HELD`, `RESUMED`, `STOPPED`), `priority` at creation, `created_at`, `created_by`, `acknowledged_by`, `acknowledged_at`, `acknowledged_via` (`TAP`, `DOSE`). Written in the same transaction as the action that creates it; no event bus, no job:
  - NEW when the order first becomes givable: at verify of v1; at signing when the version is NOT_REQUIRED; at signing of a STAT (ONCE) order.
  - CHANGED at a change (at once, before re-verification: the old version's slots are cancelled now); HELD, RESUMED, STOPPED at those actions.
  - A STOPPED notice of an order whose NEW notice was never acknowledged is still created (the nurse must see both).
- **Acknowledge** (`POST /order-notices/{id}/acknowledge`): NURSE, OWNER; under the admission row lock; `acknowledged_at is null` → set, 200; already acknowledged by the caller → 200, nothing written; by another → 409 `order-state` "<name> already acknowledged this.". A recorded dose (GIVEN or NOT_GIVEN) acknowledges every open notice of that order in the same transaction (`acknowledged_via` DOSE; OQ-76-5).
- **"Not acknowledged for N min"** is computed at read time against the settings in force (30 / STAT 5 minutes); nothing is stored or sent (OQ-76-6).
- **STAT line:** from the ONCE slot and the STAT window: `statDueBy`, remaining or overdue minutes from the server clock; resolved only by a live dose record (given or not given) or a stop.
- **Where it lives (OQ-76-4):** a new tab **"Orders"** in the Nursing sheet (third tab, after "Medicines (MAR)"); the count badge on the Admitted card (`AdmittedClinicalFlags.ordersToAcknowledge`) and on the tab; a panel **"Orders to acknowledge"** on the Safety tab for NURSE and OWNER, placed after the Medicine round panel and not added to the Safety tab number (story 76-3 note). DOCTOR reads the Orders tab (no Acknowledge button) and sees the card badge; PHARMACIST, FRONT_DESK, BILLING get 403 and no badge.
- **Polling (OQ-76-7):** `GET /order-notices/summary` (counts only: totals, per admission id the open count, STAT count, overdue count and the earliest open `statDueBy`; a `changeToken`; `asOf`) every 30 seconds while the Admitted list, the Nursing sheet or the Safety tab is on screen, through the existing `visible-poll.ts` (stops while the browser tab is hidden). When `changeToken` differs the screen reloads its list. The countdown runs from `asOf` plus the elapsed time of the page, never the device clock alone. The summary writes nothing (no access row). A failed poll keeps the last data with "Could not refresh. Showing data from 11:05 AM." (SAH-33 pattern).
- Ward scope (SAH-34): lists filter by scope; by-id actions use the guard.

### D6 · Pharmacist: queue additions, query, review after dose

- The queue (`GET /pharmacist-checks`) lists PENDING orders (QUERIED orders show under the same panel with the pill "Queried" and no Verify; they are counted in a separate `queried` number, not in `waiting`). Rows gain dose, route, start, duration, priority tag, the version number and, for a changed version, the diff lines and the change reason (OQ-76-29); the doctor's reply when a query was answered.
- **Query** (`POST /medicine-orders/{id}/query`): PENDING only; PHARMACIST or OWNER, never the orderer (the verify self rule, 403 `self-verification`; Q6); question 1 to 300 characters (OQ-76-11 limit confirmed). Row in **`ipd.medicine_order_query`** (order, version, question, asked_by, asked_at, reply, replied_by, replied_at, `closed_by` `REPLY`, `CHANGE`, `STOP`, `REJECT`). Allowed in Read-only (it makes an order not givable).
- **Reply** (`POST /medicine-orders/{id}/query-reply`): QUERIED only; OWNER, DOCTOR; reply 1 to 300 characters; head back to PENDING. Refused in Read-only (it moves toward giving; Q6).
- **Review after dose is a separate record**, not a dose state (the dose is append-only and the review has its own life): **`ipd.pharmacist_review`** (order, version, dose id unique, created_at, `closed_at`, `closed_by`, `outcome` `REVIEWED`, `VERIFIED`, `REJECTED`, `DOSE_UNDONE`). Created in the dose transaction when a GIVEN dose has `before_verification`. Listed by `GET /pharmacist-reviews` (PHARMACIST, OWNER), each with the safety check run now. **Mark reviewed** (`POST /pharmacist-reviews/{id}/mark-reviewed`) closes it; a verify or reject of that order closes it with that outcome. While the check finds a hard stop, Mark reviewed is refused (409 `order-blocked`) and only Query doctor is offered; once the order is STOPPED, Mark reviewed is allowed again so the item can close (Q5). Allowed in Read-only (record only).
- `PharmacistChecksSummary` gains `reviewsOpen` and `queried`; the Safety tab number for PHARMACIST and OWNER adds `reviewsOpen`.
- Verification On/Off: read from the ward profile in force for the patient's current ward at signing or change (D8). Orders already PENDING stay PENDING when a profile is switched Off (OQ-76-13).
- `VerifyOrderInput` gains `orderVersion` (required): a verify of a version the pharmacist did not see → 409 `order-changed`.

### D7 · Giving: medicine code, override, STAT before verification, PRN, version

Server check order on `POST /medicine-orders/{id}/doses` (each step stops the request; extends ADR-011 D5 and D4):
1. role, module, Read-only, body format (built);
2. membership, 404, client-key replay, not-admitted (built);
3. order state: STOPPED or REJECTED 409 `order-state`; ON_HOLD 409 `order-on-hold` "This order is on hold. Do not give it."; QUERIED 409 `order-not-verified`; PENDING 409 `order-not-verified` unless the current version is ONCE with priority STAT and no live GIVEN dose exists for the order (then the dose is flagged `before_verification`);
4. `orderVersion` ≠ current version 409 `order-changed` "This order was changed. Reload and check the new order.";
5. slot rules (scheduled and ONCE: a slot of today of the current version, not before start, inside the window, no live record; PRN: `slotAt` must be absent);
6. GIVEN only: identity (wristband, D7 rules below), medicine code, two identifiers, high-alert second nurse and PIN (built, unchanged), PRN rules;
7. NOT_GIVEN only: reason (built five plus `VOMITED` "Vomited" and `OTHER` "Other"; `OTHER` needs a note 4 to 200 characters, OQ-76-26).

- **Medicine code (OQ-76-16):** typed or sent by a keyboard-type scanner; normalised as the wristband (NFKC, strip white-space, control and format characters, upper case; over 100 characters = no match). Matched against **`ipd.drug_code`** (D9). Empty → 400 "Scan or type the medicine code."; not a code of the ordered drug → **409 `medicine-mismatch`** with detail "Wrong medicine. This is <name of the drug of that code>, not <ordered drug name>." or "Wrong medicine. This is an item not on this order, not <ordered drug name>."; the deny event "Stopped at the medicine check: entered <code>, expected <drug>" and audit `IPD_DOSE_MEDICINE_MISMATCH` are written and committed before the 409 (ADR-011 D6 pattern). **`<code>` is the normalised code only when it is a code in `ipd.drug_code`, otherwise the words "a code not in the medicine list"**: the story's "first 40 characters" would let a typed mobile or a 14-digit ABHA-like run reach the permanent log (the ADR-011 D4 reasoning; deviation in the safer direction).
- **Manual override (D4 spec, OQ-76-17):** `override.reasonKey` (`WRISTBAND_DAMAGED`, `NO_BARCODE`, `SCANNER_DOWN`, `EMERGENCY`) and `override.note` (4 to 200 characters after trimming, clinical text). With an override the wristband and medicine code are optional; if sent they are still checked and a mismatch is still a STOP. Two identifiers, the second nurse, allergy, PRN and order rules are never skipped. The "no override after a STOP until rescan or cancel" rule is a client rule (the server has no session state for it). Stored on the dose: `scan_method` `SCAN` or `OVERRIDE`, `override_reason_key`, `override_note` (never audited: audit holds `overrideReasonKey` and `notePresent`). **Replaced by A9 (contract 0.4.3):** the override covers the medicine code only, the wristband is always required, `WRISTBAND_DAMAGED` is refused on input, and the server refuses an override within 15 minutes of the caller's mismatch.
- **PRN (A3, OQ-76-19 defaults):** no slot; the record's `slot_at` is the database minute of recording (dose kind PRN). Refused while `now < lastLiveGiven + minInterval` → 409 `prn-too-soon`; while the live GIVEN doses in the rolling 24 hours ≥ max → 409 `prn-max-reached` (next allowed = the oldest counted dose + 24 h). Undone and in-error doses never count. The order's indication is the dose reason (per-dose reason is D7-Next). The problem detail names the IST time; no extension member is added, because `platform.api.ConflictException` carries none and changing it is a platform change; the client reloads the MAR, whose `PrnLine.nextAllowedAt` carries the instant.
- **STAT before verification (B2):** the dose row stores `before_verification true`; the review item (D6) is created in the same transaction; the NOT_GIVEN outcome is also allowed for that slot but creates no review item.
- **Version on the dose:** every new dose stores `order_version`; the insert guard checks it equals the current version and that the order is ACTIVE, or PENDING with the STAT exception.
- **Wrong patient text (OQ-76-18):** the client line becomes "Wrong patient. This band belongs to another patient. Check the patient before giving anything." (no name of either patient); the problem detail is unchanged.
- **"Checked by the system" panel:** built from the MAR answer (route, allergy chip, last given time of the order, time state); no new endpoint. Weight-based dose lines appear only for drugs a hospital configures (none shipped, BR-17).
- Ack by dose (D5) and review creation (D6) run in the dose transaction.

### D8 · Nursing settings and ward profiles (M1), no department names in code

- **Clinic settings**: new columns on the lazy row `ipd.config`: `med_verification_required` (true), `dose_window_before_min` (60), `dose_window_after_min` (60) (OQ-76-15: built values kept; spec 30/30 is the hospital's choice), `stat_window_min` (15), `unack_flag_min` (30), `unack_flag_stat_min` (5), `undo_seconds` (10). Ranges (400 outside): windows 1 to 180; STAT window 1 to 120; unack 1 to 240 and STAT 1 to 60; undo 1 to 10 (never above the spec's 10-second safety rule, Q8).
- **Profiles**: tenant table **`ipd.nursing_profile`** (`key` slug unique per clinic, `name` 1 to 60, `med_verification_required`, `vitals_every_min` 15 to 1440, optional `dose_window_before_min` and `dose_window_after_min`, `sort_order`); at most 20 per clinic. **`ipd.ward.nursing_profile_key`** (nullable, FK `(tenant_id, key)`).
- **Starter rows are data, not code:** a global reference table **`ipd.nursing_profile_template`** holds "ICU" (key `icu`, verification on, vitals 60 minutes) and "General ward" (key `general-ward`, on, 240 minutes). A clinic's profiles are materialised from the templates on the clinic's first profile or ward-profile write (same transaction, under the clinic IPD advisory lock, as `ipd.config`'s lazy row); until then reads return the template rows as the clinic's starter profiles. No Java code branches on a key or name.
- **Effective values for a patient**: the profile of the ward of the current bed, else the clinic settings (verification), else the defaults (vitals 240; windows of the clinic). Read once per request by `NursingSettingsReader` and passed into the pure rules.
- **Take effect for later events (BR-16):** verification is decided at signing or change and stored on the version; the undo window is stamped on the dose; the vitals interval is stamped on the vitals record (D9); dose windows are a display rule applied at read time (a past record is never rewritten; a slot's DUE or LATE label may change for not-yet-recorded slots, which is the purpose of the setting).
- **API**: `GET /nursing-settings` (OWNER, DOCTOR, NURSE, PHARMACIST read), `PUT /nursing-settings`, `POST /nursing-profiles`, `PUT /nursing-profiles/{key}`, `PUT /wards/{id}/nursing-profile` (OWNER only; Read-only 409). No delete of a profile in this set (a profile in use must not vanish; later story).

### D15 · Volumes and retention

- Versions: about 1.3 per order (5 to 20 million a year). Notices: 1 to 3 per order plus changes (20,000 to 100,000 a day). Holds, queries, reviews, corrections: small (under 5 % of orders or doses). Dose rows: unchanged order of magnitude; ADR-011 D13 partition plan stands, the new unique `(tenant_id, order_id, slot_at, attempt)` still contains `slot_at`.
- All new clinical tables are part of the in-patient record: never deleted, no delete grant, triggers refuse delete and truncate (ADR-006 D9). Settings and profiles are configuration: update allowed, no delete in this set.

## Options considered

- **Stored dose events with a scheduler (spec)** vs **computed slots with stored records and corrections (chosen)**: D2. A scheduler needs a multi-instance job lock (new library or new mechanism) and stores derived state that goes stale.
- **Versions as columns on the head (overwritten)** vs **version table (chosen)**: overwriting would break "doses stay on the version they were given under".
- **One generic order table with JSON payload** vs **per-kind head and version tables plus shared notice and hold tables (chosen)**: D1.
- **Undo as delete or update** vs **appended correction rows (chosen)**: history stays append-only (spec safety rule 5).
- **Review item as a dose state** vs **separate record (chosen)**: D6.
- **Per-clinic medicine codes** vs **global code table on the drug master (chosen, Q1)**: drugs are global (ADR-009 D3); GTINs are global.
- **Profiles as settings JSON** vs **table plus template table (chosen)**: wards reference a profile with a foreign key; no names in code.
- **Polling 30 s with counts (chosen)** vs **SSE** (Later, DEC-055).
- **Device id on `platform.audit_event` as a column** (platform change) vs **in the audit `after` map (chosen)**.

## Consequences

**Positive.** One slot function for every screen; nothing past is overwritten; a changed order can never be given under its old version (guard trigger plus check); A4 to A9 reuse lifecycle, notices and holds; no scheduler, push or new library; settings change behaviour without code changes.

**Negative / accepted.**
- Breaking contract changes in one release: stop needs a body, verify needs `orderVersion`, dose needs `orderVersion`, MAR enums widen. Backend and frontend ship together (0.4.0).
- Until medicine codes are loaded every give is an override (Q1).
- Reads of the MAR and the Medicine round load three more sets (versions, holds, corrections).
- 30-second polling adds about 2 requests a minute per open nursing screen (counts only, no writes).
- A changed version waits for the pharmacist, which can leave a gap in therapy (OQ-76-9, accepted by the human as written).

## Addendum · contract 0.4.2 (15 Nov 2026, QA finding on slots before the start)

Contract text aligned to the build and to story 76-1; no code change, no new operation, field, problem type, table or behaviour. `docs/api/ipd.yaml` 0.4.1 → 0.4.2.

- **A8 · Slots before a version's start, BEFORE_START, and the order of field errors (changes an approved contract line, human to confirm).**
  - *Context.* QA (SAH-76 test plan and handoff) found that 0.4.1 still carried the SAH-32 wording: a dose for a slot "before the order started" answers 409 `dose-before-start`, and `MarSlotState` BEFORE_START means "more than 60 min before verifiedAt". Since 0.4.0 an order has a start (D1, story 76-1) and D2 already says a slot exists only where `start_at ≤ slot < end_at`. The build follows D2: `DoseSlots` never generates a time before the version's start, so the dose operation finds no slot and answers 400.
  - *Decision (text follows the build).* (1) A dose time before the start of the order, or of the version that owns that time, is not a slot: it is never on the MAR, the Medicine round or the counts, and a dose for it answers **400** problem type `validation`, field `slotAt`, "This is not a dose time of this medicine today. Reload the page and try again." The approved 0.4.1 line "BEFORE_START dose-before-start" for such a time becomes this 400. (2) BEFORE_START (D2 row 7) and 409 `dose-before-start` stay, and apply only to a slot at or after its version's start, of a version verified today (IST date of the database clock), more than `windowBefore` whole minutes before that version's `verifiedAt`. A version that needs no pharmacist check has no BEFORE_START. Example: an order started 7:55 AM, verified 10:00 AM: the 8 AM slot is BEFORE_START (409); an order started 10:00 AM: there is no 8 AM slot (400). (3) Order placement `fieldErrors` order as built (`MedicineRules.strictOrder`, `OrderValues.check`): clientKey, drugKey, frequencyKey, overrideReasonKey, checkToken, priority, doseAmount, doseUnit, routeKey, startAt, durationDays, indication, prnMinIntervalMinutes, prnMaxPer24h; detail is the first message. overrideReasonKey and checkToken add an error only when present and invalid; the STAT error is in the priority place. A body missing every new field (valid SAH-31 fields) gives priority, doseAmount, doseUnit, routeKey.
  - *Options.* (a) Align the text to the build (chosen): matches story 76-1 and D2, one rule for MAR and dose path, no code change. (b) Change the code to answer 409 `dose-before-start` for times before the start: the dose path would need a second slot generator just for refusals, and the MAR would still not show those times, so the client would get a conflict for a time it never offered.
  - *Consequences.* The client never offers such a time (it is not on the MAR or the round), so only a direct API call or a stale screen meets the 400; the built client answers already cover it (MAR Give sheet: error toast with the detail "... Reload the page and try again."; Medicine round: 400 on `slotAt` closes the sheet and reloads GET /safety), so no client change. QA tests written to the 0.4.1 line are changed to 400 `slotAt`; tests for BEFORE_START after the start stay at 409. Human confirms the changed approved line (409 `dose-before-start` → 400 for times before the start).

### A9 · Override split, version-author self-check, PRN dates, replay by another user, device label

**Context.** Security M1: one override waived both the wristband and the medicine code; with `ipd.drug_code` shipped empty every Given needs an override, so the wristband became optional in practice, and "no override after a STOP" lived only in the client. Security M2: the self-verification rule compared the caller only with the author of version 1, so an OWNER (doctor and pharmacist rights) could change an order and verify the change alone. Code review #2: a PRN order's start and end were never enforced. Code review #4: `change()` answers its medicine-unit 400 after the 409 checks; the contract described field order for placement only. Security L1: a dose client-key replay did not check the caller. Security L2: the device id is client-made.

**Decision.**

1. **Override covers the medicine code only (DEC-057 answer 1A; replaces the D7 "Manual override" bullet).**
   - GIVEN always needs the wristband: empty after normalisation 400 field `wristband` "Scan the wristband first."; not the UHID 409 `wristband-mismatch` (deny entry and audit as built). A damaged band is handled by typing the UHID in the same box.
   - A non-empty `medicineCode` is always compared. A code of the ordered drug records `scan_method` SCAN and the matched code; an override sent with it is ignored (not checked, not stored). Not a code of the drug: 409 `medicine-mismatch` as built. Empty code and no override: 400 field `medicineCode` "Scan or type the medicine code.".
   - Override reasons accepted on input: `NO_BARCODE`, `SCANNER_DOWN`, `EMERGENCY` (new contract enum `OverrideReasonForScanInputKey`). `WRISTBAND_DAMAGED` is refused on input (400 field `override.reasonKey` "Choose why you cannot scan.") and stays readable on doses recorded before 0.4.3 (`OverrideReasonForScanKey`, `DoseRow.overrideReason`). `Mar.overrideReasons` lists the three.
   - **New 409 `override-after-mismatch`**, title "Override not allowed" (NEW), detail "A scan for this dose did not match in the last 15 minutes. Check the patient and the medicine, then scan the medicine code." (NEW): the request carries an override (empty code) and the caller had a wristband or medicine mismatch on the same order and the same `slot_at` (a PRN order: the same order, any time slot) with `stopped_at` within the last 15 minutes by the database clock. 15 minutes is fixed, not a setting. Audited `IPD_DOSE_REFUSED` (orderId, admissionId, refusal key `override-after-mismatch`, device), committed with the 409; no clinical event. Other users' mismatches do not count (the rule is about the person who saw the STOP). A matching scan is never refused by it.
   - Every wristband or medicine mismatch of a GIVEN request writes one row in `ipd.dose_scan_stop` in the same committed step as its deny entry and audit (prepare step and, when it happens there, the locked step, as built for the deny entry). The row holds no scanned text.
   - **GIVEN check order:** wristband (400, then 409), medicine code (409 mismatch, or 400 when empty without override), override fields (400), override-after-mismatch (409), identityConfirmed (400), high-alert second nurse format and choice (400), PRN limits (409). Run in the first transaction and again under the admission lock (A7 shape unchanged); the PIN check sits between them as built.
   - NEW client texts: toggle "Cannot scan the medicine? Manual override" under the medicine code box (replaces the reference's "Cannot scan? Manual override"); note label "What you checked instead, e.g. the strip label read against the chart"; hint "Only when the medicine code cannot be scanned. The wristband must still match. The override, your reason and your name go to the pharmacy and quality team.". The client keeps its "no override offered after a STOP until rescan or cancel" rule; on 409 `override-after-mismatch` the sheet stays open, the override closes and the detail shows under the code box.

2. **Self-check covers the author of the current version (DEC-057 answer 2A).** Verify and query answer 403 `self-verification` when the caller is the head's `ordered_by` (built texts) or the current version's `created_by`: verify "The doctor who changed this order cannot verify it. Ask the pharmacist." (NEW), query "The doctor who changed this order cannot check it. Ask the pharmacist." (NEW); titles as built. Verify checks it in both built places (plain read before the PIN, and on locked data); query in its built place after the lock. Not audited (Q11). `PharmacistCheckRow.verifyLockReason` gains `SELF_CHANGED` (order HARD_STOP, SELF, SELF_CHANGED, IPD_READONLY; hint is the verify text); `canVerify` and `canQuery` (queue and review rows) false for that caller. Accepted consequence: a one-person clinic owner cannot verify their own change; that clinic sets the ward profile's pharmacist check Off.

3. **PRN start and end (DEC-057 answer 3A).** A PRN dose (either outcome) when the database clock is before the current version's `start_at`, or at or after its `end_at`, answers 409 `dose-not-due` with the built detail "This dose cannot be given now. Reload the page."; checked in the slot step (after `orderVersion`), not audited (as the other slot answers). `PrnLine.lockReason` gains `NOT_STARTED` "Not started yet" (NEW) and `ENDED` "Ended" (NEW), against `Mar.asOf`; lock order STOPPED, ON_HOLD, NOT_VERIFIED, NOT_STARTED, ENDED, then MAX_REACHED / TOO_SOON as built.

4. **`change()` answer order documented as built (code review #4; no code change).** Role, module, Read-only, body 400 (clientKey, orderVersion, reason, then the value fields in the `OrderValues.check` order; the unit only against the unit list), membership, 404, lock, scope, not-admitted, patient, repeat, ON_HOLD and STOPPED/REJECTED 409 `order-state`, 409 `order-changed`, then the unit of this medicine 400 field `doseUnit` "Choose the unit.", then "Nothing was changed." 400 field `reason`. Chosen over moving the drug lookup before the body check: no behaviour change in a reviewed path.

5. **Dose replay by another user (security L1).** After the built "key of another order" 400, a stored dose with this `clientKey` whose recorder is not the caller answers 409 `client-key-reused` (built text) before any value is compared; nothing is written (no record-access row, no audit). Undo and recorded in error already compare the caller.

6. **Accepted for phase 1, no contract change.** (a) Record-access rows written per reload of the ward panel, Orders tab and review list (code review #5): kept; it is the access-log rule of DEC-017; volume goes to the go-live capacity review; a dedupe window would change what the access log proves and is a human decision. (b) An older version's unrecorded slot before the change time can never be given or charted not given (code review #9): stays on the go-live list.

7. **Device label is advisory (security L2):** written into D11.

**Database (db-engineer, one forward-only migration, built in parallel; names fixed here).** No data change, no backfill.
- Replace `ipd.guard_medicine_order_version_update`: the verify pair is refused when `verified_by` equals the head's `ordered_by` or the version row's `created_by` (other rules unchanged).
- Replace `ipd.guard_medicine_order_query_insert`: `asked_by` refused when it equals the head's `ordered_by` or the `created_by` of the order's current version.
- New tenant table **`ipd.dose_scan_stop`**: `id uuid pk`, `tenant_id` (default `platform.current_tenant()`, FK `platform.tenant`), `admission_id` (FK `(tenant_id, admission_id)`), `order_id` (FK `(tenant_id, order_id) → ipd.medicine_order`), `slot_at timestamptz null` (null for PRN), `check_kind text` in (`WRISTBAND`, `MEDICINE`), `actor uuid not null`, `stopped_at timestamptz not null default clock_timestamp()`. ENABLE and FORCE RLS on `tenant_id = platform.current_tenant()` (USING and WITH CHECK); `sahaj_app` insert (column list without `tenant_id`) and select only; triggers refuse update, delete and truncate. Index `(tenant_id, order_id, actor, stopped_at desc)`. Why a table: `ipd.clinical_event` has no order or slot columns, and ipd may not read the platform audit (module boundary). Retention: part of the in-patient safety record, never deleted (D15); volume small (mismatches only).
- Dose insert guard backstop (extend the built insert guard of `ipd.dose_administration`): a GIVEN row needs `identity_scan` not null; `override_reason_key` may not be `WRISTBAND_DAMAGED` on insert; a row with `scan_method` OVERRIDE has `medicine_scan` null. The column check keeps `WRISTBAND_DAMAGED` so old rows stay valid.
- RLS catalogue test must list `ipd.dose_scan_stop`.

**Options considered.**
- Override: split with server memory of mismatches (chosen) vs accept as a go-live condition (DEC-057 1B) vs a clinic switch "medicine code not required" (security M1 (c): a new setting and screen, not drawn).
- Mismatch memory: new append-only tenant table (chosen) vs reading the clinical event log (no order or slot columns; free-text matching) vs reading the platform audit (cross-module table access, refused) vs a client-only rule (bypassed by a direct call).
- Self-check: version author too (chosen) vs accept (DEC-057 2B).
- PRN dates: existing `dose-not-due` (chosen) vs a new problem type (more client cases, same handling: reload).
- change() order: document as built (chosen) vs look up the drug before the body check (behaviour change in a reviewed path).

**Consequences.**
- Identity is checked by scan or typed UHID on every Given; until medicine codes are loaded every Given still carries an override, but only for the medicine (Q1 unchanged).
- One more insert per mismatch and one indexed read per override request; no lock change (the admission row lock stays the only lock).
- Breaking for clients still sending WRISTBAND_DAMAGED or an override without a wristband: backend and frontend ship together, as 0.4.0.
- Owners of one-person clinics cannot verify their own changes.
- Java: `MedicineAdministration` / `DoseRules` (override split, scan-stop write, check order, replay recorder), `MarAssembler.prn` (NOT_STARTED, ENDED), dose decision for PRN dates, `MedicineOrderService.prepareVerify` and `verifyLocked`, `PharmacistQueryService`, the queue and review row flags, `Mar.overrideReasons`. Angular: Give sheet toggle, hint and note label, wristband required with override, 409 `override-after-mismatch` handling, `SELF_CHANGED` hint, PRN lock lines. QA: tests at PRN start − 1 min, start, end, end + 1; override within and after 15 minutes, other user's mismatch, matching scan with override; OWNER change then verify/query; replay by another nurse.
