## Context

- The admin console (ADR-003 rev 2) can be entered only by an existing admin. Today the first admin comes from the env seed (ADR-003 D5) or the dev-only sample-admin call (ADR-008). The human wants a page where a PIN opens a form that creates the first admin, and which then closes.
- A path that creates an admin is a privilege-escalation door (DEC-016): the admin owns every clinic. A 6-digit PIN has 10^6 values; it is safe only with a hard global attempt limit, narrow reach and self-closing.
- The default Spring profile is `dev` (`${SPRING_PROFILES_ACTIVE:dev}`), so a profile check alone protects nothing. ADR-008 already showed the real control: code that is **not in the production jar**.
- At request time the app is `sahaj_app`, which has no privilege on any `platform_admin*` table; the definer has no `INSERT` on `platform.platform_admin` outside dev/test databases (ADR-003 D1, ADR-008 W1).
- Crypto on the classpath (`backend/pom.xml`, checked 10 Nov 2026): `spring-security-crypto` gives `BCryptPasswordEncoder` and `Pbkdf2PasswordEncoder`. `Argon2PasswordEncoder` needs BouncyCastle at runtime, which is **not** a dependency. No new library is added by this ADR.
- The Angular dev proxy (`frontend/proxy.conf.json`) has `"xfwd": true` (ADR-008 R1), so every call through port 4200 carries `X-Forwarded-For`, `-Port`, `-Proto`. ADR-008's G3 refuses any such header; the bootstrap page is used through port 4200, so the bootstrap needs a different, still local-only rule (OQ-42-1).

## Decisions

### D1 · Where the code lives: the dev-tools source set (physically absent from a production jar)

| Option | Verdict |
| --- | --- |
| **A · dev-tools source set** (`backend/src/devtools`, Maven profile `dev-tools`, ADR-008 D2) | **Chosen.** A jar built without `-Pdev-tools` contains no controller, service, gate, database callback or PIN tool. Every runtime check becomes a second layer. Same build, directory (`target-devtools`), jar name, manifest and must-not-ship test as ADR-008. |
| B · main source, guarded by conditions only | Not chosen. The code would ship in every jar; one wrong setting (default profile `dev` + the switch) on a server opens it. |

- Packages `com.sahaj.platform.devtools.bootstrap..` (Java) and resources under `db/bootstrap-dev-tools/` (SQL). A **separate Flyway location** from ADR-008's `db/dev-tools`, because Flyway scans a location recursively and runs every callback in it: the sample-admin callback must not run when only the bootstrap is on, and the other way round.
- **Folder name rule (Revision 3, code review finding 7).** No dev-tools Flyway location may be a string prefix of another (`db/dev-tools` is a prefix of the earlier name `db/dev-tools-bootstrap`, and whether Flyway's classpath scan of `db/dev-tools` also returns `db/dev-tools-bootstrap/...` depends on trailing-slash handling). The bootstrap location is therefore `classpath:db/bootstrap-dev-tools`. The file name stays `afterMigrate__dev_tools_admin_bootstrap.sql`. The old folder `db/dev-tools-bootstrap/` must not exist in any build, and the must-not-ship list forbids both names.
- **Main code (shipped, no endpoint logic)** changes in two places:
  1. `AdminDevPathFilter` reserves a second prefix, `/api/v1/admin/bootstrap` (decoded lookup path, case-insensitive, as today). It asks **every** `DevEndpointGate` bean (`ObjectProvider.orderedStream()`), and continues only when one permits; no bean, no permit, or any exception gives the empty 404 (`AdminDevNotFound.write`). Today's `getIfAvailable()` would fail with two gate beans, so it must change. Each gate must refuse paths it does not own (the sample-admin gate already does, G1). The filter must run **before** every other filter that can answer on `/api/v1/admin/**` (request-body size limit, network filter, Spring Security), so that "off" is the empty 404 for any method, body, size or header.
  2. The production guard callback `db/guard/afterMigrate__platform_dev_tools_absent_guard.sql` (ADR-008 R3) also fails any non-dev database that holds the bootstrap objects (Data needed).
- The production jar therefore answers every `/api/v1/admin/bootstrap/**` request with the same empty 404 as `/api/v1/admin/dev/**`.

### D2 · When it is on: build, then start-time conditions, then request checks

**Start-time conditions** (a dev-tools `@Configuration`; each a `Condition`, not a startup failure; when one is false no bootstrap bean exists and the main filter answers 404):

| # | Condition | Notes |
| --- | --- | --- |
| B1 | Built with `-Pdev-tools` | the classes exist |
| B2 | Profile `dev` active and every active profile is `dev` or `test` | `DevSampleAdminConditions.profilesAllowed` (ADR-008 C1); tests use `dev,test` |
| B3 | `sahaj.admin.bootstrap.enabled` (env `SAHAJ_ADMIN_BOOTSTRAP_ENABLED`) equals `true`, ignoring case | read through the `Environment`, so `.env` works as BR1 asks. Deliberately **not** ADR-008's command-line-only rule (see H-BOOT-2) |
| B4 | `sahaj.admin.bootstrap.pin-hash` (env `SAHAJ_ADMIN_BOOTSTRAP_PIN_HASH`) is a BCrypt hash matching `^\$2[aby]\$(1[2-6])\$[./A-Za-z0-9]{53}$` (cost 12 to 16) | missing, blank, other format or cost below 12: off (BR2) |
| B5 | Admin realm on: `sahaj.admin.enabled=true` and both admin secrets present | `@ConditionalOnAdminRealm` (ADR-008 C3) |
| B6 | No proxy configuration, no cloud platform | `DevSampleAdminConditions.noProxyConfiguration` (ADR-008 C4, R6): otherwise `getRemoteAddr()` could come from a header |
| B7 | `server.address` is a loopback literal | `DevSampleAdminConditions.bindsToLoopback` (ADR-008 C5); `application-dev.yml` sets `127.0.0.1` |

The java-developer moves these shared static checks out of `DevSampleAdminConditions` into a small dev-tools helper both features use (no copy).

**Startup log (BR2).** A dev-tools bean created whenever B1 holds and B3 is `true` writes exactly one line, with no value of any secret:
- all of B2 to B7 hold: `WARN Admin bootstrap registration is on (dev-tools build). /admin/register works from this machine until an admin exists.`
- otherwise: `WARN Admin bootstrap registration is off: <reason>.` where reason is one fixed phrase: `the PIN hash is missing or not a valid BCrypt hash (cost 12 to 16)`, `the active profiles are not dev`, `the admin realm is off`, `proxy settings or a cloud platform are present`, `server.address is not a loopback address`. First failing reason only. The hash value, its length and its prefix are never printed.
- B3 not `true`: nothing is logged. A production jar logs nothing (it has no such class).

**Request checks** (the bootstrap `DevEndpointGate.permits`, all must pass, otherwise the same empty 404). They implement OQ-42-1: local through port 4200, local on port 8080, nothing else.

| # | Check |
| --- | --- |
| K1 | Lookup path is exactly `/api/v1/admin/bootstrap/unlock` or `/api/v1/admin/bootstrap/register`, method `POST` (else 404, never 405; `OPTIONS` is 404, so no CORS preflight ever succeeds) |
| K2 | `request.getRemoteAddr()`, parsed by `IpLiterals.parse` (never resolves a name), is loopback (`127.0.0.0/8`, `::1`, or the IPv4-mapped form `::ffff:127.x.x.x`) |
| K3 | Forwarding headers **may only narrow, never widen.** Allowed, each at most once: `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Port`, `X-Forwarded-Host`. Any other header of ADR-008's G3 list (`Forwarded`, `X-Forwarded-Prefix`, `X-Forwarded-Server`, `X-Original-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, `Client-IP`, `True-Client-IP`, `CF-Connecting-IP`, `Fastly-Client-IP`, `X-Cluster-Client-IP`, `Via`) refuses. `X-Forwarded-For`: split on `,`, trim; **every** element must be an IP literal (no port, no name, not empty) that is loopback. `X-Forwarded-Host`, if present, passes K4. `X-Forwarded-Proto`, if present, is `http` or `https`. `X-Forwarded-Port`, if present, is 1 to 5 digits. These values are only checked, never used as the caller address |
| K4 | `Host` is `localhost`, `127.0.0.1` or `[::1]`, optionally with `:<port>` (stops DNS rebinding: a rebound page sends its own host name) |
| K5 | `Origin` absent, or exactly `http://` or `https://` + one of the K4 hosts + optional `:<port>`, nothing after it. `Sec-Fetch-Site` absent or exactly `same-origin`. (A page on any other site cannot call it; `curl` sends neither header and passes) |
| K6 | `Content-Type` is `application/json` (parameters such as `charset=utf-8` allowed). A form post from another page cannot reach the handler |

Why K3 is safe: the socket address (K2) must already be loopback. A remote caller that writes `X-Forwarded-For: 127.0.0.1` still has a non-loopback socket and fails K2. A local forwarder that adds headers (the Angular proxy with `ng serve --host 0.0.0.0`, nginx with `X-Forwarded-For`) puts the remote address into `X-Forwarded-For` and fails K3. The remaining hole is a local forwarder that adds **no** header (a raw port proxy or tunnel): see the threat table; the PIN, the global lock and K4/K5 are the controls there. ADR-008's per-start console nonce is not used here: the page would need a second secret field that is not in the requirement or the mockup (option recorded in H-BOOT-6).

**Per request, in the service (database):** no row in `platform.platform_admin` (active or not). Otherwise the same empty 404 (BR4), written with `AdminDevNotFound.write` so the bytes are identical. Checked on every unlock and register, and again atomically at creation (D6).

**Security chain.** A dev-tools `SecurityFilterChain` with `securityMatcher` `/api/v1/admin/bootstrap/**` and **`@Order(0)`**, the same order as the sample-admin chain (ADR-008 D4). The admin chain (`AdminSecurityConfig`) and the admin-unavailable chain (`AdminUnavailableConfig`) hold `@Order(1)` with matcher `/api/v1/admin/**`, which also covers `/bootstrap/**`; Spring Security uses the **first** chain whose matcher matches, so the bootstrap chain must sort before them, and 0 does. Its order relative to the sample-admin chain does not matter: the two matchers (`/api/v1/admin/bootstrap/**` and `/api/v1/admin/dev/**`) are disjoint, so no request can match both and whichever of the two is tried first gives the same result. (Equal orders are legal; Spring sorts them stably.) If a later dev chain overlaps either matcher, it must take a distinct order and this note must be revisited. The chain is: stateless, CSRF off (K5, K6 and the `SameSite=Strict` binding cookie replace it), CORS off, no form login, no basic, **no JWT filter** (a clinic token, admin token or cookie other than the binding cookie is never read: BR14), `permitAll`. Filters: `RequestLogContextFilter` (request id), `AdminNetworkFilter` (as ADR-008 D4). Controllers carry `@PublicEndpoint`. The transaction binds nothing: `TenantBindingTransactionManager` sets neither `app.tenant_id` nor `app.admin_*` (anonymous principal), and every database function refuses when a tenant is bound.

**Responses.** Every response, including errors, has `Cache-Control: no-store` and `Pragma: no-cache`. The 404 is the ADR-008 D3 bytes (no body, no `Content-Type`, no CORS, no `WWW-Authenticate`). Any unexpected failure is a bodyless 500 (ADR-008 R4 pattern: message-free, cause-less exception wrapped before Spring's resolvers; the log line has the class and SQLSTATE only).

**`instance` in problem documents (Revision 3, security I2).** Spring Framework 6 fills a `null` `ProblemDetail.instance` with the raw request URI when it writes the body. The raw URI can hold bytes the caller chose that the lookup-path check K1 does not see (for example a `;name=value` path parameter, or another percent-encoding of the same path), so the answer would echo caller input. Options: (a) leave it to Spring (echoes the raw URI); (b) set it to an empty URI (writes `"instance": ""`, which is legal but meaningless and differs from every other admin answer); (c) **set it explicitly to the operation's own fixed path, chosen**. Every problem document from the two bootstrap operations (400, 401, 423, 429) has `instance` exactly `/api/v1/admin/bootstrap/unlock` or `/api/v1/admin/bootstrap/register`, a constant chosen by the controller, never read from the request. Because it is not `null`, Spring leaves it alone. Bodyless answers (404, 500) and the filter's 413 are not affected. `admin.yaml` lists `instance` in `Problem`.

- **Main-code marker (Revision 3 (g)).** Main code already has `com.sahaj.platform.web.ProblemInstanceScrubber`, a `@RestControllerAdvice` `ResponseBodyAdvice` that sets `instance` to `null` on every `ProblemDetail` just before it is written. It exists for the same reason as this section: Spring fills `instance` with the request path, which can hold a caller value (an id, a malformed token), and `platform.yaml` and the other admin operations have no `instance`. It runs after Spring's fill, so it also cleared the bootstrap controller's fixed value. The java-developer added the marker annotation `com.sahaj.platform.web.KeepProblemInstance` (type level, runtime, no attributes); the scrubber's `supports()` returns `false` for a return value whose containing class carries it. Only `BootstrapController` (dev-tools source set) carries it; no main-code class does, so in a production jar the marker exists but changes nothing. Scope: it covers only bodies returned by the marked controller's own handler methods; a problem written by the global `ProblemExceptionHandler` or by `ProblemErrorController` for a bootstrap request is still scrubbed. Reviewed and accepted: no tenancy, authentication, security-chain or module-boundary change (both classes are in `platform.web`, the dev-tools controller already depends on that package), no new data in any answer.
- **Rule for the marker.** A controller may carry `@KeepProblemInstance` only if **every** `ProblemDetail` it returns has `instance` set to a constant chosen in code. Spring fills a `null` `instance` before the scrubber runs, so at that point a constant and a copied request path cannot be told apart: a marked controller that forgot to set it would echo the raw URI. `BootstrapController` sends every problem through one helper that sets the fixed path, and R3-U14 / R3-I10 check each problem type. Any further use of the marker, and any use in the main source set, needs a revision of this ADR (a test that no main-code class carries it is recommended, owner java-developer).
- **Request URIs written differently (observed by the java-developer in the `BootstrapEndpointTest` MockMvc slice, R3-U14).** A path with `;` parameters (for example `/api/v1/admin/bootstrap/unlock;x=y`) passes the gate (the lookup path drops `;` content) and is then refused by the Spring Security request firewall with `400`; in the MockMvc slice the answer is empty. A differently percent-encoded path (for example `/api/v1/admin/bootstrap/%75nlock`) answered an empty `404` there. Neither echoes a byte of the request, and every request that reaches the controller gets the fixed path. **On a real server the bytes may differ and stay safe** (to be confirmed by the qa-engineer in R3-I10 over HTTP): the firewall's 400 goes through the container's error dispatch to `ProblemErrorController`, which answers the generic `bad-request` problem (`type`, `title` "Bad Request", `status`, no `detail`, no `instance`: the error dispatch is not the marked controller, so the scrubber clears it); and a `%75nlock` path, which the gate decodes to the allowed path, may be matched by the controller mapping and then carries the fixed `instance`. What is fixed in every environment: no answer on a bootstrap path holds any byte of the raw request URI, and `instance`, when present, is exactly one of the two operation paths.

**Request bodies (Revision 2).** Both bodies are read by one strict reader (duplicate keys and trailing tokens fail). Two kinds of 400, never mixed:

- **Unreadable body: `400 bad-request`**, no `fieldErrors`, the shared admin `BadRequest` text: `type` `https://sahaj.in/problems/bad-request`, `title` "Bad Request", `detail` "The request could not be understood. Check it and try again." Cases: the body is empty or not JSON; it is not a JSON object; a key appears twice; something follows the object; it has a field the schema does not list; a listed field holds a value that is neither a string nor `null` (number, boolean, array, object). The page always sends a well-formed body, so only a hand-made call sees this; naming a field would be wrong (the fault is the shape, not a value), and the unknown name is never echoed.
- **Readable body with a missing, `null` or blank field: `400 validation`** with `fieldErrors` and the fixed texts of the stories table (SAH-42 "Field errors", "Blank PIN"). A missing field and a `null` field are treated as an empty string.

| Call | Case | Answer | Counted / ticket |
| --- | --- | --- | --- |
| unlock | unreadable body (list above) | `400 bad-request` | not counted, not audited |
| unlock | `pin` missing, `null`, empty or whitespace only | `400 validation`, `[{field: pin, message: "Enter the PIN."}]` | not counted, not audited (BR7f) |
| unlock | any other string | judged as a PIN (D3) | counted when the try starts, before the compare (D4, Revision 3); a correct PIN then resets the count |
| register | body unreadable **and** no valid ticket could be read from it | `401 bootstrap-ticket-invalid` (the ticket check comes first, D6 step 1) | cookie cleared |
| register | valid ticket read, rest of the body unreadable (unknown field, non-string value) | `400 bad-request` | ticket not spent |
| register | readable, field errors | `400 validation` with `fieldErrors` (D6 step 2) | ticket not spent |

Order of answers is unchanged: unlock is closed (404), locked (423), then body (400), then (Revision 3) waiting for the turn (429 after 10 s), then the PIN; register is closed (404), locked (423), ticket (401), then body (400 bad-request), then form (400 validation). So a caller without a ticket never learns anything from the body checks, and a closed feature is always the empty 404 whatever the body. A body over 4 KB is 413 and a non-JSON `Content-Type` is the empty 404 (K6), both before this step. Nothing in any 400 echoes a submitted value or field name.

### D3 · The PIN: BCrypt cost 14, constant-time compare, made by a hidden-prompt tool

**Algorithm.** BCrypt via `BCryptPasswordEncoder` from `spring-security-crypto` (present). Argon2id would need BouncyCastle, a new runtime library: not chosen without the human (H-BOOT-5). PBKDF2 is available but adds a second hash format to the admin realm for no gain at this size.

- Cost: the tool writes **14** (about 1 s per check on a laptop). The server accepts 12 to 16 (B4), so a hash made elsewhere at 12 (the team's password cost) also works.
- Honest limit: a 6-digit PIN cannot survive an offline attack on its hash. 10^6 BCrypt-14 checks is days on one core and hours on a GPU. The hash keeps the PIN out of plain sight in `.env`; it does not protect it from someone who can read `.env` (who also holds the admin JWT and TOTP keys, i.e. has the machine). The online controls (D4, reach) are what make 6 digits acceptable, and only on a developer machine (DEC-034).
- **Compare.** `BCryptPasswordEncoder.matches` (Spring's `BCrypt` compares the final bytes without early return). Wrapped in one dev-tools class `BootstrapPinVerifier.matches(char[] typed)` with a unit test (story 2). Input rules before the compare: a missing, `null`, blank or whitespace-only PIN is a 400 form error ("Enter the PIN."), **not counted** (BR7f); an unreadable body is `400 bad-request`, not counted (D2 "Request bodies"). Anything longer than 64 characters or 72 UTF-8 bytes is **a wrong PIN, counted**, and is checked against a fixed dummy hash of the same cost so the time does not differ. The typed PIN is compared exactly as sent (no trimming, no digit rule: the PIN may later be longer or not numeric, BR5). The `char[]`/`byte[]` copies are zeroed after use; the request DTO's `toString()` prints no value.
- The hash is read once at start into the verifier; it is not a property exposed by any endpoint, and never logged.

**How the human makes the hash (OQ-42-10).** A tiny command-line tool in the dev-tools source set (absent from production jars): `com.sahaj.platform.devtools.bootstrap.BootstrapPinHashTool` with a `main` that

1. stops with "Run this in a terminal window (no console found)." when `System.console()` is null (IDE consoles), so it never falls back to echoing input;
2. reads the PIN twice with `System.console().readPassword("New registration PIN: ")` and `("Type it again: ")`, which do not echo;
3. refuses (and prints only a fixed reason) when the two differ, or the PIN is shorter than 6 or longer than 64 characters or over 72 UTF-8 bytes;
4. prints **only** the hash (`$2a$14$...`) on one line, zeroes both arrays, and exits. Nothing else is printed, nothing is written to disk.

The human runs, in PowerShell, after `mvn -f backend/pom.xml -Pdev-tools -DskipTests package`:

```
java "-Dloader.main=com.sahaj.platform.devtools.bootstrap.BootstrapPinHashTool" -cp backend\target-devtools\sahaj-backend-devtools-<version>.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

The command line holds no PIN, so shell history holds no PIN. The human pastes the printed hash into `.env` as `SAHAJ_ADMIN_BOOTSTRAP_PIN_HASH='<hash>'` (single quotes: the value contains `$`, which some `.env` loaders expand; if a loader mangles it, B4 fails and the startup line says so). The PIN is never pasted into a chat, an issue, a file or a test. Alternative if the human already has Apache tools: `htpasswd -nBC 14 x` (prompts without echo; copy the part after `x:`; `$2y$` is accepted). `scripts/` is human-owned: the human may wrap the `java` line in a script; no agent writes it.

### D4 · Global wrong-PIN count and 60-minute lock, in the database, serialised

One platform-level row (`platform.platform_admin_bootstrap_state`, Data needed) holds the count, the lock end, the open ticket and (Revision 3) the lease of the one try being judged. It survives a restart (BR7b).

#### Revision 3: count first, judge after (security M1)

**The defect it fixes.** Revisions 1 and 2 counted a wrong PIN in `admin_bootstrap_unlock_failed`, called **after** the BCrypt compare, in the same transaction as the compare's `begin`. If that call (or its 5th-try branch that writes the lock and the `LOCKED` audit row) raised for any reason, the transaction rolled back: the wrong guess was not counted and the caller saw a 500, while a correct PIN still took the other branch and answered 200. Every failure that hits the wrong-PIN path and not the right-PIN path turns the endpoint into an unlimited oracle (about one guess per second at BCrypt 14).

**Why "count first in the same transaction" is not enough.** Moving `failures + 1` into `begin` but keeping one transaction does not close it: any failure after the compare (the audit insert, the lock write, the commit itself, a dropped connection) rolls the whole transaction back, the increment with it, and the wrong-PIN path still differs from the right-PIN path in the answer (500 against 200). The general rule is: **the try must be durably counted before the compare's result can exist.** In PostgreSQL that means the count is committed in its own transaction before the compare starts.

| Option | Verdict |
| --- | --- |
| A · Count in `begin`, one transaction, compare under the row lock (the review's sketch) | Not chosen. A rollback after the compare undoes the count; the oracle remains for every failure after the compare. |
| A2 · As A, plus a savepoint around the post-compare calls and a forced commit | Not chosen. Safety then depends on every Java code path catching and committing correctly; a lost connection or a failed commit still loses the count. Fail-open by construction, only less likely. |
| **B · Two short transactions: claim (count and commit), compare with no transaction, judge** | **Chosen.** Once the claim has committed, nothing that happens later (exception, rollback, crash, killed connection, JVM exit) can give the try back. The worst a failure can do is leave a try counted and unjudged, which fails closed. |
| C · Count in Java memory | Not chosen. Lost on restart (BR7b), not shared between processes. |

**Serialising without holding a row lock through BCrypt.** A row lock cannot outlive the commit that makes the count durable, so the "one compare at a time" rule moves from the row lock to a **lease** in the state row: `try_id uuid` and `try_expires_at timestamptz` (both set or both null). `begin` gives the lease to the caller's try when it counts it; only the holder of a live lease may be judged; a new try cannot start while a live lease exists. Lease length: **30 seconds** (a constant in the SQL; BCrypt cost 16, the slowest accepted, takes a few seconds on a laptop). Effects:
- At most **one try is in flight** across all callers and all processes, as before. No database transaction, row lock or pooled connection is held during the BCrypt compare (better than before: the row stays free for `register`, which does not need the lease).
- The count can never pass 5 and is exact: each try takes exactly one count slot, in order.
- A request that dies after its claim (exception, crash, killed connection) leaves the try counted and the lease in place until it expires; the next `begin` after the expiry records it in the audit (`ADMIN_BOOTSTRAP_UNLOCK_UNJUDGED`, D7) and clears the lease.

**Unlock, step by step (dev-tools service; READ COMMITTED; never `REPEATABLE READ` or higher).** The service method itself is **not** transactional (`@Transactional(propagation = NEVER)`, so calling it inside a transaction fails at once); it runs up to three separate short transactions through a `TransactionTemplate`:

1. **Read the body** (D2 "Request bodies"), in memory, no database.
2. **Body unreadable, or `pin` missing/null/blank: peek, never count.** One read-only transaction: `admin_bootstrap_ticket_status(null, null)`, which returns `CLOSED` (empty 404), `LOCKED` with `locked_until` (423), or anything else (the 400 of D2). No row lock, no count, no audit, `begin` is never called. So the answer order of D2 (closed, locked, body) holds and a blank PIN or unreadable body is never counted (BR7f).
3. **Claim (transaction T1).** Java makes a fresh random `try_id` (`UUID.randomUUID()`) and calls `admin_bootstrap_begin(try_id)` (row `FOR UPDATE`, `lock_timeout` 10 s). It returns `(outcome, failures, locked_until)`:
   - `CLOSED`: an admin exists; nothing written; commit; empty 404.
   - `LOCKED`: a lock is in force; nothing counted, no compare, no audit of this request; commit (the commit also keeps the one `ADMIN_BOOTSTRAP_UNLOCK_UNJUDGED` row and the cleared lease when this `begin` found a run-out lease, D7); `423` with `retryAfterSeconds` computed from `locked_until` (below).
   - `BUSY`: another try holds a live lease; nothing counted; commit. Java waits 250 ms and repeats step 3 (each attempt its own transaction, a new `try_id` not needed but allowed) until **10 seconds** from the first attempt have passed (measured with an injected `Clock`), then answers `429 rate-limit`, `Retry-After: 5`, `retryAfterSeconds: 5`; **not counted**. A `55P03` from `begin` (row lock wait over 10 s) gives the same 429, not counted.
   - `COUNTED`: in the same statement the database has added 1 to `failures`, given the lease to `try_id` (`try_expires_at = clock_timestamp() + 30 s`) and, **if this is the 5th try**, already set the lock (`locked_until = clock_timestamp() + 60 min`) and cleared the ticket columns (BR7e). Commit.
   - **The compare must not start until T1's commit has returned without error.** If the commit throws, answer the bodyless 500 and never compare (the database decides whether the try was counted; either way no result is produced).
4. **Compare (no transaction).** `BootstrapPinVerifier.matches` (D3: dummy hash for over-long input, constant time). The PIN copies are zeroed afterwards. If the verifier throws: bodyless 500, no judge call; the try stays counted (and, if it was the 5th, the lock stays).
5. **Judge (transaction T2).**
   - Wrong: `admin_bootstrap_unlock_failed(try_id, ip, request_id)`. It does **not** change the count. It checks that `try_id` holds a live lease, clears the lease, writes `ADMIN_BOOTSTRAP_UNLOCK_FAILED` ("wrong PIN ({failures} of 5)") and, when the row is locked (this try was the 5th), `ADMIN_BOOTSTRAP_LOCKED` with `after_json.lockedUntil`. Returns `(failures, locked_until)`. Commit, then: `failures` 1 to 4: `401 bootstrap-pin-invalid` with `triesLeft = 5 - failures` (4 to 1); `failures = 5` (`locked_until` set): `423 bootstrap-locked`, `retryAfterSeconds = 3600`, `Retry-After: 3600`, and the one WARN lock line (D8). Any other pair (for example 5 without a lock) is a bodyless 500.
   - Correct: `admin_bootstrap_unlock_succeeded(try_id, ticket_hash, binding_hash)`. It checks the live lease, then sets `failures = 0` (BR7c), `locked_until = null` (this lifts the lock that the 5th try's own claim set, so "4 wrong, then correct, unlocks" still holds: no other lock can coexist with a live lease, because `begin` refuses to count while locked), replaces the ticket (BR8, expiry `clock_timestamp() + 5 min`), clears the lease. Not audited (OQ-42-9). Commit, then `200` with the ticket and the binding cookie (D5).
   - **Any exception from T2 rolls back T2 only.** `SB001` (an admin appeared in between): empty 404. Everything else (`SB003`, `SB004`, `55P03`, `42501`, `22023`, any other SQLSTATE, a failed commit): bodyless 500. **Never 200 and never 401 after a failed judge.** T1's count stays in every case.

**Rollback paths, all fail closed.**

| Failure | What is rolled back | Try counted? | What the caller learns |
| --- | --- | --- | --- |
| Body unreadable or PIN blank | nothing written | no (decided before `begin`, BR7f) | 400; nothing about the PIN |
| `begin` waits over 10 s (`55P03`) or `BUSY` for 10 s | T1 (nothing written) | no | 429; nothing about the PIN (no compare ran) |
| T1 fails or its commit fails | T1 | no | 500; no compare ran |
| Request dies after T1, before or during the compare (exception, crash, connection drop, JVM exit) | nothing (T1 committed) | **yes**; lease expires after 30 s; next `begin` writes `UNJUDGED` | 500 or no answer; no result |
| Verifier throws | nothing | **yes** | 500 |
| `unlock_failed` raises (audit insert, lock audit, anything) | T2 | **yes** (and the 5th try's lock stays) | 500, same as a failed correct-PIN judge |
| `unlock_succeeded` raises | T2 | **yes** | 500 (the correct PIN did not unlock; try again after the lease expires, or after the lock if it was the 5th) |
| T2 commit fails | T2 | **yes** | 500 |

Since a try is counted whatever happens after T1, a failure that hits only the wrong-PIN path costs the attacker the same try as a normal wrong PIN: at most 5 guesses per 60 minutes, as designed. A failure on the 5th try leaves the lock in force even when the PIN was right; that is the intended fail-closed cost (the human waits or runs the clear-lock runbook).

**What does not change.** No compare, count or audit of the refused request while a lock is in force (the lock still caps CPU). The only row a `begin` may write during a lock is the single `UNJUDGED` row for an earlier counted try whose lease ran out (D7); it is written once, because the same `begin` clears the lease. A correct PIN as the 5th try unlocks. A correct PIN resets the count to 0. The count restarts at 0 when a lock ends (`begin` clears an expired lock). The dummy-hash path for over-long input is counted like any other non-blank PIN (the claim comes before the compare, so the over-long case cannot be uncounted either). The ticket slot is untouched by a wrong PIN (except that the 5th try's claim clears it, BR7e) and replaced only by `unlock_succeeded`. `triesLeft` values are unchanged for the caller: after the n-th wrong PIN in a row, `triesLeft = 5 - n`; Java takes `n` from the `failures` that `unlock_failed` returns (the count already holds this try), **not** `failures + 1`.

**Register is unchanged** except that `ticket_status` and `register` now also return `locked_until` (D6 step 1), and register never calls `begin` (which would count a try).

Numbers are constants in the database functions (5 tries, 60 minutes, 5 minutes, 10-second lock wait, 30-second lease), not settings. The database clock (`clock_timestamp()`, not `now()`, which is frozen at transaction start) is the only clock that sets or judges a lock or a ticket: Java does not pass times in, so no caller can move a lock. Tests that need "30 minutes later", "5 minutes and 1 second later" or "the lease ran out" move the stored `locked_until` / `ticket_expires_at` / `try_expires_at` as `sahaj_migrator` (time travel by data).

**`retryAfterSeconds` (and `Retry-After`) for a lock** is computed in Java, only for the answer, from the `locked_until` the database returned: `ceil(locked_until - Instant.now())` in seconds, clamped to 1 to 3600 (the contract's range). The 5th wrong PIN answers the fixed 3600. Java and the database run on one machine, so the clock difference does not matter; the database alone decides whether the lock holds. The UI shows `ceil(seconds / 60)` minutes.

No time decay of the count (OQ-42-5): four wrong PINs a week apart plus one lock.

### D5 · The ticket: two halves, both hashed at rest, single use, 5 minutes

| Option | Verdict |
| --- | --- |
| One token in the JSON body | A copy works from any browser: not "bound to the browser". |
| One token in an `HttpOnly` cookie only | Bound to the cookie jar, but rides along automatically. |
| **Body ticket + `HttpOnly` binding cookie (chosen)** | Both are needed. A copied body ticket from another browser has no cookie; a cookie alone has no ticket. Same body-token pattern as the ADR-003 pre-auth token. |

- **Ticket**: 256 random bits (`SecureRandom`), Base64url without padding (43 characters), returned in the unlock body; the page keeps it in component memory only (never storage, URL or history). Sent back as `ticket` in the register body. Never in a URL or header.
- **Binding**: another 256 random bits in cookie `sahaj_admin_bootstrap`, `HttpOnly; SameSite=Strict; Path=/api/v1/admin/bootstrap; Max-Age=300`, `Secure` except when the existing dev-only `refresh-cookie-secure: false` applies (plain `http://localhost`). The path covers only the two bootstrap calls; the cookie never reaches any other admin or clinic endpoint.
- **At rest**: only `HMAC-SHA256(k, value)` hex of each, with `k = HMAC-SHA256(SAHAJ_ADMIN_JWT_SECRET, "sahaj-admin-bootstrap-ticket-v1")` (ADR-003 D3 keyed-hash pattern, its own label). Someone who can run SQL cannot compute a stored value. The equality test on keyed hashes in SQL leaks nothing usable through timing.
- **Valid** when: both hashes equal the stored pair, `ticket_expires_at > clock_timestamp()` (clock starts at unlock, not at the last form try), no lock, no admin. One slot only: a new unlock replaces it.
- **Spent** only by a successful creation (D6). An invalid form does **not** spend it (OQ-42-7); a database failure rolls back and does not spend it.
- **Refused** (missing, empty, malformed, unknown, expired, foreign cookie, replaced, already spent): `401 bootstrap-ticket-invalid`, the response clears the cookie (`Max-Age=0`). While locked: `423 bootstrap-locked` instead (story 3). Once an admin exists: the empty 404.
- **Useless elsewhere**: it is not a JWT, carries no role, is stored in its own table, and the admin JWT filter and pre-auth lookups never see it.
- Survives a restart (it is in the database); that is allowed and harmless (5 minutes).

### D6 · Registration and enrolment (OQ-42-3 option a)

**Register, one transaction** (READ COMMITTED; `CLOSED`, `LOCKED` and `INVALID` write nothing of their own, so the transaction commits and the controller maps the outcome afterwards, as for unlock):
1. Gate (D2), then `admin_bootstrap_ticket_status(ticket_hash, binding_hash)` returns `(status, locked_until)` with status `CLOSED` (empty 404), `LOCKED` (423), `INVALID` (401) or `VALID`. Checked **before** the form, so nobody without a ticket learns anything from validation. It takes no lock and never waits.
   - **`LOCKED` from `ticket_status` or `register` (Revision 3):** both now return `locked_until` with the status, so Java computes `retryAfterSeconds` as in D4 from that value (clamped to 1 to 3600). The Revision 1 follow-up call to `admin_bootstrap_begin()` is **removed**: `begin` now counts a try and must never be called by register.
2. Validation in Java, with the existing code: `AdminProvisioning.prepare(email, fullName, password)` (trim and lower-case email, pattern and length, name 1 to 120 trimmed, `AdminPasswordPolicy`: 12 to 64 characters, at most 72 UTF-8 bytes, not containing the email part before `@` case-insensitively; then `AdminPasswordHasher` BCrypt 12). Errors: `400 validation` with `fieldErrors`; an unreadable body (unknown field, non-string value, and the other cases of D2 "Request bodies") is `400 bad-request` without `fieldErrors`. No breached-password check (OQ-42-2). The ticket is not spent.
   - **Field errors, fixed texts (stories table "Field errors"):** `fullName` "Enter the full name." (missing, `null`, blank after trimming, or over 120 characters after trimming); `email` "Enter a valid email."; `password` "The password must be 12 to 64 characters and must not contain the first part of your email." The stories' "That email is already used." cannot occur: register runs only while no admin exists, and an email clash at insert means one does (`CLOSED`, empty 404). "The two passwords do not match." is the page's own check (OQ-42-4).
   - **Control characters (Revision 3, code review finding 9).** JSON allows `\u0000` and other control escapes inside a string; PostgreSQL `text` cannot store `U+0000` and refuses it at insert, which gave a bodyless 500 (rolled back, ticket unspent). Options: accept the 500 and document it; strip the characters (changes what the owner typed, silently); **refuse them as a field error (chosen)**. Rule, applied by the bootstrap service to the **raw** value before any trimming (Java's `String.trim()` removes control characters at the ends, so checking after trimming would let a leading `\u0000` through as a different name): `fullName` or `email` containing any character of Unicode general category `Cc` (U+0000 to U+001F and U+007F to U+009F, which includes `\u0000`, tab, line feed and carriage return), or an unpaired UTF-16 surrogate (a lone `\uD800`-style escape, which the JDBC driver would otherwise turn into `?`), is a field error with the existing fixed text: `fullName` "Enter the full name."; `email` "Enter a valid email.". No new text. A bad email in this sense is "the first wrong of email or password", so the password is then not judged (the two-error rule below). The password is not checked for control characters: it is never stored as text (BCrypt only) and ADR-003 D2.1 has no composition rule. The check sits in the bootstrap service, not in the shared `AdminProvisioning` (changing the ADR-003 paths is a separate story). A 500 for these inputs is a defect.
   - **At most two field errors, by design (Revision 2).** The name is checked by the bootstrap service itself; email and password go through the shared `AdminProvisioning.prepare`, which stops at its first refusal (email before password, since the password rule needs the email). So the answer holds `fullName` (if wrong) plus the **first** of `email` or `password` that is wrong; a wrong password is reported only once the email is right. Kept, not widened to all errors: `prepare` is the single source of the ADR-003 D2.1 rules for every admin-creating path, and changing its contract for a once-per-database form is not worth a second rule copy; the page checks required fields and the password length before sending; a rejected form does not spend the ticket, so the owner fixes and sends again within the 5 minutes. Clients must not assume the list is complete.
3. `admin_bootstrap_register(ticket_hash, binding_hash, admin_id, email, full_name, password_hash, ip, request_id)`: takes **the same transaction advisory lock key as ADR-008's `admin_dev_create_sample_admin`** (so the two creation paths serialise), then the state row `FOR UPDATE`, both waits bounded by `SET lock_timeout = '10s'` (a register queued behind unlocks, each holding the row for about a second of BCrypt, must not wait without limit). A wait over 10 s raises `55P03`: roll back, `429 rate-limit` with `Retry-After: 5` and `retryAfterSeconds: 5`; nothing is created, the ticket is not spent and the same ticket may be sent again while it is valid (`admin.yaml` `bootstrapRegister` 429). Then it returns (Revision 3: as `(outcome, locked_until)`, `locked_until` set only with `LOCKED`) `CLOSED` if any admin exists, `LOCKED`, `INVALID`, or inserts the admin (**not enrolled**: TOTP columns null, `active = true`, no tenant), clears the ticket, writes `ADMIN_BOOTSTRAP_ADMIN_CREATED`, returns `CREATED`. A unique violation on email is mapped to `CLOSED` (it can only mean an admin exists). Two simultaneous registers: one `CREATED`, the other `CLOSED` → empty 404 (BR4).
   - **Revision 5: this call is the last database step of the register transaction.** After it returns `CREATED`, Java makes no further database call; the only thing left is the commit. A failed commit (or any exception between `CREATED` and the commit) rolls the transaction back: no admin, ticket unspent, no `ADMIN_BOOTSTRAP_ADMIN_CREATED` row, bodyless 500; the owner may send the same ticket again while it is valid. (If the connection drops during the commit itself, the outcome is unknown to Java; a later register then answers either `201`/`401` or, if the commit did land, the empty 404, and the owner signs in at `/admin/sign-in`. Same class as page-review I-5.)
4. **(Revision 5, removed.)** Up to Revision 4, Java issued an ADR-003 ENROL pre-auth token here through `platform.admin_preauth_create`. It does not any more: register writes nothing to `platform.platform_admin_preauth` and calls no ADR-003 sign-in function. Its failure path ("pre-auth issue fails after `CREATED`, everything rolls back") no longer exists.
5. Answer `201` **with no body** (no `Content-Type`, `Content-Length: 0`), `Cache-Control: no-store`, `Pragma: no-cache`, and the binding cookie cleared (`Max-Age=0`). No `Location` (the admin has no resource in this API).

| Option for the 201 (Revision 5) | Verdict |
| --- | --- |
| Keep `{next: ENROL, preAuthToken, expiresInSeconds}` | Not chosen (human, L-4): a live credential in an answer no client reads |
| `{next: SIGN_IN}` | Not chosen: a constant that says nothing the status does not; needs a schema, a DTO and a redacting `toString()` for no information |
| **`201` with no body** | **Chosen.** Smallest and most honest: "created; the registration is closed"; the next step is fixed and documented (sign in). Easy to assert: status 201, empty body, no `Content-Type`, cookie cleared, no row in `platform_admin_preauth` |

**Enrolment = the existing sign-in step, at `/admin/sign-in` (Revision 4, DEC-035 option C; Revision 5: the 201 has no body).** On `201` the page `/admin/register` drops all its state (PIN, ticket, name, email, both password fields) and navigates to `/admin/sign-in`. It does **not** call `/auth/totp/enrol` or `/auth/totp/verify` and has no Step 3 ("Set up your authenticator app") card. That step stores the secret encrypted (`TotpSecretCipher`), shows the **10 recovery codes once** (not new logic; OQ-42-3 default), audits `ADMIN_TOTP_ENROLLED` and `ADMIN_SIGNED_IN`, sets the `sahaj_admin_rt` cookie and opens the console. The same path covers a browser closed after register: the admin exists, the registration is closed, and sign-in offers enrolment.

| --- | --- |
| A · a root service hands the pre-auth token to `AdminSignInPage` in memory | Not chosen by the human. Passes a token between pages, which ADM-1 was designed to avoid, and changes the reviewed ADM-1 page |

- Consequence for the server (Revision 5, replaces the Revision 4 note and its recommendation, which the human accepted): register issues no pre-auth token and returns no body (steps 4 and 5). The first sign-in at `/admin/sign-in` issues its own ENROL pre-auth token through the unchanged ADR-003 path (`/auth/login` → `admin_preauth_create`), so the enrolment path is exactly what it was. An admin created by register is never left without a way to enrol: any admin with null TOTP columns gets `next: ENROL` at sign-in.
- In the dev profile `sahaj.admin.totp.dev-bypass` is on, so any 6 digits confirm. The secret is still stored; the human should still add the key to a real authenticator app (D2.6) so the admin works when the bypass is off.

**Why the admin has no tenant.** ADR-003 D1: a platform admin is a separate identity in `platform.platform_admin`, without `tenant_id`, membership or `app_user` link; it sees clinics only through the audited definer functions of D4 there. Giving it a tenant would put a "belongs to everyone" credential inside the clinic RLS tables. Registration therefore binds no tenant and writes no tenant table (BR11, BR14).

### D7 · Audit

In `platform.platform_admin_audit` (append-only, ADR-003 D7), written **by the database functions** in the same transaction, kind `AUTH`, `auth_step` null, `target_tenant_id` null, with `ip` (socket address) and `request_id`:

| Action | Outcome / refusal code | Admin id, name | Summary | Other |
| --- | --- | --- | --- | --- |
| `ADMIN_BOOTSTRAP_UNLOCK_FAILED` | `REFUSED` / `pin-invalid` | none | "Bootstrap registration: wrong PIN ({n} of 5)" | none |
| `ADMIN_BOOTSTRAP_LOCKED` | `REFUSED` / `locked` | none | "Bootstrap registration locked for 60 minutes" | `after_json = {"lockedUntil": "<ISO 8601 UTC>"}` |
| `ADMIN_BOOTSTRAP_UNLOCK_UNJUDGED` (Revision 3) | `REFUSED` / `try-unjudged` | none | "Bootstrap registration: a counted try ended without a result" | written by `admin_bootstrap_begin` when it finds a lease that ran out (the try was counted but its judge never committed), once, at the first `begin` after the lease's 30 seconds, whether or not a lock is in force (Data needed 3, step (2) before (3)); `ip` and `request_id` null (they belong to the lost request, which is not stored) |
| `ADMIN_BOOTSTRAP_ADMIN_CREATED` | `APPLIED` | new admin's id and name | "First admin created through bootstrap registration" | none |
| `ADMIN_BOOTSTRAP_LOCK_CLEARED` | `APPLIED` | none | "Bootstrap registration lock cleared by hand" | written only by the human-run runbook (OQ-42-14) |

**Audit and the count (Revision 3).** `UNLOCK_FAILED` and `LOCKED` are written by the judge (T2), because only then is it known that the PIN was wrong; a correct unlock stays unaudited (OQ-42-9), so the claim (T1) cannot write a "failed" row in advance (the audit table is append-only). If T2 fails, the try is counted but has no row at that moment; the lease then runs out and the next `begin` writes `ADMIN_BOOTSTRAP_UNLOCK_UNJUDGED`, so every counted try ends up with exactly one of `UNLOCK_FAILED`, `UNLOCK_UNJUDGED`, or (correct PIN) no row. **Timing (Revision 3 (f)).** `begin` clears a run-out lease (step (2)) before it checks the lock (step (3)), so the `UNJUDGED` row is written at the **first `begin` after the 30-second lease runs out**, also while the 60-minute lock still holds; that `begin` then answers `LOCKED` (423) and its commit keeps the row. Later `begin` calls find no lease and write nothing. Chosen over "at the first `begin` after the lock ends" because it records the lost try sooner (within the lock, not up to 60 minutes later), keeps one fixed step order with no special case, cannot repeat (the lease is cleared in the same update), and changes neither the count, the lock nor any answer. Residual: when the unjudged try was the 5th, the lock is in force without a `LOCKED` row (only `UNJUDGED`); the state row shows the lock. Accepted (dev only; the count, not the audit, is the control).

Never in any row: a PIN (right or wrong), any typed text, a hash of anything, a ticket or binding, a password, an email, a TOTP secret, a try id. Not audited: a correct unlock (OQ-42-9), a refusal while locked, a blank PIN, an invalid ticket, validation errors, and every 404 (BR12). The two other dev paths keep their own actions (`ADMIN_DEV_SAMPLE_*`, the seed writes none).

### D8 · Logging

- No request or response body logging on `/api/v1/admin/bootstrap/**` (and none may be added). Request DTOs (`pin`, `ticket`, `password`, `email`) and the unlock response DTO (`ticket`; Revision 5: register has no response DTO) have `toString()` that prints no value, so Spring `DEBUG` "Read"/"Writing [...]" lines carry nothing.
- Allowed lines: the startup line (D2); `INFO Bootstrap registration: wrong PIN ({n} of 5)` with request id; `WARN Bootstrap registration locked until <lockedUntil>`; `INFO Bootstrap registration: admin created` with admin id and request id. Never the name, email, PIN, hash, ticket, cookie, password or key.
- **The lock line (Revision 2).** Written **exactly once per lock**, by the unlock call whose wrong PIN sets the lock (the 5th), after the commit, at `WARN`, with the request id from the MDC. (Revision 3: after the commit of the judge T2; if T2 fails there is no lock line, only the 500 line with class and SQLSTATE.) `<lockedUntil>` is the `locked_until` returned by `admin_bootstrap_unlock_failed`, printed as `Instant.toString()` (ISO 8601 UTC, e.g. `2026-11-10T06:05:00Z`), the same value the `ADMIN_BOOTSTRAP_LOCKED` audit row holds. An unlock or register **refused because a lock is already in force** writes no log line (it is not audited either, D7): a hostile local loop must not be able to fill the log, and the one line plus the audit row already say when the lock ends.
- Exceptions carry no request data (ADR-008 R4); a database error is logged as class plus SQLSTATE.
- The binding cookie header is never logged (no header logging on this path).

### D9 · Frontend (only after the human signs off DEC-013 item 16)

Route `/admin/register` in the lazy admin feature, outside the console shell, no link from anywhere (BR16). Stays in every build (OQ-42-11 default): the bundle holds no secret, and the server answers 404 everywhere else. Calls go through the dev proxy (`/api`), with `withCredentials` for the binding cookie. Revision 4 (DEC-035): the app has no "page not found" screen; an unknown address goes to the home page through the `**` route, and a 404 from either call (closed feature) does the same, so a closed feature looks like the home page. The PIN, ticket and passwords live in component memory only and are cleared after use; no `localStorage`, no URL, no history state. On the register 201 (no body, Revision 5) the page navigates to `/admin/sign-in` (D6); it does not read a body. The PIN field is `type="password"` with `autocomplete="one-time-code"` (browsers ignore `autocomplete="off"` on password fields and may offer to save the PIN; Chromium does not offer to save one-time codes; checked by hand in Chrome and Edge, DEC-035 question 2). Texts are the UI's own fixed texts from the stories table, never the problem `title`/`detail`.

## Threats and mitigations

| Threat | Mitigations | Residual |
| --- | --- | --- |
| **Brute force of the PIN** | 5 wrong tries lock everyone for 60 minutes, stored in the database, survives restart; (Revision 3) each try is counted and committed **before** the compare, under a one-try lease, so parallel tries cannot overshoot; no compare during a lock; BCrypt 14 per try; reach loopback only | Expected time to guess online: about 10^6 / 5 per hour, decades. None practical |
| **Fail-open count (security M1)** | Revision 3: the claim commits the count before the compare; the judge only records the outcome; any failure after the claim leaves the try counted (D4 "Rollback paths"); forced-failure ITs prove it | A failed judge on a correct 5th try leaves the lock in force (fail closed; clear-lock runbook) |

## Consequences

**Positive.** The human creates the first admin from a page with a PIN, then the page closes by itself. Production jars carry none of it. No new library. Password, hashing, enrolment, recovery codes and sign-in are the existing ADR-003 code. The app still connects only as `sahaj_app`; no tenant table is read or written.

**Negative / accepted.** A third dev way to make the first admin. One more dev-only table and five functions in dev/test databases, created by a callback (not a versioned migration). The main reserved-path filter grows a second prefix and multi-gate logic. The human must start the backend with `-Pdev-tools` to use the page. A local process can lock the human out for 60 minutes. The `.env` switch is weaker than ADR-008's command-line rule (H-BOOT-2). Revision 3: an unlock is now two database transactions and a 30-second lease; a server failure during the 5th try locks the human out even with the right PIN (fail closed); a 500 on unlock costs a try; the Windows local-peer exposure (M3) rests on an operating rule until the human decides H-BOOT-2 or H-BOOT-6.

## Usage note (for the human, once approved and built)

0. Not before the skipped database ITs have run green (security review condition), and with a new PIN of at least 10 random characters that was never typed in a chat (security M2).
1. Make the hash (D3); put it and `SAHAJ_ADMIN_BOOTSTRAP_ENABLED=true` in `.env`.
2. Before starting: stop containers (Docker Desktop), WSL in mirrored networking mode, VS Code port forwarding, dev tunnels, `netsh interface portproxy` rules, `ng serve --host 0.0.0.0` and published container ports. **Turn the switch on only for the minutes needed** (Revision 3, security M3).
3. `mvn -f backend/pom.xml -Pdev-tools spring-boot:run`; check the startup line says "is on".
4. `npm --prefix frontend start`; open `http://localhost:4200/admin/register` on the same machine.
5. Enter the PIN and create the admin; the page then opens `/admin/sign-in`. Sign in with the same email and password, enrol the authenticator, save the recovery codes. (A 500 on unlock has still used one try; wait 30 seconds before trying again, Revision 3.)
6. **Straight away:** set `SAHAJ_ADMIN_BOOTSTRAP_ENABLED=false` and remove the hash from `.env`; restart. (It is already closed because an admin exists.) Then the tools of step 2 may be started again.
7. The whole time the switch is on: no tunnels, port proxies, containers, WSL mirrored mode, `ng serve --host 0.0.0.0` or published container ports.
