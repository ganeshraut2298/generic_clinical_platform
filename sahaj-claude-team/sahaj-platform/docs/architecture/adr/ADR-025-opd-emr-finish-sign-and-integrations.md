## Context

Facts checked in the code and contracts on 13 Nov 2026 that decide the shape:

1. **Module graph** (Spring Modulith verifies it): `platform ← patient ← opd ← billing ← ipd`, plus `ipd → opd.api` and `ipd → billing.api`. **opd must never import billing or ipd; patient must never import opd.** Every reach from opd into billing or ipd is a port declared in `opd.api` and implemented by the other module (ADR-020 D9, ADR-022 D1).
2. **Follow-ups (SAH-14):** `FollowUpService.createForConsultDone` runs inside `VisitService.moveStage` when a visit leaves WITH_DOCTOR and the visit's workflow version has the `followup` step on; due = visit day + `followUpDays`; reason "Review after treatment"; `insertIfAbsent` on the unique source visit (one per visit).
3. **OPD vitals step stores no values** (ADR-020 context; the Vitals step is a stage of `opd.visit`). **SAH-28 Emergency registration has no vitals fields** (name, age, sex, mobile, complaint, level). Only the IPD nursing chart (`ipd.vitals`: BP, pulse, SpO₂, temperature °C, RR, recorder, time; SAH-30) holds nurse vitals.
4. **IPD medicine orders (SAH-31, ADR-009)** use ipd's own catalogue (`DrugKey`, 14 drugs), four `FrequencyKey`s, four override reasons and a `checkToken`; roles OWNER and DOCTOR; idempotent by `clientKey`; BLOCKED and NEEDS_REASON are 200 outcomes. The EMR prescription component (ADR-022 D4) uses opd's medicine master. **The two lists do not map.**
5. **IPD charges (SAH-25)** are a fixed ipd charge-service list, added by OWNER, FRONT_DESK, NURSE. **DEC-042 H8 (decided): IPD round and ER records create no bill lines.**
6. **An Emergency case has no patient until admitted** (ADR-005); statuses WAITING, SEEN, ADMITTED, RELEASED, REFERRED; release and refer are OWNER, NURSE, DOCTOR under the clinic IPD advisory lock and the case row lock. There is no "sent to OPD" close reason.
7. **Admission (SAH-23)** is OWNER, FRONT_DESK, NURSE only; a DOCTOR who is not the owner cannot admit (OQ-45-31 default accepted: the doctor sends a request). `AdmissionType` is `planned | emergency | daycare | maternity`.
8. **Patient record:** `allergy` and `chronic` are free text up to 400 each, no version column, last write wins (patient.yaml 0.2.0). The SAH-31 allergy-status function already reads "no known allergy" text as NONE_KNOWN.
9. **Billing** computes the consultation line from `opd.visit.fee_paise` on read; EMR lines are `bill_item.source_kind = 'EMR'` synced by `EmrVisitChargePort` (ADR-022 D7).
10. **OQ-43-27 is answered** (one record per IPD day and per ER case): the `encounter-drafts-not-enabled` guard of ADR-020 D8 can go.
11. **CLAUDE.md still lists six modules**; the human's edits for `notifications` and `integration` (DEC-040) are not done, so no sending code, queue table or consent kind is built (DEC-040: "Agents build the in-app parts … once the module rules exist").

## Decisions

### D1 · The sign is one database transaction, orchestrated in opd, with fixed lock order and an idempotency key

`POST /emr/records/{id}/sign` (header `Idempotency-Key`, body `revision` plus the finish choices) runs `EmrSignService.sign` (`com.sahaj.opd.application.emr.finish`), one `@Transactional` method, READ COMMITTED. Every other module is reached through a port that runs **in the caller's transaction** (`Propagation.MANDATORY` on the opd side, REQUIRED on the implementations), so any refusal anywhere rolls back everything: the record stays DRAFT, no bill line, follow-up, appointment, order, round mark or case close survives (SAH-51-2 "nothing is half done", SAH-67-1/2, SAH-69-3, SAH-63-3).

**Steps, in this order** (the order is also the lock order; nothing may lock in another order):
1. *(Emergency only)* `EmrEmergencyPort.lockCase` takes ipd's clinic IPD advisory lock and the case row lock **before** the record lock, because an ipd admission from the case takes the same IPD lock first and then reaches opd (D10). Status not WAITING or SEEN → 409 `case-closed`.
2. Lock the record row (`select … for update`). SIGNED: same idempotency key and same request hash → 200 replay of the stored `sign_result`; otherwise 409 `emr-record-signed` ("Already signed by Dr. <name>."). Stale `revision` → 409 `emr-record-changed`. Edit hold of another doctor not expired → 409 `emr-record-held` (D4).
3. Access: own patient (OPD: the visit's doctor; IPD round: the admitting doctor, H8; Emergency: IPD scope), OWNER with doctor details any (ADR-020 D10, D9). Then *(IPD_ROUND and ER_ASSESSMENT)* IPD Read-only → 409 `ipd-read-only` (opd's slug, as on open and draft save; security pre-review L2). A SIGNED record has already been answered in step 2, so a replay still works in Read-only. The ipd ports that write (`EmrRoundPort.recordSignedRound`, `EmrEmergencyPort.close`, `EmrIpdOrderPort.place`) also run ipd's own IPD gate as a backstop; if it ever fires inside the sign, opd answers the same `ipd-read-only`.
4. Readiness, recomputed by the server: `stillNeeded` empty, no unreviewed allergy alert, encounter open (IPD ADMITTED, ER case WAITING/SEEN), Emergency outcome chosen, profile blockers (`SpecialtyFinishContributor.blockers`). Any → 409 `emr-not-ready` with `blockers` (the client opens the first missing section; the dialog never opened in this state).
5. Lock the encounter's own rows: OPD `opd.visit` (stage compare-and-set later).
6. Encounter work (D6 OPD, D8 IPD, D9 Emergency), then the profile's `SpecialtyFinishContributor.apply` (D7), then the patient record write-back (D13).
7. `EmrUsageRecorder.recordSignedVisit(tenantId, signerMembershipId, signedAt, items)` with the distinct master items of the record (complaints, diagnoses, investigations, advice, medicines with a `medicineId`); typed items and IPD order rows cannot reach it (`MasterItemRef`). This is the only caller (ADR-019 D10; the convention test lists `EmrSignService`).
8. Set `status = SIGNED`, `signed_at` (database transaction time), `signed_by` user and membership, clear the edit hold, store `sign_idempotency_key`, `sign_request_hash` and `sign_result` (ids, counts, outcome keys; no clinical text, at most 8 KB), `revision + 1`.
9. Mark a linked treatment-course sitting done (`done_at`, ADR-022 D12) when the record's OPD visit is linked to one.
10. One audit `EMR_RECORD_SIGNED` (D18). Publish `EmrRecordSigned` (D16) **after commit**.

**Idempotency.** The key is per user action (a uuid made when the dialog's confirm is first tapped, kept for retries after a network loss). The request hash covers the body. Same key and body after success → the first result, 200, `replayed: true`. Same key, other body → 409 `idempotency-conflict`. A retry after a rolled-back failure simply runs again (nothing of the first try exists). Every side effect is also idempotent by its own key (bill lines by source key, follow-up by source visit, appointment by follow-up, IPD orders by row `clientKey`, round mark by admission and date, case close by status), so even a partial replay cannot duplicate.

**Why one transaction and not events:** the stories require all-or-nothing with a visible error and a retry; an after-commit event cannot refuse the sign (the same reasoning as ADR-019 D10 and ADR-022 D1). The ports keep opd free of billing and ipd imports.

### D2 · "Check before completing" is a server preview; the summary rows are composed in the client

`POST /emr/records/{id}/finish-check` (same access as the sign, no idempotency key, body = the finish choices the dialog has so far) answers `EmrFinishCheck`:
- `ready` and `blockers` (STILL_NEEDED with the section list, ALLERGY_ALERT, IPD_ORDER_BLOCKED, ENCOUNTER_CLOSED, HELD_BY_OTHER, ER_OUTCOME_REQUIRED, PATIENT_REQUIRED, profile keys);
- **Closed encounter (DEC-051 D2, 0.6.3):** a discharged admission or an Emergency case no longer WAITING or SEEN answers 409 `encounter-closed`, the same as the draft save. It is checked after access and before readiness, and nothing is checked or written. `ENCOUNTER_CLOSED` and `CASE_CLOSED` stay in the blocker enum but are not returned for that state.
- `effects`: workflow move (from, to), follow-up (due date, "Books an appointment on that day", first free slot or "No free slot found…"), bill lines (name, qty, unit price `unitPaise`, line total `amountPaise` = qty × unit price per DEC-051 D4, state NEW / ON_BILL / ALREADY_BILLED with "Already billed. Ask billing to adjust."; `billTotalPaise` is the sum of the line totals), patient record update rows (fields, removals needing the tick, conflict), IPD order rows with their SAH-31 outcome, Emergency (triage level, outcome), profile effects (0.6.1: one named block per profile, D7 "Profile effects"), `prints` (0.6.1, D19);
- `info` rows that never block (advisory alerts such as ANC);
- `share`: WhatsApp and ABHA `available: false`, reason "Needs the WhatsApp service" / "Needs the ABDM service" (D16).

It is a POST because the IPD order check follows SAH-31 to the letter: a hard stop writes SAH-31's own deny clinical event and `IPD_MED_ORDER_BLOCKED` audit, and NEEDS_REASON writes its record-access row (D8). For OPD and Emergency it writes nothing. The summary rows ("Complaints · Headache 2 days", "Not recorded") are composed in the browser from the in-memory record by the shared composer that already builds the live case paper (ADR-022 D9), with the profile's rows from the specialty registry (ADR-023 D1). The server's `stillNeeded` and `blockers` win. "Back to edit" calls nothing.

### D3 · A signed record is immutable in the application and in the database; corrections are addenda

- **Application:** every write path on a SIGNED record answers 409 `emr-record-signed` ("This visit is signed"): draft save, department switch, admission advice, copy items, chemo order writes, surgery booking, admission request. Allowed after signing: print preferences (ADR-022 D9, not clinical), addenda (append), reprint (read), and one data link (Emergency patient, D10).
- **Database (db-engineer):** a `before update` trigger on `opd.emr_record`: when `old.status = 'SIGNED'`, refuse any change except `print_language`, `paper_size`, `updated_at`, `updated_by`, and `patient_id` from null to a value on an ER_ASSESSMENT record. `status` can never go back. No DELETE grant (already). The signed values are therefore frozen together with the snapshot reference (already immutable targets, ADR-020 D8).
- **Chemo order:** SENT/HELD rows were already immutable (ADR-023 D6). A DRAFT order of a signed record is frozen by a second trigger rule: no update when the record is SIGNED (the order row carries `record_id`; the trigger reads the record's status).
- **Addendum:** `POST /emr/records/{id}/addenda` (header `Idempotency-Key`), SIGNED records only (DRAFT → 409 `emr-record-not-signed`), the record's doctor or OWNER with doctor details (`clinic.consultation.write`, own patient; IPD/ER: IPD scope). Body `reason` 1 to 200, `text` 1 to 4,000, plain text, trimmed, no control characters (400 `validation`). Stored in `opd.emr_record_addendum` (append-only: select and insert grants only, deny-mutation trigger), stamped with user, membership and database time; at most 50 per record (400 `addendum-limit`). The record view, history details and case-paper context return `addenda` newest last: "Addendum · <date and time> · Dr. <name>: <reason>. <text>". An addendum never changes the record, the workflow step, bill lines, the follow-up or orders (SAH-51-5; changes there follow their own module rules). Audit `EMR_ADDENDUM_ADDED` (record id, addendum id; never the text).
- **Who may add an addendum (H29, narrows the line above for IPD and Emergency; DEC-048, code pre-review finding 11).** OPD_VISIT: the visit's doctor or OWNER with doctor details (unchanged). IPD_ROUND: the doctor who signed the note (`signed_by_membership_id`), the admission's admitting doctor, or OWNER with doctor details. ER_ASSESSMENT: the doctor who signed the assessment, or OWNER with doctor details. Any other doctor, even one with IPD scope for that ward, gets 403 `not-own-patient`; a correction to another doctor's signed note stays with that doctor (or the owner). IPD scope (403 `outside-scope`) and the VISITING_DOCTOR refusal on IPD and Emergency records are checked first, as for every EMR call. Replay of the same key still needs the same record and the same hash (already built).

### D4 · One editor at a time: a two-minute edit hold on the record, plus the revision check

Mechanism: **both** a lease and the existing optimistic revision.
- Columns on `opd.emr_record`: `edit_hold_membership_id`, `edit_hold_user_id`, `edit_hold_expires_at`.
- **Taken** by `POST /emr/records/open` for a writable record, by `PUT /emr/records/{id}/edit-hold` ("Edit this visit"), and implicitly by any draft save, when the hold is free, expired or the caller's. **Renewed** to now + 120 seconds (database clock) by every draft save (manual or auto) and every `PUT …/edit-hold`. The client's 30-second autosave tick sends a draft save when there are changes and a hold renewal when there are none, so "has not saved for 2 minutes (four missed autosaves)" means four missed ticks (closed tab, lost network). The value 120 s is a constant flagged in SAH-51-4 (H5).
- **Released** by `DELETE /emr/records/{id}/edit-hold` when the doctor leaves the EMR (best effort; expiry covers a closed tab) and by the sign.
- **Held by another:** open answers the record read-only with `editHold {holderName, expiresAt, mine: false, canTakeOver}` and the banner "Open for editing by Dr. <name>"; draft save, sign, hold renewal → 409 `emr-record-held` (extension `holderName`, a staff name; not logged).
- **Take over:** OWNER with doctor details only, `PUT …/edit-hold {takeOver: true}` after the client's "Dr. <name> is editing. Take over?"; the previous holder's next tick gets 409 `emr-record-held` and the screen turns read-only. Audit `EMR_EDIT_HOLD_TAKEN_OVER` (record id, previous holder membership id). Anyone else sending `takeOver: true` → 403 `forbidden`.
- **Take over by the admitting doctor (H35; security pre-review L6).** On an IPD_ROUND record the admission's admitting doctor may also take over (the doctor who alone may sign it, H8), with the same audit `EMR_EDIT_HOLD_TAKEN_OVER`; `EmrEditHold.canTakeOver` is true for that doctor. OPD_VISIT and ER_ASSESSMENT: OWNER with doctor details only. The previous holder is read under the record row lock before the take-over (code pre-review finding 5), so the audit names the hold actually replaced. No maximum hold lifetime in this phase: a hold lasts while its holder saves or ticks; an idle tab loses it after 120 s.
- **Same doctor on two tabs** shares the hold; the revision check (409 `emr-record-changed`, "Reload") stops silent overwrites. Two signs at once: the record row lock serialises them; the second sees SIGNED → 409 `emr-record-signed` "Already signed by Dr. <name>."
- Hold columns are not audited (noise); only take-over is.

### D5 · Autosave and conflict handling

- Same endpoint `PUT /emr/records/{id}/draft` with a new optional `saveKind: MANUAL | AUTO` (default MANUAL, so today's clients behave as before). AUTO writes **no** `EMR_RECORD_DRAFT_SAVED` audit (SAH-51-3); MANUAL writes it as today. Safety audits inside a save (allergy review, MLC flag, chemo second check cleared, estimate signature, consent, Form F, oncology decision) are written whatever the kind.
- Client rules (angular-developer): tick every 30 s while the EMR is writable; save at once on part switch and on "Save draft" (restarts the clock); status text "Saving…", "Saved <time>", "Offline. Your changes are not saved yet.", "Not saved: <reason>" with Retry, in an `aria-live="polite"` region; values kept in memory only (OQ-43-28 default: nothing in localStorage, sessionStorage or IndexedDB); `beforeunload` warning while unsaved; no autosave on a signed or read-only record. 409 `emr-record-changed` → "Reload"; 409 `emr-record-held` → read-only with the banner; 409 `emr-record-signed` → read-only.
- Body and section limits stay (64 KB, 32 KB). No draft content in any log line.
- **IPD and ER drafts are switched on** (OQ-43-27 answered): `encounter-drafts-not-enabled` is no longer answered.

### D6 · OPD finish: workflow move, follow-up, appointment, bill lines

- **Workflow move:** new `VisitService.finishConsultation(tenantId, actorUserId, visitId)` (same module, same transaction). If the stage is before WITH_DOCTOR, it walks forward to WITH_DOCTOR as `startConsultation` does; from WITH_DOCTOR it moves one step forward through the visit's own workflow version (skip rules and fee timing exactly as `moveStage`, without the stage-owner check: the doctor's sign is the act). A stage already after WITH_DOCTOR → `ALREADY_MOVED` (sign continues). A compare-and-set that fails (someone moved the card meanwhile in an unexpected way) → 409 `workflow-move-refused` and the sign rolls back. Outcome `stage {outcome MOVED | ALREADY_MOVED, to}`.
- **"Consult done"** on the Queue card is hidden by the client for DOCTOR, VISITING_DOCTOR and OWNER with doctor details on OPD cards ("Open EMR" instead); `PATCH /visits/{id}/stage` is unchanged for every role (front desk and owner keep moving cards; a later sign then reports ALREADY_MOVED). SO-45-27 follow-up, H3.
- **Follow-up choice is a shared component** bound to `followup.next_visit` on OPD_VISIT records (ADR-022 D2 pattern): `{component: FOLLOW_UP, schemaVersion: 1, interval: D3 | D7 | D15 | M1 | M3 | null}`; `followup.reason` becomes COVERED (the reason is fixed, OQ-43-32). Done = an interval chosen. Legacy `next_visit`/`reason` values from earlier drafts show as `legacyValues`. The view returns the computed `dueDate`.
- **At sign** (before the stage move): with an interval, `FollowUpService.setForVisit(visit, dueDate, reason "Review after treatment")`: due = the visit's Asia/Kolkata day + 3, 7, 15 days, or 1 or 3 calendar months (`LocalDate.plusMonths`, end-of-month clamped). Insert, or when the visit already has an open follow-up (made by an earlier card move) update its due date (audit `FOLLOW_UP_DUE_CHANGED`, dates only); a RETURNED one is left alone. Created whether or not the clinic's `followup` step is on (the doctor's explicit choice, H4). Then the stage move runs; its `createForConsultDone` finds the row and does nothing (unique source visit). Without an interval, the stage move applies SAH-14 as today.
- **Appointment:** with an interval, `AppointmentService.bookFirstFree(patient, visit doctor, dueDate, maxDays 7, visitType FOLLOW_UP, source EMR)` books the first free slot of the due date or the next working days of that doctor (SAH-11 slot settings, leave and taken slots respected) and stores `follow_up.appointment_id`. None within 7 days → the follow-up keeps the date only and the result says "No free slot found. Book the appointment from Appointments." (SAH-51-6 analyst default, H6). Appointment source gains `EMR`.
- **Bill lines:** a final `EmrVisitChargePort.syncEmrLines` with the record's active BILL_TODAY services (ADR-022 D7 rule, idempotent by item id; a paid bill refuses removals and qty changes → the sign answers 409 `already-billed` and the dialog had shown it). Lines already synced by draft saves are not duplicated. The result counts lines and total for the audit and the message.
- **Print:** after a 200 the client prints the prescription in the record's print language (SAH-48-3, SAH-55-2); "Not valid without signature" disappears because the context now says signed.

### D7 · `SpecialtyFinishContributor` (ADR-023 D9), one per profile

```java
package com.sahaj.opd.application.emr.finish;
public interface SpecialtyFinishContributor {
    String profile();                                   // gm, dental, og, paeds, physio, onco, surgery
    List<FinishBlocker> blockers(FinishContext ctx);    // e.g. physio "Pick the treatments given today first"
    ProfileEffects preview(FinishContext ctx);          // read only, for finish-check
    ProfileResult apply(FinishContext ctx);             // Propagation.MANDATORY, inside the sign transaction
}
```
`FinishContext` holds tenant, actor, record (values, snapshot, screen state), visit row, the request's profile choices and the sign idempotency key. Package-private beans, called only by `EmrSignService` (convention test).

| Profile | apply (all idempotent) |
| --- | --- |
| dental (SAH-69-3) | Plan rows done today → `EmrVisitChargePort.addPricedLines` with source key `plan:<rowId>:<sittingNo>`, amount = the row's server-computed charge share (ADR-023 D4 split rule; tariff or typed amount, H17 of DEC-044), label = procedure (≤ 120); adding to a paid bill is allowed (a new open line), never a change. Next sitting (choice D3, D7, D14, M1; default D7; "Confirm" only when every row is done): a planned DENTAL course sitting with the open rows + appointment on the first free slot as D6. Follow-up: one per visit, see H7. |
| physio (SAH-63-3) | The linked REHAB sitting done (D1 step 9); next session added as a planned sitting; appointment in the chosen slot (`physio.nextSlot {date, time}`) or date only; package complete → nothing booked. |
| onco (SAH-70-2) | Cycle charge stays on the CHEMO course sitting (course account, ADR-022 D12); follow-up due = next cycle date when no interval is chosen. Visit bill line for the cycle: not built (H9). Prints are client side. |
| surgery (SAH-71-3) | Nothing new written: the OT booking already added the SURGERY sitting with `admissionRequested` (ADR-023 D8); prints are client side. |
| og, paeds, gm | No writes; preview rows only (paeds next vaccine suggests an interval, client side). |

**Dental "done today" (H28; code pre-review finding 7).** A plan row counts as done in this visit when it was marked done on or after the record's open day (Asia/Kolkata date of the record's `created_at`) and up to the sign, not only on the sign's calendar day; so a draft marked done before midnight and signed after midnight keeps its bill line. The same rule feeds `doneTodayRowIds`, the finish-check `doneRows` and the sign's `addPricedLines`, so preview and sign agree. A row with no amount (no charge share for the sitting, or amount source NONE) makes **no** bill line and is shown in the dialog as "Not in tariff"; a ₹ 0 line is never written.

**Profile effects (0.6.1, DEC-047).** `preview` returns one named block, `EmrFinishCheck.effects.profile` = `EmrFinishProfileEffects` (OpenAPI `oneOf` with discriminator `profile`; Java: a sealed `ProfileEffects` with one record per profile). Rule: the block carries the facts the client cannot read from the record view (counts over other records, course and slot facts, server charges) **plus** the few computed values its lines need, so the client composes each line from one object; section rows stay with the shared composer (D2). The line words are in each schema's description.

| Profile | Keys | Source (server) | Dialog lines (client) |
| --- | --- | --- | --- |
| gm | `profile` | — | composer rows only |

### D8 · IPD round: sign the day's note, round done, new orders through SAH-31

- **Record:** one IPD_ROUND per admission per Asia/Kolkata day (OQ-43-27). Copy from last visit for IPD_ROUND takes the **previous signed IPD_ROUND of the same admission** (not the department rule), marked "Copied from <date>". The same day after signing opens read-only with "Add addendum".
- **New medicines use ipd's catalogue.** On IPD_ROUND records the Prescription field `rx.drug` binds to a new component **IPD_ORDERS** instead of PRESCRIPTION: `{component: IPD_ORDERS, schemaVersion: 1, rows: [{id, drugKey, frequencyKey, overrideReasonKey, checkToken, orderId, orderedAt}]}`, at most 20 rows; `id` is the client uuid and becomes the SAH-31 `clientKey`; `orderId`, `orderedAt` are server-stamped. Options come from `GET /emr/records/{id}/ipd-order-options` (catalogue, frequencies, override reasons via `EmrIpdOrderPort.options`). Draft saves validate keys only (400 `validation`). Form MEDICINE_LIST fields on IPD_ROUND records are not stored (shown disabled "Medicines are ordered in the Prescription section"), so no second, unchecked path exists (OQ-43-24). `prescriptionIsOrder` becomes true on IPD_ROUND records.
- **Check** (finish-check): `EmrIpdOrderPort.check(tenant, actor, admissionId, lines)` runs ipd's existing `MedicineSafetyCheck` against the live orders and the patient's allergy, and applies SAH-31's own handling of BLOCKED (deny clinical event, `IPD_MED_ORDER_BLOCKED`, committed in the finish-check transaction) and NEEDS_REASON (access row). The dialog lists "Not ordered: <first hard stop>" and disables the confirm until the row is removed; a warning row shows SAH-31's lines and the reason select ("Reason to continue (recorded in the audit trail)").
- **Place** (sign): `EmrIpdOrderPort.place(...)` calls the **same ipd application service** as `POST /ipd/admissions/{id}/medicine-orders` for each row without `orderId`, with its `clientKey`, reason and `checkToken` (sign body `ipdOrderReasons`). PLACED (or replayed) → the row gets `orderId`; any BLOCKED or NEEDS_REASON at that moment (the chart changed) → the sign rolls back with 409 `ipd-order-not-placed` and `rows` outcomes; the dialog re-checks. **The rows carry no clinical text (DEC-051 D3, 0.6.3):** each row (`EmrIpdOrderNotPlacedRow`) holds the row id, the drug name, the outcome (BLOCKED / NEEDS_REASON), the check kind (the first SAH-31 `FindingCode`) and a fixed reason chosen by outcome. It never holds the SAH-31 finding text, which can contain the patient's allergy text. Problem details never carry clinical text. The doctor sees the allergy on the record and the full SAH-31 lines in the re-check (finish-check's `EmrFinishOrderCheck`). ipd writes its own `IPD_MED_ORDERED`, clinical events, pharmacist list entry and nursing chart line as today. **opd holds no medicine-order logic.**
- **Hard stop at sign is recorded (H31; security pre-review M1).** The sign must not depend on the client having called finish-check. Before placing anything, the sign runs `EmrIpdOrderPort.check` on every row without `orderId`. When any row is BLOCKED, ipd writes SAH-31's deny clinical event and `IPD_MED_ORDER_BLOCKED` audit through a `Propagation.REQUIRES_NEW` method of its own (a separate, committed transaction), and the sign then refuses with 409 `ipd-order-not-placed` and the `rows` outcomes; the outer sign transaction rolls back as before, but the hard-stop record stays. Rules for that inner step: it sets the tenant on its own connection like every transaction (ADR-002); it only inserts (deny event, audit) and takes **no** row lock the sign already holds (record row, admission row, IPD advisory lock), so it cannot wait on its own caller; it runs before the sign's first ipd write. Only the hard stop gets this path; a NEEDS_REASON row without a reason at sign still rolls back with the sign (its record-access row is the finish-check's, as SAH-31). The placement step keeps its own SAH-31 checks (the chart may change between check and place); a BLOCKED found there is handled the same way. Answer and response body are unchanged from 0.6.0.
- **Round mark:** `EmrRoundPort.recordSignedRound(tenant, actor, RoundNote(admissionId, roundDate, recordId, signedAt, ordersPlaced, investigationsAdvised))` inserts `ipd.round_note` (unique admission + date; ALREADY_RECORDED is success) and the clinical event "Signed the daily progress note". NOT_ADMITTED → 409 `encounter-closed` "This admission is closed" and the note stays a draft. `investigationsAdvised` is the active investigation item texts joined with "; " (≤ 1,000): the only clinical text ipd receives, for the nursing sheet line "Investigations advised: …" (no lab order, OQ-45-28).
- **Cards:** `AdmittedClinicalFlags.roundDoneToday` (OWNER, DOCTOR, NURSE) → flag "Round done" (good, tick icon, foldable into "+N"); `NursingSheet.latestRound {roundDate, signedAt, doctorName, investigationsAdvised}`.
- **No bill lines** for IPD rounds (DEC-042 H8 stands; SAH-68-2 criterion 2 differs, H1).
- After success the client returns to IPD → Admitted with the same filter.

### D9 · Emergency finish: outcome, then sign, in one action

Outcome (`erOutcome.kind`) is required: DISCHARGE, ADMIT, REFER_OUT, SEND_TO_OPD. Through `EmrEmergencyPort` (ipd implements, runs the SAH-28 code paths):
- **DISCHARGE** ("Discharge from ER") → `close(RELEASE)`: the SAH-28 "Treat and release" update (RELEASED, closedAt, mobile cleared, `IPD_ER_RELEASED`). Prescription prints as SAH-51-6.
- **REFER_OUT** → `close(REFER)` (REFERRED, `IPD_ER_REFERRED`); `referTo` (1 to 120) and `referNote` (≤ 300) become the record's `referralLine` "Referred to <place>. <note>" for the case paper; ipd receives no text.
- **ADMIT** → creates an admission request (D10) with `emergencyCaseId`, type emergency, the record attached; sets `admissionAdvised`; the case stays WAITING/SEEN until an admit role admits it with the existing `emergencyCaseId` path.
- **SEND_TO_OPD** → needs `opdPatientId`, an existing patient of the clinic chosen with the existing patient search (an Emergency case has no patient; H2). opd issues a token through new `VisitService.issueTokenForDoctor` (the SAH-9 logic: visit type and fee rule, first stage, follow-up closing) for that patient with the signer as doctor (409 `opd-doctor-not-available` when the signer is not an active OPD doctor); then `close(SENT_TO_OPD, patientId, visitId)`: new status SENT_TO_OPD (closed, never reopens), patient set, bay freed, mobile cleared, `IPD_ER_SENT_TO_OPD` audit. The record's `patient_id` is set in the same transaction (before SIGNED).
- Case closed by someone else → 409 `case-closed` and nothing is written. OQ-43-3: no alert to anyone.

### D10 · Admission request (OQ-45-31) and the pre-filled sheet

- **Lives in opd** (`opd.emr_admission_request`): the request is made from the EMR and holds EMR facts; ipd already depends on `opd.api`, as for course sittings (ADR-022 H13), so ipd reads it through a new opd.api port `EmrAdmissionRequestPort` (implemented by opd). No new module edge.
- `GET /emr/records/{id}/admission-prefill` (OPD_VISIT, ER_ASSESSMENT): patient (id, name, age, sex, mobile through `patient.api`; for an Emergency case without patient: the case name, age and sex, no mobile), suggested type (emergency for an Emergency visit type or ER case, else planned), diagnoses (active diagnosis names), OT procedure and stay from `sx_plan` when booked, the open request (if any), the patient's open admission (`EmrEncounterSource.openAdmissionOf`: "Already admitted · <IP number>"), and `canAdmitDirectly` (OWNER with doctor details). Screen only, never logged.
- `POST /emr/records/{id}/admission-request` (header `Idempotency-Key`; DRAFT records; doctor or owner with doctor details): `admissionType` planned | emergency | daycare, `plannedStayDays` 1 to 60 ("IPD n days"), `note` ≤ 300. One OPEN request per record (a repeat returns it, 200). Sets `admissionAdvised`. Audit `EMR_ADMISSION_REQUESTED` (record id, request id, type; never diagnoses or note).
- **IPD side:** `GET /ipd/admission-requests` (OWNER, FRONT_DESK, NURSE; module on/trial) lists open EMR requests and course sittings with `admissionRequested` (through `TreatmentCoursePort.openAdmissionSittings`), newest first, with patient name, age, sex (or the case display name), type, stay, requesting doctor, diagnoses text and note, and "Admit" opening the existing sheet pre-filled. `POST /ipd/admissions` gains `admissionRequestId`. In ipd's admission transaction ipd calls `EmrAdmissionRequestPort.onAdmitted(AdmittedFacts(admissionId, patientId, emergencyCaseId, admissionRequestId))`: opd marks the named request and every other OPEN request of that patient or that case ADMITTED (with the admission id), and sets `patient_id` on the case's ER_ASSESSMENT record when it is null (allowed on a signed record, D3). Lock order there is ipd's (IPD lock → opd rows), consistent with D1 step 1.
- The owner path uses the same request: the owner's "Admit" creates the request and opens the sheet with it, so one path marks the visit.
- **Follow-up after the static reviews (opd.yaml 0.6.2, ipd.yaml 0.3.1):**
  - *Prefill mobile (H34; security L3).* `patient.mobile` is returned only when `canAdmitDirectly` is true; null for every other caller (the doctor who only sends a request does not need it).
  - *Request checks (L7).* In this order after role, access, module state and not-applicable: idempotency (below); SIGNED → 409 `emr-record-signed`; encounter closed (OPD visit finished or cancelled, Emergency case not WAITING or SEEN) → 409 `encounter-closed`; another doctor's unexpired edit hold → 409 `emr-record-held` (D4); open admission → 409 `already-admitted`; an OPEN request of the record → 200 with it; else 201. A closed Emergency case therefore never reaches the IPD list through a new request.
  - *Idempotency bound to the record (L1).* The client key is looked up per clinic as before, but replays only when the stored request belongs to **this** record and the request hash matches; the hash covers the record id, type, stay and note. Same key on another record or with another body → 409 `idempotency-conflict`, and nothing of the other record is returned. The keys of requests the sign makes (Emergency outcome ADMIT, D9) are `sign-` + the record id as 32 hex digits; the sign first reuses the record's OPEN request when there is one (partial unique per record), else inserts with that key. Client keys starting `sign-` are refused with 400 `validation` (the admission-request header's pattern `^(?!sign-)[A-Za-z0-9_-]{8,64}$`), so no client can pre-take a sign key and block a later ADMIT sign. A client uuid never starts with `sign-`. The server key fits the existing column check `^[A-Za-z0-9_-]{8,64}$` (37 characters): **no database change**.
  - *IPD list contents (H33; security M3).* `GET /ipd/admission-requests`: `diagnoses` and `note` for OWNER and NURSE; null for FRONT_DESK, whose row shows patient, type, stay, requesting doctor and time, and whose "Admit" opens the sheet with an empty reason (SAH-23 stores a blank reason as "Under evaluation"). Nurse rows stay hospital-wide (a request has no ward yet); the list writes no record-access row (unchanged).
- Record view `admission {state NONE | ADVISED | REQUESTED | ADMITTED | ALREADY_ADMITTED, requestId, admissionId, ipNumber}` drives "Send admission request", "Admission requested", "Admitted", "Already admitted". IPD OFF → SAH-52-4 unchanged ("Advise admission + referral").
- The deposit on the sheet is SAH-23's rule; the course 40 % rule only for a course advance (SAH-67-3).

Levels come from `EmrEmergencyPort.triageScale` (the clinic's SAH-28 scale, or the SAH-28 default "3 colours" when the clinic has no Emergency settings, also with IPD off), exposed as `GET /emr/triage-levels`.

### D12 · Vitals read (SAH-68-1, merged with SAH-72 when scheduled)

`GET /emr/records/{id}/encounter-vitals` → `{current: reading | null, earlier: {recordedByName, recordedAt} | null, sources: {opd: NOT_CAPTURED, er: NOT_CAPTURED, ipd: AVAILABLE}}`. Reading = values with units (BP systolic/diastolic, pulse, SpO₂, temperature with unit, RR), `recordedByName` (platform `TeamMemberPort`), `recordedAt`, `sourceEntryId`.
- **IPD_ROUND:** latest `ipd.vitals` of the admission on the round date through `EmrVitalsSource.latestNursing` (ipd implements; ipd scope applies); `earlier` = latest before that day.
- **OPD_VISIT and ER_ASSESSMENT: nothing to read** (fact 3). Answered as `NOT_CAPTURED`; the card shows nothing new. Capturing nurse vitals in OPD or at triage is new scope (H10).
- The client pre-fills empty vitals fields only and sends `prefill {source, sourceEntryId}` with the section; the server stamps `prefilledFrom {source, entryId, recordedByMembershipId, recordedAt}` when the values equal the source, and clears it when the doctor changed them (the doctor is then the recorder). The nurse's entry is never edited. The client re-reads the endpoint on each autosave tick; a newer `sourceEntryId` shows "New vitals recorded. Use them?". No copy is stored except what the doctor saves. Never logged.

### D13 · Patient record write-back (SAH-68-3)

- At open the record stores `patient_facts_fingerprint` = SHA-256 of the patient's allergy and chronic texts as read (through a new `PatientClinical.factsFingerprint`, computed by patient).
- The visit's confirmed list: Allergies section items (active, joined with "; ") and the Long-term conditions (`history.past_illness` / `chronic` section items as the developer lists from the seed, joined with "; "), each ≤ 400 (longer → finish-check blocker "Shorten the list to 400 characters"). Changed when the joined text differs from the patient's text at open. A removed allergy is written only with `confirmAllergyRemoval: true`; otherwise the removed item is kept in the written text.
- Explicit "None" for allergy → the text "No known allergy" (the only path that writes it; OQ-45-23).
- **Long-term conditions are a union, never a removal (H30; code pre-review finding 12).** The written chronic text is the patient's existing text with every condition label of the visit that is not already in it added (compared trimmed and case-insensitively per "; " item); nothing is removed and front-desk free text is kept as it was. "Changed" means at least one label was added. Removing a condition stays a patient-record edit (patient.yaml), not an EMR action; no `confirm…Removal` field exists for conditions. The 400-character limit applies to the combined text (finish-check blocker "Shorten the list to 400 characters"). Allergies keep the rule above (removal only with `confirmAllergyRemoval`).
- In the sign transaction opd calls `patient.api PatientClinicalUpdatePort.updateFacts(tenant, actor, patientId, expectedFingerprint, change)`: fingerprint differs → CONFLICT, nothing written, **the sign still completes** with `patientRecord: CONFLICT` ("The patient's record changed. Review before updating"); otherwise UPDATED or NOT_CHANGED. Patient writes `allergy_recorded_at/by` with the allergy and audits `PATIENT_CLINICAL_FACTS_UPDATED` (patient id, field names; never values). The front-desk PATCH clears `allergy_recorded_*` when it changes the allergy text.
- **The story's "visit signed" event to the patient module is not built:** patient cannot depend on opd (cycle). The signed visit appears in Past visits and history because they read opd's signed records (ADR-022 D10). `EmrRecordSigned` (D16) exists for modules above opd.

### D14 · Bill lines and the visit-type fee (SAH-68-2)

- OPD bill lines: D6 (final sync) and D7 (dental priced lines, new source `EMR_PLAN`). IPD round and ER: none (H1).
- Finish preview amounts (DEC-051 D4, 0.6.3): `EmrFinishBillLine.amountPaise` is the line total (qty × unit price), `unitPaise` is the unit price and `qty` the quantity, both for display. A dental plan line has qty 1, so its unit price equals its total. `billTotalPaise` is the sum of the line totals.
- Visit type change: when the visit bill has no payment (`EmrVisitChargePort.hasPayment` false), opd recomputes `opd.visit.fee_paise` with SAH-9's `feeFor(doctor fee, type, follow-up fee)` where FOLLOW_UP gets the follow-up fee only when the patient was seen by the same doctor within the clinic's window (else the full fee), and NEW, REVISIT and EMERGENCY the full fee (H11). Billing shows it at once (it reads the fee). With a payment: the type changes, the fee does not, and `Visit.feeChange.outcome = ALREADY_BILLED` ("Already billed. Ask billing to adjust.").
- Follow-up list: unchanged SAH-14 screens; `FollowUp` gains `appointmentDate`, `appointmentTime` (the booked time). The diagnosis never appears in the reason.

### D15 · Reprint of a signed prescription (SAH-51-6)

`GET /visits/{visitId}/prescription-print`: SIGNED OPD record only (else 409 `emr-record-not-signed`); OWNER, FRONT_DESK, PHARMACIST any visit; DOCTOR, VISITING_DOCTOR own visits; NURSE, BILLING, COUNSELLOR 403 (analyst default, H12). Answers the case-paper context plus the signed record's **print-on sections only** (values), addenda and `reprint: true` ("Reprint" on the paper); the client prints with the shared composer. Audit `EMR_PRESCRIPTION_REPRINTED` (visit id, record id). Front desk and pharmacist get no other EMR access.

**Labels (0.6.1, DEC-047).** The 0.6.0 answer had signed values but no labels, so choice keys could not print as words. Options: (a) send what the composer already uses for the live case paper; (b) server-composed print lines; (c) a key-to-label map per field. **Chosen (a):** `EmrReprint` gains `layout` (the record's frozen `EmrSnapshot` reduced to the printed sections: field definitions, option labels, form definitions), `specialty` (the profile block of `EmrSpecialtyView`, computed from the signed values with the signing day, Asia/Kolkata, as "today", so ages and vaccine states read as when signed) and `specialtyReference` (the profile's `EmrSpecialtyReference`: product labels, no patient data). One composer prints both papers, so a reprint can never word a value differently from the original. (b) would put a second composer in Java that drifts from the client's; (c) cannot cover specialty components, whose labels live in the reference. The Paediatrics reprint also prints the vaccination card (SAH-62-4: "front desk can reprint a signed card through SAH-51 reprint"). The snapshot is already stored; the reference is the existing service; the only new server work is the `asOf` day for the specialty computation (H20).

**Specialty block by role (0.6.2, H32; security pre-review M2, code pre-review finding 3; supersedes the "profile block" part of H21).** The record's doctor (DOCTOR or VISITING_DOCTOR of the visit) and OWNER get the whole profile block. FRONT_DESK and PHARMACIST get `profile`, `mode`, `hiddenSectionKeys`, `tagNote` and, inside the profile block, only the keys that a section listed in `sections` (Print on prescription on, not mode-hidden) reads when the composer prints it; every other key is left out (the block's keys are optional in the schema), and `vitalsFlags` only when the vitals section prints. Paediatrics additionally keeps the immunization data the vaccination card prints (vaccines with states as of the signing day, next due, counts), because front desk reprints the card here (SAH-62-4); `dateOfBirth` stays null for PHARMACIST (0.5.3). Never sent to these two roles unless the section that reads it is printed: Obstetrics dating, EDD, gestational age, ANC results, `formFRequired`/`formFCount` (PCPNDT); Oncology decision and lab flags; Surgery payer and deposit; the Dental estimate. Implementation: one server-side map per profile from section key to the block keys its print lines read, kept next to the profile's print rows so the client composer and the map change together (java-developer; a unit test per profile fails when a printed line reads a key the map does not list). `layout` and `specialtyReference` are unchanged (H24 stands).

## Options considered

| Question | Chosen | Rejected |
| --- | --- | --- |
| Sign mechanics | One transaction, ports in the caller's transaction, fixed lock order, idempotency key + stored result | Saga with compensations (half-done states visible to billing and nurses); events after commit (cannot refuse the sign) |
| One editor | Two-minute lease + revision | Revision only (no "Open for editing by" banner, two doctors type for minutes then one loses); pessimistic lock held across requests (impossible over HTTP) |
| Immutability | Application guard + database trigger with an allow-list of columns | Application only (a later bug or SQL edits a signed record); copy to an archive table (doubles storage) |
| IPD medicines | IPD_ORDERS component with ipd's catalogue, placed by ipd's own service through a port | Mapping opd master to ipd drugs (no mapping exists; a wrong map is a safety fault); a second check in opd (parallel logic, forbidden by OQ-43-24) |
| Round done | Small `ipd.round_note` row written through a port | ipd reading opd records per card (breaks ADR-013 fixed set queries) |
| Admission request home | opd table read by ipd through `opd.api` | ipd table written through an opd.api port (works, but splits the EMR facts and duplicates the course-sitting pattern) |
| Patient "visit signed" event | Not built (cycle); history reads opd | patient listening to opd (module cycle) |
| Autosave audit | `saveKind` on the existing save | A second endpoint (two write paths for the same data) |
| Profile effects (0.6.1) | One named block per profile, discriminated by `profile` | Free keys (client and server guess names); server-composed summary text (a second composer, against D2) |
| Reprint words (0.6.1) | Snapshot, profile block and reference with the reprint, same client composer | Server print lines (drift from the client composer); per-field label maps (miss specialty keys) |
| Extra prints (0.6.1) | Client browser prints from data already loaded; list in the sign answer | Print endpoints or stored PDFs (documents service is not phase 1) |

## Consequences

Positive: one all-or-nothing sign for every encounter; no module cycle and no new module edge (all new reaches are ports in existing directions); IPD medicines keep exactly one checked path; signed records are protected by the database; retries are safe at every layer; the DEC-040 work can attach later without touching the sign.
Negative / accepted: the sign transaction touches up to four modules and holds row locks for its duration (one patient's rows; expected well under a second); the IPD and Emergency doctor needs ipd's catalogue in the EMR; nurse vitals pre-fill works only for IPD until OPD and triage capture exist; several defaults wait for the human.
