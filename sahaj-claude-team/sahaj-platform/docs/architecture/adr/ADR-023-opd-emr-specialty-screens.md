# ADR-023 · Doctor EMR phase 4: specialty screens (Dental, General Medicine, Obstetrics & Gynaecology, Paediatrics, Physiotherapy, General Surgery, Medical Oncology), their rules and engines, and the chemotherapy order with an independent second check

Stories: SAH-49, SAH-69 (Dental), SAH-60 (General Medicine), SAH-61 (Obstetrics & Gynaecology), SAH-62 (Paediatrics), SAH-63 (Physiotherapy), SAH-64, SAH-71 (General Surgery), SAH-65 (Oncology assessment and decision), SAH-66, SAH-70 (Oncology order sheet, second check, after the order).
Mockup: `docs/design/mockup/EMR-Configuration-Smart-Clinic.html` (`window.__DC_SRC`: `SCREENS`, DoctorDental, DoctorGeneral, GeneralTreatment, DoctorGynae, DoctorPaeds, DoctorPhysio, DoctorSurgery, DoctorOncology, OncologyTreatment; library `S`, `DEPTS`, `REQ`, `PART_T`).
Module: **opd** only. Reads platform (team, colleague PIN) and patient through their `api` packages. No change to billing or ipd contracts (`billing.yaml` 0.2.0 and `ipd.yaml` 0.2.0 stay). No new module, library or external service.
Status: PROPOSED (12 Nov 2026). Stories pre-approved by the human (DEC-039 addendum). The `contract` stage (this ADR and `docs/api/opd.yaml` 0.5.0) needs the human's approval. Items under "Stopped for the human" are defaults written into the contract, not choices: each is outside the mockup or differs from it. H1-H19 answered in DEC-044 (all defaults accepted except H8: length and head-circumference centile notes hidden). **0.5.1 follow-up (12 Nov 2026, D13):** fixed reference list names, mockup items the 0.5.0 contract left out, the visit-mode section rule, and the "Second checks" menu key (`docs/api/opd.yaml` 0.5.1, `docs/api/platform.yaml` 0.1.1); additive, under DEC-039 (the mockup wins). **0.5.2 follow-up (13 Nov 2026, D14):** chemo-check list order, what the chemo fingerprint covers, and the surgery blood chip as an enum (`docs/api/opd.yaml` 0.5.2); clarifying, found by QA and the java-developer.
Builds on: ADR-020 (record model D8, value kinds D3, snapshot, Done rule, permissions D11), ADR-022 (component binding D2, one write path, server-stamped properties, course D12, ports D1, case paper D9, extension points), ADR-010 and ADR-014 (staff PIN, colleague check), ADR-002 (tenancy, audit), DEC-039 (rules as drawn, tagged), DEC-041, DEC-042, DEC-043.

Tag used on every rule value below: **"value from the EMR mockup, accepted by the human in DEC-039, not clinically reviewed"** (written "tagged").

## Context

Facts checked on 12 Nov 2026:

- The mockup itself routes the doctor screen by starter: `SCREENS = { gm, dental, og, paeds, physio, onco, surgery }`. The other eight starters (ortho, eye, ent, derm, diab, cardio, ayush, psych) have no drawn screen and use the generic renderer (SAH-47-3).
- Each drawn screen is a set of cards. Almost every card matches one library section of the department (`dental_chart`, `tx_plan`, `anc`, `growth`, `immunization`, `rom`, `sx_plan`, `onc_tox`, `onc_labs` …). Three facts belong to the screen, not a section: the visit mode (Obstetrics "Antenatal / Gynae", Physiotherapy "First visit / Session n") and Oncology's "Today's decision".
- The Medical Oncology starter hides `exam` (mockup `DEPTS` off list) while #DoctorOncology draws "2 · Examination" and its footer asks for "systemic exam".
- The mockup's 3D jaw is drawn with CSS 3D transforms (`preserve-3d`, `rotateY`, `translateZ`); the growth and trend charts are inline SVG. Neither needs a library.
- The chemotherapy second check must be visible to a nurse or pharmacist who never opens the EMR, and must be refused at send time without it. That needs a query "orders waiting for me" across records, which the record JSON (ADR-020 D8) cannot answer.
- `StaffPinPort.checkColleague(tenantId, callerUserId, colleagueMembershipId, requiredRole, pin)` exists (ADR-011 D7, ADR-014) with a durable pair cap, lockout and fail-closed answers; its NOT_ELIGIBLE text and pair-cap text name "nurse".
- Nothing is signed until SAH-51 (phase 5). Every "from earlier signed visits" read is empty until then, as in ADR-022 H12.

## Decisions

### D1 · How specialty screens plug into the shared frame

**Screen registry by starter key, generic renderer as fallback.**

- The record's snapshot `starterKey` (ADR-020 D8; a COPY department keeps its source's starter; a BLANK department has none) selects a **specialty profile** fixed in code: `gm`, `dental`, `og`, `paeds`, `physio`, `onco`, `surgery`. Any other starter or none → profile `generic` (today's behaviour, unchanged).
- Profiles apply to **OPD_VISIT records only**. IPD_ROUND and ER_ASSESSMENT records keep the generic renderer and the shared components (H16): the mockup draws specialty screens only from the OPD queue.
- A profile is a fixed list of **section editors**: section key → specialty component (table D3). The frame (header, parts, section cards, order, footer, Save draft, right panel) stays the shared one. A section card whose key has an editor in the record's profile renders that editor; every other section renders with the generic renderer and the ADR-022 components. If the owner hides a section, its editor is not shown and any engine that needs it treats its inputs as "Not recorded". Layout settings (shown, required, part, order, print, copy, who can fill) keep their meaning for every section.
- Server: `com.sahaj.opd.application.emr.specialty.SpecialtyProfiles` (registry) and one binder per component. The binding is computed on read like ADR-022 D2 (never stored in versions). The record view's layout sections carry `specialtyEditor {component, profile}`; the library fields of a bound section return `valueKind COVERED`.
- Client: one registry file (`features/emr/specialty/specialty-registry.ts`, angular-developer) mapping component → lazily loaded Angular component, and profile → screen chrome (mode switch, summary strip, finish label, footer texts). Unknown component → generic renderer. Adding a specialty later is a registry entry plus binders, no frame change.

### D2 · Where specialty data is stored

**Inside the EMR record document (ADR-020 D8), except the chemotherapy order, which is a table.**

| Data | Storage | Why |
| --- | --- | --- |
| Tooth chart, dental plan rows and estimate state, lab work, consent ticks, vitals entries, general signs and systems, ANC check, Form F tick, growth measurements, vaccines given today, milestones, pain, ROM and MMT tables, special tests, goals, modalities, home exercises, session note, surgical exam, fitness, surgery plan and OT booking stamp, pre-auth, pre-op orders, side-effect grades, oncology exam and lesions, pre-chemo labs, ECOG, take-home, next cycle, referrals, cycle note | Record section values, as a component value under the reserved field key **`specialty`** of the anchor section (`sections.<key>.values.specialty`), with `component` and `schemaVersion` | Clinical values of one visit; one write path (draft save with revision); immutable after signing; read whole per record or per patient; same scale argument as ADR-022 D3 |
| Visit mode, Oncology decision | Record column **`screen_state jsonb`** (`{schemaVersion, profile, mode, oncDecision}`) | Facts of the screen, not of a section; must exist even if the owner hides a section |
| Chemotherapy order with second check | Table **`opd.chemo_order`** | Must be listed for the named checker ("waiting for my second check") without reading records; a database rule must make "sent without a confirmed check" impossible; summed per patient for the lifetime anthracycline dose |
| OT booking | Record (`sx_plan`) + a sitting of the patient's SURGERY course (ADR-022 D12) | No module holds an OT schedule (OQ-45-28): date and slot are text; the sitting is the admission request SAH-67-3 reads |
| Earlier visits (ANC table, vitals history, trends, growth points, earlier cycles, physio progress) | Read on demand from the patient's records and orders (no copy) | ADR-022 D10 pattern: application filter over one patient's rows, capped |

- **Rejected:** a table per specialty item (tooth rows, plan rows, vaccine rows, growth points): billions of rows a year at target scale and joins on every record read (ADR-022 D3 reasoning); storing the chemo order in the record JSON (the checker list and the database send guard would be impossible).
- The reserved field key `specialty` must never be used by a library field (new check on `opd.emr_section_field`, data item 8).
- **Legacy values:** a section filled with generic values in phases 2 and 3 that gains an editor keeps them; the view returns them as `legacyValues` (read-only) until the first specialty save replaces them.
- **Server-stamped properties** (ignored when sent, as ADR-022): every `…At`, `…ByMembershipId`, vaccine `givenOn`, plan row `doneOn`, estimate signature, consent and Form F stamps, goal `achievedOn`, OT booking, `pregnancyCourseId`, decision suggestion and stamps.

### D3 · Profiles, anchor sections and components

| Profile | Section key → component |
| --- | --- |
| gm | `vitals` → VITALS_LOG, `exam` → EXAM_GENERAL. Trend and history read; visit templates (D10) |
| dental | `dental_chart` → TOOTH_CHART, `tx_plan` → DENTAL_PLAN, `dental_done` → DENTAL_DONE (derived, stores nothing), `dental_lab` → LAB_WORK, `consent` → CONSENT_CHECKLIST (one item per plan row) |
| og | `anc` → ANC_CHECK, `pcpndt` → FORM_F, `gyn_exam` → GYNAE_EXAM; screen mode ANC or GYNAE |
| paeds | `growth` → GROWTH, `immunization` → IMMUNIZATION, `milestones` → MILESTONES, `wtdose` → WEIGHT_DOSE (stores nothing; adds prescription rows) |
| physio | `pain` → PAIN_SCORE, `posture` → POSTURE_GAIT, `rom` → ROM_TABLE, `mmt` → MMT_TABLE, `special_tests` → SPECIAL_TESTS, `func_scales` → OUTCOME_SCALES (0.5.1, D13), `goals` → GOALS, `modalities` → MODALITIES, `hep` → HOME_EXERCISES, `sessions` → SESSION_NOTE; screen mode FIRST_VISIT or SESSION |
| surgery | `sx_findings` → SURGICAL_EXAM, `sx_fitness` → SURGERY_FITNESS, `sx_plan` → SURGERY_PLAN, `sx_consent` → CONSENT_CHECKLIST (five fixed items), `sx_preauth` → PREAUTH, `sx_preop` → PREOP_ORDERS |
| onco | `vitals` → VITALS_LOG (°C), `onc_tox` → ONC_TOX, `onc_bsa` → ONC_EXAM (the whole "2 · Examination" card, H1), `onc_labs` → ONC_LABS, `onc_ecog` → ONC_ECOG, `onc_regimen` → CHEMO_PLAN (take-home, next cycle, referrals, cycle note; the order itself is `opd.chemo_order`); decision in `screen_state` |

Every other section of these departments (Intraoral, Menstrual history, Feeding history, Infertility workup, WHO checklist, Operation notes …) renders with the generic renderer, as the stories say. Shapes, limits and Done rules of every component are in `opd.yaml` 0.5.0 (`EmrSpecialtyValue` and the schemas it lists).

**Done rules** (server, extend ADR-020 D8; a copied value still needs confirmation): VITALS_LOG one entry in this record ("Record general examination"; nurse values never make it Done, SO-45-43); EXAM_GENERAL one sign or system marked and every Abnormal system has text; TOOTH_CHART one tooth not Healthy or "All teeth healthy" confirmed; DENTAL_PLAN one row; DENTAL_DONE one row done on this record's date; LAB_WORK one item; CONSENT_CHECKLIST at least one item and all items ticked; ANC_CHECK one of today's values; FORM_F no obstetric scan ordered in this record, or "Form F filled and declaration signed" ticked; GYNAE_EXAM one finding and the chaperone recorded (name or "Declined by patient"); GROWTH today's weight; IMMUNIZATION "Schedule reviewed" or one vaccine given today; MILESTONES one milestone toggled; PAIN_SCORE a score; ROM_TABLE, MMT_TABLE one value; SPECIAL_TESTS one result other than Not done; OUTCOME_SCALES one score (0.5.1); POSTURE_GAIT a gait; GOALS one goal; MODALITIES one treatment given; HOME_EXERCISES one exercise; SESSION_NOTE text; SURGICAL_EXAM one finding; SURGERY_FITNESS summary "Fit for surgery", or PAC "Fit with caution" with no test pending or abnormal (SAH-64-2); SURGERY_PLAN booking state BOOKED; PREAUTH sent; PREOP_ORDERS one tick; ONC_TOX all nine grades confirmed; ONC_EXAM weight, height and every system marked (five systems from 0.5.1: heart, lungs, abdomen, nervous system, spine and bones); ONC_LABS all seven values and the drawn time; ONC_ECOG a grade; CHEMO_PLAN the order is SENT or the hold is recorded.

**Footer items.** The view adds `stillNeededItems [{key, sectionKey, label, count}]` in footer order: required sections not Done (label = section name in lower case, or the profile's label: `sx_plan` "OT booking", `onc_tox` "n side effect grade(s)", `onc_bsa` "systemic exam", `onc_regimen` "send chemo order" or "record the hold") plus profile items: onco `ONC_DECISION` "today's decision"; physio in SESSION mode `PHYSIO_TREATMENT_TODAY` ("Select at least one treatment given today."). For the onco profile the items `onc_tox`, `onc_bsa`, `onc_regimen` and `ONC_DECISION` are listed whenever the section is shown, whatever its Required setting (stories SAH-65-1, SAH-70-2; H2). `stillNeeded` (keys) and `readyToComplete` keep their ADR-020 meaning and include these items. A section hidden by the visit mode (D13.3) is never listed and never blocks `readyToComplete`, whatever its Required setting.

**Copy from last visit** per component (only when the section's copy is on, as ADR-020): TOOTH_CHART copies teeth, shade, gum (confirm needed); GROWTH copies into `previous` (comparison only, never today's values); GOALS copies open and achieved goals; ONC_EXAM copies lesion names and baselines (today's sizes empty); ROM_TABLE, MMT_TABLE, SPECIAL_TESTS copy rows; DENTAL_PLAN copies rows still Planned or In progress (SAH-49-2 carry-over); every other component copies nothing. All depend on SIGNED records (SAH-51).

**Case paper map additions** (ADR-022 D9): `immunization` (vaccines given today) and `modalities` → 8 Procedures & services; `tx_plan`, `dental_done` → 8; `wtdose`, `onc_regimen`, `sx_preauth`, `sx_preop` → NONE (their own prints); every other specialty section → 4 Examination. The text of each line is composed in the client by the shared case-paper function (one formatter per component).

### D4 · Rules and engines: code or global reference data

**Rule: numbers that drive a computed rule live in code; long lookup tables that a clinical reviewer will extend or replace wholesale live in global reference tables.**

- **In code** (pure classes in `com.sahaj.opd.domain.emr.specialty`, no Spring, no database; every constant has the tag and the story id in its Javadoc; every number has a unit test whose name carries the tag): vitals flags GM (C-1) and Oncology (C-1, C-8); dental conditions, surfaces (M O D B L), mobility G0–G3, shades, gum tones, suggestions with phases, root canal 3 sittings (1–6), next-sitting intervals (C-3); estimate split (equal parts rounded to ₹ 50, last takes the rest); ANC thresholds, Naegele (EDD = LMP + 280 days; a dating-scan EDD wins), scan windows, due orders, symptoms, supplements (C-4); paediatric dose table and maths (C-5); NPRS, gait, modalities with default parameters, package of 10 sessions (C-6); surgery lists, procedure defaults, deposit rule, booking rule, fitness summary, pre-op orders, consent items (C-7, L-3, B-1, B-3); oncology symptoms, events, BSA, cap, weight-change rule, response category, lab gates, 72-hour rule, ECOG, suggestion engine, decisions and reasons, dose levels, reduction reasons, rounding, 5% deviation, lifetime anthracycline limit, safety checks, take-home list, referrals, next-cycle intervals (C-8).
  Why code: the numbers are tangled with logic (a band without its comparison is meaningless); a value change must pass code review and tests, never a silent data update; the release version identifies the rule set a record was computed with.
- **Global reference tables** (opd schema, no `tenant_id`, SELECT only for `sahaj_app`, changed by migration only, table comment with the tag): IAP immunization schedule (groups, windows, vaccines); growth bands (today only the drawn 18-month bands; WHO tables load into the same table when the human supplies the source, OQ-45-32); milestones by age band (18 months only); joint reference (knee ROM normals, MMT groups, special tests; other joints when supplied); chemotherapy protocol library (four drawn protocols with drugs, dose per m², vial step, infusion minutes, notes, pre-medicines, interval, emetic risk).
  Why tables: these are the lists a reviewer will replace in bulk; a table holds many rows that the code reads generically.
- **The server is the authority.** `GET /emr/specialty-reference/{profile}` returns the lists and thresholds (with the tag) so the screen computes live; every draft save and record read recomputes on the server and returns the result in `EmrRecordView.specialty`; the server's answer wins (ADR-020 D8 pattern). Where a value is entered from a calculation (paediatric dose, chemotherapy doses) the server recomputes and refuses a mismatch (400 `dose-calculation-mismatch`).

Engines, exactly as drawn (constants in the contract descriptions):

- **Oncology** (C-8). BSA = √(height cm × weight kg ÷ 3600), 2 decimals; used = min(2.0, BSA) when "Cap at 2.0 m²" is on. Weight change % = (today − cycle 1 weight) ÷ cycle 1 weight × 100; |change| ≥ 10 → "recalculate doses" and the order recomputes from today's weight. Cycle 1 weight = the weight on the patient's first SENT order (none → today's weight, change 0). Lesions: baseline sum B, previous sum P, today T; % = (T − B) ÷ B × 100; nadir = min(B, P); from-nadir % = (T − nadir) ÷ nadir × 100; response PD when "New lesion seen" or (from-nadir ≥ 20 and T − nadir ≥ 0.5 cm), else CR when lesions exist and T = 0, else PR when % ≤ −30, else SD; per lesion green ≤ −30 %, red ≥ +20 %. Lab fails: Hb < 8, ANC < 1,500, platelets < 100, creatinine > 1.5, bilirubin > 1.5, ALT > 100, LVEF < 50; "counts and organ" = all but LVEF; labs fresh when drawn within 72 hours before now. Fever = temperature ≥ 38 °C. Fever or admission event = confirmed grade of "Fever with low counts" ≥ 1, or events "Fever ≥ 38 °C at home" or "Admitted" (mockup; H3). ECOG fit at ≤ 2. **Suggestion, in order:** STOP when ECOG ≥ 3; else DELAY_1_WEEK when a count or organ lab fails or fever; else CHANGE_REGIMEN when response PD or LVEF < 50; else GIVE_REDUCED when worst confirmed grade ≥ 3 or a fever or admission event; else GIVE_AS_PLANNED. Reasons list (tick or cross): ECOG; counts and fever; worst grade; response; heart (LVEF and abnormal heart exam); line ready for vesicant (port with Flushes freely, Blood return seen, No redness or swelling). Patient alerts: grade ≥ 3, a lab out of range, fever, weight change ≥ 10 %, cumulative > 400 mg/m², port without blood return.
- **Chemotherapy doses** (C-8). Calculated = dose per m² × BSA used × level ÷ 100 (1 decimal); rounded = round(calculated ÷ vial step) × vial step; final = rounded unless edited; |final − calculated| > 5 % of calculated → "More than 5% from calculated" (red, analyst addition). Levels 100, 90, 80, 75; below 100 needs a reduction reason; decision GIVE_REDUCED pre-selects the next level down. Lifetime doxorubicin = latest "Earlier doses before this clinic" (mg/m², entered on the order) + Σ doxorubicin mg/m² × level ÷ 100 of the patient's SENT orders in this clinic + this cycle's; red above 400; check passes at ≤ 450. Other drugs "No lifetime limit".
- **Paediatric dose** (C-5): mg = min(max mg, round(weight × mg/kg)); ml = round(mg ÷ mg-per-ml, 1 decimal); paracetamol 15 mg/kg max 500 (120 mg/5 ml = 24 mg/ml; 250 mg/5 ml = 50 mg/ml), ibuprofen 10 mg/kg max 400 (20 mg/ml); fixed frequency texts. No weight today → no dose (no estimate from age).
- **ANC** (C-4): BP high at ≥ 140 systolic or ≥ 90 diastolic → "Possible pre-eclampsia"; Hb < 11 mild, < 10 moderate, < 7 severe; fundal height mismatch when |fundal cm − GA weeks| > 2; fetal heart outside 110–160; risk chips; scan states Done / Due (GA in or past the window) / later.
- **Growth** (C-5): weight only (H8, DEC-044: no note for length or head circumference). Note = first WEIGHT band whose age range holds the child's age and whose upper bound is above the value; no band → "Centile not available for this age". Age from date of birth (patient.api addition, D11).
- **Immunization** (C-5, H9): given = a given date in this record or any earlier record of the patient; due today = the group's window holds today's age and not given; overdue = the group's window ends before today's age and not given; else later. "Mark all due as given" marks due today only.
- **Surgery** (C-7, B-1, B-3): deposit = round(package × 0.5 ÷ 1,000) × 1,000 for Self, else ₹ 10,000; booking needs an active diagnosis item, all consent items ticked and, when the payer is not Self, pre-auth sent; fitness summary as SAH-64-2.
- **Physio** (C-6): ROM bar = right ÷ normal maximum × 100 (extension with normal 0°: 100 % at 0°, else 90 %); MMT 0–5; special tests cycle Not done → Positive → Negative.
- **Dental** (C-3): suggestions by condition; plan dedupe on tooth + procedure ignoring case; estimate from the clinic tariff (H17), else "Not in tariff" with a typed amount; estimate signature cleared when the plan's fingerprint (rows, teeth, procedures, amounts) changes.

### D5 · Oncology decision

Written by the draft save (`screen.oncDecision {choice, reasonKey}`). In the same transaction the server computes the suggestion from the record's stored values; if `choice` differs and `reasonKey` is null → 400 `decision-reason-required` ("Pick a reason (saved with the note)."). It stores choice, reason, the suggestion at that moment, `decidedAt`, `decidedByMembershipId` and writes audit `EMR_ONC_DECISION_RECORDED` (suggestion, choice and reason keys only). On every later read the view returns `suggestedNow` and `factsChanged` ("Facts changed. Suggested now: <decision>"); the recorded decision stays until confirmed again. Nothing is sent or ordered by the decision.

### D6 · Chemotherapy order and the independent second check (SAH-66, DEC-039 addendum, SO-45-42)

**The order** is one row of `opd.chemo_order` per OPD_VISIT record of the onco profile, created on the first save of the sheet. It holds the doctor's inputs (protocol, level, reduction reason, edited final doses, pre-medicines not given, allergy confirmation, new consent signed today, scheme state, earlier outside doxorubicin) and a **server-computed snapshot**: BSA used and source, weight change, each drug's calculated, rounded and final dose, lifetime total, labs and drawn time, the decision, every safety check with pass or fail. All maths and checks are recomputed on every sheet save, every record draft save of the same record and at send.

**Fingerprint** (stated in full in 0.5.2, D14). SHA-256 of a canonical text that covers everything the checker is shown, every input behind it and everything that is sent: the doctor's stored inputs (protocol, level, reduction reason key and text, edited final doses, pre-medicines not given, allergy confirmation, new consent signed today, scheme state, earlier outside doxorubicin), the server-computed values (weight and height used, BSA raw, used, cap and source, every drug's calculated, rounded and final dose, lifetime earlier, this cycle and total, labs values and drawn time, decision), every check's key and pass or fail, and the named checker. "What the checker confirmed is what is sent": changing any covered value after the second check clears it, even when every check still passes.

**Safety checks** (9 as drawn + 1 from the story): decision recorded (a Give decision); fit to treat today (no count or organ fail, no fever); labs within 72 hours; BSA from today's weight (weight and height recorded in this record); cumulative dose within limit; dose-reduction reason (level 100 or a reason); allergies reviewed (doctor confirms; "No known drug allergy" written only then, OQ-45-23); consent for this regimen (an earlier SENT order of this protocol for the patient, or "New consent signed today"); scheme / TPA approval (APPROVED or PREAUTH_RAISED pass; NOT_IN_PACKAGE fails; SELF_PAY passes, H5); **line ready for vesicant** only when the protocol has a vesicant drug (H4).

**Lifecycle.**
1. DRAFT: the doctor edits through `PUT /emr/records/{id}/chemo-order` (order `revision`).
2. Name a checker: `PUT …/chemo-order/checker` only when every check passes (409 `checks-failing`, "Clear the red checks before the second check."). The checker is an ACTIVE membership of the clinic with role NURSE, PHARMACIST, DOCTOR, VISITING_DOCTOR or OWNER with doctor details, and is **never the prescriber**: neither the record's doctor nor any membership that saved the order (400, "The second check must be done by someone other than the prescriber."). Options from `GET …/chemo-order/checker-options`. Naming only: stage "Second check" not marked; "Waiting for <name> to confirm the second check".
3. Confirm, way (a) **own sign-in**: the checker, signed in on their own session, lists `GET /emr/chemo-checks` (orders naming their membership, DRAFT, not confirmed; oldest named first, D14), reads `GET /emr/chemo-checks/{orderId}` (read-only summary; no EMR record access is granted) and `POST /emr/chemo-checks/{orderId}/confirm {fingerprint}`. Caller ≠ named checker → 403 `not-named-checker`; caller is a prescriber → 403 `checker-is-prescriber`; fingerprint ≠ current → 409 `chemo-order-changed` (re-read).
4. Confirm, way (b) **colleague PIN** at the prescriber's device: `POST /emr/records/{id}/chemo-order/second-check {orderRevision, fingerprint, pin}` by the prescriber's session. opd first checks (plain read, no lock) that a checker is named, checks pass and the fingerprint matches; then calls `StaffPinPort.checkColleague(tenantId, callerUserId, checkerMembershipId, <checker's role>, pin)` **outside any transaction** (ADR-010 D9: own platform transaction; wrong tries count even if opd then fails); then, in its own transaction under the order row lock, re-checks revision and fingerprint (409 `chemo-order-changed`) and records the confirmation. All SAH-38 rules apply unchanged: lockout, pair cap per (prescriber, checker) for 7 days, per-caller bucket, fail closed (503 `pin-check-failed` "We could not check the PIN. Try again."), no tries left shown. The PIN is never stored, logged, audited or echoed.
5. Recorded: checker membership and user id, role, way (SIGN_IN or PIN), time, and the confirmed fingerprint. "Second check confirmed by <name>, <role>, 11:05 AM IST".
6. **Cleared when the order changes:** any save (sheet or record draft) after which the fingerprint differs from the confirmed one clears the confirmation in the same transaction, writes audit `CHEMO_SECOND_CHECK_CLEARED`, and the view says "Order changed after the second check. A new confirmation is needed." Naming another checker also clears it.
7. Send: `POST …/chemo-order/send {revision, fingerprint}`. Refused with 409 `second-check-not-confirmed` ("The second check is not confirmed yet.") unless confirmed with the current fingerprint; 409 `checks-failing` unless every check passes; the database check refuses status SENT without a confirmation equal to the order's fingerprint (second line). SENT stamps time and prescriber; "✓ Sent to pharmacy". No message goes anywhere (OQ-45-28). Retrying a SENT order with the same fingerprint answers 200 with the order (one order).
8. Hold: `POST …/chemo-order/hold` when the decision is DELAY_1_WEEK or STOP: status HELD with kind, reason text, date. No second check.
9. SENT and HELD rows are immutable (trigger). A correction after sending is an addendum with a new order and a new second check (SAH-51-5, phase 5: column `supersedes_order_id` reserved now).

Stages: Decided, Doses checked, Second check (confirmed only), Pharmacy (Sent), Chair (disabled "Later": no chair schedule, OQ-45-28; the next cycle date is kept in the course and the order sheet).

**Platform reuse (java-developer, additive, no platform.yaml change):** the colleague texts of `StaffPinException` and `ColleaguePinCheck` name "nurse". Add `StaffPinException.Subject.CHECKER` with neutral texts (H7): pair cap "Too many wrong PIN tries for this person. Choose another checker."; not eligible "Choose a checker from the list."; the other texts as the colleague ones. opd handles NOT_ELIGIBLE itself (it never reaches it, because it validates the checker first). Slugs and statuses unchanged.

### D14 · 0.5.2 follow-up (13 Nov 2026; found by QA F-1, F-2 and the java-developer; clarifying)

Contract: `docs/api/opd.yaml` 0.5.2. No path, no new field, no migration.

1. **"Waiting for my second check" is oldest named first.** `GET /emr/chemo-checks` sorts by `checker_named_at` ascending, then order id ascending (stable pages). 0.5.0 said "newest first"; the database design (`ix_chemo_order_tenant_checker_waiting` carries `checker_named_at`) and the code already sort oldest first. Oldest first is the safe order for a queue: the order that has waited longest, usually the patient already in the chair, is on top and cannot slide to page 2 when more orders are named. Rejected: newest first (an old order can be buried; nothing in the mockup asks for it, the page is not drawn, H7).
2. **The fingerprint covers the check inputs, not only the check results.** 0.5.0 hashed "every check result", so a change that keeps a check green (scheme PREAUTH_RAISED ↔ APPROVED, "New consent signed today" ticked or unticked while an earlier SENT order of the protocol exists, pre-medicines not given, earlier outside doxorubicin below the limit) did not clear a confirmed second check. The checker's summary shows the check texts that come from those inputs, so the checker relied on them. Decision (patient safety): the canonical text covers
   - (a) every doctor input stored on the order: `protocolKey`, `levelPct`, `reductionReasonKey`, `reductionReasonText`, the edited final doses (by drug key), `premedsNotGiven` (sorted), `allergyConfirmed`, `consentNewSigned`, `scheme`, `priorOutsideDoxorubicinMgM2`;
   - (b) every server-computed value of the sheet or the summary: weight and height used, BSA raw, used, capped and source, each drug's calculated, rounded and final mg (in protocol order), lifetime earlier, this cycle and total, the labs values and drawn time, the decision;
   - (c) each check's key and pass or fail;
   - (d) the named checker's membership id.

   **Not covered:** display text (check `detail`, labels, names), relative times ("drawn 20 h ago"), `revision`, save timestamps: they change without the order changing, or repeat a covered fact. **Canonical form:** UTF-8, starts with the version tag `chemo-fp-v2`, fields in the fixed order above, one `name=value` per line, sets sorted by key, numbers as plain decimals without trailing zeros, null as the literal `null`, booleans `true`/`false`. **Rule for later changes:** a new order input, or a new value shown on the sheet or the summary, joins the fingerprint with a new version tag. Effect: any DRAFT confirmed under the 0.5.1 text no longer matches after the next save and is cleared as any change (audit `CHEMO_SECOND_CHECK_CLEARED`, view state CLEARED); a send with the old fingerprint is 409 `chemo-order-changed`. Only development data exists, so no migration. The database rules (`confirmed_fingerprint = fingerprint`) are unchanged. Rejected: keep hashing results only (a checker's confirmation would survive a change of the payer state or consent the checker saw); hash the whole stored row (would include `revision` and timestamps and clear on every no-op save).
3. **`SpPreopOrders.blood` is an enum:** `NOT_NEEDED`, `GROUP_AND_SAVE`, `ONE_UNIT_RESERVED` or null, the three chips of the mockup's "Blood" row (`chipsRow('Blood', …)`, single choice) and the keys the reference list `surgeryBlood` already returns. 0.5.0 allowed a free string of 40 characters although the description already said the key is stored. Write: any other value is 400 `validation` (fieldErrors on `blood`). Read: a stored value outside the set (none expected; nothing is released) is returned as null and the chip shows unselected. Tagged C-7. Rejected: keep a free string (a typo would be stored and match no chip).
