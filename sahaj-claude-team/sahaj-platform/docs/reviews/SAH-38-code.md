## Checked and correct
Migrations (V2026_12_01_1000 additive; defaulted columns and checks, `create or replace` guard, append-only table with RLS enabled and forced, select and insert policies only, 5-column insert grant, no-update/delete/truncate trigger, `at` from `clock_timestamp()`, `seen_through` capped at the database clock; V2026_12_02_1000 only indexes and comments; guard SECURITY INVOKER with `search_path = pg_catalog`); guard rules (a)-(g) and `StaffPinOps.fifthWrongTry` agree with the trigger; fail-closed 503 scope (`DataAccessException`/`TransactionException` that is not a code fault; `isCodeFault` keeps integrity, permission, bad-grammar and invalid-API-usage errors as 500; rolls back so nothing is counted; log holds ids and exception class only; `set local` inside the ops transaction); pair cap (after the row lock, after no-PIN and locked, before the hash; PAIR_LIMIT → 429 `colleague-pin-limit` without a retry time; right PIN of a pair with wrong tries writes RIGHT_AFTER_WRONG plus audit); colleague-caused locks never switch off; notice and "Got it" (counts only, `markSeen` writes only when an unseen try lies in range, DB cap on `seen_through`); history OWNER-only from the re-read membership, 403 for others, 404 unknown; Team page `colleagueTries7d` only for an owner viewer via one grouped query, reset example now shows 3; audit values are ids, states, kinds and numbers only; frontend (OnPush/signals, 44 px, live region exists before filled; ward line only for high-alert after `pin-locked`, `pin-not-set`, `rate-limit` or `colleague-pin-limit`, always with no other nurse, never after `wrong-pin` or 503; fixed "That PIN is not right."); module boundaries; no skipped tests.

## Done well
Durable table plus database guard make the rules hard to bypass from code; every decision uses the database clock; the pair cap is exact because of the row lock; explicit and tested split between code fault and outage; the notice carries counts and no names.
