## Answers to the points asked
1. **Posting transaction:** sound.
   - `StockPosting` is the only ledger and balance writer. It inserts missing destination rows in sorted order, then locks every balance row of each store and product in one `ORDER BY product, batch, state FOR UPDATE` statement, stores in ascending id.
   - Everything is worked out in memory and refused before writing (`insufficient-stock` with every failing line up to 100, `batch-expired`), then balances and ledger are written: all or nothing.
   - The Java comparator (text order of the uuid) matches PostgreSQL's unsigned uuid order.
   - Expiry runs inside every movement (`EXPIRY_QUARANTINE`, SYSTEM, `damage.expired`). The read sweep uses `SKIP LOCKED`; sweep and movement take AVAILABLE before QUARANTINE, so there is no cycle.
   - GRN, debit note, adjustment and opening-stock order is client key, store, document, PO, number, batches, balances. No unit `FOR UPDATE` follows a number. Exceptions: M-1, m-2.
2. **Money:** paise are half-up everywhere. The debit-note GST reversal is per line at the product rate (OQ-79-13). The payable is the invoice total as typed, due = invoice date + credit days. Credit goes to the note's own receipt first, then oldest due, under `FOR UPDATE ORDER BY due_date, id`; `take = min(open, remaining)`, so a payable never goes negative. 1720's `ck_vendor_payable_settled` closes round-4 m-3. The frontend's BigInt half-up matches the backend. One drift: m-4.
3. **Approval engine:** levels copied at submit; "who decides" worked out on every read; the raiser is excluded, and the level-1 approver at level 2; with nobody left the owners are shown as "needs another approver". Self-approval is checked before the version and state checks. A handler refusal rolls everything back. Defects: M-1, m-3, m-8.
4. **Schedule X:** the PIN is verified between two transactions and the signer is rechecked inside the posting transaction. The signer lands only on the Schedule X lines of GRN and VENDOR_RETURN. The hold, release, opening stock and expiry moves carry no signer. 1730's 17 types match ADR-029 P7. `SecondSignerInput.toString` masks the PIN; no log line carries a PIN. Defects: M-2, m-5, m-6.
5. **Actor ids:** `caller.actorId()` (membership id) everywhere in WP-D and WP-E; no `userId` written as an actor.
6. **Gate order:** mostly right; the exception is m-1.
7. **Frontend:** the PIN field is `type="password"`, `autocomplete="off"`, cleared on success and on error in all three dialogs, and sent only with the post. No storage or console use. Dialogs carry titles or aria labels; the quantity helpers show "—" for null. Gaps: m-10, n-2.

## Notes (checked, no finding)
- Contract and status codes: self-approval 403 `self-approval`; level-2 refusal; `alreadyDecided` carries the current request; `schedule-x-pharmacist` and `second-signer-invalid` are used as written.
- SecondSignerService lists active PHARMACIST and OWNER members except the caller, the set `ScheduleXSignature` accepts.
- Replays answer the current state (200); a key held by someone else, or used for another operation, is 409 `client-key-reused`.
- Migration 1720: `next_document_no` keeps the union of the 1220, 1280, 1380 and 1710 bodies and adds `FOR SHARE`; the L14 ledger trigger, the approval guards, the forward-only indent guard and the ledger index are additive, with NOT VALID then validate. 1730 replaces two functions, each from its latest body, and adds the audit signer column.
- Audit rows and log lines hold ids, counts and totals; the vendor representative's name is in the audit row only.
- Frontend: OnPush, typed forms, API only in `*.api.ts`, no storage, no console, dialog names present.
