# SAH-42 · Platform admin bootstrap registration behind a PIN (local dev only)
Module: platform
Mockup screen: Sahaj admin portal (platform admin view), sign-in card `pAdminLogin` (`docs/design/mockup/sahaj-mockup.html` line 5095; ADM-1) is the pattern to reuse. **The registration page itself has no screen in the mockup.** This is a deviation under rule 1: the page is a minimal reuse of the `pAdminLogin` card (same brand bar, same side panel and card layout, same field style), it adds no other screen, and it is listed for the human's sign-off (see "Mockup deviation" and OQ-42-13). Nothing is built on that page until the human signs it off.
Source: Human, chat, 10 Nov 2026 ("a function to register as admin in the admin portal; once I create the admin I will disable it; I have one static PIN ... when I put this PIN that interface will open"). Decision record: `docs/decisions/DEC-034-admin-bootstrap-registration-pin.md` (answers: local dev only; keep the 6-digit PIN with an attempt limit). The PIN itself is **not written anywhere in the repository**, including this file.

## Problem
The Sahaj admin console (ADM-1) can only be entered by an admin who already exists. Today the first admin comes from an environment seed or from the dev-only sample-admin call (DEC-016, ADR-008), both of which the human finds awkward. The human wants a page in the admin portal where, after typing a secret PIN, the **first** platform admin can be created, and which then switches itself off.

A page that creates an admin is a privilege-escalation door: whoever gets through it owns every clinic on the platform (DEC-016). A 6-digit PIN has only 1,000,000 values, so it is safe only with a hard attempt limit, an off-switch, a self-closing rule and a narrow reach. These safeguards are the substance of this story.

## Who uses it (roles) and in which setting
- **Anonymous caller on the developer's own computer** (the only role). No admin exists yet, so no one can be signed in. The person is the human owner of the platform setting up the Sahaj admin console on a local machine (profile `dev`, `127.0.0.1`).
- **Not used by:** clinic users (owner, doctor, visiting doctor, nurse, front desk, billing, pharmacist), who are in a different login realm and see nothing of this page; a signed-in clinic token or admin token sent to these calls is ignored. No clinic setting, no ward or front-desk use.
- **Created by it:** one Sahaj platform admin (the single phase-1 admin role `PLATFORM_ADMIN`, label "Platform admin", ADR-003 H5). The finer admin roles in the mockup (Super admin, Support, Billing, Read-only auditor) are not created here.
- **Reviewers:** security-reviewer and the human, who must be able to verify each safeguard with a test.

## In scope / Out of scope
In scope:
1. An **unlock step**: the page asks for the PIN first and shows nothing else.
2. After a correct PIN, a **registration form**: name, email, password and confirm password. It creates the FIRST platform admin. The page then drops everything it holds and goes to `/admin/sign-in`; the owner **signs in once there with the same email and password (typed a second time)**, and the **existing first-sign-in step** enrols the authenticator app (two-step sign-in is always on for admins, ADR-003 D2.6). The registration page itself never shows the authenticator key, the `otpauth://` link or recovery codes. *(Reworded 11 Nov 2026 after DEC-035, option C.)*
3. Safeguards, each testable (business rules BR1 to BR14): off-switch in `.env`; self-closing; dev profile and loopback only; PIN stored only as a hash; 5 wrong PINs lock the feature for 60 minutes for everyone, remembered across a restart; a single-use 5-minute ticket between unlock and register; audit of unlock failures, the lock and the creation; empty 404 when off or closed.
4. The minimal page (BR15 to BR17) and its states: loading, error, locked, success, and the closed/off state.

Out of scope (not built, not designed here):
- Creating a **second** admin, resetting or re-enrolling an admin, changing a password, or any "forgot" flow with the PIN (a separate story).
- Any use **outside the dev profile** (staging, production, shared servers). Not available, not behind a hidden option.
- Email, SMS or WhatsApp (verification mails, "welcome" messages). Notifications are not in phase 1.
- Recovery codes: this story adds no recovery-code logic of its own. The registration page never shows them; the existing first-sign-in step at `/admin/sign-in` shows whatever it always shows (see OQ-42-3).
- Showing the authenticator setup on the registration page, or handing a sign-in token from the registration page to the sign-in page (DEC-035 option C: not built; the ADM-1 sign-in page is unchanged).
- Any new text or link on the sign-in page after a fresh registration (OQ-42-16 asks the human; nothing is added).
- A status or "is it on?" endpoint, a health item, or any other screen or admin menu entry.
- Clinic (tenant) creation, plans, modules: other ADM stories.
- Making the human's PIN hash (a helper is a request to the human and architect, OQ-42-10).
- Changing any existing admin sign-in behaviour (login, lockout, tokens).

## Business rules (numbered)
**Availability and reach**
BR1. **Off unless switched on.** The feature works only when `SAHAJ_ADMIN_BOOTSTRAP_ENABLED=true` is set by the human in `.env` (read at application start). Default is off. A change takes effect at the next start. While off, **every** request to either step (unlock and register), by any method, with any body, answers the same **empty 404** (no body, no content type, nothing that says the feature exists).
BR2. **Fail closed.** If the switch is on but the PIN hash is missing, blank or not a valid hash, or the admin realm is not enabled (ADM-1 settings and tables), the feature behaves as off (empty 404). The startup log says in one line, with no secret, why it is off.
BR3. **Reach: dev profile, loopback only (human decision, DEC-034 Q1).** The feature answers only when the dev profile is active and the caller comes from the local machine (loopback address). Any other profile, or any other caller, gets the same empty 404. No option to widen this exists in this story. (Note: the default Spring profile today is `dev`, so the profile check alone is weak; the off-switch default and BR4 are the real controls. See OQ-42-1 for calls that come through the Angular dev server.)
BR4. **Self-closing.** The moment **any** platform admin exists (active or switched off, created by the env seed, the dev sample-admin call, this page, or by hand), both steps answer the empty 404, even with the switch on, even with a valid ticket. This is checked on every request, not only at start. Creation itself is atomic: only one registration can succeed. If register calls arrive together or repeat with the one valid ticket (there is a single ticket slot, so a second valid ticket cannot exist, BR8), exactly one gets 201 and creates the admin, and every other call gets the same empty 404 (a call that waits more than 10 seconds for its turn gets 429 and creates nothing). *(Reworded 11 Nov 2026 after QA.)*

**The PIN and the lock**
BR5. **The PIN is never stored or shown.** Only a slow hash of the PIN is kept (`SAHAJ_ADMIN_BOOTSTRAP_PIN_HASH` in `.env`). The PIN is never in code, documents, `.env.example`, logs, audit rows, error messages, responses, test files or the repository. It is compared in constant time. Code and page must not hard-code "6 digits": the human may later set a longer PIN by changing only the hash (DEC-034).
BR6. **Five wrong PINs lock the feature for 60 minutes, for everyone.** The count is global (not per address or per browser, because the caller address cannot be trusted). On the 5th wrong PIN the feature locks for 60 minutes.
BR7. **Lock rules.** (a) While locked, even the correct PIN is refused and does not count; the answer says the feature is locked and for how long. (b) The lock is stored in the database and **survives a restart**; a restart does not clear the count or the lock. (c) A correct PIN resets the wrong-PIN count to zero. (d) When the 60 minutes end, the count starts again at zero. (e) A lock cancels every ticket that is still open (BR8). (f) A blank PIN is a form error, not an attempt, and is not counted. (OQ-42-5 holds the choices (c) to (e) for the human.)
BR8. **Ticket between unlock and register.** A correct PIN returns a short ticket. It is valid for **5 minutes**, usable **once**, **bound to the browser** that unlocked (a copy used from another browser is refused), and useful for the registration step only. A new unlock replaces any earlier ticket: there is one ticket slot, so at most one ticket is valid at any time. It is consumed when the admin is created, and creating the admin also closes the feature (BR4), so a used ticket is answered by the empty 404, not by "took too long". A form rejected for invalid input does not consume it (OQ-42-7); an expired, reused, unknown or foreign ticket gets the "unlock took too long" answer, not a 404 (the feature is on).

**Registration**
BR9. **Fields and rules.** Full name, work email, password (and, subject to OQ-42-4, confirm password). Email is trimmed and lower-cased, must look like an email, and may not already belong to an admin. Name is required and has a length limit. The **password rules are the same as the sign-in's** (ADR-003 D2.1): 12 to 64 characters, at most 72 bytes in UTF-8, must not contain the part of the email before "@" (case-insensitive), no other composition rules. The server checks them; the page repeats them for the user. There is no breached-password check in ADR-003 today (OQ-42-2). Field texts: "Enter the full name." and "Enter a valid email."; there is no "email already used" text (an existing admin closes the feature). The server reports at most two field errors per try (the name, plus the first wrong one of email then password), so the page checks the required fields and the password length itself and the owner may send again with the same ticket. A request body that cannot be read (a hand-made call) is a 400 bad-request with no field error, not counted as a PIN try and not spending the ticket. *(Added 11 Nov 2026, ADR-018 Revision 2.)*
BR10. **Two-step sign-in is mandatory, and the enrolment is the existing sign-in step.** The new admin cannot reach the console without enrolling an authenticator app (key for manual entry or `otpauth://` link, then a 6-digit code). That enrolment happens **only at `/admin/sign-in`**, in the existing first-sign-in step, exactly as the sign-in does at first use; it is **not** shown on the registration page (DEC-035 option C, ADR-018 D6). When the admin is created the page drops every value it holds (name, email, both passwords, ticket) and goes to `/admin/sign-in`; nothing is carried over and nothing is pre-filled, so **the owner types the email and the password a second time** to sign in. The password is stored as the sign-in stores it (BCrypt, strength 12) and the authenticator secret is stored encrypted, using the existing admin code, not a second implementation. *(Reworded 11 Nov 2026 after DEC-035.)*
BR11. **The new admin** belongs to no clinic: no tenant, no membership, no link to any clinic user. Role: platform admin.

**Audit, privacy and tests**
BR12. **Audit** (ADR-003 D7 append-only admin audit): one entry for each wrong PIN (unlock failure), one for the lock, one for the creation of the admin (admin id and name). Each entry has time, caller address and request id. **No entry holds a PIN (right or wrong), a password, a hash, a ticket, an authenticator secret or an email.** The answers "off" and "closed" write nothing.
BR13. **Nothing sensitive in logs or responses.** No log line, error message or response holds the PIN, a ticket, the password, the hash, or the authenticator secret (except the one-time enrolment answer to the new admin, which is never logged). The server's wrong-PIN answer is the same text whatever was typed. Responses to these calls are not cached. The one log line that carries a time is the lock line: written once per lock, when the 5th wrong PIN sets it, with the lock end time and the request id; refusals during a lock write no log line. *(Added 11 Nov 2026, ADR-018 Revision 2.)*
BR14. **Tenant and realm rule.** These calls never bind a clinic (`app.tenant_id` is not set), never read clinic data, and are served by the admin realm only. The app still connects as `sahaj_app`. A clinic token, an admin token or a cookie sent with the request is ignored.
BR15. **Tests use their own PIN.** Automated tests set a throwaway PIN (and its hash) inside the test itself, and never read the human's `.env` or hash. The real PIN is never typed into any test, fixture, screenshot or document.

**The page (minimal, mockup deviation)**
BR16. **One new route**, `/admin/register`, in the admin area, outside the console shell, built from the `pAdminLogin` pattern: the brand bar with "Back to website", the side panel with the pill "Sahaj team only", and one glass card. It shows **one step at a time**: Unlock, then Create the first admin; after the admin is created the page leaves for `/admin/sign-in` (BR10) and has no third step. The Registration PIN field is password-type with `autocomplete="one-time-code"`, because browsers ignore `autocomplete="off"` on password fields and may offer to save the PIN; Chromium browsers do not offer to save `one-time-code` fields (DEC-035 question 2; QA checks this by hand in Chrome and Edge). No other screen, no menu item, no link from the sign-in page or the website. *(Reworded 11 Nov 2026 after DEC-035.)*
BR17. **States**: loading (calls in progress, button disabled and labelled as busy), error (field and call errors, fixed texts, no server text), locked (with minutes left), success, and **closed/off** (the server answered the empty 404, and the app shows what it shows for any unknown address, which is the home page; the app has no separate "page not found" screen; nothing on the page reveals that the feature exists). Plain English, sentence case, no emoji. Accessible by keyboard and screen reader; usable at 360 px; touch targets at least 44 px (`.claude/rules/angular.md`). The new texts are listed in the stories for sign-off.

## Patient-safety and privacy points
- **No patient data is involved.** The calls take no patient input and read no clinic data. Never log patient names, mobile numbers, ABHA numbers or clinical notes (unchanged).
- **Privilege escalation is the risk.** An attacker who guesses the PIN or finds the page open gets full control of the platform, which can switch modules on for every clinic and see clinic-level counts. Controls: off by default, dev-and-loopback only, self-closing, global attempt limit, single-use short ticket, audit.
- **The PIN is treated as already known.** The human typed it into a chat (DEC-034), so the chat history holds it. It must never reach a file; the human may change it at any time by changing the hash. Consider a new PIN before the tool is used on any shared machine (not allowed in this story anyway).
- **Lock-out of the human is possible.** Five wrong tries lock everyone for 60 minutes, including the human. This story gives no reset; the wait or a human-run database step clears it (OQ-42-14).
- **Admin accounts are not recoverable here.** If the first admin loses the password or the authenticator, this story has no reset; a human fixes it in the database (ADR-003 H16). The page asks for the password twice (confirm password) before submit so that a typo does not waste the one chance; the authenticator key is shown by the existing sign-in step, where it can be copied.
- **Audit shows who and when, never secrets** (BR12). The caller address in the audit is for forensic use only.
- The admin email is personal data of a Sahaj staff member, not a patient: it is stored for sign-in, never logged and never written to the audit.

## Plan or entitlement
None. It is a platform tool, not a clinic feature: no plan, no module flag, no per-clinic setting. It is unlocked only by the `.env` switch (BR1).

## Dependencies (human-only and other owners, no design here)
- ADM-1 admin tables and the role `sahaj_admin_definer` must be active (parked migrations, DEC-016). The `.env` keys for the admin realm (`SAHAJ_ADMIN_ENABLED`, `SAHAJ_ADMIN_JWT_SECRET`, `SAHAJ_ADMIN_TOTP_KEY`) and the two new keys (`SAHAJ_ADMIN_BOOTSTRAP_ENABLED`, `SAHAJ_ADMIN_BOOTSTRAP_PIN_HASH`) are set by the human; `.env.example` is human-owned.
- The wrong-PIN count and the lock must be stored in the database (BR7b), so a new place for them is a request to the db-engineer after the architect's design. Tickets may live in memory or the database (architect); a restart invalidating a 5-minute ticket is acceptable.

## Open questions for the human
Each has a safe default taken under DEC-023 if you do not answer. Full wording and defaults are in `docs/stories/SAH-42.md`, "Open questions".
- **OQ-42-1** How does "loopback only" work when the page is used through the Angular dev server (port 4200 forwards with forwarding headers)? Architect decides; human confirms.
- **OQ-42-2** There is no breached-password check in the admin sign-in rules (DEC-034 assumed one). Add a check, or keep the ADR-003 password rules only? Default: ADR-003 rules only.
- **OQ-42-3** ANSWERED 11 Nov 2026 (DEC-035, option C). The admin is created when the details are accepted; the page then goes to `/admin/sign-in` and the existing first-sign-in step does the enrolment (key, code and the recovery codes it always shows). The registration page does not show the authenticator setup or the recovery codes. The owner types email and password twice. Other options (a token hand-over, a shared component) were not chosen.
- **OQ-42-4** Add a "Confirm password" field (a typo cannot be fixed afterwards)? Default: yes.
- **OQ-42-5** Wrong-PIN count: reset by a correct PIN, restarts after a lock, a lock cancels open tickets? Default: yes to all.
- **OQ-42-6** Show "{n} tries left" after a wrong PIN? Default: yes.
- **OQ-42-7** Does an invalid form (weak password) consume the ticket? Default: no.
- **OQ-42-8** What if the switch is on in a non-dev profile? Default: empty 404, application still starts.
- **OQ-42-9** Is a successful unlock also audited? Default: no (only the three events asked for).
- **OQ-42-10** How the human makes the PIN hash without the PIN landing in a shell history or chat. Request to the architect and human.
- **OQ-42-11** Should the production frontend build leave the route out? Default: route stays; when the server says 404 the app shows what it shows for any unknown address (the home page).
- **OQ-42-12** Wrong-PIN text and the other new texts: confirm wording. Includes the built texts that await sign-off (busy labels, the safety-net line, "That PIN is not right.", route title, aria-label, passwords cleared after a failed create): see "Open wording" in `docs/stories/SAH-42.md`.
- **OQ-42-13** Sign-off of the deviation: new page and fields not in the mockup.
- **OQ-42-14** How to clear a lock early (human-run database step) if the human locks himself out. Default: wait 60 minutes; the db-engineer may add a small runbook.
- **OQ-42-15** (new 11 Nov 2026) Text the page shows if the server ever answers 400 bad-request (a body it cannot read; the page never sends one). Default: "Something went wrong. Try again." (the built page uses the same line for 429, 500, 413, 403 and unknown answers too).
- **OQ-42-16** (new 11 Nov 2026, from DEC-035) After a fresh registration the owner lands on `/admin/sign-in` with nothing that explains why he must sign in now. Should the sign-in page show a one-line explanation after a fresh registration? It would be new wording and a change to the ADM-1 page. **Default: no; nothing is added to the sign-in page.** The human decides and gives the wording if yes.
