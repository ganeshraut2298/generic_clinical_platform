## How the tests are built

Every integration test goes through the real application (profile `test`, whole Spring context, MockMvc through the real security chain) against the real `sahaj_test` PostgreSQL database as `sahaj_app`. Nothing is mocked. Clinics, doctors, patients, visits, records, services, forms, courses, payments and admissions are made through the real endpoints. Direct SQL is used only where no endpoint exists or a probe must show a constraint: a signed record (`update ... set status = 'SIGNED'`, because SAH-51 does not exist: it is the one update the column grant allows), a sitting marked done (what SAH-51 will do in the sign transaction), a discharged admission, probing a constraint inside a transaction that is always rolled back, and reading rows back. Throwaway data only: made-up names and mobile numbers. Tenant isolation is proven both through the endpoints (404, empty lists) and in SQL (clinic B sees none of clinic A's rows as `sahaj_app`; no clinic bound sees none; an insert naming another clinic is refused). Idempotency and concurrency are proven with two real threads.

## Not covered (and why)

1. **IPD rounds and Emergency records in history and copy.** Drafts for IPD_ROUND and ER_ASSESSMENT answer 409 `encounter-drafts-not-enabled` (OQ-43-27), so no earlier round record exists and "this admission's earlier notes first" (SAH-50-1.5) cannot be reached. The scope path that can be reached (a visiting doctor, FORBIDDEN) is covered; OUTSIDE_SCOPE is unreachable for the two allowed roles (a doctor's IPD scope is every patient, ADR-017), as finding F-1 of SAH-53 said.
2. **BODY_MAP and TOOTH_CHART inside a form** (SAH-57-4.5, SAH-59-1.8) and **chains of show-if** (59-2.5): the pure rules are unit-tested by the java-developer (`EmrFormValues`); no IT field of these types is built.
3. **Copy from last visit per form field** (SAH-59-5.6): needs a signed earlier entry of the same form and the per-field copy flag; the department-level copy flow is in `EmrRecordsIT`. A next-pass IT.
4. **Diagnosis code search in history** (50-3.2): the code is stored as the item's key and `code`; the search text covers the item text and code of signed records, the IT searches by name only.
5. **Marathi and Hindi advice text** (48-3.2, 56-2.5): no source exists (null in the master); fixed headings in three languages are covered.
6. **Everything that waits for DEC-040**: WhatsApp, ABHA, receipt send, PDF. The "not available" state is covered (`share.available` false, `needs-whatsapp-service`).
7. **Playwright**: none in this pass (see the head of this document).
8. **Load and index use** of the new queries (history over 500 records, course lists) is not measured; the history search is in the application over one patient's rows by design (ADR-022 D10).

## Risks in the tests themselves (a red result may be the test's assumption, not the code)

These are assumptions read from the code that could not be confirmed against a running database. If a test fails for one of them the first look is the assertion, then the code.
1. Where a live form lands in a department's working layout (the test checks only that every section after it is in the Treatment part) and that a record's `layoutSource` stays STARTER when only a form is appended.
2. The exact wording of publish-check messages (`The first band must start at or below the lowest possible score (1)`, `Bands must run from the lowest score to the highest`) and the en dash in `Outside 0–10`.
3. `GET /billing/revenue` `days` list contains course money, and `modes` lists a mode with no money or not.
4. `depositPaise` of an admission detail is the sum of all its deposits (the course deposit included).
5. The Flyway version strings (`2026.12.10.1000` and `2026.12.9.1000`, Flyway drops the leading zero of a part).
6. The receipt `collectedByName` is non-blank (the owner may have no name; the code falls back to "Someone").
7. SQLSTATE of the NOT NULL or check that refuses a desk deposit with no mode (`23514` or `23502` accepted).
