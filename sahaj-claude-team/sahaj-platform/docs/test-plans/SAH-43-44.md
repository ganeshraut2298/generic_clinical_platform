Module: opd (reads doctor details and the clinic's specialty through `platform.api`).

## How the tests are built

Every test goes through the real application (profile `test`, the whole Spring context, MockMvc through the real security chain) against the real `sahaj_test` PostgreSQL database as `sahaj_app`. Nothing is mocked. Clinics are made by a real sign-up and the real setup wizard; doctors and staff are added through the real Team endpoint. The few direct writes are the ones no endpoint exists for (a doctor's specialty text, an owner's doctor details, a clinic's specialty, a membership status) and are done as `sahaj_app` with the clinic bound, committed, the way the owning module would. The usage counts are written through `EmrUsageRecorder` inside a transaction, exactly as the sign step of SAH-51 will write them (there is no REST call that writes them). Expected lists and tables are typed in the tests from the stories (the section table of `SAH-44.md`) or worked out from plain reads of the master tables, never copied from the application's query. Data is throwaway: made-up names, registration numbers and mobile numbers.

Three facts about the fixtures, found while running the first version of these tests, that the next person should know: (1) the setup wizard already gives the clinic's owner a doctor profile, so "an owner without doctor details" is a clinic that has only signed up (`bareOwnerClinic`), and "an owner with doctor details" is written as an upsert; (2) the free plan allows 5 users in total (the Team endpoint answers 409 `plan-limit` past that) and a new clinic starts with two, so `addStaff` falls back to a second sign-up plus a membership row when the clinic is full; (3) `canEdit` follows the membership read fresh, not the role in the token, so "canEdit is false" is asserted only for real people.

## Differences found while planning (for the owner of the document or code, not fixed by QA)

1. **Clinic id in a body (44-2).** The story says the clinic id in a body "is ignored". The contract (`additionalProperties: false`) and the built code refuse any unknown field with 400. The tests follow the contract. Either reading never lets a body choose the clinic. Tech lead to confirm the wording of the story (business-analyst).
2. **TRUNCATE on the referenced template tables.** The design note S-16 expects 42501 "immutable" for TRUNCATE on all three tables. For `emr_template` and `emr_template_section`, which other tables point at, PostgreSQL may refuse a plain TRUNCATE for the foreign key first (0A000). The test accepts either for the plain statement and requires 42501 "immutable" for `TRUNCATE ... CASCADE`. The data is protected either way (db-engineer to note in the design).
3. **A wrong role with a body that has an unknown field** gets 400 before the 403 (java finding 7: the body is read before the role check). Not asserted either way; no data is exposed.
