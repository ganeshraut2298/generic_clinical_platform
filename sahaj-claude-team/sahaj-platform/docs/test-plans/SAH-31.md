# Test plan SAH-31 · IPD medicine orders, safety checks, pharmacist check, and the platform staff PIN (backend)

Story: `docs/stories/SAH-31.md` (15 acceptance criteria). Decisions: DEC-017 (personal staff PIN; pharmacist = OWNER and PHARMACIST), ADR-009 (medicine orders), ADR-010 (staff PIN), DEC-014 (safer reading). Contracts: `docs/api/ipd.yaml` (`GET /admissions/{id}/emr`, `POST /admissions/{id}/medicine-orders`, `POST /medicine-orders/{id}/stop|verify|reject`, `GET /pharmacist-checks`, `GET /pharmacist-checks/summary`) and `docs/api/platform.yaml` (`GET|PUT /me/pin`, `POST /me/pin/code`, `POST /team/{id}/pin/reset`, `TeamMember.pin`, the `pin` line of `GET /setup/overview`, the PHARMACIST menu). Database: `docs/database/SAH-31.md` (21-item QA list) and `docs/database/SAH-31-pin.md` (26-item QA list).

This is the **backend** part of the plan (integration tests on the real `sahaj_test` database, as `sahaj_app`, MockMvc through the full filter chain, profile `test`). The Playwright specs are written by another QA agent and are not listed here. The two java-developer hand-backs ("What QA must test") were not available as files when this plan was written; the coverage list below is built from the task brief, both design notes, ADR-009, ADR-010, DEC-017 and the two contracts. Any item of a hand-back that is not in the table is a gap to be named by the tech lead.

- `WardNameGuardIT`: the ambiguous `assertThat` was already replaced by `assertError` before this pass; nothing to change.

## How time, people, the PIN and the database are handled
- **Pepper.** `PinPepper` makes 32 random bytes per JVM run and `@WithPinPepper` puts them in the test context (no value is committed). The classes that test a missing pepper blank it with a test property source and run in their own context.
- **People.** The Team endpoint holds five people per clinic (`PlanLimits.MAX_USERS`) and a test hospital already has the owner and a doctor, so `PinTestSupport.staff` makes a person the way a second clinic membership is made elsewhere in these tests: a real sign-up of a new mobile (own user id, own mobile) and a committed membership in the clinic with a display name; the token is signed for that real user and role. A person who has never been sent a code (the "send a code first" case) is made through `POST /team`.
- **The code.** Read from the one permitted dev/test log line (`LogOtpSender`), never from an answer. `allowResend` moves the last send time back so a second code can be requested inside a test without waiting 30 seconds; it does not expire the code.
- **Time.** Application code cannot write a time. A lock already over, a window older than 24 hours and lock count 2 are written by the table owner (`sahaj_migrator`, RLS lifted in the same transaction) with `trg_staff_pin_guard_update` switched off and on again inside one committed transaction (`forcePinRow`). Orders with chosen times for paging are inserted by the owner (`insertPending`).
- **Rate limit seam.** Since the review fix pass the in-memory limits are four buckets per person: failed PIN checks (10 per 5 minutes; wrong, locked and not-set results count, a right PIN never does), PIN saves (10 per 5 minutes, its own bucket), code requests (5 per hour) and owner resets (30 per hour; an unknown or foreign membership id is 404 before the allowance is touched). `freshPinAllowance` forgets one person's count in the first two (`pinFailures` and `pinSets`, by reflection) so a lockout test (five tries, fifteen for the third lock) is not stopped by the limit. The limits have their own tests that do not call it (`StaffPinCheckIT.tenFailedChecks...`, `tenNotSetChecks...`, `rightPinsNeverUseTheAllowance...`, `savingAPinHasABucketOfItsOwn...`, `StaffPinIT.tenPinOperations...`, `fiveCodeRequests...`, `thirtyResets...`, `anUnknownMembershipIdOnReset...`, `PharmacistCheckIT.tenFailedPinChecks...`, `MedicineReviewFixIT.twelveRightPins...`).
- **Races** are forced: a second connection holds the admission row, each request is started and seen waiting in `pg_stat_activity` (`awaitLockWaiters`), then the lock is released. The two first PIN saves are forced by holding the latest one-time code row so both requests pass the code check and meet the primary key.
- **Database errors** (23505 / 23514 / 23503) are forced by a trigger the table owner creates and drops for one clinic only (the technique of `failingInsert`).
- **Privacy checks** look at the audit rows of this story (`IPD_MED_*`, `PLATFORM_PIN_*`) and at the clinical events; digits of a PIN are looked for as a stand-alone token so a UUID or a time cannot match by chance.
- Expected texts are written in the tests from the contract and the ADRs, not read from the code. `sahaj_test` is not cleaned; every test uses its own new clinic.

## Review fix pass (docs/reviews/SAH-31-code.md and SAH-31-security.md): criterion to test

Tests broken by design and fixed (nothing weakened; each now asserts the new rule):
- `PinTestSupport.freshPinAllowance` clears both `pinFailures` and `pinSets` (it used the removed `pinOperations`); every caller works again (`StaffPinCheckIT`, `PharmacistCheckIT`, `StaffPinPepperIT`, `MedicineSupport`).
- `StaffPinCheckIT.tenPinOperations...SharedBetweenChecksAndSaves...` (the shared bucket is gone) is replaced by four tests (R1 below).
- `PharmacistCheckIT.theQueueLists...AndWritesNothing` now proves: one access row per distinct patient on a served page (the owner's call is a second access), the summary writes nothing, and no audit row, event, order or PIN row changes. `theRightPinAndTheCurrentToken...` expects +1 access row (the answer carries the next page with the other order). `aPharmacistWithoutAPin...` takes its snapshot after the queue read (a read is an access now). `tenPinOperations...` was renamed `tenFailedPinChecks...` (10 failed checks, the 11th verify with the right PIN is 429).
- `MedicineOrderFlowIT` privacy checks now look at the whole audit trail of the clinic (`allAuditText`), not only the rows of SAH-31, because the patient rows no longer hold the allergy text.
