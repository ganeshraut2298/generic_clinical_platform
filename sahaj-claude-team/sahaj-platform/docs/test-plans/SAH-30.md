## How time and the database are handled
- Vitals are append-only (privilege and trigger, also for the table owner), so an old reading is never updated: `VitalsSupport.insertVitalsAt` INSERTs one row with an explicit `recorded_at` as `sahaj_migrator`, in ONE transaction with `NO FORCE ROW LEVEL SECURITY`, the insert and `FORCE` again (the method of `IpdBillingSupport.backdate`). `vitalsAged(n)` dates it n whole minutes and 30 seconds ago, so it reads n minutes for the next half minute whatever the speed of the test (239, 240, 241 and 300 minutes are tested).
- An escalation is closed or acknowledged the same way (the Safety board story does not exist yet): one `update` as the owner with `NO FORCE`; the guard trigger allows OPEN to ACK and OPEN to DONE.
- Statements that must fail (`update`, `delete`, `truncate`, column inserts, checks) run as `sahaj_app` with the tenant bound, one per transaction, rolled back. The same statements run as the owner (rolled back) prove the triggers.
- A forced database failure (`VitalsSupport.failingInsert`) creates a `before insert` trigger on `ipd.clinical_event` or `platform.audit_event` limited to the test clinic (`when new.tenant_id = <clinic>`), runs the request, and drops the trigger and its function. The request ends 500 and everything the save wrote must be gone.
- The row lock test holds `select ... for no key update` on one admission in another connection; a save on it must wait, everything else must not.
- Expected values (scores, words, toasts, event lines, messages) are written in the tests from the story and the contract, never read back from the code. Test values are fakes: names "Zubin Wadkar nnnn", mobile numbers from `uniqueMobile()`.
