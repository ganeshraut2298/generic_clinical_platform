## How time and the database are handled
Arrival times in the past cannot be written by `sahaj_app` (`arrived_at` has no grant) and the application clock cannot move, so `EmergencySupport.arrivedAt` runs, in ONE transaction as the table owner `sahaj_migrator`, `NO FORCE ROW LEVEL SECURITY`, the single-row update and `FORCE` again (the method of `IpdBillingSupport.backdate`). `waited(case, n)` sets the arrival to n whole minutes and 30 seconds ago, so the case has waited exactly n minutes (rounded down) for the next half minute whatever the speed of the test. Expected values (targets 5/30/120 and 0/10/30/60/120, the level names, the toasts) are written in the tests from the story, never read back from the code.

## Findings (application, not changed by QA)

- **F1 (fixed, front end): `/app/emergency` was not routed.** The route is mounted now (menu guard `emergency`); the four route cases pass on both projects (8 runs). History: the menu item, the header button and a typed URL used to land on Today through the `**` redirect.
- **F2 (decided, front end): no beds, the Emergency queue still works.** Decision: a hospital with IPD on and no beds yet may use the queue, because the menu item and the badge are shown and the server accepts registrations. `/app/emergency` renders the queue and Quick registration with zero beds (`<app-emergency>` is outside the no-beds branch of `ipd.page.html`); `/app/ipd` on the board tab still shows "Add your wards and beds to start". Four e2e cases cover both (mock `bedsTotal` 0). Not asserted, because the page decides it: whether the tab strip shows on `/app/ipd` with zero beds.
- **F3 (closed, back end and database): ordering by `recorded_at`.** Closed by the fix pass (migration `V2026_11_24_1000`: `recorded_at` and `arrived_at` default to `clock_timestamp()`, and the Java code reads one database clock after the clinic lock). `EmergencyConcurrencyIT` now compares by the stored `recorded_at` (no `xmin`) and checks the chain of the events; it passes. Original finding: `recorded_at` is the transaction start time (`now()`), taken before the clinic lock is won. Two re-triages that race may therefore be stored in the order opposite to their `recorded_at`, so "latest event by time" can differ from the case's final level. `EmergencyConcurrencyIT` compares by the writing transaction (`xmin`) and passes; the level history shown to a user should order by the write order (for example by `clock_timestamp()` or an event number) when it is built.
- **F4 (closed, contract and test): "then id".** The contract now says "then id (as a UUID compare: java.util.UUID order, not the PostgreSQL uuid order)" and `EmergencyIT.casesOfOneLevelAndOneInstantAreOrderedByTheJavaUuidCompare...` fixes that order. Original finding: The queue's third sort key is `UUID.compareTo` in Java (signed comparison), which differs from PostgreSQL's uuid order. The contract does not say which; the test only requires a fixed order.
- **F5 (low, contract): the order of target values is not checked.** Targets such as Red 120 and Green 5 are accepted by the API and the database (the design note says so). Decide whether an increasing order is required.
- **F6 (human-owned gate): `node scripts/validate.mjs frontend` fails on its second step.** `npm test -- --watch=false --browsers=ChromeHeadless` is refused by the vitest runner ("The browsers option requires @vitest/browser-playwright..."); `npm test -- --watch=false` passes (107 files, 1,038 tests). `scripts/` is human-owned.
