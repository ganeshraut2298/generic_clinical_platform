## How the tests work

- The backend is **not** running. Every call is mocked with `page.route()`; shapes are copied from the two contract files. The notice, the seen call and the history are answered by `sah31-world.ts`; the Give sheet runs against the SAH-32 MAR mock, and each test forces the answer it needs with `m.doseAnswer`.
- The PIN of the second nurse (`4827`), a wrong PIN (`6150`) and the time of the newest try (`05:40:12.345678`) appear nowhere else, so "not in the page, a field, storage, the console or a URL" is a real search (`expectNowhere`).
- The one-retry-a-minute rule uses `page.clock` (the store compares `Date.now()`); a route change is a click on a sidebar link made from the page (the drawer is closed on a phone).

## Findings

No app defect found in the notice, the Team page or the Give sheet texts. Observations:

- The banner's "Got it" button is `mat-flat-button` and the live-region wrapper stays in the page when there is no notice (by design, so the first notice is announced).
- Team page: `pin.colleagueTries7d` is `0` for the owner on rows with no tries; the screen shows nothing for 0, as AC 8 says. A missing number (a non-owner) is never shown as 0.
- Script defect, not an app defect: `node scripts/validate.mjs frontend` passes `--browsers=ChromeHeadless` to `ng test`, and the Angular test runner (vitest) refuses it ("The browsers option requires either @vitest/browser-playwright ..."). So the gate fails before the build. `npm --prefix frontend test -- --watch=false` runs 1,984 unit tests and passes. `scripts/` is human-only; the fix is to drop the flag.

### Re-run after the developer's fixes for F-1 and F-3 (7 Nov 2026, fresh production build)

This story's own specs (`medicine-round`, `colleague-pin`) passed in the regression run; F-1 and F-3 belong to SAH-36 and are listed here because the three stories share one run.

- `admitted-cards.spec.ts` (136 runs, both projects), three runs in a row: run 1 **131 passed, 5 failed**; run 2 **132 passed, 4 failed**; run 3 **134 passed, 2 failed**.
- **F-3 is fixed**: `layout › F-3 ...` (the 360 px Table view must not scroll the page sideways) passed 6 of 6 (3 runs × 2 projects). The test was not changed.
- **F-1 is NOT fixed**: the free-bed test (`#ad-bed`) failed 6 of 6 (3 runs × 2 projects) and the no-free-bed test (`#ad-move-row`) failed 4 of 6 (it passed on both projects in run 3). The slow-read (800 ms) test passed 6 of 6. Cause, from a focus log added for the run (a temporary spec copy, deleted afterwards): the focus order was `Transfer button → SELECT#ad-bed (1469 ms) → Close button (1472 ms)`. The new code does focus `#ad-bed`, but 3 ms later the dialog's own opening step (first tabbable control, the Close button) takes the focus back, and it stays there (checked 1.5 s later). So `dialogRef.afterOpened()` still fires before Material's initial-focus step, or the `afterNextRender` runs before it. The same happens with no free bed (focus ends on the Close button, `#ad-move-row` not focused). Suggested fix for the owner: open the dialog with `autoFocus: false` when `startView` is `move` (in `ipd.page.ts`, `openById`), or move the focus one step later (for example after `dialogRef.afterOpened()` plus a macrotask or a second render).
- One extra red in run 1: `layout › 360 px: one card per row whatever the setting ... 44 px high` on the phone timed out at 30 s inside the loop that measures each control (`locator.evaluate` waiting on the first "Show more" button). It passed in runs 2 and 3, on desktop in run 1, and 2 of 2 when run alone twice. Treated as a load flake (the machine was also running the backend tests), see below.
- Regression, once, both projects: `medicine-round`, `colleague-pin`, `safety`, `discharge`, `bed-transfer` together: **572 passed, 0 failed** (9.1 minutes).
- Known flakes seen earlier, checked again: `medicine-round › a late high-alert row ...` on desktop (`dialogReady` did not see the Give sheet leave its opening state within 7 s under load): 2 of 2 passed alone, and it passed inside the 572-run regression. `emergency › stale queue: a failed 60-second reload ...` on desktop (a poll that timed out under load): 4 of 4 passed alone, twice in a row (8 of 8 over two runs).
