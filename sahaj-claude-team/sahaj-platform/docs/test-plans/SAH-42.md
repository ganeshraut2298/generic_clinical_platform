# Test plan SAH-42 · Platform admin bootstrap registration behind a PIN (local dev only)

Requirement `docs/requirements/SAH-42.md` (BR1 to BR17) · stories `docs/stories/SAH-42.md` (SAH-42-1 to -6, OQ-42-1 to -14) · decision `docs/decisions/DEC-034-admin-bootstrap-registration-pin.md` · design `docs/architecture/adr/ADR-018-admin-bootstrap-registration-pin.md` (Revisions 1 to 3; tests R3-I1 to R3-I13 in section 8.4) · contract `docs/api/admin.yaml` 0.5.0 (`bootstrapUnlock`, `bootstrapRegister`) · database `docs/database/SAH-42.md` (cases S1 to S38) and `SAH-42-admin-bootstrap.sql` · runbooks `docs/database/runbooks/admin-bootstrap-clear-lock.sql` and `dev-tools-sample-admin-cleanup.sql`.
Mockup screen: Sahaj admin portal, sign-in card `pAdminLogin` (pattern only). **The `/admin/register` page is not in the mockup** (DEC-013 item 16, rule 1: a deviation for the human's sign-off). **Update 11 Nov 2026 (the page is built): section 11 is the Playwright e2e of the page, `frontend/e2e/admin-register.spec.ts`; the rows below marked "page" point to it.** Sections 1 to 10 are the server side. **Update 11 Nov 2026 (DEC-035, human answer): option C (after "Create admin" the page goes to `/admin/sign-in`; the e2e tests only that hand-off), the PIN field says `autocomplete="one-time-code"`, and a closed or switched-off feature shows what the app shows for any unknown address (the home page).** **The page has never run against the real backend: every server answer in the e2e is made in the browser (`page.route`). Real-backend checks are the manual items M-4, M-5 and C1 in section 10, for the human.**
Results of the runs: `docs/reviews/QA_REPORT_SAH-42.md`. **Revision 3 update (11 Nov 2026):** the tests were moved to the ADR-018 Revision 3 shapes (count first, judge after; lease; folder `db/bootstrap-dev-tools`; guard text), and extended (section 8.4). Security rule for every test: the human's real PIN is not known to any test. Each test sets its own throwaway PIN (`qa-pin-7f3k`, deliberately not six digits), password, hash and e-mail inside the test JVM.

The application is started like a developer starts it (`AppRun`: real command-line arguments, a simulated environment for `SAHAJ_ADMIN_BOOTSTRAP_ENABLED` and `SAHAJ_ADMIN_BOOTSTRAP_PIN_HASH`, profile `dev,test`, random loopback port, database `sahaj_test`). A refusal is judged by bytes: the same empty 404 as every other dev-only path that is off (`RawHttp.Response.fingerprint`).

```bash
# all under the backend + frontend locks, one Maven at a time
mvn -f backend/pom.xml -Pdev-tools verify            # unit tests of both source sets + every IT, dev-tools build (jar in backend/target-devtools)
node scripts/validate.mjs backend                    # the gate: mvn verify, normal build (production-only ITs run, dev-tools ITs are not compiled)
# only the SAH-42 ITs of the dev-tools build:
mvn -f backend/pom.xml -Pdev-tools verify -Dtest=NoSuchTest -Dsurefire.failIfNoSpecifiedTests=false "-Dit.test=Bootstrap*IT,PackagedJar*IT,DevToolsGuardCallbackIT"
```

```bash
# Revision 3, the run the merge approval must require (code review finding 4): the database ITs are mandatory, a missing human
# prerequisite FAILS (canary) instead of skipping
mvn -f backend/pom.xml -Pdev-tools verify -Dtest=NoSuchTest -Dsurefire.failIfNoSpecifiedTests=false "-Dit.test=Bootstrap*IT,PackagedJar*IT,DevToolsGuardCallbackIT" -Dsahaj.bootstrap.requireDb=true
```

Time is never waited for: a lock "30 minutes later", a ticket "5 minutes and 1 second old" or "the lease ran out" is made by moving the stored time as `sahaj_migrator` (`BootstrapDb.lockFor`, `lockEndedAgo`, `ticketEndsIn`, `expireLease`, `leaseLiveFor`; every move respects the table's check constraints: a lease is two columns set or cleared together, a lock needs count 5 and no ticket), as the database design prescribes (the functions read only `clock_timestamp()`). Only the real waits really wait: the 10-second lock wait (S23, the register 429), the 10-second BUSY poll (R3-I4) and the slow-compare tests (a BCrypt cost-16 hash, a few seconds per try).

"Runs now" in the tables below means: needs none of P1 to P3. A DB test whose HUMAN precondition (P1 to P3) is missing is skipped with `PRECONDITION NOT MET: ...`, never passed. A failing test is reported to the owner of the code, not changed or removed.

**Skip or fail (Revision 3, code review findings 2 and 3, security condition):**
1. Only P1, P2, P3 skip (`BootstrapDb.assumePrerequisites`). Everything else fails.
2. After the application start attempt (`BootstrapSupport.ensureObjectsOrSkip`) the five functions, the state table and its two lease columns MUST exist, and no Revision 2 function shape may remain (`BootstrapDb.requireObjectsAfterStart`): a callback that did not run or did not create them is a failure, never a skip. A database that still holds the Revision 2 shapes is upgraded by that same start (the callback drops the old shapes).
3. A stray admin row fails (`BootstrapDb.failIfAnAdminExists`): the message says admin and audit rows are append-only, names `SampleAdminDb.cleanup` and `node scripts/validate.mjs db`, and says that the cleanup runbook `dev-tools-sample-admin-cleanup.sql` removes the dev-tools objects and grants but deletes no admin row.
4. Canary `BootstrapPrerequisitesCanaryIT`: with `-Dsahaj.bootstrap.requireDb=true` (or `SAHAJ_BOOTSTRAP_REQUIRE_DB=true`) a missing P1, P2 or P3 FAILS the build and names the item; without the property it is a skip with the same text. A stray admin row fails in both modes. A third canary test checks, in require mode, that a table that exists has all five Revision 3 functions and no old shape.
