## How time, roles and the database are handled
- Expected texts (409 details, field messages, event lines, labels, audit key sets) are written in the tests from the story, ADR-007 and the contract, never read back from the code.
- Every person is a real member (added through the Team endpoint, own user id, own name, role in the membership and in the token), so "two doctors" are two users. The older `clinic.as(role)` style (owner's user id, token role chosen) is used for roles that must be refused and for the mismatch cases.
- Role changed in the membership but not in the token: `setMembershipRole` / `setMembershipStatus` on a real member; positive controls before and after.
- **Review fixes: how a past senior call is made.** `ipd.ews_senior_call` is append-only (even for the owner), so a row cannot be back-dated by an update, and the 60-second throttle is read against the database clock, so waiting would make the tests slow and timing based. The seam is the table owner: `VitalsSupport.insertSeniorCall` INSERTs a row with a chosen `called_at` (an insert is allowed; the statement runs with row level security lifted on the table, as for escalations) and `SafetyTestSupport.forceSeniorCalls` sets the stored count with the guard trigger switched off inside one committed transaction (it is switched on again before the commit). The request then runs through the real stack. Entries are placed 10 seconds either side of the limit (50 s old throttled, 70 s old not). For the cap, the count is forced to 32,766 and a real call takes it to 32,767, so the last accepted call and the 409 after it are both real; no part of the cap is left to unit level. A closed escalation is moved back in time the same way (`ageClosedEscalation`, trigger off inside one transaction) because its closing time is stamped by the trigger and a closed row is final.
- A person who signed in by OTP is rejected by the sign-in filter (401, SAH-3) once its 60-second cache of "is the membership active" has run out, so the R3 tests that deactivate a member use a signed token for the real user and role (it reaches the service, which is what R3 is about); the OTP person is used where only the role matters (`DischargeChecksIT`, `DischargeIT`).
- The application cannot write a time. Escalations with a chosen raise time, re-open time or acknowledgement, and clinical events with the same `at`, are INSERTed by `sahaj_migrator` in one transaction with `NO FORCE ROW LEVEL SECURITY` on the table and `FORCE` again (as `IpdBillingSupport.backdate` does). The escalation tables list `ipd.admission` too, because the guard reads the admission and the owner would see none under FORCE.
- The overdue edges are tested a safe margin away from the limit (High at 14:15 and at 15:20, Medium at 59:15 and 60:20), because the clock runs between the insert and the request. The exact edge (15:00 not past, 15:00.001 past) is a unit test (`EscalationClockTest`, java-developer) and is not repeated here.
- Races are forced: a second connection holds the admission row, each request is started and seen waiting in `pg_stat_activity` (`awaitLockWaiters`), then the lock is released, so the first in the queue runs first. Only the free-for-all tests are timing based, and they assert invariants, not an order.
- Statements that must fail run as `sahaj_app` or the owner in a transaction that is rolled back; the check constraints behind the trigger are proved with the trigger disabled in a rolled-back owner transaction (`VitalsSupport.ownerNoGuardErr`).
- A forced failure (`failingInsert`) proves the discharge rollback.
- `sahaj_test` is not cleaned (four checks are NOT VALID because of old DONE rows of the SAH-30 helper); every test uses its own new clinic.
