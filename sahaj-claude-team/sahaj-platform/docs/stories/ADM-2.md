# ADM-2 · Organizations directory and organization detail (Sahaj admin portal, read-only)
Mockup screen: Sahaj admin portal (platform admin view) — sidebar Platform Management → Organizations (`orgDirPage`, route `clinics`); organization detail `aClinic` (header, tabs Plan and billing and Modules read-only, `aModules`)
Module: platform (admin packages `com.sahaj.platform.*.admin`); the admitted-patients count comes from `ipd` through a read-only port in `platform.api`
Parent design: `docs/architecture/adr/ADR-003-sahaj-admin-portal.md` (rev 2, section ADM-2), contract `docs/api/admin.yaml` v0.2.0, decisions DEC-011, DEC-012. Depends on ADM-1 (admin sign-in and shell).

Split for building (each part is one build):
- **ADM-2a** Organizations list: search, filters with counts, chips, sort, table, pager.
- **ADM-2b** Organization detail, read-only: header, tabs Plan and billing and Modules, audit entry on every read.

## 1. Stories

### ADM-2a · As a Sahaj admin, I want to find any organization by name, code, owner mobile or city and narrow the list with filters that show counts, so that I can reach a clinic that needs help without opening its records
Priority: Must

### ADM-2b · As a Sahaj admin, I want to open one organization and see who it is, its plan, its modules and how many patients are admitted now (a count only), so that I can answer a clinic's question without seeing any patient
Priority: Must

Roles: only the Sahaj platform admin (`PLATFORM_ADMIN`, one role in phase 1; the mockup's Super admin, Support, Billing and Read-only auditor roles are out of scope, ADR H5). No clinic role (owner, doctor, visiting doctor, nurse, front desk, billing, pharmacist) can open or call any of this. A platform admin belongs to no clinic and sees every organization by design. The directory shows organization-level facts and counts only, never a patient.

## Acceptance criteria

### ADM-2a · Organizations list

1. Given an admin signed in with both factors (ADM-1), then the sidebar group **Platform Management** shows **Organizations** (mockup: building icon, route `clinics`); it opens `/admin/clinics`; the breadcrumb reads "Platform Management › Organizations". Other Platform Management items of the mockup (Dashboard, Subscription Plans, Feature Management, Platform Configuration, Global Masters, Audit Logs) and the Operations group are not shown.
2. Given the page, then the heading is "Organizations" and the lead reads "{N} organizations. Search, filter and act on them in bulk." N is all organizations on the platform, written with Indian digit grouping (1,25,000). The mockup's header controls "Saved views…" and **Export** are not shown (out of scope). The mockup text "act on them in bulk" is kept although bulk actions are out of scope (OQ-2-9).
3. Given the search area, then a segmented control **All fields · Name · Code · Owner mobile · City or state** (default All fields) and a search box with the placeholder that follows the field: All fields "Name, code, city, owner or mobile"; Name "Organization name"; Code "Code, e.g. SSC or K104512"; Owner mobile "At least 4 digits"; City or state "City or state". The search runs as the admin types, after a short pause (mockup 180 ms), and always returns to page 1. Search is case-insensitive.
4. Given **All fields** and text typed, then an organization matches when every typed word is found in its name, code, city or owner name, or when the typed digits (4 or more) are inside the owner's mobile number. **Name** matches text anywhere in the name. **Code** matches a code that starts with the text. **Owner mobile** matches the typed digits (non-digits ignored) inside the owner's mobile. **City or state** matches the city (the state is not stored, OQ-2-3). "Code" is the clinic web address because there is no separate code (OQ-2-4).
5. Given **Owner mobile** and between 1 and 3 digits typed, then the hint "Type at least 4 digits of the owner's mobile to search" shows under the box and no search is sent (the list stays as it was). The API refuses fewer than 4 or more than 10 digits with 400.
6. Given the segmented control **Any time · 30 days · 90 days · 1 year** (title "Signed up in the last…", default Any time), then the list shows only organizations created within that period. The filter is combined with the search and the other filters.
7. Given the left panel "Filters", then it has these filters in this order, each with its options and a live count, multi-select (several values in one filter mean "or"; different filters mean "and"): **City**, **Status** (Active, Inactive, Suspended), **Plan** (Free year, Pro), **Specialty** (General practice, Dental, Paediatrics, Homeopathy). The mockup's State, Health, Type and Partner filters are not built (OQ-2-2, OQ-2-3) and the brief's IPD filter is not built until the human confirms it (OQ-2-1).
8. Given a filter, then the count beside each option counts the organizations that match the search, "Signed up" and every other active filter, but not that filter itself (mockup `odMatch(o, except)`), so an admin sees what choosing that option would give. Options are sorted by count (highest first), then A–Z. A selected option stays in the list even when its count is 0; an unselected option with count 0 is disabled. Counts use Indian grouping.
9. Given a filter with more than 6 options, then only 6 show and the link **Show all {N}** expands it; **Show fewer** collapses it. Given a filter with more than 8 options (in practice City), then a "Find {filter name in lower case}" box (for example "Find city") narrows the options typed. A **Clear** link appears in a filter heading while at least one of its options is selected and clears only that filter.
10. Given a search or any filter or Signed up choice, then removable chips show above the results: the search as a magnifier chip with the typed text in quotes; each selected filter as a chip with the filter name in small type and the value (for example "Plan Free year"); Signed up as "Signed up Last 30 days", "Last 90 days" or "Last 365 days"; each chip has a remove button (aria label "Remove {value}" and "Clear search"); and a **Clear all** link resets search, filters and Signed up. The mockup's "Save as view" is not shown.
11. Given the result bar, then it reads "{n} organizations" ("1 organization" when n is 1) and " of {N}" when the list is filtered; and **Sort** has Best match, Name A–Z, Recently active, Newest (default Best match). Best match works only for an All fields search with text; with no text or another field it behaves as Name A–Z. Recently active puts the most recent sign-in first (never-signed-in last); Newest puts the latest sign-up first. The mockup's "Most visits" is not shown (no visit data on this screen).
12. Given the table, then the columns are **Organization** (round initials badge, the name in bold, and under it "{code} · {owner name}"), **Location** (city), **Plan** ("Free year" or "Pro"), **Status** (pill Active, Inactive or Suspended) and **Last active** ("Today", "Yesterday", "{n} days ago", or "—" when no member has ever signed in). The typed search text is highlighted in the name and code. The mockup's selection tick boxes, Branches, Visits 7d and pin star are not shown. The whole Organization cell is a button that opens the detail (ADM-2b).
13. Given Status, then **Suspended** means the clinic's account is not active; **Inactive** means no staff member signed in during the last 7 days (or never); otherwise **Active**. (The mockup's "Grace period" status needs billing and is not available.)
14. Given the pager, then it reads "Showing {from}–{to} of {n}" with the page-size choice **25 · 50 · 100** (default 25), a previous button (aria label "Previous page"), "Page [number box] of {pages}" and a next button (aria label "Next page"); typing a page number jumps to it; previous is disabled on page 1 and next on the last page. A page past the end shows an empty page with the real total; changing a filter, the search or the page size goes back to page 1.
15. Given no organization matches, then the table is replaced by the search icon, the bold text "No organizations match", "Remove a filter or search a different field." and the button **Clear all filters**.
16. Given a slow or failed network, then the previous result stays visible with a loading mark while a new search runs (the mockup shows a skeleton on first load); on failure an error notice shows with a retry (text not in the mockup, OQ-2-10). Filters and the search are not lost.
17. Given any list request, then the answer contains organization-level fields only: id, name, code, owner name, city, specialty, plan, status, joined date, last active, and the IPD state, HRA flag and bed limit (carried by the contract but not shown in the list, OQ-2-1). It never contains a patient, a staff member other than the owner's name, an email, or a mobile number (the typed mobile digits are matched in the database and never returned).
18. Given the request, then each call writes one audit entry `ACCESS` / `CLINICS_LISTED` in `platform_admin_audit` with the admin (from the signed-in session, never from the request), the filters used and the number of results, and **never the typed search text** (it may be part of an owner's mobile). (Volume question: OQ-2-6.)
19. Given roles and tenants: a request with no token, a clinic token, a pre-auth token or an ended admin session answers 401 and writes no audit entry; a signed-in clinic user who types `/admin/clinics` in the browser is taken to `/admin/sign-in`; a request from a network that is not allowed answers 403 `admin-network-denied`. The admin request never sets a tenant, so a plain query on any tenant table returns nothing; the list works only through the audited database function.
20. Given 10,000 organizations, then the list (including the filter counts) answers within 1 second at the 95th percentile on the dev machine, and paging never loads more than 100 rows.

### ADM-2b · Organization detail (read-only)

21. Given a row of the list, then `/admin/clinics/{id}` opens with the breadcrumb "Platform Management › Organizations › {organization name}" (the first two are links back to the list; the list keeps its search, filters and page when the admin goes back). Above the header the teal notice reads "Platform view: usage, billing and support only. This clinic's menus, masters and settings are in Organization Management." The mockup's **Manage configuration** button is not shown (Organization Management is out of scope).
22. Given the header panel, then it shows the initials badge, the name as the page heading, the health pill (**Healthy**, **Needs help**, **Inactive**, **Suspended**), the line "{code} · {city} · {specialty} · {slug}.sahaj.in" and the line "Owner {owner name} · mobile ••••• {last 5 digits} · joined {date} · {plan text}". Only the last 5 digits of the owner's mobile are shown; the full number is never sent to the browser. Empty values show "—". The mockup's "Demo clinic" pill is not shown. The header has no action buttons in ADM-2b (the mockup's Open support session, Reset owner sign-in, Extend free period, More… are out of scope; Change plan or price arrives in ADM-3). Open questions: state in the location line (OQ-2-3), the code and web address being the same word (OQ-2-4), the date format (OQ-2-5), the plan text (OQ-2-7).
23. Given the health pill, then **Suspended** = the account is not active; **Inactive** = no staff sign-in in the last 7 days; **Needs help** = the clinic setup wizard is not finished; otherwise **Healthy**. (The mockup also uses setup percentage, visits and "Payment due"; those do not exist yet, OQ-2-8.)
24. Given the tabs, then **Plan and billing** (default) and **Modules** are shown, in that order of the mockup's list. Usage, Settings for this clinic and Support are not shown; **Activity log** is added by ADM-3. The mockup opens the Usage tab first (OQ-2-11).
25. Given **Plan and billing**, then the panel "Current plan" shows one row: Plan = "Free year" or "Pro". The rows Next renewal, UPI AutoPay and GST invoice to, the buttons Change plan and Extend free period, and the Invoices panel are not shown in ADM-2b.
26. Given **Modules**, then the panel "Modules for this clinic" shows the sub-line "Plan → module → clinic settings → role → user. Each layer can only narrow what the one above allows." and the rows, in the mockup order: **OPD** "Core · always on" with the pill On; **In-patients (IPD)** with the sub-line "{n} patients admitted now" ("1 patient admitted now") or "No admissions", and the control Off · Trial · On · Read-only with the clinic's current effective state selected (an expired trial reads as Read-only), disabled; **Bed limit** "Beds the clinic can add in IPD setup" with the number and the − and + buttons, disabled; **Staff, timings and leave (HRA)** "Add-on · the owner can also switch it" with Off · On, disabled; **Pharmacy · Lab** "Phase 2" with the pill "Not available yet". The mockup's **WhatsApp** row is not shown (OQ-2-12).
27. Given the Modules tab, then the right-hand panel "What switching IPD off does" shows the five items exactly as the mockup (Menus: "Emergency and IPD leave every sidebar and Go to…"; APIs: "Calls to /api/v1/ipd/* return 403 MODULE_NOT_ENABLED"; Masters and bill heads: "Wards, beds, bed charges and deposit heads are hidden from setup and bills"; Scheduled jobs: "Midnight bed charges and deposit alerts skip this clinic"; Data: "Kept. Read-only for 90 days, then hidden. Never deleted by a switch") and the warning "IPD cannot be switched off or made read-only while patients are admitted. They must be discharged first." Two lines do not match the product: the APIs line names `MODULE_NOT_ENABLED` while the product answers the problem type `module-off`, and "Read-only for 90 days, then hidden" is a rule the product does not yet apply (OQ-2-13).
28. Given the count of admitted patients, then it is a number from the IPD module through a read-only port, never a list, name or any patient field; an organization without IPD shows "No admissions".
29. Given an unknown or malformed organization id, then the page shows a not-found state (the API answers 404 for an unknown id, 400 for a malformed one) and a link back to the list. Another tenant's id is not "foreign": the admin may open any organization.
30. Given each time the detail is read (opening the page, or reloading it), then one audit entry `ACCESS` / `CLINIC_VIEWED` is written in `platform_admin_audit` with the admin from the signed-in session, the organization id, the time, the request id and the address. Switching between the two tabs does not read again and writes nothing more. A read that fails (404, 401) writes no entry. The entry holds no patient data and no owner mobile.
31. Given the privacy rule of the mockup strip ("Platform view: counts only. Patient records stay inside each organization."), then no response of this story holds a patient name, a patient mobile, an ABHA number, a clinical note, an admission reason or the answers of the setup wizard; the database function can read only the columns it needs (admission status and tenant, never the reason).
32. Given roles, tenants and access: same rules as AC 19 (401 without a live admin session, 403 from a network that is not allowed, clinic roles refused).
33. Given a slow or failed network on the detail, then a loading mark shows and, on failure, an error notice with a retry (text not in the mockup, OQ-2-10).

## 3. Technical design

Notes for the architect and developers; the design itself is in ADR-003 and is not repeated here.

- **Cross-tenant reads.** The admin request path never sets `app.tenant_id`. The list and the detail run only through `SECURITY DEFINER` functions owned by the role `sahaj_admin_definer` (DEC-012), each starting with the session guard and writing its own audit entry in the same transaction.
- **Derived values.** Last active = latest `last_login_at` over the clinic's active members. Status, health, owner (earliest active owner) and the defaults for a clinic with no module row (IPD off, HRA off, bed limit 25) are defined in ADR-003 "Functions". Labels (Free year, Pro, General practice, …) are added in Java.
- **Count across modules.** `IpdOccupancyPort` in `platform.api`, implemented in `ipd`; `platform` never reads `ipd` tables.
- **Frontend.** Lazy feature `/admin`, routes `/admin/clinics` and `/admin/clinics/:id`; the ADM-1 placeholder "Organizations coming in the next release" is replaced. The admin interceptor attaches the admin token only to `/api/v1/admin/**`.

Gaps between the mockup and the contract, for the architect (each needs the human's answer first, see the open questions):
1. **State** is not stored (`clinic_profile` has `city` only), so `ClinicSummary` and `ClinicDetail` have no state (OQ-2-3).
2. **Health** is in `ClinicDetail` but not in `ClinicSummary`, and there is no `health` facet or query parameter, although the mockup has a Health filter (OQ-2-2).
3. **IPD facet and `ipd` parameter** are in the contract but not in the mockup (OQ-2-1).
4. **Plan text with the free-year day** ("Free year · day 214 of 365") has no field; `planLabel` is "Free year" or "Pro" (OQ-2-7).
5. **`code` is the slug**, so the header "{code} · … · {slug}.sahaj.in" repeats one value (OQ-2-4).
6. The contract does not say that the All fields search also matches the owner's name (the mockup does); the architect to state it in `adminListClinics`.
7. The list has no "owner asked for IPD" marker; `ipdRequestedAt` is only in the detail and not shown (OQ-2-14).

## 5. Tasks
### Tasks — Backend
db-engineer: `platform.admin_list_clinics`, `platform.admin_get_clinic`, `ipd.admin_admitted_count`, grants and policies for `sahaj_admin_definer` (migration, after the human creates the role). java-developer: admin directory service and controller, `IpdOccupancyPort` in `platform.api` with its `ipd` implementation, label mapping, escape of `%`, `_` and `\` in search text, no search text in logs or audit; unit tests. Real-database tests by qa-engineer (facet counts, paging limits, privacy, audit entries, a clinic session still sees only its own tenant).
### Tasks — Frontend
Organizations page (search with field switch, Signed up switch, filters with counts, chips, sort, table, pager, empty state), organization detail header, tabs Plan and billing and Modules (read-only), not-found state, back link that keeps the list state; unit tests with mocked HTTP.

## 6. Out of scope, Open questions
Out of scope (shown in the mockup, not built here): Saved views and "Save as view"; Export list; bulk selection, Bulk job, Pin and the organization picker (Ctrl O); the State, Health, Type and Partner filters and the "Show only alerts" shortcuts (WhatsApp 90%, free year ending); the Branches and Visits 7d columns and sort by visits; the 25,000-sample note; the Usage, Settings for this clinic and Support tabs; Invoices, renewals, UPI AutoPay, GST; the header actions on the detail; Manage configuration and Organization Management; the Dashboard and every other Platform Management item; Ctrl K palette, notifications bell, help panel, org switcher; admin roles other than one; the Demo clinic pill.

Open questions (for the human; defaults are what the stories above use until answered):
- **OQ-2-1 IPD filter.** The contract has an `ipd` filter (from the brief); the mockup directory has none. The mockup is the design, so it is not built. Default: not built. Say yes if you want it (then an "IPD" filter with Off, Trial, On, Read-only is added; no mockup screen to follow).
- **OQ-2-2 Health filter.** The mockup has a Health filter (Healthy, Needs help, Inactive, Payment due, Suspended) and the detail already derives health, but the contract has no health facet. Default: not built. Say yes and the architect adds `health` to the contract (4 values, no "Payment due").
- **OQ-2-3 State.** The state of a clinic is not stored. The mockup shows "{city}, {state}" in the detail header, the state under the city in the Location column, a State filter, and the search field "City or state". Default: city only everywhere, label **City or state** kept as drawn, search matches the city only. Options: rename the field to "City", or add a state to the clinic profile in a separate story.
- **OQ-2-4 Code.** There is no clinic code like the mockup's "SSC" or "K104512". Default: the clinic web address (slug) is shown as the code; before setup finishes it has none, so the code shows "—". The placeholder "Code, e.g. SSC or K104512" and the header line "{code} … {slug}.sahaj.in" then show the same word twice. Do you want a separate code, or the placeholder and header changed?
- **OQ-2-5 Date format.** The mockup writes "joined 24 Oct 26"; the project rule for UI text is "24 Oct 2026". Default: "24 Oct 2026".
- **OQ-2-6 Audit volume.** The contract writes one `CLINICS_LISTED` entry for every list call, including every pause while typing and every filter click, and keeps entries 7 years. This may bury the useful `CLINIC_VIEWED` entries. Default: as the ADR (every call). Options: log only searches by owner mobile and the first call of a visit; or only detail reads.
- **OQ-2-7 Plan text.** The mockup shows "Free year · day 214 of 365" and, for Pro, the plan name only. The free-year length is a Plans and billing setting that is out of scope. Default: "Free year" and "Pro" only.
- **OQ-2-8 Health rule.** The mockup says Needs help when setup is under 60% or fewer than 25 visits in 7 days, and "Payment due" for a grace period. Default: Needs help = setup wizard not finished; no "Payment due". Confirm.
- **OQ-2-9 Lead text.** "Search, filter and act on them in bulk." promises bulk actions that do not exist. Default: shown as drawn. Or drop the last words.
- **OQ-2-10 Texts not in the mockup.** Loading and error texts of the list and detail, the not-found text, the "Page past the end" behaviour. Default: "We could not load organizations. Try again." / "We could not load this organization. Try again." / "This organization was not found." with a **Back to organizations** link. Please approve or change.
- **OQ-2-11 Default tab.** The mockup opens the Usage tab; Usage is out of scope. Default: Plan and billing opens first.
- **OQ-2-12 WhatsApp row.** The mockup's Modules tab has a WhatsApp row ("From the plan", On). The product has no WhatsApp yet (Later). Default: hidden. Or show it with the pill "Later" as the clinic's own Plan and modules page does.
- **OQ-2-13 Two mockup lines that do not match the product.** "Calls to /api/v1/ipd/* return 403 MODULE_NOT_ENABLED" (the product's problem type is `module-off`) and "Read-only for 90 days, then hidden" (no such timer exists). Default: shown exactly as drawn. Or reword them.
- **OQ-2-14 Who asked for IPD.** The owner presses **Request IPD** and the request is stored, but nothing in the mockup's directory or detail shows an admin which clinics asked, so the admin cannot find them except by searching. Default: not shown (the contract carries `ipdRequestedAt` for later). Should the Modules tab show "Requested on {date}", and should the list get a filter for it?
