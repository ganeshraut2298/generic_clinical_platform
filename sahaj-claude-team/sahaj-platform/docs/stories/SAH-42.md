# SAH-42 · Stories: Platform admin bootstrap registration behind a PIN (local dev only)
Requirement: `docs/requirements/SAH-42.md`. Module: platform.
Mockup screen: Sahaj admin portal (platform admin view), sign-in card `pAdminLogin` (`docs/design/mockup/sahaj-mockup.html` line 5095). **The registration page is not drawn in the mockup.** It is a minimal reuse of the `pAdminLogin` card, a deviation under rule 1 for the human's sign-off (OQ-42-13, DEC-013). No other screen is added. The deviation is signed off under DEC-013 item 16. After the first admin is created the page does not show the authenticator setup: it goes to `/admin/sign-in`, where the owner signs in once and the existing first-sign-in step enrols the authenticator (DEC-035 option C, 11 Nov 2026), so **the owner types the email and the password twice** (once on the page, once at sign-in).
Rule numbers (BR1 ...) refer to the requirement. The real PIN is not written in this file, and no test may use it: examples use "a throwaway PIN set in the test".
Roles in every story: **anonymous caller on the local machine** (no admin exists yet). Wrong role = a clinic user (owner, doctor, visiting doctor, nurse, front desk, billing, pharmacist) or a signed-in admin token: ignored (BR14).
Traceability (updated 11 Nov 2026, after QA and ADR-018 Revision 2): BR1 to BR4 -> SAH-42-1 (BR4 race: criterion 9, reworded); BR5 to BR7 -> SAH-42-2, -3 (BR12/BR13 lock log: SAH-42-3 criterion 13, new); BR8 -> SAH-42-4 (criteria 3 and 6 reworded); BR9 to BR11 -> SAH-42-5 (criteria 7 and 8 reworded, 19 new; SAH-42-2 criterion 12 new for the unreadable body); BR12 to BR15 -> SAH-42-3, -5, -6; BR16, BR17 -> SAH-42-2, -3, -5. Contract: `docs/api/admin.yaml` 0.5.0 and `docs/architecture/adr/ADR-018-admin-bootstrap-registration-pin.md` Revision 2. Criterion numbers are unchanged; new criteria are added at the end of their story.
DEC-035 changes (11 Nov 2026, human answer): SAH-42-5 criteria 2 (second half), 9, 10, 11, 18 reworded and 20, 21 added (BR10, BR16, BR17); the "Step 3 card" text rows are not used on this page; SAH-42-2 criterion 1 and BR16 (PIN `autocomplete="one-time-code"`); the closed/off wording in SAH-42-1 criterion 11, SAH-42-2 notes, SAH-42-6 criterion 7 and the texts table (the home page, no separate "page not found" screen); SAH-42-2 criterion 13 added; section "Open wording" added to the texts; OQ-42-3 answered; OQ-42-16 added. Criteria 12 and 13 of SAH-42-5 are kept (closed browser; the page closes). Criterion numbers are unchanged; new criteria are added at the end of their story.
Single ticket slot (ADR-018 D5, `docs/database/SAH-42.md`): at any time at most one ticket is valid, and a new unlock replaces it. So "two valid tickets" cannot exist, and only one registration can ever succeed. Every later register call, concurrent or repeated, gets the empty 404 (the admin now exists) or, with a bad ticket before that, 401.

### SAH-42-1 · As the platform owner setting up locally, I want the registration to exist only when I switch it on, only on my own computer in the dev profile, and to close itself once any admin exists, so that nobody else can ever use it to become an admin
Priority: Must
## Acceptance criteria
- Given `SAHAJ_ADMIN_BOOTSTRAP_ENABLED` is absent or not `true`, when anyone sends the unlock or register call (any method, any body), then the answer is a **404 with an empty body** and no content type, the same for both calls and the same as for an unknown admin path, and nothing is written to the database or the audit. (BR1)
- Given the switch is `true` but the PIN hash is missing, blank or not a valid hash, when the unlock call is sent, then the answer is the same empty 404, and the startup log has one line saying the registration is off and why, without any secret. (BR2)
- Given the switch is `true` and the PIN hash is valid but the admin realm is not enabled, when the unlock call is sent, then the answer is the same empty 404. (BR2)
- Given the switch and hash are right but the active profile is not `dev` (for example `test` alone, `prod`, `staging` or `dev,prod`), when the unlock call is sent, then the answer is the same empty 404. (BR3, OQ-42-8)
- Given the switch is on in the dev profile, when the caller is not on loopback (for example `10.0.0.5`, `192.168.1.20`, `2001:db8::1`), then the answer is the same empty 404, even with a correct PIN or a valid ticket. (BR3)
- Given the switch is on in the dev profile and the caller is on loopback (`127.0.0.1` and `::1`), when the unlock call is sent, then the feature answers (story 2). (BR3)
- Given one platform admin already exists (created by the env seed, the dev sample-admin call, this page, or by hand; active or switched off), when the unlock or register call is sent, then the answer is the same empty 404, even with the switch on and even with a valid ticket. (BR4)
- Given no admin exists and the page is mid-way (ticket issued), when an admin is created some other way before the register call, then the register call answers the same empty 404 and creates nothing. (BR4)
- Given no admin exists and one valid ticket with its binding cookie (there is only one ticket slot, so only one ticket can be valid), when several register calls carrying that ticket and cookie arrive at the same moment or one after another (for example ten), then exactly one call gets **201** and creates the admin, and every other call gets the **empty 404** (the admin now exists, so the feature is closed); there is one admin row and one creation audit entry. A call that waits more than 10 seconds for its turn gets 429 with `Retry-After` 5 instead and creates nothing. A call whose ticket or cookie is not the valid one (missing, foreign, replaced) gets 401 while no admin exists, and the empty 404 once one does. (BR4, BR8) *(Reworded 11 Nov 2026 after QA: "two valid tickets" cannot happen.)*
- Given a request carries a clinic token, an admin token or a cookie, when it reaches either call, then the credential is ignored: the answer is the same as without it, and no clinic is bound to the request. (BR14)
- Given the switch is turned off in `.env` and the app is restarted, when the page `/admin/register` is opened and the PIN sent, then the server answers the empty 404 and the app shows what it shows for any unknown address (the home page); no "closed" or "off" message appears, and nothing on the page reveals that the feature exists. (BR1, BR17) *(Reworded 11 Nov 2026, DEC-035: the app has no separate "page not found" screen.)*
## Notes for design
Exact reach checks for loopback (and how a call that comes through the Angular dev proxy is judged, OQ-42-1) are for the solution-architect. The 404 must be byte-identical for all the "off" reasons so that it reveals nothing. The existing dev sample-admin endpoint (ADR-008) already solves a similar reach rule; whether to share that code is the architect's call. No role other than the anonymous caller exists for this story.

### SAH-42-2 · As the platform owner, I want the page to ask for the PIN first and show nothing else until it is right, so that a stranger who finds the page sees no form and learns nothing
Priority: Must
## Acceptance criteria
- Given the feature is on and open, when `/admin/register` is opened, then only the **Unlock registration** card shows: the field **Registration PIN** (password-type, `autocomplete="one-time-code"` so that the browser does not offer to save the PIN, because browsers ignore `autocomplete="off"` on password fields; `inputmode` numeric allowed but no 6-digit rule in code) and the button **Unlock**. No name, email or password field is in the page. (BR5, BR16)
- Given the PIN field is empty or blank, when the owner presses **Unlock**, then "Enter the PIN." shows next to the field, no call is made and nothing is counted. The server gives the same answer to a readable call whose `pin` is missing, `null`, empty or only spaces (400 with the one field error "Enter the PIN.", not counted, not audited). (BR7f) *(Extended 11 Nov 2026, ADR-018 Revision 2.)*
- Given a wrong PIN (the test sets a throwaway PIN and types another), when the owner presses **Unlock**, then the answer is "That PIN is not right. {n} tries left.", the field is cleared and focused, no ticket is issued, and the wrong-PIN count goes up by one. (BR6)
- Given wrong PINs 1, 2, 3 and 4, when each is sent, then the texts read "4 tries left", "3 tries left", "2 tries left", "1 try left", and the 5th wrong PIN gives the locked state (story 3). (BR6)
- Given the wrong answer, when the response is read, then it is the same text and shape whatever was typed (digits, letters, a very long string, a string with spaces), and a string longer than the allowed length is also a wrong PIN, not a different error. (BR13)
- Given a correct PIN (the throwaway PIN of the test), when the owner presses **Unlock**, then a ticket is returned, the wrong-PIN count is reset to zero, and the page moves to the **Create the first admin** card. The PIN is not kept in the page, the URL, local storage or the browser history. (BR5, BR7c, BR8)
- Given the PIN call is in progress, when the owner waits, then the button is disabled and shows a busy label, and a second press does nothing (no double count). (BR17)
- Given the server cannot be reached (offline or slow), when **Unlock** is pressed, then "We could not reach the server. Check that the app is running and try again." shows, the count does not change on the page, and the field keeps focus. (BR17)
- Given the human changes the hash in `.env` to the hash of a longer PIN (for example 10 characters) and restarts, when that PIN is entered, then it unlocks with no code change and no change to the page. (BR5)
- Given a PIN is typed, when the request is made, then the PIN travels only in the request body, never in the URL or a header, and the response and the page never echo it. (BR13)
- Given the PIN hash in the process, when the PIN is compared, then the comparison is constant-time (unit test with the compare function; no timing test of the HTTP call is required). (BR5)
- Given the feature is on, open and not locked, when a hand-made unlock call has a body that cannot be read (empty or not JSON, not an object, a repeated key, something after the object, a field other than `pin`, or a `pin` that is not text), then the answer is **400 bad-request** ("Bad Request", "The request could not be understood. Check it and try again.") with **no field error**; it names no field and echoes no value; the wrong-PIN count does not change and nothing is audited. When the feature is closed or off the same call gets the empty 404, and while locked the 423, both before the body is looked at. (BR7f, BR13) *(New 11 Nov 2026, ADR-018 Revision 2 D2 "Request bodies".)*
- Given the unlock call is answered with 429, 500, 413, 403 or an unknown status, or with the 400 bad-request, when the page shows the result, then it shows "Something went wrong. Try again." (see "Open wording"), never the server's own text, the PIN field is cleared, and the page stays on the Unlock card. (BR13, BR17, OQ-42-15) *(New 11 Nov 2026, DEC-035: the text is built and awaits wording sign-off.)*
## Notes for design
Hash algorithm (Argon2id or bcrypt) and how the human makes the hash are for the architect (OQ-42-10); the project already uses BCrypt 12 and has no Argon2 library. The card follows `pAdminLogin`: same brand bar, side panel, glass card, field and button style, Material outline field per DEC-013 item 8. Screen states: loading (busy button), error (inline text, `role="alert"`), locked (story 3), success (moves to the next card), closed (the home page, as for any unknown address).

### SAH-42-3 · As the platform owner, I want five wrong PINs to lock the feature for 60 minutes for everyone, and to stay locked after a restart, so that nobody can guess the PIN by trying
Priority: Must
## Acceptance criteria
- Given no wrong PIN has been entered, when 5 wrong PINs are entered one after another, then the first 4 get "That PIN is not right. {n} tries left." and the 5th gets the locked state "Registration is locked. Try again in 60 min.". (BR6)
- Given the feature is locked, when the **correct** PIN is entered, then it is refused with the locked text, no ticket is issued, and the count does not change. (BR7a)
- Given the feature is locked at 11:05 AM IST, when the lock is checked at 11:35 AM IST, then the text says "Try again in 30 min."; at the 60th minute the lock ends and the next PIN is checked normally. (BR6, BR7d) *(test with a controllable clock)*
- Given the feature is locked, when the application is stopped and started again, then it is still locked for the remaining time, and a correct PIN is still refused until the lock ends. (BR7b)
- Given 3 wrong PINs and a restart, when 2 more wrong PINs are entered, then the feature locks (the count survived the restart). (BR7b)
- Given 4 wrong PINs, when the correct PIN is then entered, then it unlocks and the count goes back to zero; 4 more wrong PINs afterwards do not lock the feature. (BR7c)
- Given the lock has ended, when the next wrong PIN is entered, then it counts as wrong PIN 1 of 5 (the count restarted at zero). (BR7d)
- Given the lock is global, when wrong PINs come from two browsers (or two addresses on loopback), then they add up: 3 from one and 2 from another lock the feature for both. (BR6)
- Given a ticket was issued and the feature then locks (wrong PINs from another browser), when the register call is sent with that ticket, then it is refused with the locked text and no admin is created. (BR7e, OQ-42-5)
- Given each wrong PIN, when it is processed, then one audit entry "unlock failed" is written with time, caller address and request id, and **no PIN, no typed text and no hash**; the 5th also writes one audit entry "registration locked" with the lock end time. A blank PIN, a refusal while locked, and the 404 cases write no audit entry for the PIN. (BR12)
- Given the audit table, when the entries of a full test run are read, then no column of any row holds a digit sequence equal to the throwaway PIN or to any wrong PIN used in the test. (BR12, BR15)
- Given the locked state on the page, when the owner sees it, then the card shows the locked text with `role="alert"`, the PIN field and **Unlock** button are disabled, and nothing else is shown. (BR17)
- Given the 5th wrong PIN sets the lock, when the call is processed, then the application log holds exactly **one** WARN line for that lock, "Bootstrap registration locked until {time}", where {time} is the lock end time in ISO 8601 UTC (the same time the "registration locked" audit entry holds), with the request id and nothing else (no PIN, no typed text, no hash). An unlock or register call refused because a lock is already in force writes no log line. (BR12, BR13) *(New 11 Nov 2026, ADR-018 Revision 2 D8.)*
## Notes for design
Count and lock end are stored in the database (a place for them is a request to the db-engineer, not designed here). The 60 minutes and the 5 tries are fixed numbers in this story, not settings. A way to clear a lock early is OQ-42-14; this story does not build one. Locked state on the page: the countdown is minutes only, no live timer is required.

### SAH-42-4 · As the platform owner, I want a correct PIN to give a short single-use ticket that only the registration step accepts, so that a leaked ticket or a second browser cannot create the admin
Priority: Must
## Acceptance criteria
- Given a correct PIN, when the ticket is issued, then it is random, valid for 5 minutes, usable once, and bound to the browser that unlocked. (BR8)
- Given a valid ticket, when it is sent to the register call within 5 minutes from the same browser with valid details, then the admin is created and the ticket is spent. (BR8)
- Given the ticket was spent by the successful creation of the first admin, when it is used again (a repeat of the same register call, or a replay), then the answer is the **empty 404** (an admin now exists, the feature is closed) and no second admin is created. A spent ticket can never give "Your unlock took too long. Enter the PIN again.", because spending it is the same step that closes the feature. That 401 answer is for a ticket that, while no admin exists, is expired, replaced by a later unlock, cancelled by a lock, or does not match the browser's cookie. (BR4, BR8) *(Reworded 11 Nov 2026 after QA.)*
- Given a ticket 5 minutes and 1 second old, when it is used, then it is refused with "Your unlock took too long. Enter the PIN again." and the page returns to the Unlock card. (BR8) *(test with a controllable clock; 4 minutes 59 seconds still works)*
- Given a ticket issued to one browser, when it is sent from another browser (different cookie jar or client), then it is refused with the same message, and the first browser's ticket is still valid. (BR8)
- Given a second correct unlock after the first (there is one ticket slot, so only the newest ticket is valid), when the first ticket is then used, then it is refused with 401 "Your unlock took too long. Enter the PIN again." and nothing is created; the second ticket works once, and after that every register call gets the empty 404. Two valid tickets never exist side by side. (BR8, OQ-42-5) *(Reworded 11 Nov 2026 after QA: states the one-slot rule.)*
- Given a ticket, when it is sent to any other admin call (sign-in, refresh, clinics, me), then it is not accepted, it carries no role, and it grants nothing. (BR8)
- Given a missing, empty, malformed or random ticket, when the register call is sent, then the answer is the same "took too long" refusal and no admin is created, and no audit entry holds the ticket. (BR8, BR12)
- Given a rejected form (for example a weak password), when the owner corrects it within the 5 minutes and presses **Create admin** again, then the same ticket still works once. After the 5 minutes it does not. (BR8, OQ-42-7)
- Given the application is restarted, when a ticket issued before the restart is used, then it may be refused with the "took too long" text; this is accepted and the owner enters the PIN again. (BR8, architect's call whether tickets survive a restart)
## Notes for design
How the ticket is bound to the browser (for example a cookie that the page cannot read, or a value held in page memory plus a binding the server checks) is for the solution-architect. The ticket is never logged or audited. It travels in the register call only, not in a URL. Its 5-minute clock starts at the unlock, not at the last form try.

### SAH-42-5 · As the platform owner, I want, after the PIN, a short form to create the first admin with name, email and password, and then to sign in once at the admin sign-in where my authenticator app is set up, so that I can use the admin console and the registration closes for good
Priority: Must
## Acceptance criteria
- Given a valid ticket, when the page shows **Create the first admin**, then it has the fields **Full name**, **Work email**, **Password** (and **Confirm password** if OQ-42-4 is accepted), the hint under Password, and the button **Create admin**, in that order. Password fields use `autocomplete="new-password"`, and the email field `autocomplete="username"`. (BR9, BR16)
- Given valid details (name 1 to the allowed length, email `first.admin@example.test`, a 16-character password that does not contain `first.admin`), when **Create admin** is pressed, then the admin is created with the single platform admin role, no tenant and no membership, the password is stored as a BCrypt (strength 12) hash, and the page drops every value it holds (name, email, both passwords, ticket) and goes to `/admin/sign-in`. It does not move to an authenticator step. (BR9, BR10, BR11, BR16) *(Reworded 11 Nov 2026, DEC-035 option C.)*
- Given the email is typed in capitals or with spaces, when the admin is created, then it is stored trimmed and lower-case, and the sign-in with the lower-case email works. (BR9)
- Given a password shorter than 12 characters, longer than 64 characters, longer than 72 bytes in UTF-8 (for example 40 characters from a script with 3-byte characters), or containing the part of the email before "@" (any letter case), when **Create admin** is pressed, then the field error "The password must be 12 to 64 characters and must not contain the first part of your email." shows, no admin is created, and the ticket is not spent. The same rules apply as for the dev seed and the sign-in (ADR-003 D2.1). (BR9)
- Given a password that is allowed by ADR-003 but is a common one (for example `passwordpassword`), when **Create admin** is pressed, then it is accepted, because there is no breached-password check in the sign-in rules (OQ-42-2). If the human answers OQ-42-2 with a check, this criterion changes. (BR9)
- Given the two password fields differ (OQ-42-4 accepted), when **Create admin** is pressed, then "The two passwords do not match." shows, no call is made, and nothing is created. (BR9)
- Given an empty name (or one over 120 characters after trimming) or an invalid email (no "@", over 254 characters), when **Create admin** is pressed, then the matching field error shows ("Enter the full name." under Full name, "Enter a valid email." under Work email), no admin is created and the ticket is not spent. An email that already belongs to an admin cannot occur on the first admin (an existing admin means the feature is closed and the answer is the empty 404, not a field error); no "email already used" text exists. (BR9, BR4) *(Reworded 11 Nov 2026, ADR-018 Revision 2 D6 step 2.)*
- Given a valid ticket and a register call whose body cannot be read (a field other than `ticket`, `fullName`, `email` or `password`, or one of those holding something that is not text), when it is processed, then the answer is **400 bad-request** with no field error, nothing is stored or echoed, and the ticket is not spent. A readable body with a missing, `null` or blank field is a normal field error (a missing or `null` field counts as empty). A call with no valid ticket gets 401 first, so it learns nothing from the body. (BR8, BR9) *(Reworded 11 Nov 2026, ADR-018 Revision 2 D2 "Request bodies": it was "ignored or rejected".)*
- Given the admin was created and the page went to `/admin/sign-in`, when the registration page is searched (screen, page source, browser storage, URL, history), then it never showed or held an authenticator key, an `otpauth://` link, a recovery code, a code field or the texts "Set up your authenticator app" and "Confirm and sign in"; the page asked for no authenticator code and made no call that returns a key. (BR10, BR13) *(Reworded 11 Nov 2026, DEC-035: was "the authenticator step shows".)*
- Given the owner is now at `/admin/sign-in` after the creation, when he types the **same email and password a second time** (the sign-in page receives nothing from the registration page and no field is pre-filled), then the existing first-sign-in step runs: it shows its own enrolment (key for manual entry with **Copy key**, the `otpauth://` link, the field **Code from authenticator app**, the button **Confirm and sign in**, and the recovery codes it always shows), and a correct 6-digit code enrols the authenticator and signs him in exactly as after any first sign-in (the admin console opens and the toast reads "Signed in as {name} · Platform admin"). This story changes no text or behaviour of that step (OQ-42-3, answered). (BR10, BR16) *(Reworded 11 Nov 2026, DEC-035.)*
- Given the owner is in the sign-in's enrolment step, when a wrong code is entered, then the sign-in's own text ("That code is not right.") and its own limit apply, the admin is not signed in, and after the limit the owner starts again at `/admin/sign-in`, where the first sign-in offers the enrolment step again. This story adds no wording or limit. (BR10) *(Reworded 11 Nov 2026, DEC-035.)*
- Given the owner closes the browser after **Create admin** and before signing in, when `/admin/register` is opened again, then the server answers the empty 404 (an admin exists) and the app shows what it shows for any unknown address (the home page), and the owner signs in at `/admin/sign-in` with the email and password and enrols there. (BR4, BR10, OQ-42-3)
- Given the first admin was created, when the unlock or register call is sent again by anyone, then the answer is the empty 404, with the switch still on. (BR4)
- Given the creation, when the audit is read, then exactly one "admin created through bootstrap registration" entry exists, with the admin id and name, time, caller address and request id, and with **no email, no password, no hash, no authenticator secret, no ticket and no PIN**. (BR12)
- Given the creation, when the logs of the run are searched, then the password, its hash, the authenticator key, the `otpauth://` text, the ticket and the PIN are nowhere in them (including `DEBUG` for `org.springframework.web`, `security` and `jdbc`). (BR13)
- Given the database fails during creation, when the call returns, then the answer is an error with no database text, nothing is half-created (no admin without a password hash), the ticket is not spent, and the owner can try again within the 5 minutes. (BR8, BR13)
- Given **Create admin** is in progress, when the owner presses it again, then the second press does nothing and the busy button label shows. (BR17)
- Given the screen at 360 px width, when either card of the page shows (Unlock registration, Create the first admin), then there is no horizontal scroll, labels and errors are readable, fields and buttons are at least 44 px high, focus goes to the first field, to the first error, or to the card heading when locked, and every field has a visible label and an error linked to it (`aria-describedby`). (BR17)
- Given a valid ticket and a readable form with several faults (for example an empty name, an invalid email and a weak password), when **Create admin** is pressed, then the server returns **at most two field errors**: the name error if the name is wrong, plus the first wrong one of email, then password (a password is judged only once the email is valid). The list is not always complete: the page checks the required fields and the password length before it sends, shows every error it can find itself, and the owner sends again with the same ticket while it is valid. No call that is refused for its form spends the ticket. (BR8, BR9) *(New 11 Nov 2026, ADR-018 Revision 2 D6 step 2.)*
- Given **Create admin** was pressed and the answer is a refusal that leaves the page on the form (a field error, or a safety-net answer), when the result shows, then **both password fields are empty** and Full name and Work email keep what was typed, so the owner types the password twice again. (BR9, BR13) *(New 11 Nov 2026, DEC-035: built, awaiting the human's wording sign-off, see "Open wording".)*
- Given **Create admin** is answered with 429, 500, 413, 403 or an unknown status, or with the 400 bad-request, when the page shows the result, then it shows "Something went wrong. Try again." with no field error and no server text, and the ticket is not shown or kept anywhere the owner can see. (BR13, BR17, OQ-42-15) *(New 11 Nov 2026, DEC-035: built, awaiting wording sign-off.)*
## Notes for design
New fields and texts are listed above for sign-off. The creation re-uses the existing admin code (hashing, password policy, TOTP encryption) rather than a second copy (see ADR-008 D5 for the shared pieces). The enrolment is **not** part of this page: the existing first-sign-in step at `/admin/sign-in` does it (DEC-035 option C; the architect aligns ADR-018 D6). The admin can always finish enrolment later at `/admin/sign-in`. The sign-in page gets no link to this page and, for now, no new text (OQ-42-16). The known cost of this design is that the owner types email and password twice; no sign-in token is handed from the registration page to the sign-in page.

## Open questions
Each has a safe default taken under DEC-023 if the human gives no answer. The human may override any of them. None is a clinical or legal rule.

- **OQ-42-1 · "Loopback only" through the Angular dev server.** The Angular dev server (port 4200) forwards `/api` to the backend and, since the dev sample-admin hardening (ADR-008 R1), adds forwarding headers; a loopback check that refuses forwarded calls would block the page when it is opened at `http://localhost:4200/admin/register`. Options: (a) the owner uses the page through port 4200 and the architect lets the reach check accept a forwarded call only when the immediate caller is loopback **and** every forwarded address is loopback; (b) the page is opened through the backend on port 8080 (needs the frontend served there). **Default: (a), as the architect designs it.** The human confirms the reach is still local only.
- **OQ-42-2 · Breached-password check.** DEC-034 says "the breached-password check are the same as the sign-in", but ADR-003 D2.1 has none (only length, 72 bytes and the email part). A check needs a list of known passwords inside the app (no external service). **Default: no breached-password check; ADR-003 rules only.** If you want one, say so; it is a small separate item with a list approved by you.
- **OQ-42-3 · ANSWERED 11 Nov 2026 (DEC-035, option C).** The admin is created when the details are accepted; the page then goes to `/admin/sign-in` and the existing first-sign-in step enrols the authenticator and shows the recovery codes it always shows. The registration page shows neither; the owner types email and password twice. The original question follows for the record. Order of authenticator enrolment, and recovery codes. (a) Create the admin when the details are accepted, then run the existing enrolment step; if the browser closes, the admin finishes enrolment at the normal sign-in (the registration is already closed). (b) Create nothing until the first correct code is confirmed (a half-finished registration leaves nothing, but the ticket and state must live longer and the design is bigger). The existing enrolment step also shows 10 recovery codes once; you listed recovery codes as out of scope. **Default: (a); the existing step is unchanged, so it still shows its 10 recovery codes (this story adds no recovery-code logic).** Say if the codes should not be shown here.
- **OQ-42-4 · Confirm-password field.** There is no reset in this story, so a typo in the password would lock the first admin out and need a human database fix. **Default: add "Confirm password".** It is a field not in the mockup.
- **OQ-42-5 · Count and ticket rules.** (a) A correct PIN resets the wrong-PIN count; (b) when a lock ends the count restarts at zero; (c) a lock cancels any open ticket; (d) a new unlock replaces the older ticket. **Default: yes to all four.** The count has no time decay (four wrong PINs a week apart plus one wrong PIN does lock).
- **OQ-42-6 · Show the tries left.** Telling the owner "{n} tries left" helps him avoid locking himself, and helps an attacker only by showing what the rule already says. **Default: show it.** Alternative: never show it.
- **OQ-42-7 · Does an invalid form consume the ticket?** **Default: no.** A weak password or empty name lets the owner correct and press again within the 5 minutes. "Single use" means one successful creation.
- **OQ-42-8 · Switch on in a profile other than dev.** **Default: empty 404 and the application starts**, as for the dev sample-admin (ADR-008 H-DEV-4). Alternative: refuse to start, which is louder but breaks a deployment by a flag typo.
- **OQ-42-9 · Audit of a correct unlock.** **Default: not audited** (you asked for failures, the lock and the creation). A correct unlock is followed by the creation entry in practice. Say if you also want it.
- **OQ-42-10 · How the human makes the PIN hash.** The PIN must not be typed on a command line that is saved in shell history, or in a chat. Request to the architect: one documented way (for example a small prompt-style command that reads the PIN without echo and prints only the hash). `scripts/` is human-owned, so the human adds it or runs the documented command. **Default: the architect documents one way in the design note.**
- **OQ-42-11 · Route in the production frontend build.** **Default: the route stays in every build** and, when the server answers 404, the app shows what it shows for any unknown address (the home page); the backend refuses everywhere except local dev anyway. Alternative: leave the route out of the production build (smaller surface, a small build rule).
- **OQ-42-12 · Wording.** All texts in "Texts for sign-off" are new; confirm or change them. This includes the section "Open wording" (built, awaiting the human's wording sign-off): "Unlocking…", "Creating admin…", "Something went wrong. Try again." for 429, 500, 413, 403 and unknown answers, "That PIN is not right." when the count is missing, the route title "Create the first admin · Sahaj", the aria-label "About this page", and clearing both password fields after a failed create.
- **OQ-42-13 · Mockup deviation sign-off.** Approve (or reject) the new page `/admin/register`, the fields Full name, Registration PIN and Confirm password, and the texts. The BA asks the tech lead to add this as an item in `docs/decisions/DEC-013-ui-deviations-for-sign-off.md`. **Rule 1 stop: no page is built until you sign it off.** The server side (stories 1, 3, 4 and the server part of 2 and 5) can be designed and built without the page.
- **OQ-42-14 · Clearing a lock early.** If the owner locks himself out, the lock runs 60 minutes. **Default: wait; no reset is built.** The db-engineer may add a human-run runbook to clear the lock.
- **OQ-42-15 · Text for an unreadable request (new 11 Nov 2026).** The server answers a body it cannot read with 400 bad-request and no field error. The page never sends such a body, so the text is a safety net only. **Default: "Something went wrong. Try again."** (new text, not in the mockup; no clinical or legal content). Confirm or change it with OQ-42-12.

- **OQ-42-16 · An explanation line on the sign-in page (new 11 Nov 2026, from DEC-035).** After a fresh registration the owner lands on `/admin/sign-in` with nothing that says why he must sign in now (code review finding 3).
