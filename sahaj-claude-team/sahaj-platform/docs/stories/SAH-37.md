## 1. Stories

### SAH-37-1 · As the owner, I want to open Clinic setup → Patient card, keep my changes as a draft and publish them as a numbered version, so that staff see the new card only when I decide and I can always see what is live
Priority: Must

### SAH-37-2 · As the owner, I want to choose the card layout, a starting template, the default cards per row and which sections show and in what order, so that the card fits how my ward works
Priority: Must

### SAH-37-3 · As the owner, I want to choose which fields show, in what order, under which name, and have the safety fields stay locked, so that the card is short and still never hides an allergy, an early warning or the alerts
Priority: Must

### SAH-37-4 · As the owner, I want to choose which quick actions appear on the card and in what order, so that staff tap only what my clinic uses and still cannot do what their role may not do
Priority: Should

### SAH-37-5 · As the owner, I want a live preview of my draft for each role and a chosen patient, on desktop or tablet width, so that I check what each person will see before I publish
Priority: Must

### SAH-37-6 · As a nurse, doctor, front desk user or owner, I want the Admitted cards to follow the published setup, and as the owner I want a "Customize card" button there, so that the card my clinic designed is the one on the ward
Priority: Must

### SAH-37-1 · Entry, draft and publish, versions, history
1. Given IPD is Trial, On or Read-only, when the user opens Clinic setup, then the group "In-patients (IPD)" lists "Patient card" after "Discharge" with the cards icon, the text "What each admitted patient's card shows: layout, sections, fields and quick actions. Changes go live when you publish.", the "Affects" chips Doctor, Nurse, Front desk, and the three tips of the mockup ("Most clinics use the standard card as it is. Change it only when staff keep asking for the same missing detail.", "Fewer fields read faster on a ward round. Hide what nobody looks at.", "Publish after the evening round, so the next shift starts with the new card."). Given IPD is Off, then the entry is not in the menu and the API answers 403 `module-off`. (Rule 1; the changed text drops "workflow stages", OQ-37-3.)
2. Given a clinic that never published, when the owner opens the section, then the bar shows the pill "Sahaj standard card · v1 live" (teal), the text "No unpublished changes", the buttons Reset to default (disabled, tooltip "Already the default"), Save draft and Discard draft not shown, and **Publish disabled**; "Published versions" lists "v1 · Sahaj standard patient card (default) · Sahaj · When the clinic was created" with the pill "Live". (Rule 2, 4.)
3. Given the owner changes anything on a tab, then only the draft changes; the bar shows the pill "Draft · N change(s) not published" (amber, edit icon; "1 change", "2 changes" ... where N counts the changed parts among layout, sections, fields and quick actions), and after Save draft also "· saved 11:05 AM"; Publish becomes enabled; staff still see the live card. (Rule 4.)
4. Given a draft, when the owner taps **Save draft**, then the draft is stored on the server (it survives closing the browser and signing in on another device), the toast reads "Draft saved. Staff still see the live card until you publish.", and a Clinic setup change-history line "Patient card draft saved" is added with who and when. Given the owner leaves the page without saving, then the screen warns before leaving and, if they leave, the unsaved edits are lost; the saved draft is kept. (Rule 4, 18; the warning is new, OQ-37-8.)
5. Given a draft, when the owner taps **Discard draft**, then the draft is removed on the server, the screen shows the live setup again, and the toast reads "Draft discarded. The live card is unchanged.". Given there is no draft, then Discard is not shown.
6. Given a draft, when the owner taps **Reset to default**, then the draft becomes the Sahaj standard setup (the live setup is untouched), and the toast reads "Draft reset to the Sahaj standard card. Publish to apply it.". Given the draft already equals the default, then Reset is disabled. (Rule 4; the toast drops "including roles and access", OQ-37-8.)
7. Given a draft that differs from the live setup, when the owner taps **Publish**, then the draft becomes the live setup as the next version (v2, v3 ...), the draft is removed, the old version stays in the list, the bar shows "Customized · v2 live" (blue; "Sahaj standard card · v2 live" teal if the published setup equals the default), and the toast reads "Patient card v2 is live for every role. Layout, fields updated." with the changed parts named (first letter capital). A change-history line "Patient card v2 published · layout, fields" is added. Given the published setup equals the default, then the version's line reads "Back to the Sahaj standard card"; otherwise "Changed: layout, fields". (Rule 4, 18.)
8. Given the draft equals the live setup (for example the owner changed a switch and changed it back), then the draft pill is not shown, Publish is disabled and nothing is published. Given Publish is tapped twice quickly, then one version is made.
9. Given "Published versions", then each row shows "v<n>", what changed, "<person> · <date, time>" (for example "<owner's name> · 24 Oct 2026, 11:05 AM IST"), the latest row has the pill "Live"; the list is newest first; there is no restore button. (Rule 4.)
10. Given a user who is not the owner (FRONT_DESK, NURSE, DOCTOR), when they open the section, then they see the **live** setup only with every control disabled (as the mockup's `ro()`), the foot text "set by the clinic owner", and **never** the owner's draft or its pill; the draft is not sent to them by the server. A call to save, discard, reset or publish by any of them answers 403. (Rule 3.)
11. Given a role without any IPD access (BILLING, PHARMACIST, VISITING_DOCTOR), then they do not see the section and the API answers 403. Given a user of another clinic, then they never read or change this clinic's setup, draft or versions (row-level security; the clinic comes from the signed-in user). (Rule 2, 19.)
12. Given two owners, when the second saves or publishes after the first already published or saved a newer draft, then the server refuses with a message "The card setup was changed by someone else. Reload to see it." and stores nothing; nothing is overwritten silently. (Rule 17; new text, OQ-37-6.)
13. Given a slow network, then Save draft and Publish show a busy state and cannot be pressed twice; given a failed or offline save, then the screen keeps the owner's edits on screen, shows "We could not save the draft. Try again." and does not claim it was saved. Given the setup cannot be loaded, the screen shows "We could not load the card setup. Try again." with **Try again**. (New texts, OQ-37-8.)
14. Given IPD is Read-only, then the owner can read the section but Save draft, Discard draft, Reset and Publish are not offered and the server refuses them with the existing IPD Read-only message. (OQ-37-10.)
15. Given the Clinic setup Overview, then the "Patient card" tile summary reads "<Layout> · Sahaj default|customized · v<n>" with " · draft" appended for the owner when a draft exists (for example "Standard · Sahaj default · v1"). (Mockup `tileSum`.)
16. Given the history and the versions, then they hold no patient name, UHID, mobile, allergy, diagnosis or vitals; the names of the parts changed only. (Rule 18, 19.)

Notes for design
- A clinic's live setup and draft are clinic data (tenant), so they need row-level security like every tenant table. A clinic that never published may have no stored row: the Sahaj standard v1 is the fallback.
- The same "Clinic setup change history" that other sections use is the place for rule 18 lines. The architect decides whether the versions list is the same store.
- Draft equality ("differs from live") is decided by the server on a canonical form of the setup, not by comparing text in the browser.

### SAH-37-2 · Layout, templates, cards per row, sections
17. Given the tab **Layout and sections** (first tab), then the screen shows, top to bottom: the panel "Start from a template" with the text "New clinics get the Sahaj standard card automatically. A template only changes your draft." and three template buttons (**Small clinic** "Compact card, no billing", **Nursing home** "Standard card with deposit action", **Hospital** "Expanded card, billing section, all actions"); the panel "Card layout" with three choices **Compact** "Key facts on one line, icon actions. Fits 4–5 cards a row.", **Standard** "Sections with labels and vital tiles. The Sahaj default.", **Expanded** "Every field and section titles." (each with a small picture, `aria-pressed` for the chosen one) and the row "Cards per row" "Default on desktop. Each person can switch it on the patient list; tablets show 2, phones 1." with the choices 2, 3, 4; the panel "Sections". (Rule 5, 6, 7; the template and Expanded texts drop the words about stages and the nursing note, OQ-37-3, OQ-37-5.)
18. Given the owner taps a template, then the draft layout, sections, fields and quick actions are replaced as the template says (Small clinic: layout Compact, Billing section off; Nursing home: layout Standard, Deposit action on; Hospital: layout Expanded, Billing section on, every quick action on, "IP number" and "Admission type" on) starting from the Sahaj standard setup; "Cards per row" and nothing outside the draft changes; the locked safety items stay on; the toast reads "<Template> template applied to your draft. Publish to use it.". (Rule 6, 9.)
19. Given the owner chooses a layout, then the draft layout changes and the preview redraws at once; nothing is hidden or removed from the sections or fields by the choice itself. (Rule 5.)
20. Given the owner chooses 2, 3 or 4 cards per row, then it becomes the draft's default; the choice shows `aria-pressed`. Given it is published, then the Admitted page opens with that many per row (story 6). (Rule 5.)
21. Given the panel **Sections**, then its text reads "Drag to change the order, or use the arrows. Switch off a section to hide it from every card." and it lists Card header "Name, identifiers and bed · always first", Workflow status "Alerts" (the mockup says "Stage and alerts", OQ-37-3), Admission and bed "Dates, ward and room", Care team "Doctor", Vitals "Latest readings with status", Clinical "Diagnosis and allergies", Billing "Running bill and deposit"; each row shows "<N> of <M> fields on", a drag handle and Move up / Move down buttons, and a switch "Show <section>". (Rule 7.)
22. Given the Card header, then its row has a lock icon and the pill "Always on", it stays first, nothing can be dropped above it, and it has no switch. Given Workflow status, Vitals and Clinical, then each shows the pill "Safety · always on" (green) instead of a switch. (Rule 9.)
23. Given the owner switches off Admission and bed, Care team or Billing, then the row dims, its fields do not appear on any card, and "<N> of <M> fields on" stays. Given a section that holds a locked safety field (for example the owner has moved Allergies into Billing), then its switch is refused with the toast "This section holds a safety field (<names>). Move it out first." and stays on. (Rule 7, 9.)
24. Given the owner drags a section row (mouse), then the order changes; given a keyboard or touch user, then Move up and Move down (with the accessible names "Move up" and "Move down" plus the section name) do the same; moved focus stays on the moved row; both methods work in the preview at once. The last move is announced politely ("<Section> moved to position 3"). No order can put the Card header anywhere but first. (Rule 7.)
25. Given a user who is not the owner, then the template buttons, layout, cards-per-row choices, switches, handles and arrows are disabled and drag does not start. Given a call made by a non-owner, the server answers 403. (Rule 3.)
26. Given an unknown template, layout, number of columns or section sent straight to the server, then it answers 400 with a message and stores nothing. Given a setup that has the Card header, Workflow status, Vitals or Clinical section off or out of place, then the server answers 400 "The <section> section is a safety section and stays on." and stores nothing. (Rule 16, 9.)

Notes for design
- The three picture buttons, the template cards and the switches follow the mockup classes (`pcpresets`, `pclays`, `pcrow`, `sw`). Colour is never the only signal for the chosen layout (`aria-pressed` and a visible border/tick).
- Templates are fixed Sahaj content, not clinic data; they are applied in the browser to the draft and validated by the server on Save/Publish.

### SAH-37-3 · Fields, labels, locked safety fields
27. Given the tab **Fields**, then the text reads "Drag a field to reorder it or move it to another section. Type a new label to rename it; leave it empty to keep the standard name." and each section is a group (heading = section name; the pill "Section off" when off) listing its fields in order, each row with a drag handle, a label box (placeholder = the standard name, accessible name "Label for <standard name>"), a small line "<standard name> · <group>" (groups: Patient and admission, Contact details, Clinical details, Vitals and early warning, Billing), a switch "Show <standard name>" and Move up / Move down. An empty section shows "Drop a field here". (Rule 8.)
28. Given the catalogue, then the fields listed are exactly those with data in phase 1: Patient name, UHID (labelled "MRN" in the mockup; the card and search use "UHID", OQ-36-8), Age and gender, Bed, IP number, Mobile, Alerts, Admitted on, Length of stay, Ward, Room, Admission type, Doctor, BP, Pulse, SpO₂, Temp, RR, Early warning, Last recorded, Diagnosis, Allergies, Running bill, Deposit, Payer. "Workflow stage" and "Assigned nurse" are not listed. The default placement and on/off state are those of the mockup's `pcDefault`: Card header (Name, UHID, Age and gender, Bed on; IP number, Mobile off), Workflow status (Alerts on), Admission and bed (Admitted on, Length of stay, Ward, Room on; Admission type off), Care team (Doctor on), Vitals (all seven on), Clinical (Diagnosis, Allergies on), Billing section off with Running bill, Deposit, Payer. (Rule 8; OQ-37-1, OQ-37-3.)
29. Given a locked field, then its row shows no switch: **Patient name** shows the pill "Required" and is fixed (cannot be moved or switched off); **UHID, Alerts, Early warning and Allergies** show the pill "Safety · always on" (green, lock icon, tooltip "Patient safety: cannot be hidden"). Given the owner tries to switch it off (keyboard, touch or a call to the server), then the toast reads "<Field> is a safety field and cannot be hidden." and the server answers 400. (Rule 9.)
30. Given the owner drags or moves a safety field to another section, then it is allowed only when that section is switched on; otherwise the toast reads "<Field> is a safety field. Move it to a section that is switched on." and nothing moves. Given a field is moved into the Card header, then it is placed after the patient name, never above it. (Rule 8, 9.)
31. Given the owner types a label, then the draft keeps it (trimmed; empty means the standard name), the preview shows it at once, and the card shows it as the field's heading or tooltip. A label is at most 40 characters, plain text (no markup is run: `<b>x</b>` shows as typed). Given a longer label, then the box stops at 40 and the server answers 400 on a longer one. (Rule 8, 16; OQ-37-8.)
32. Given a safety field (UHID, Alerts, Early warning, Allergies) or the name, then its label box is disabled and shows the standard name, so no clinic can rename "Allergies" into something else; the server refuses a changed label for them. (Rule 9. Different from the mockup, which allows renaming them: OQ-37-1.)
33. Given a field the role may not see (rule 11), for example Running bill for a nurse, then the owner can still switch it on in the setup; the card for that role shows nothing for it, the server does not send it, and the preview shows it under "Hidden for <role>". Given Mobile switched on, then only OWNER and FRONT_DESK cards show it. (Rule 11; OQ-37-4.)
34. Given the Vitals section, then the readings BP, Pulse, SpO₂, Temp and RR are each switchable (one tile each; Early warning and Last recorded sit below them), the Early warning field is locked; given no vitals have ever been recorded, then the card shows "No vitals recorded yet" (not blanks), and "Last recorded" reads "Not recorded" in amber. (Rule 9; mockup `pcnov`, `vtime`.)
35. Given a user who is not the owner, then every field control is disabled and the server answers 403 to a call. Given an unknown field key, a duplicate field, a field in a section the catalogue does not allow, or a setup that lacks a locked field, then the server answers 400 and stores nothing; given a stored setup that lacks a locked item (for example an older version), then the server adds the item back when the card is read. (Rule 3, 9, 16.)
36. Given a keyboard user, then every switch has role "switch" with `aria-checked`, every label box a visible or accessible label, every move button an accessible name ("Move up <field>"), and focus stays on the moved row. Given a screen reader, the pill "Safety · always on" is read out. (Accessibility.)
67. **Duplicate label (V15).** Given I am the owner on the Fields tab, when I give a field a label that matches, ignoring case and extra spaces, the standard name of any other card field (for example "Allergies" for Diagnosis) or the label of another field, then Save draft and Publish are refused with "This name is already used by another field." under that field's label box. Nothing is saved. When two fields share a new label, the message is on the later field only. A label equal to the field's own standard name, in any case or spacing, is never a V15 error and is accepted. Only the exact standard name (same case) is stored as empty, with no change counted; a case or spacing variant such as "bed" is a real label, stored as typed (see AC 69). The server refuses the same setup with 400 at `setup.sections[i].fields[j].label` even when the browser check is bypassed. (Rule 16, 22; DEC-032, stricter than the mockup.)
68. **Inline label errors.** Given I edit a label, when I leave the box or press Save draft or Publish and the label has a control, invisible or text-direction character, is over 40 characters, or duplicates another field's name, then the message ("Label cannot contain control or text-direction characters", "Keep the label to 40 characters." or "This name is already used by another field.") appears under that box in the existing error style, the box is marked invalid for screen readers, and nothing is sent. When the server refuses a save with field errors, each label message appears under its own box, focus moves to the first box in error, and any other messages are listed in the banner. The message clears when I type in that box. (Rule 16, 22; DEC-032, a state the mockup does not draw.)
69. **Label equal to the standard name.** Given a field with a custom label, when I type exactly the field's own standard name (in the same case), then the field shows as unchanged for the pill, Reset, the unsaved check and Publish, the same as the server counts it. (Rule 4, 8, 22; DEC-032.)

Notes for design
- Each field belongs to one data group (the mockup's `g`), which decides who may see it (rule 11). The group decides access, not the section it sits in.
- Fields with no data (stage, nurse) stay out of the catalogue so the owner never switches on a field that would be empty. Adding them later is a catalogue change.
- Moving a field between sections is a drag in the mockup; the arrows must also move a field across a section border (up from the first field enters the previous section, down from the last enters the next).

### SAH-37-4 · Quick actions
37. Given the tab **Quick actions**, then the text reads "Shown at the bottom of each card, in this order. Each role sees only the actions it is allowed to use." and each action is a row with a drag handle, the icon, the name, a one-line description, a switch "Show <action>", Move up / Move down, and a small line "who" (shield icon) with the roles that may use it. The actions, in the default order, are **Nursing** "Record vitals and a nursing note", **EMR** "Clinical record, medicines and results", **Transfer** "Move to another bed", **Discharge** "Summary, final bill and bed release", **Deposit** "Running bill and deposit". Nursing, EMR, Transfer, Discharge are on and Deposit is off. "Case paper" and "Update stage" are not listed (OQ-37-3). (Rule 10.)
38. Given the "who" line, then it is read-only and shows the fixed rule: Nursing "Owner, Nurse, Doctor"; EMR "Owner, Nurse, Doctor"; Transfer "Owner, Nurse, Front desk"; Discharge "Owner, Doctor"; Deposit "Owner, Front desk". The button "Change who can use each action" is **not shown** (Roles and access is out of scope). (Rule 10, 11; narrower of mockup and server, OQ-36-4.)
39. Given the owner switches an action off, then it is hidden on every card for everyone; given on, it shows only to the roles of the "who" line, and not when IPD is Read-only for Transfer, Discharge and Deposit. The setup never makes an action available to a role that the server refuses. (Rule 10.)
40. Given the owner switches the **Deposit** action on, then the Admitted card shows **Deposit** (deposit icon) to OWNER and FRONT_DESK, which opens the admission sheet at the "Running bill and deposit" part, as the name does today (SAH-23); it takes no other action by itself. (Closes OQ-36-3 as the mockup's Nursing home and Hospital templates do.)
41. Given the owner moves an action, then the card shows the actions in that order (drag with the mouse or Move up / Move down), and the first action shown to a role is drawn as the primary button when it is Nursing (as the mockup). Given all actions are off, then the card has no action row and the patient's name still opens the admission sheet. (Rule 10.)
42. Given Nursing or EMR switched off on the card, then the same sheets remain reachable from the admission sheet as built in SAH-30/31, so no clinical function is lost; nothing about the sheets changes. (Rule 10.)
43. Given a non-owner, then the switches and arrows are disabled and the server answers 403 to a change; given an unknown action key or a duplicate, 400. Given any role calls an action endpoint that its role may not use, then the server refuses whatever the setup says (SAH-36 AC44). (Rule 3, 10, 16.)

Notes for design
- The setup holds only "on" and the order; the abilities by role and the clinic state stay the SAH-36 server rule (`AdmittedCardAbilities`).
- The "who" line is derived from the same rule; the architect decides whether the server sends it or the screen holds the table (one place only, no copy that can drift).

### SAH-37-5 · Live preview
44. Given any tab, then a panel "Live preview" (`aria-label` "Live preview") sits beside the editor (below it on narrow screens) with the title "Live preview", the small line "Showing your draft" when a draft exists or "Showing the live card" otherwise, and a switch **Desktop** / **Tablet** (`aria-pressed`). (Rule 12.)
45. Given the controls under it, then **View as** is a select of OWNER ("Owner / Admin"), Doctor, Nurse, Front desk (the roles that have the Admitted list; Visiting doctor and Billing are not offered, OQ-37-4) and **Patient** is a select of the admitted patients "<name> · <bed>"; the default role is Nurse and the default patient is the first admitted patient. (Rule 12.)
46. Given a role and a patient, then the preview draws the card in the draft's layout (or the live card when no draft) exactly as story 6 draws it for that role, with the same fixed access rule: fields the role may not see are absent, not greyed. Given the owner edits anything, then the preview redraws at once without a reload. (Rule 11, 12.)
47. Given the preview card, then it is inert: the name is plain text (not a button), the action buttons cannot be tabbed to or activated, no sheet opens, nothing is saved, and no call writes data. (Rule 12.)
48. Given fields or actions the chosen role cannot use, then a line under the card reads "Hidden for <role>: N field(s), M action(s)" with a lock icon (only fields and actions that the owner switched on count). (Rule 12.)
49. Given Desktop, then the note reads "Desktop: cards fill the width, 4 to 5 to a row on a 1440 px screen." for Compact (3 to 4 for Standard, 2 to 3 for Expanded); given Tablet, the card is drawn 768 px wide with the note "Tablet: cards sit two to a row at 768 px width. Buttons stay at least 44 px tall." (Rule 12.)
50. Given nobody is admitted, then the Patient select offers one **fictional** sample patient clearly marked as an example ("Example patient", never a real name or number) and the preview works; the sample is built in the screen and is never saved or sent. (Rule 12, 19.)
51. Given the preview of a patient with a High early warning score, then the card has the red outline and the flag text as on the ward; given a patient with an unseen escalation, the "Not seen · N min" flag shows with the minutes of the last load. (Rule 12; flags unchanged.)
52. Given the preview is drawn for another role, then no data the owner's own role could not already read is requested; the preview applies the fixed access rule to the owner's own answer, or to a server preview of the same rule, as the architect decides, and never logs in or reads as the other role. (Rule 12, 19.)
53. Given a slow network or a failed patient load, the preview shows the sample patient with the notice "Could not load patients. Showing an example." (OQ-37-8). Given a screen reader, the panel has an accessible name and a polite live region announces nothing on every keystroke (the redraw is silent).

Notes for design
- The preview and the Admitted page must use the same drawing code, so what the owner approves is what staff see.
- A server-side preview endpoint is not wanted unless the architect shows that the browser cannot apply the fixed rule safely.

### SAH-37-6 · The Admitted cards use the published setup; Customize card
54. Given a published setup, when the Admitted tab is in Cards view, then every card follows it: the layout (Compact, Standard, Expanded), the sections in order, their fields in order with the owner's labels, the switched-on fields only, the quick actions in order, and the grid opens with the published "Cards per row" (the person's own choice during the visit still wins, SAH-36 AC1). Given no setup was ever published, then the Sahaj standard card (v1) is drawn. (Rule 13.)
55. Given the **Standard** layout, then each non-header section is a block of "label: value" pairs, the Vitals section is five tiles (BP mmHg, Pulse /min, SpO₂ %, Temp °C, RR /min) with "—" for a missing value, and the actions are buttons with icon and word (Nursing is the primary button). Given **Compact**, then each section is one line of values separated by "·" without section titles, Vitals shows only BP, SpO₂ and Pulse, and actions are icon-only buttons at least 44 px with tooltip and accessible name "<Action> for <patient name>". Given **Expanded**, then every switched-on field shows with section titles and the actions are buttons with icon and word. All three keep the card an article named "<patient name>, bed <bed>", equal heights in a row and the action row at the bottom. (Rule 13.)
56. Given a role (rule 11), then the card shows only the groups it may see; the server does not send a field the role may not see; FRONT_DESK never gets vitals, early warning, allergies or diagnosis even if the setup shows them; NURSE and DOCTOR never get billing fields or the Deposit low flag; Mobile only to OWNER and FRONT_DESK. A section that has no visible field for the role is not drawn. (Rule 11.)
57. Given the **locked fields**, then every card of OWNER, DOCTOR and NURSE always shows the patient name, UHID, the flags line (all SAH-36 flags and their order, safety flags never folded), the Early warning field and the Allergies field, whatever was published; the Allergies field shows "None known", "Not recorded" or the recorded text in red; the Early warning field shows "<score> · <Low|Medium|High>" or "—" when there are no vitals. Given a stored setup that lacks any of them, then the server adds it back before the card is drawn. (Rule 9; OQ-37-2.)
58. Given a vital reading, then a tile that is outside the normal range carries the word "Check" or "Critical" and a title ("Outside normal range" / "Critical") besides its colour, per the rule the human approves in OQ-37-11 (rule 20); the Early warning score and the Medium or High flags keep the SAH-30 rule and their meaning. Given the Early warning is High, the red outline of SAH-36 stays. (Safety; OQ-37-11.)
59. Given the **Table** view, then it is unchanged by the setup; the search, ward filter, paging, flags, 60-second reload, polite announcements and focus rules of SAH-36 apply to the cards in all layouts. Given a "Showing N of M patients", the paging works with the chosen layout. (Rule 13.)
60. Given the owner publishes while staff have the Admitted page open, then each person sees the new card at the next reload (at most 60 seconds, or when they reopen the page), without being signed out or asked to reload, and a card is never half old and half new (one setup per reload). (Rule 14; OQ-37-7.)
61. Given the published setup cannot be read or is invalid, then the page shows the Sahaj standard card and the notice "Could not load the card setup. Showing the standard card." and the patient list still loads; the patient name, bed and the locked fields are always on a card. (Rule 13; new text, OQ-37-8.)
62. Given the user is the **owner**, then the toolbar shows the button **Customize card** (sliders icon, "ghost" style) after the view switch; it opens Clinic setup → Patient card. Given FRONT_DESK, NURSE or DOCTOR, then the button is not in the page at all (not disabled) and the section is only readable. (Rule 15.)
63. Given the setup is published, then no record-access row is written for reading the setup or for the list (DEC-021); opening Nursing, EMR or the admission sheet from a card writes the rows it writes today. The setup, versions and history hold no patient data. (Rule 19.)
64. Given a tablet (width 768 px), then cards sit two to a row, every button and chip is at least 44 px high; given 700 px or narrower, one per row, whatever is published (SAH-36 AC6). Given a long label, name, ward or room, it is cut with an ellipsis and the full text is in the tooltip and the accessible name. (SAH-36 AC4.)
65. Given another clinic published a different card, then it never appears here (the setup is read for the signed-in user's clinic only). Given IPD Read-only or Trial, then the card is drawn from the same published setup; the actions follow SAH-36 AC44 and AC51. Given IPD Off, the existing lock page shows. (Rule 2, 10.)
66. Given a slow network, the SAH-36 loading and "Try again" states show; the cards never show a previous clinic's or a previous user's setup after sign-out and sign-in.

Notes for design

## 3. Open questions
Per DEC-023 the **Recommended** option is applied unless the human answers. "SAFETY" marks a question that touches a clinical safety field or what a clinician may lose from the card. "Needs human" marks the ones where the tech lead should ask even though a default exists.

- **OQ-37-1 (SAFETY, needs human). The default card, and whether safety labels can be renamed.**
  (a) The mockup's Sahaj standard card (v1) shows more than the card SAH-36 built: vital tiles, Diagnosis, an Allergies line, and (not buildable) stage and assigned nurse. SAH-36 left the tiles, Diagnosis and Allergies lines out as "not on the minimum card" (SAH-36 section 0). Options: **A (Recommended)** the default setup is the mockup's `pcDefault` limited to fields that have data (this story's AC28): the day the owner opens SAH-37, nothing changes until a publish, but "Reset to default" and a clinic with no published setup get the fuller card with tiles, Diagnosis and Allergies for OWNER, DOCTOR and NURSE. Reason: the locked safety fields (Early warning, Allergies) only make sense if they are on the default card, and an always-visible Allergies line removes the doubt of OQ-36-6 ("Not recorded" looked safe). B: the default stays the SAH-36 card and the extra fields are Off by default; but then Allergies and Early warning (locked "always on") cannot be Off, so B has to add those two anyway. Either way the list answer carries more clinical values (diagnosis, five vitals) for three roles.
  (b) The mockup lets the owner rename any field, including Allergies, Early warning, UHID and Alerts. **Recommended:** their labels are fixed (AC32), because a clinic could otherwise relabel "Allergies" into something that no longer says allergy. This differs from the mockup (a locked field with a free label).
- **OQ-37-2 (SAFETY, needs human). Compact layout drops "None known" and "Not recorded" for allergy.** In the mockup's Compact layout the clinical line hides the Allergies field unless an allergy is recorded, so a patient whose allergy was never asked looks like one with none, although the field is "always on". **Recommended:** Compact also shows a short "Allergies: Not recorded" (amber) or "Allergies: None known" so the locked field is always visible in every layout; differs from the mockup. Alternative: build exactly as the mockup and rely on the Alerts line.
- **OQ-37-3 (proceed; depends on OQ-36-2). What is not listed because no data exists.** The tab "Workflow stages", the field "Workflow stage", the action "Update stage", "Assigned nurse" and the action "Case paper" are not built: no stage or nurse data exists, and print is "soon". **Recommended:** do not show them (no dead switches), change the mockup texts that mention stages ("Stage and alerts" becomes "Alerts"; "5 stages", "all 8 stages" are removed from the template texts; the section description drops "workflow stages"), and add them in the stage story after the human accepts the stages (OQ-36-2). Reason: a switch for a field that is always empty misleads the owner.
- **OQ-37-4 (proceed; sign-off). The fixed access rule while Roles and access is out of scope.** The card needs a rule for who sees which group. **Recommended:** the mockup's default matrix, narrowed to what the server already enforces (rule 11): Mobile OWNER and FRONT_DESK only (the mockup also gives it to doctor and nurse; the server sends mobile to owner and front desk only); Billing OWNER and FRONT_DESK; Clinical and Vitals OWNER, DOCTOR, NURSE; Patient and admission all four. Actions as SAH-36 (OQ-36-4). "View as" lists the four roles that have the list, not Visiting doctor or Billing. Non-owners read the live card only and never see the draft (the mockup shows the shared draft to every role because it is a single-user demo). Not editable until Roles and access is decided.
- **OQ-37-5 (SAFETY / privacy, needs human). Expanded layout "Last nursing note".** The mockup's Expanded card shows the latest nursing note (free clinical text) of every patient to roles that can see vitals. **Recommended:** do not build the note line in this story; Expanded shows every other field and section titles. Reason: free text can carry anything (a diagnosis, a family matter) and would sit on a shared screen for many patients; SAH-36 kept it off the card for the same reason. If the human wants it: OWNER, DOCTOR, NURSE only, first 120 characters, no record-access row (as the list), clinical sign-off.
- **OQ-37-6 (proceed). Two owners editing at once.** The mockup has a single shared draft in memory. **Recommended:** one draft per clinic; Save draft and Publish refuse when the setup changed since this owner loaded it ("The card setup was changed by someone else. Reload to see it."), nothing overwritten silently.
- **OQ-37-7 (proceed). When a published change reaches staff.** **Recommended:** at the next 60-second reload or page open (AC60); no push, no forced reload, no notification (not in phase 1). The mockup shows it at once because it is one user. The tip "Publish after the evening round" stays.
- **OQ-37-8 (proceed; sign-off). Label limits and wording not in the mockup.** Label at most 40 characters, plain text; the warning before leaving with unsaved edits; the busy, error and conflict messages ("We could not save the draft. Try again.", "We could not load the card setup. Try again.", "Could not load patients. Showing an example.", "Could not load the card setup. Showing the standard card."); the changed texts of OQ-37-3 and the Reset toast (drops "including roles and access"); the fixed labels of safety fields. **Recommended:** as written; the human confirms wording.
- **OQ-37-9 (proceed). History, tile, search and the admin line.** **Recommended:** Save draft and Publish are written to the Clinic setup change history (as the mockup `cfgLog`; Discard and Reset are not, as in the mockup); the Overview tile line is built (AC15); the setup search entries ("Patient card layout", "Card fields and labels", "Quick actions on the card") are added only if the app already has a setup search; the Sahaj admin portal's per-clinic "IPD patient card" line is a later admin story. Reason: smallest slice that follows the mockup without touching the platform admin portal.
- **OQ-37-10 (proceed). IPD Read-only.** The mockup is silent. **Recommended:** the owner can read the section but cannot save, discard, reset or publish while IPD is Read-only (the clinic is in read-only because of its plan), matching the other IPD setup sections (architect confirms how they behave today). The cards are still drawn from the published setup.
- **OQ-37-11 (SAFETY, needs human). "Check" and "Critical" marks on vital tiles.** The mockup marks a tile "Check" or "Critical" by its own limits (`vStat`: for example SpO₂ under 92 is Critical, under 95 is Check; pulse over 100 or under 50 is Check). These limits are not the approved SAH-30 early-warning bands and differ from them at the edges (SpO₂ 95 scores 1 point but is not a Check). A clinical rule must not be guessed. **Recommended:** the server marks a tile from the SAH-30 per-reading points (3 points = Critical, 1 or 2 = Check, 0 = no mark), so no new threshold exists and the clinical sign-off OQ-30-6 covers it; the words and colours stay as the mockup. Alternative: show readings with no mark until a doctor approves the mockup limits.
- Shared and still open: OQ-33-2 and OQ-30-3 (ward scoping, Roles and access), OQ-30-6 (clinical sign-off of the score bands), OQ-36-2 (stages), OQ-36-7 (record-access policy for the list; this story widens the list data, see OQ-37-1), the go-live conditions of DEC-017/DEC-018.

## 4. Technical notes (for the architect; not a design)
- Two new things are stored per clinic: the live setup with its version history, and at most one draft. Reading the live setup is allowed to the four list roles; the draft and every write to OWNER. Row-level security as for any tenant table.
- The server owns the locked-item rule (validate on save and publish, repair on read). The screen mirrors it with messages; it is not the protection.
- The list answer (`GET /admissions`) must carry the extra card facts only for the roles that may see them, and ideally only the fields the published setup switches on. No per-patient calls.
- Tile marks, the early-warning score and Vitals due stay server rules; the browser does no clinical calculation.
- The setup is not patient data, but a label is free text typed by the owner: output-encode it everywhere (no markup, no `innerHTML`).
- Frontend: a Clinic setup page with four parts (status bar, tabs, editor, preview), one card component shared with the Admitted page and the preview, drag-and-drop with a keyboard/touch alternative.

## 5. API (`/api/v1/ipd`; proposals for the architect, details are theirs)
| Method | Path | Role | Change |
|---|---|---|---|
| GET | `/card-setup` | OWNER, FRONT_DESK, NURSE, DOCTOR | The live setup and its version; for OWNER also the draft and the version list |
| PUT | `/card-setup/draft` | OWNER | Save the draft (validated) |
| DELETE | `/card-setup/draft` | OWNER | Discard the draft |
| POST | `/card-setup/publish` | OWNER | Make the draft the next version |
| GET | `/admissions` | OWNER, FRONT_DESK, NURSE, DOCTOR | Gains the extra card facts, role-gated, absent not null |
