## 0. Safety summary
- **Additive only.** Every statement either creates a new object (tables, indexes, functions, triggers, policies) or adds to an existing one. The only changes to existing objects: one new column `platform.module_entitlement.pharmacy_on` (not null, default false) and the replacement of the check `platform.membership.ck_membership_role` by a wider list (adds `STORE_STAFF`). The wider check admits every old value, so no row can fail it and **no row is changed**. No drop of data, no rename, no update, no delete anywhere.
- **Fix round 1 (A3, C4).** A3 swaps one check constraint on the new table `store_staff` (same name, `<= 89`). It is added `NOT VALID` and validated in a guarded block: if a dev or test row already has a 91-calendar-day delegate period the migration does not fail and does not change data, it raises a WARNING and the constraint stays NOT VALID (enforced for new rows) until someone fixes the row and validates by hand. I could not query `sahaj_dev` or `sahaj_test` (the permission system refused psql), so I could not say beforehand whether such a row exists; the guarded form makes that safe for both sessions. C4 adds one trigger function and one trigger; no row changes.
- **Backward compatibility.** The previous app version runs unchanged against the new schema (a new column with a default, a wider check, new schema objects it never touches). With `pharmacy_on` false every existing screen and API answers as before.
- **Not done: `platform.admin_set_modules`.** See section 7 (finding). It does not exist in any migration, so there is nothing to extend; the admin function set is parked (ADM-2 and ADM-3, role `sahaj_admin_definer`). Reported to the tech lead; no admin function was written.
- **Must-do before the app starts:** the Flyway placeholder `sahajSampleData` must be defined (section 5.1). Without it Flyway refuses to start.

## 2. Conventions used, and deviations (for the record)

- Every pharmacy tenant table: `id uuid pk default gen_random_uuid()`, `tenant_id uuid not null default platform.current_tenant()` with FK to `platform.tenant`, `unit_id uuid not null` with the same-tenant composite FK `(tenant_id, unit_id)` to `pharmacy.unit (tenant_id, id)`, `created_at/created_by/updated_at/updated_by/version` (immutable tables keep `created_*` only), `timestamptz`, text with `check` instead of enums, no cross-module FK except `platform.tenant`. Membership ids are opaque uuids, checked through `TeamMemberPort`.
- Same-tenant composite FKs inside the schema: `(tenant_id, x_id)` references `(tenant_id, id)`. Each parent has `unique (tenant_id, id)`.
- **Row level security.** `ENABLE` + `FORCE` on every table. One policy per command for `sahaj_app` on `tenant_id = platform.current_tenant()` (select, insert, update; immutable tables select and insert only) as ADR-028 D2 says, instead of the older single `for all` policy. **No delete grant and no delete policy anywhere.** `sahaj_migrator` has no policy on tenant tables (as everywhere in the project).
- **Grants.** Each table gets `revoke all ... from sahaj_app`, `revoke all ... from public`, then an explicit grant. This holds even if the default privileges of `schemas.sql` (which grant four commands) are present.
- Deviations from `.claude/rules/postgresql.md`, all following ADR-028 and the built modules:
  1. **Money.** Document amounts are `bigint` paise; unit rates `numeric(14,4)` rupees; percentages `numeric(5,2)`. The rule file says `numeric(12,2)`; DEC-063 accepted paise and the human has not yet edited the rule file.
  2. **Singular table names** (`pharmacy.store`, not `stores`), as `ipd.drug` and `platform.membership` already do (ADR-028).
  3. `pharmacy.unit.code` is `text` with `check (code ~ '^[A-Z0-9]{3}$')`, not `char(3)` (the project rule prefers text with check; no padding surprises).
  4. **Trigram GIN indexes cannot start with `tenant_id`.** Same as `ix_patient_name_trgm`; RLS filters after the index. All other indexes start with `tenant_id`.
  5. Policy names are `p_<table>_select|insert|update` (the older tables use `p_<table>_tenant`).
- **Deliberate exception (review F-17): `pharmacy.document_counter` has no `id`, `created_at`, `created_by` or `version` column.** Why: (1) it is a counter, not a business record: its natural key `(tenant_id, unit_id, doc_type, fiscal_year)` is the primary key and a surrogate `id` would never be used to find a row; (2) it is written only by `pharmacy.next_document_no()`, which has no user id to give (`created_by` would be fake) and only does `INSERT ... ON CONFLICT DO UPDATE`; (3) optimistic locking with `version` would make two concurrent callers fail and retry, but the counter must serialise them: the row lock taken by the upsert does that, race-free and gap-free, so a `version` column would add a failure mode and no safety; (4) who took which number is recorded on the document that carries it (SAH-79), and that is the audit. It keeps `updated_at` (set by the function). The exception covers pure counter rows only; a row that holds business data gets the full column set. C4 adds the trigger that stops the value going down.

## 3. Tables

Column types are as in the migrations; this section gives keys, checks and the query each index serves.

### 3.1 The duplicate key (`dup_key`) format
Stored in `catalogue_product.dup_key` and `product.dup_key` (own rows). Computed in Java for products; the seed uses an equal SQL rule. Format: `lower(salt) || '|' || strength || '|' || lower(form)` where salt and form are trimmed with runs of spaces collapsed to one, and strength has all spaces removed, is lower case, and a value in grams is written as milligrams (`1 g` becomes `1000mg`, `21 g` becomes `21000mg`). Example: `ceftriaxone|1000mg|injection`; `amoxicillin + clavulanic acid|500mg+125mg|tablet`. Advice only (answer 409 `possible-duplicate`); the database never rejects on it. **java-developer: implement the same normalisation**, or the seeded rows will not match a hand-typed own product.

**`opening_stock_import` constraints.**
- Unique `(tenant_id, id)`; `unique (tenant_id, uploaded_by, client_key)` (create replay).
- Partial unique `(tenant_id, store_id) where status = 'WAITING_APPROVAL'` and the same where `status = 'APPROVED'` (at most one of each per store).
- `ck_opening_stock_import_approver_differs`: `status <> 'APPROVED' or decided_by <> uploaded_by` (**the fixed rule: nobody approves their own request**).
- `ck_opening_stock_import_decision`: `decided_by` and `decided_at` are set exactly for `APPROVED` and `REJECTED` (so the null case of the previous check cannot slip through).
- Reject: reason set exactly when `REJECTED`; for `OTHER` a note of at least 4 characters after trimming. `submitted_at` set for `WAITING_APPROVAL`, `APPROVED`, `REJECTED`. `replaced_by_import_id` set exactly when `REPLACED`, and its FK is **deferrable initially deferred** (the new import and the one it replaces can be written in either order inside one transaction). `NOT_ACCEPTED` needs `error_count >= 1`. `created_by = uploaded_by`.
- Triggers (SQLSTATE 23514): a new import must start as `DRAFT`; `APPROVED`, `REJECTED`, `NOT_ACCEPTED`, `REPLACED` are final (no update at all; **since SAH-79 D3 one exception: an `APPROVED` import not yet posted may be updated once to set `posted_at` and `posted_by`, and nothing else**, after which it is final too); transitions allowed: `DRAFT` to `DRAFT`, `NOT_ACCEPTED`, `WAITING_APPROVAL`, `REPLACED`; `WAITING_APPROVAL` to `APPROVED`, `REJECTED`, `REPLACED`; store, uploader, client key, row count never change; a waiting import keeps its totals.

**Lines and issues (answer to the ADR's open choice).** Lines are updatable while the parent is `DRAFT` (a re-sent row updates the same `(import_id, row_no)` line, trigger-guarded; `row_no` must be at most `row_count`). Issues cannot be deleted (no delete grant), so a re-sent row **marks its old issues `superseded` (false to true, the only allowed update; trigger) and inserts new ones**; current issues are those with `superseded = false`. Both tables are writable **only while the import is `DRAFT`**: write the issues and totals first, change the import status last, in the same transaction.

- **Who-columns hold different ids by table.** On `opening_stock_import` (`uploaded_by`, `decided_by`, `created_by`) and on `opening_stock_line` and `opening_stock_line_issue` (`created_by`) the value is the **membership id** (an opaque uuid, like `store_staff.membership_id`). ### 10.1 Counter `line_rows_written` (DEC-077 item 2, security I7, I8)
- Rows written (inserted or changed) for the import while it is a DRAFT; the service caps it at 2 x `row_count` under the import row lock. `line_request_count` stays, unused; not renamed or dropped.
- Guard rule, new message `opening stock import line counter cannot go down` (23514): in DRAFT, `line_rows_written` and `line_request_count` may not decrease. This also covers the update that leaves DRAFT (status change and counter in one statement: the counter may stay or rise). Once the import is WAITING_APPROVAL both counters are frozen (existing message `opening stock import totals are fixed once submitted`); APPROVED compares the whole row, so they are frozen there too; the other states are final.

### 10.2 Owner rejects a DRAFT (DEC-076): exactly what changed
- `guard_opening_stock_import_update()` (`create or replace`, `search_path = pg_catalog`, not SECURITY DEFINER, execute revoked from public and `sahaj_app`): the DRAFT branch accepts `REJECTED` as a new status. The message `opening stock import cannot go from draft to <status>` now fires for APPROVED only. Everything else of the 1350 body is unchanged.
- `ck_opening_stock_import_submitted`: old `status in (DRAFT, NOT_ACCEPTED, REPLACED) or submitted_at is not null`; new `status not in (WAITING_APPROVAL, APPROVED) or submitted_at is not null`. WAITING_APPROVAL and APPROVED still need `submitted_at`; REJECTED may have it (rejected while waiting) or not (rejected as a draft). Weaker only for REJECTED, so no existing row can fail it (tiny table; lock timeout 30 s).
- Kept unchanged: `ck_opening_stock_import_decision` (`decided_by` and `decided_at` set exactly for APPROVED and REJECTED), `ck_opening_stock_import_approver_differs`, `ck_opening_stock_import_reject` (reason key required, note of 4+ characters for OTHER).

### 10.3 Backstop for L9 (DEC-077 item 1)

### 10.4 `document_counter.last_issued_at` and series locking (DEC-078 item 4)
- `next_document_no(text)`: same signature, ten types, `search_path`, privileges (execute for `sahaj_app` only), behaviour and result; the upsert also sets `last_issued_at = now()` on insert and on conflict.
- **How the service decides "a number of the current financial year has been issued":** the series is locked when a counter row exists for `(tenant, unit, doc_type)` with `coalesce(last_issued_at, updated_at) >= 1 April 00:00 IST of the current financial year`. For a series that restarts each year (BILL by default) the counter row of the current `fiscal_year` exists exactly when a number of this year was issued; for a series that never restarts (`fiscal_year = 0`) the one row lasts for ever, so the time test makes it "this year". Rows from before the migration have a null `last_issued_at`; there is no backfill (the counter guard trigger refuses an update that does not raise `next_value`). The function has always set `updated_at = now()` on each issue and nothing else writes the counter, so the `coalesce` gives the same instant. The query is served by the primary key `(tenant_id, unit_id, doc_type, fiscal_year)` and reads a handful of rows.

## 11. Functions replaced by more than one migration (QA defect D-1, migration `1710`)

**The rule.** Flyway runs migrations in version order, and a function replaced by several migrations takes its body from the highest version. So **a replacement carries every earlier change**. Before you `create or replace` a function that is in the table below (or any function an earlier file already replaced), diff your body against the winning one, keep every line you do not mean to remove, and add the function to this table. Build the new body from the winning version, not from the version you remember. Do not give a lower number to a file written later.

What went wrong: `1350` (posting) was built on the body of `1260`, so it undid `1270` (DRAFT to REJECTED; counters never down in DRAFT, frozen once waiting). Reject of a draft answered 500 and a counter could go down. `1380` (ten document types) was built on `1220`, so it undid `1280` (`last_issued_at` set in the upsert). ### 11.2 Lower-numbered siblings and a database that already ran the higher versions
Flyway has no out-of-order setting here (default `false`). A database that applied `1300` to `1700` before `1270`, `1280` and `1290` existed will refuse to start (validate: "detected resolved migration not applied") until it is dealt with. Only `sahaj_dev` and `sahaj_test` can be in that state (nothing is in production). Ways to cope, in order of preference:
1. Rebuild the database (`node scripts/setup/create-database.mjs`, then start the app; the test profile cleans `sahaj_test` by itself).
2. Or start once with `spring.flyway.out-of-order=true` (environment variable `SPRING_FLYWAY_OUT_OF_ORDER=true`), let `1270`, `1280` and `1290` run, then switch it off. This is safe whatever order they run in: the body in `1270` is already the union of 1100, 1260, 1270 and 1350, and the body in `1280` already has the ten types and `last_issued_at`, so even when they run after `1710` the final functions are still right. (Only `1220`, `1260`, `1350`, `1380` carry stale bodies, and they are always overwritten by a later version.)
3. The migrations `1270` to `1290` themselves must not be renumbered (they may have run elsewhere).
On a database that has `1710` but not `1270`, only the columns are added by `1710`; the relaxed `ck_opening_stock_import_submitted` and the store-active trigger of `1270` and the credit-tier columns of `1290` are missing, so a draft reject can still fail on the check. Rebuild or run `1270` out of order.
