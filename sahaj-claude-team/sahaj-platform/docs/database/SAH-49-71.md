## Rules kept
Additive and forward-only. No `V2026_12_08_*` file and no merged or earlier file was edited. Nothing is dropped, renamed or rewritten. The only changes to existing tables: two new columns/keys on `opd.emr_record` (nullable `screen_state`, one extra unique key), one new check on the global `opd.emr_section_field`, an extended column grant, and new rows in the global `opd.medicine`. Global-table files never mention the clinic column (the `validate.mjs db` static rule). Every new clinic table: `tenant_id uuid not null default platform.current_tenant()` with FK to `platform.tenant`, `ENABLE` + `FORCE` row level security, one policy `to sahaj_app` on `platform.current_tenant()`, tenant-first indexes, composite keys including the clinic column for every reference inside the module and to `patient.patient`, no foreign key to `platform.membership`, no DELETE grant.

### Seed (counts verified by script, see "Static checks")
- **Immunization:** 9 groups, windows (end exclusive) as the analyst reading in ADR-023 H9 / DEC-044: Birth 0 days-6 weeks; 6 weeks 6-10 w; 10 weeks 10-14 w; 14 weeks 14 w-6 months; 6-9 months; 9 months 9-12 m; 12 months 12-15 m; 15 months 15-16 m; 16-18 months 16-19 m. 30 vaccines in drawn order (Birth 3, 6 weeks 6, 10 weeks 5, 14 weeks 5, 6-9 months 3, 9 months 1, 12 months 1, 15 months 3, 16-18 months 3). Keys are the label in lower case with other characters made `_` (`bcg`, `opv_0`, `hep_b_1`, `dtwp_1`, `typhoid_conj`, `dtwp_booster_1`, `varicella_1` ...). "Varicella 1" falls in the 15-month group whose window ends before 18 months, so it is overdue for the 18-month child, as the mockup draws.
- **Growth bands:** **5 WEIGHT rows only**, age 18 to 18 months, sex null: below 8.6 "Below 3rd centile" (alert), below 9.8 "~15th centile", below 11 "~25-50th centile", below 13.7 "~50-97th centile", no upper bound "Above 97th centile" (alert). **No LENGTH or HEAD_CIRC row is seeded**: the mockup draws those two notes as fixed text ("~40th centile", "~50th centile") independent of the value, and the human decided in DEC-044 (H8) to hide them until real WHO tables exist. The table already accepts those measures (a future WHO migration adds rows). ADR-023 "Data needed" item 3 listed the two rows; DEC-044 overrides it.
- **Milestones at 18 months (6):** `walks_alone`, `climbs_stairs_with_help` (gross motor), `scribbles_with_crayon` (fine motor), `feeds_self_with_spoon`, `points_to_show_interest` (social), `says_6_or_more_words` (language).
- **Knee (11):** ROM `flexion` 0-135, `extension` 0-0, `flexion_passive` 0-135; MMT `quadriceps`, `hamstrings` (the two groups the strength line draws; WOMAC is a score, not a muscle group); SPECIAL_TEST `mcmurray_medial`, `lachman`, `patellar_grind`, `anterior_drawer`, `valgus_stress`, `apley_compression`. Sample right/left degrees of the mockup are patient values and are not seeded.
- **Chemotherapy protocols (4), from `REG`:**

  `definition` = `{"schemaVersion":1,"drugs":[{drugKey,name,dosePerM2,infusionMinutes,vialStepMg,vesicant,anthracycline,note?}],"premeds":[{key,text,minutes}]}`; drug keys `doxorubicin`, `cyclophosphamide`, `paclitaxel`, `docetaxel`; pre-medicine keys are scoped to their protocol (`ondansetron_iv`, `dexamethasone_iv`, `aprepitant_oral`, `pheniramine_iv`, `famotidine_iv`, `dexamethasone_oral`). - **`opd.medicine` (10 rows, insert only):** Paracetamol syrup 120 mg / 5 ml, Paracetamol syrup 250 mg / 5 ml, Ibuprofen syrup 100 mg / 5 ml (names exactly as the mockup `MEDS`), Ferrous ascorbate 100 mg, Calcium 500 mg + Vitamin D3 (mockup `SUP`), Ondansetron 8 mg, Dexamethasone 4 mg, Pegfilgrastim 6 mg, Benzydamine mouthwash, Loperamide 2 mg (mockup `THM`). ## Clinic tables
### `opd.emr_record` (existing, partitioned) · two additions (file 1100)
- `screen_state jsonb` null; `ck_emr_record_screen_state_shape` (null, or an object with numeric `schemaVersion`) and `ck_emr_record_screen_state_size` (<= 8 KB). Catalog-only change on the parent and every partition; the previous app version never reads or writes it. No index. `grant update (screen_state)` to `sahaj_app`.
- `uq_emr_record_tenant_id_created_at unique (tenant_id, id, created_at)`. **Why (deviation, see below):** the primary key `(id, created_at)` has no clinic column; a foreign key check ignores row level security, so an order pointing at `(id, created_at)` could name another clinic's record. A unique key on a partitioned table must contain the partition key and this one does. It is **not** a "one record per encounter" rule (that stays advisory lock + find-or-insert). Cost: one unique index per partition (24 monthly + default) built under a table lock; negligible while the table is small (records exist since phase 2). **Ops note:** before this runs on an environment holding millions of records, a human plans the build window.

**Checks (all in the table, each an integration test):**
- `ck_chemo_order_checker_pair`: the four checker columns are all null or all set.
- `ck_chemo_order_checker_independent`: checker ≠ `prescriber_membership_id` and ≠ `last_edited_by_membership_id`.
- `ck_chemo_order_confirmation_pair`: the five confirmation columns are all null or all set.
- `ck_chemo_order_confirmer_is_checker`: `confirmed_by_membership_id = checker_membership_id` (a null checker fails it).
- `ck_chemo_order_confirmation_current`: `confirmed_fingerprint is null or confirmed_fingerprint = fingerprint`.
- `ck_chemo_order_cleared_has_no_confirmation`: `confirmation_cleared_at` only while there is no confirmation.
- `ck_chemo_order_sent`: SENT ⇒ `confirmed_at` set, `confirmed_fingerprint = fingerprint`, `sent_at` and `sent_by` set. `ck_chemo_order_sent_stamp`: `(status = 'SENT') = (sent_at is not null)` and `sent_at`/`sent_by` together. `ck_chemo_order_sent_reason`: SENT ⇒ `level_pct = 100` or a reason key or text.
- `ck_chemo_order_held`: HELD ⇒ `hold_kind` and `held_at` set; any other status ⇒ the three hold columns null.

**Keys and indexes (and the query each serves):**
- PK `id`; `uq_chemo_order_tenant_id (tenant_id, id)` (composite FKs).
- `uq_chemo_order_tenant_record (tenant_id, record_id) where supersedes_order_id is null`: one order per record; the sheet read `GET/PUT /emr/records/{id}/chemo-order`.
- `ix_chemo_order_tenant_checker_waiting (tenant_id, checker_membership_id, checker_named_at) where status = 'DRAFT' and checker_membership_id is not null and confirmed_at is null`: `GET /emr/chemo-checks` ("waiting for my second check", oldest first, 20 a page). Tiny partial index.
- `ix_chemo_order_tenant_patient_sent (tenant_id, patient_id, sent_at) where status = 'SENT'`: cycle 1 weight (first SENT), lifetime doxorubicin (sum), consent per protocol (an earlier SENT of this protocol), cycle number, the oncology cycles block.

**Trigger** `trg_chemo_order_immutable` (before update or delete, per row) and `trg_chemo_order_no_truncate` (before truncate) call `opd.deny_chemo_order_change()`: an UPDATE is allowed only when `old.status = 'DRAFT'` (so DRAFT → SENT and DRAFT → HELD work); every UPDATE of a SENT or HELD row, every DELETE and every TRUNCATE is refused for every role, owner and `sahaj_migrator` included, with SQLSTATE 42501.

**Grants (`sahaj_app`):** select, insert; update only `course_id, cycle_no, status, protocol_key, level_pct, reduction_reason_key, reduction_reason_text, inputs, snapshot, fingerprint, doxorubicin_mg_m2, prior_outside_mg_m2, last_edited_by_membership_id, checker_membership_id, checker_role, checker_named_at, checker_named_by, confirmed_by_membership_id, confirmed_by_user_id, confirmed_via, confirmed_at, confirmed_fingerprint, confirmation_cleared_at, sent_at, sent_by, hold_kind, hold_reason, held_at, revision, updated_at, updated_by`. Never `id`, `tenant_id`, `record_id`, `record_created_at`, `patient_id`, `prescriber_membership_id`, `supersedes_order_id`, `created_*`. No delete, no truncate. RLS: one `for all to sahaj_app` policy on `platform.current_tenant()`.

**What the java-developer must know**
1. **Clearing is one UPDATE.** Any save that changes `fingerprint` must set `confirmed_by_membership_id`, `confirmed_by_user_id`, `confirmed_via`, `confirmed_at`, `confirmed_fingerprint` to null and `confirmation_cleared_at = now()` in the same statement, or the check `ck_chemo_order_confirmation_current` (23514) refuses it. Same for naming another checker (the confirmation must go in that UPDATE).
2. **The prescriber/last editor is the checker only by mistake:** `last_edited_by_membership_id` is set on every save. If the named checker ever saves the order, the row violates `ck_chemo_order_checker_independent` (23514); the application must refuse that save with the contract's 400 first (or clear the checker).
3. SENT: set `status = 'SENT'`, `sent_at`, `sent_by` in one UPDATE while `confirmed_fingerprint = fingerprint`. HELD: `status`, `hold_kind`, `hold_reason`, `held_at`. After that no UPDATE succeeds (42501, message contains "immutable"); map it to 409 `chemo-order-sent` if it is ever reached.
4. The database does not see the application's rule "the checker is an ACTIVE membership with a listed role" or "no other saver": both stay in code. `checker_role` is a copy of the role at naming time.
5. `opd.emr_record` access by the order goes through `(record_id, record_created_at)`: carry `created_at` from the record view or read it with the record.

### `opd.emr_visit_template` (file 1120) · tenant, RLS
Columns: `id`, `tenant_id`, `name` 1-60, `sub_line` null or 1-120, `items jsonb` (object, numeric `schemaVersion`, <= 32 KB), `created_by_membership_id` not null, `active` default true, `created_at`, `created_by`, `updated_at`, `updated_by`. Keys: PK `id`, unique `(tenant_id, id)`, **unique `(tenant_id, lower(name))`** (one name per clinic ignoring case; also serves the list by name). Grants: select, insert; update only `active, updated_at, updated_by`; no delete. One `for all` policy. At most 100 per clinic is an application rule (400 `visit-template-limit`). Items hold master keys or text only, never patient data. `schemaVersion` is stored inside `items` (the contract's `EmrVisitTemplateItems` has no such property: the java-developer adds it on write and drops it on read).

## Tenant scope and RLS
Global tables: no clinic, no RLS, SELECT only. Clinic tables (`chemo_order`, `emr_visit_template`): enabled, forced, one policy on `platform.current_tenant()` (no escape expression), with no tenant bound nothing is visible or insertable. Another clinic's order, template or record is invisible; inserting with another clinic's `tenant_id` is refused; the composite keys refuse a record, patient, course or superseded order of another clinic (23503).

## Backward compatibility (previous app version against the new schema)
Yes. All six global tables and the two clinic tables are new and unused by the old code. `emr_record`: the new column is nullable with no default, the update grant is only extended, and the extra unique key is implied by the primary key (no old insert can violate it). `emr_section_field` check: every existing row passes, and the old app never writes the table. `opd.medicine`: new rows only (old code lists them; schedule text may read "SOS", "Once", "0-1-0" like existing rows). Flyway and the new privileges are the only dependencies.

## Deviations from ADR-023 "Data needed" (each small; none changes a contract field)
1. **No LENGTH or HEAD_CIRC growth rows** (DEC-044 H8 overrides item 3). The weight bands stay (they depend on the value).
2. **Extra unique key `(tenant_id, id, created_at)` on `opd.emr_record`** so the order's composite FK includes the clinic (otherwise a cross-clinic pointer is possible). The ADR said "composite FK to the partitioned record" without the clinic column.
3. **Added column `chemo_order.confirmation_cleared_at`** (the view state CLEARED "Order changed after the second check" must survive a read, and the audit table is not a read model) and the **stricter check `confirmed_fingerprint = fingerprint` for every status** (the ADR demanded it for SENT only). It makes "a stale confirmation" impossible, not only "sending with one".
4. **`ix_chemo_order_tenant_checker_waiting` also carries `checker_named_at`** (the list is oldest-naming first).
5. **Seed medicines use the mockup's names**: "Ferrous ascorbate 100 mg" (the ADR said "Iron") and "Calcium 500 mg + Vitamin D3"; **Loperamide 2 mg added** (it is in the mockup take-home list `THM` but not in the ADR list). Names, forms ("Capsule" for loperamide is my choice, not drawn) and usual-dose text are not clinically reviewed. No prescription defaults (the mockup does not draw frequency + days + when for any of them).
6. `emr_chemo_protocol.protocol_key` is a pattern check, not a closed list of four, so a later protocol is a new row (immutable table), not a constraint change; the four keys are in the contract enum (code).
7. `emr_visit_template` carries both `created_by_membership_id` (ADR) and `created_by` (house rule); the name is unique across active and switched-off rows (ADR: unique per clinic).

## Questions for the human, the architect or the BA
1. The four chemotherapy protocols, doses and vial steps are mockup values and not clinically reviewed; they drive dose calculation. A clinical reviewer should check them before real use. Same for the paediatric weight bands (centile text for 18 months only) and the immunization windows (analyst reading).
2. A clinic-specific protocol library (ADR-023 H6) will need a tenant table beside the global one: not built.
3. `sahaj_test` (and `sahaj_dev`) are not recreated by me. These migrations are additive on top of the existing history, so no recreate is needed for them alone; the earlier path-(a) rewrite of the `V2026_12_08_*` files still requires a recreated database if it has not been done.
