## 1. opd.emr_record (partitioned by month; new columns go to every partition)

| Column | Type | Null | Check |
| --- | --- | --- | --- |
| `signed_by_membership_id` | uuid | yes | none (application checks the membership) |
| `sign_idempotency_key` | text | yes | `^[A-Za-z0-9_-]{8,64}$` |
| `sign_request_hash` | text | yes | 64 lower-case hex |
| `sign_result` | jsonb | yes | object, at most 8,192 bytes |
| `edit_hold_membership_id`, `edit_hold_user_id` | uuid | yes | with `edit_hold_expires_at`: all three or none (`ck_emr_record_edit_hold_set`) |
| `edit_hold_expires_at` | timestamptz | yes | |
| `patient_facts_fingerprint` | text | yes | 64 lower-case hex |

- `status` already allows `SIGNED` (SAH-53). The existing `ck_emr_record_signed` ties `signed_at` and `signed_by` to SIGNED. New `ck_emr_record_signed_complete`: SIGNED implies `signed_by_membership_id` and `sign_idempotency_key` not null and no edit hold (the sign clears it, D1 step 8). I added "no edit hold" to the ADR rule.
- Grants: the table-level `select, insert` already covers the new columns at insert (open stores the hold and fingerprint). Column update grant added for all eight. No delete, as before.
- Indexes: none new. The copy-from-last for IPD rounds (previous signed IPD_ROUND of the same admission: `where tenant_id, ipd_admission_id = ?, status = 'SIGNED', round_date < ? order by round_date desc limit 1`) is served by the existing `ix_emr_record_tenant_admission_round (tenant_id, ipd_admission_id, round_date)`; an admission has a handful of rows. There is no unique key on `sign_idempotency_key`: a unique index on a partitioned table must contain `created_at`, and the sign reads the key from the record row it has already locked.
- Cost: nullable columns without default are a catalog change. The two checks scan the table once; before this release no record could be SIGNED, so they cannot fail.

### Signed-record immutability (`opd.guard_signed_emr_record`, trigger `trg_emr_record_signed_guard`)
Before update or delete, for each row (cloned to every partition, also future ones). When the OLD row is SIGNED:
- DELETE is refused;
- an UPDATE is refused (SQLSTATE 42501, message "opd.emr_record is immutable once signed ...") unless the only changed columns are `print_language`, `paper_size`, `updated_at`, `updated_by`, or `patient_id` from null to a value on an `ER_ASSESSMENT` record;
- it is an allow-list on `to_jsonb(row)`, so columns added later are frozen by default; `status` can never leave SIGNED; the ER patient link works once (a second change finds `patient_id` not null).
- The DRAFT to SIGNED update passes (old row DRAFT). The sign must write `status, signed_at, signed_by, signed_by_membership_id, sign_idempotency_key, sign_request_hash, sign_result, revision, updated_*` and clear the hold in that one update. **After signing, a print-preference save or the ER patient link must not change `revision`** (it is frozen; this follows the ADR allow-list).

### New records must be DRAFT (`opd.require_draft_emr_record_insert`, trigger `trg_emr_record_insert_draft`; security review I2, 13 Nov 2026)
Before insert, for each row, in the same unmerged file as the signed guard (edited in place; no database has run it). A row whose `status` is not `DRAFT` is refused with SQLSTATE 23514 (check_violation: the value is wrong, not a missing privilege). SIGNED is reached only by the DRAFT to SIGNED update. Same style as the signed guard: `search_path = pg_catalog`, `revoke all ... from public` and from `sahaj_app`.
- PostgreSQL 16: a BEFORE ROW trigger on a partitioned table is allowed (since 13); the trigger on the parent is cloned onto every partition (existing, default, future) and fires on the partition the row is routed to; a direct insert into a partition fires it too. It does not modify the row, so routing is unaffected. `INSERT ... ON CONFLICT` and `COPY` fire it as well; it applies to every role including the owner.
- Order: BEFORE triggers run before check constraints, so an insert with status SIGNED now fails here (23514) and no longer on `ck_emr_record_signed`. That constraint is still reached by the sign update (case 1).
- The application insert (`JdbcEmrRecordRepository.INSERT`) writes the literal `'DRAFT'`; the other inserts leave `status` to its default `'DRAFT'`.

### Chemo order frozen with its record
`opd.deny_chemo_order_change()` is replaced (same name, so `trg_chemo_order_immutable` and `trg_chemo_order_no_truncate` are untouched): a DRAFT order is refused an update when its record (key `tenant_id, record_id, record_created_at`) is SIGNED (42501). SENT and HELD stay immutable; delete and truncate stay refused. The sign sets the record to SIGNED last, so no order write may come after that update in the sign transaction (none is planned). A corrected order (`supersedes_order_id` set) is frozen like any DRAFT order once its record is signed; if the later correction flow must update it, that is a new migration.

### Referral line of an Emergency refer-out (DEC-048 H22, 13 Nov 2026)
`ck_emr_record_referral_needs_advice` (defined in the unmerged `V2026_12_08_1040__opd_emr_tenant_tables.sql`, edited in place: no migration of that file has run on a kept database, `sahaj_test` is recreated under DEC-039 path (a)) is relaxed from `admission_advised or referral_line is null` to:

```sql
check (admission_advised or referral_line is null or encounter_type = 'ER_ASSESSMENT')
```

- Why in that file and not a later one: `encounter_type` and `referral_line` are both in `opd.emr_record` from V2026_12_08_1040; no later migration adds an outcome column, so there is nothing later to wait for. An in-place edit leaves no second constraint to explain.
- Why only the encounter type: the Emergency outcome (REFER_OUT) is not stored on `opd.emr_record`. It is in `sign_result` (json, no fixed key a check could rely on) and as status REFERRED on `ipd.emergency_case` (another module, no foreign key). `ER_ASSESSMENT` is the narrowest condition the table itself can see. OPD visit and IPD round records keep the old rule exactly (a referral line only with "Admission advised").
- What the database no longer guarantees: that an Emergency record with a referral line and `admission_advised = false` is a refer-out. The sign (`EmrSignService`, REFER_OUT only) guarantees it. `admission_advised` keeps its meaning (the doctor advised admission; the ADMIT outcome creates an admission request).
- Column length and blank checks (`ck_emr_record_referral_line`, 1 to 300 characters) are unchanged. The signed-record trigger does **not** allow `referral_line` (its allow-list is `print_language`, `paper_size`, `updated_at`, `updated_by`, and `patient_id` from null to a value on an ER_ASSESSMENT record), so a referral line can be changed only while the record is DRAFT (the DRAFT to SIGNED update passes because its old row is DRAFT) and is frozen once signed; no trigger change (corrected 13 Nov 2026, security review I1).
- Backward compatible: the check only becomes wider; every row that passed before passes now.

## 2. opd.emr_record_addendum (new, append-only)

`id` uuid pk · `tenant_id` · `record_id`, `record_created_at` (composite key to `emr_record (tenant_id, id, created_at)`, `uq_emr_record_tenant_id_created_at`) · `reason` 1 to 200 after trim · `addendum_text` 1 to 4,000 after trim · `created_by_membership_id`, `created_by_user_id` not null · `idempotency_key` not null (8 to 64) · `request_hash` not null (64 hex) · `created_at` default `clock_timestamp()`.
- Differences from the ADR list: the ADR's `text` column is named `addendum_text` (avoids a column called text); `request_hash` added because the contract answers 409 `idempotency-conflict` for a key reused with another body.
- Keys: unique `(tenant_id, id)`, unique `(tenant_id, idempotency_key)`.
- Index `ix_emr_record_addendum_tenant_record_created (tenant_id, record_id, created_at)`: record view, history details, case-paper context (oldest first, shown newest last) and the count for the 50 limit.
- RLS: select and insert policies only. Grants: `select`; `insert (record_id, record_created_at, reason, addendum_text, created_by_membership_id, created_by_user_id, idempotency_key, request_hash)`. Trigger `platform.deny_audit_mutation` refuses update, delete, truncate for every role (42501, "append-only").
- The application checks: record SIGNED, at most 50 per record (400 `addendum-limit`), doctor or owner with doctor details. Text never in a log line or audit value.
- Volume: a few rows per thousand records; no partitioning. Retention: for ever (clinical).

## 3. opd.emr_admission_request (new)

`id` · `tenant_id` · `record_id`, `record_created_at` (composite key to the record) · `encounter_type` OPD_VISIT or ER_ASSESSMENT · `opd_visit_id` null (composite key to `opd.visit (tenant_id, id)`) · `er_case_id` null (opaque ipd id) · `patient_id` null (composite key to `patient.patient`) · `requested_by_membership_id` not null · `admission_type` planned, emergency, daycare · `planned_stay_days` null 1 to 60 · `reason_text` null 1 to 200 · `procedure_text` null 1 to 200 · `note` null 1 to 300 · `status` OPEN (default) or ADMITTED · `admission_id` null (opaque) · `admitted_at` null · `idempotency_key` not null · `request_hash` not null (added, as above) · `created_at/by`, `updated_at/by`.
- Checks: OPD_VISIT has visit and patient and no case; ER_ASSESSMENT has case and no visit (patient stays null until admitted); ADMITTED has `admission_id` and `admitted_at`, OPEN has neither.
- Indexes (each with its query): unique `(tenant_id, record_id) where status = 'OPEN'` (one open request per record; the repeat finds it); `(tenant_id, created_at desc) where status = 'OPEN'` (IPD "Admission requests" list, newest first, 200); `(tenant_id, patient_id) where OPEN and patient_id is not null` and `(tenant_id, er_case_id) where OPEN and er_case_id is not null` (onAdmitted closes every open request of the patient or the case). Unique `(tenant_id, id)` and `(tenant_id, idempotency_key)`.
- Grants: `select`; column insert (everything except id, tenant, status, created_at); column update only `status, admission_id, admitted_at, updated_at, updated_by`. No delete. Trigger `opd.guard_emr_admission_request`: an ADMITTED row never changes (42501); delete and truncate refused for every role.
- Volume: tens a day per hospital, a few a day per clinic. Retention: life of the clinic, no cancel in phase 5 (H14).

## 4. opd.appointment and opd.follow_up
- `ck_appointment_source` widened to PHONE, WHATSAPP, FRONT_DESK, EMR (not valid then validate). `visit_type` unchanged (the EMR books FOLLOW_UP).
- New `uq_appointment_tenant_id (tenant_id, id)`: target of the composite key. Plain build (precedent `uq_visit_tenant_id`): it blocks writes to `opd.appointment` while it builds. **Run at a quiet time on a database that already holds millions of appointments** (phase 1 tables are small; at 10,000 clinics plan a `concurrently` build first).
- `follow_up.appointment_id uuid null` with `fk_follow_up_appointment (tenant_id, appointment_id)` (null skips the check); `follow_up.interval_key text null` in D3, D7, D14, D15, M1, M3. No index (read by the appointment's primary key; appointments are never deleted). Grants: table-level, unchanged.

## 5. opd.visit
- `ck_visit_type` widened with EMERGENCY. `triage_level smallint null` (1 to 5), `triage_scale smallint null` (3 or 5). Checks: `(visit_type = 'EMERGENCY') = (triage_level is not null)`, level and scale both null or both set, `triage_level <= triage_scale`. Every existing row passes; all added not valid then validated. No index (the Queue reads today's visits by `created_at`). Moving a visit back to another type must null both columns in the same update.

## 6. ipd.round_note (new, insert-only)
`id` · `tenant_id` · `admission_id` (composite key to `ipd.admission`) · `round_date date` · `emr_record_id uuid` (opaque) · `signed_by_user_id`, `signed_by_membership_id`, `signed_at` not null · `orders_placed int >= 0` default 0 · `investigations_advised` null 1 to 1,000 · `created_at`.
- Unique `(tenant_id, admission_id, round_date)` (the day rule, also serves the latest note of an admission), unique `(tenant_id, emr_record_id)` (one note per record, added), unique `(tenant_id, id)`. Index `(tenant_id, round_date, admission_id)`: the Admitted list asks which admissions have a note on today's date.
- RLS: select and insert only; trigger `platform.deny_audit_mutation` refuses update, delete, truncate. Grants: select; column insert. A retry uses `insert ... on conflict (tenant_id, admission_id, round_date) do nothing` (ALREADY_RECORDED is success).
- Volume: one row per admitted patient per day at most (a hospital with 50 beds: under 20,000 a year). Retention: life of the clinic.

## 7. ipd.emergency_case and ipd.admission
- `ck_emergency_case_status` gains SENT_TO_OPD. `sent_to_opd_visit_id uuid null` (opaque). `ck_emergency_case_patient_admitted` (same name) is widened to "patient only with ADMITTED or SENT_TO_OPD" (the SAH-28 check would otherwise refuse the patient of a sent case). New `ck_emergency_case_sent_to_opd`: SENT_TO_OPD has patient, visit, `closed_at`, `closed_by`; only SENT_TO_OPD has a visit id. The existing closed, admitted and open-bay rules already fit SENT_TO_OPD (bay freed by the open-bay index; a closed status needs `closed_at` and `closed_by`).
- `ipd.guard_emergency_case_update()` replaced (the SAH-28 version plus SENT_TO_OPD in both lists): a SENT_TO_OPD case never updates again, and `mobile` must be cleared in the update that sets it (an update to a closed status that leaves `mobile` not null is refused, 23514). Column update grant: `sent_to_opd_visit_id` (status, patient_id, closed_*, mobile already granted).
- `ipd.admission.admission_request_id uuid null` (opaque, no key), insert grant only, partial unique `(tenant_id, admission_request_id) where not null` (one admission per request; added). No update grant.

## 8. billing.bill_item
- `source_kind` check gains EMR_PLAN. `source_key` length check widens 1 to 40 into 1 to 80 (widening only). New `label text null` 1 to 120, allowed only when `source_kind = 'EMR_PLAN'` (`ck_bill_item_label_kind`; I did not make it required). `service_id` was already nullable; new `ck_bill_item_service_or_plan`: null only for EMR_PLAN (null `source_kind` counts as not EMR_PLAN). `bill_item` has never had a line without a service (`BillingService` rejects it), so validation passes; if one existed the migration would stop on purpose.
- The unique `(tenant_id, bill_id, source_key) where source_key is not null` covers `plan:<rowId>:<sittingNo>`; `ck_bill_item_source_pair` unchanged. Grants unchanged (table-level select, insert, update, delete).

## 9. patient.patient
- `allergy_recorded_at timestamptz null`, `allergy_recorded_by uuid null` (opaque user id), `ck_patient_allergy_recorded_pair` both or neither (not valid then validate). No backfill; no index; grants table-level, unchanged. The front desk change of the allergy text must clear both (application).

## Tenant scope, volume and retention
All three new tables are per clinic, RLS enforced, never deleted. Rows per tenant per year: addenda tens; admission requests hundreds at most; round notes up to one per admitted day (IPD only). No partitioning beyond the existing `emr_record` monthly partitions (partition upkeep unchanged: `opd.emr_record_ensure_partitions`).

## Backward compatibility
The previous application version runs on the new schema: new columns are nullable or defaulted and unused by it, checks are only widened, and it never writes SIGNED with the new rules (it cannot sign). The new checks (`ck_emr_record_signed_complete`, the immutability trigger, `ck_bill_item_service_or_plan`, the visit and case checks) apply to the new version's writes. Rollback is a later forward migration.
