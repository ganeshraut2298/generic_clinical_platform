## 0. Safety summary
- **Additive only.** Every statement creates a new object (tables, indexes, functions, triggers, policies, partitions, seed rows) or adds to an existing one. Changes to existing objects, all widening or adding: two nullable columns on `opening_stock_import`; one nullable column on `store`; four check constraints replaced by the same list plus new values (`document_series`, `document_counter`, `reason_default`, `reason`); one new check on `reason_default_state`; two functions replaced by `create or replace` with the same signature and privileges (`guard_opening_stock_import_update()`, `next_document_no(text)`); 23 new global `reason_default` rows. **No drop of data, no rename, no update or delete of an existing row, no rewrite.** No applied migration (1000 to 1260) is edited.
- **Constraint replacement** is `drop constraint if exists` then `add constraint` in the same transaction (the way V2026_12_17_1000 widened the role check). The new list contains every old value, so no existing row can fail it. The four tables are tiny (hundreds of rows at most), so the brief lock is harmless; `set local lock_timeout = '30s'` is at the top of every file.
- **Backward compatibility.** The previous app version (SAH-78 build) runs unchanged against this schema: new tables it never touches; new nullable columns; wider checks; the seeded reasons use list keys the SAH-78 code ignores (`JdbcReasonRepository`/`ReasonService.lists` skip a list key they do not know; the working tree already carries the eleven-list enum). The old guard messages are unchanged.
- **Flyway** runs out-of-order off. SAH-79 WP-D takes `V2026_12_17_1300` to `1390`; the folder held nothing above `1260` and no `V2026_12_18_*` or later file when I wrote them. The IPD SAH-77 range (`V2026_12_18_*`) is untouched.
- **Not verified against a live database by me.** The Maven session 25860 was running, so `node scripts/validate.mjs db` was not run (section 11); and I have no database credentials in this session (the `.env` read is refused). I reviewed every statement by hand against PostgreSQL 16 rules and the patterns of migrations 1000 to 1260 and the SAH-53 partition code. QA runs the gate first (section 11, "First thing to run").

## 2. Conventions used, and deviations

All SAH-78 conventions apply (section 2 of `SAH-78-pharmacy-masters.md`): `id uuid` default `gen_random_uuid()`; `tenant_id uuid not null default platform.current_tenant()` with FK to `platform.tenant`; `unit_id` with the same-tenant composite FK to `pharmacy.unit`; same-tenant composite FKs `(tenant_id, x_id)` to `(tenant_id, id)`; `tenant_id` leads every index except where a table's own key is chosen for its query; `ENABLE` and `FORCE` row level security with one policy per command for `sahaj_app` on `tenant_id = platform.current_tenant()`; `revoke all` from `sahaj_app` and `public` then an explicit grant; no delete grant or policy anywhere; singular table names; `fk_`, `ix_`, `uq_`, `ck_`, `trg_`, `p_` prefixes; `timestamptz`; text with `check`; paise as `bigint`, rates `numeric(14,4)`, percentages `numeric(5,2)`, quantities `integer`.

Differences and choices worth knowing (each is also listed in section 12):

1. **Who-columns are membership ids** on every Phase 2 table (`created_by`, `raised_by`, `decided_by`, `actor_membership_id`, `posted_by`). They are plain `uuid` columns with no foreign key and the database cannot check which kind a row holds; the posting and approval services take them from the signed-in membership (as the SAH-78 opening-stock tables already do; see section 3.5 of the SAH-78 note).
2. **Time columns that order events use `clock_timestamp()`, not `now()`** (`stock_ledger.occurred_at`, `document_event.occurred_at`, `approval_decision.decided_at`). `now()` is the transaction start: a transaction that started first but waited for the balance lock would write an earlier time than the transaction it waited for, and "stock moved since the count" (79-17) compares times. Rows are inserted after the locks are held, so `clock_timestamp()` is in lock order.
3. **Vocabulary patterns instead of lists where later work packages add values.** `document_event.doc_type` and `event`, and `stock_ledger.doc_type`, are checked with `^[A-Z][A-Z_]{1,39}$` rather than a fixed list, so WP-E to WP-H do not have to widen a check for each new document. Fixed vocabularies stay lists: ledger `txn_type` (24 values of the contract), `state`, approval types, statuses.
4. **The shared deny trigger** `pharmacy.deny_append_only_mutation()` (SQLSTATE `42501`, message `"<table> is append-only (<UPDATE|DELETE|TRUNCATE> refused)"`) serves `document_event`, `stock_ledger` (parent and every partition) and `approval_decision`, and will serve `vendor_payable_entry` in WP-E.
5. **Grants on the ledger are table-level `select, insert`** (as the task says), not column-level. `occurred_at` is therefore defaulted by the database but not enforced against a client value: that is a service rule (the posting service never sends it).
6. **Partitions have no grant for `sahaj_app`**; they have `ENABLE` + `FORCE` row level security and two policies each (select, insert), as the SAH-53 EMR partitions do. `RowLevelSecurityCatalogIT` will see them (section 11).

**Reconciliation (79-4, 79-18).** For every store, batch and state, `sum(qty_in - qty_out)` over the ledger equals `stock_balance.qty`. The database cannot enforce this across two tables without a trigger that would serialise every posting; the posting service writes both in one transaction under the balance lock, and a QA test plus the ledger report check it. Query for QA:

```sql
select b.store_id, b.batch_id, b.state, b.qty, coalesce(sum(l.qty_in - l.qty_out), 0) as ledger_qty
  from pharmacy.stock_balance b
  left join pharmacy.stock_ledger l on l.tenant_id = b.tenant_id and l.store_id = b.store_id
       and l.batch_id = b.batch_id and l.state = b.state
 group by b.store_id, b.batch_id, b.state, b.qty
having b.qty <> coalesce(sum(l.qty_in - l.qty_out), 0);   -- must return no row
```

### 3.3 D2d · ledger partitions

- Monthly range partitions `pharmacy.stock_ledger_yYYYYmMM` on `occurred_at`, bounds written as IST (`'2026-11-01 00:00:00+05:30'` to the next month), so a line posted at 00:30 IST on 1 December lands in December. **41 partitions, Nov 2026 to Mar 2030** (`select pharmacy.create_ledger_partitions(date '2026-11-01', 41)` at the end of D2d). **No default partition**: a month with no partition makes the insert fail loudly (SQLSTATE 23514, "no partition of relation ... found for row"), instead of collecting rows that would later block creating that month. The app answers 503 `database-busy` for that case; the startup warning below makes it visible months earlier.
- **`pharmacy.create_ledger_partitions(p_from_month date, p_months integer) returns integer`**: SECURITY INVOKER, `set search_path = pg_catalog`, `execute` revoked from `public` and `sahaj_app`, so only the owner `sahaj_migrator` can call it. Idempotent: an existing month is skipped. `p_months` is 1 to 120. For each new month it creates the partition, enables and forces row level security, creates `p_<partition>_select` and `p_<partition>_insert` for `sahaj_app`, revokes every privilege from `sahaj_app` and `public`, and creates the statement-level `trg_stock_ledger_no_truncate` (statement triggers are not inherited). The row-level `trg_stock_ledger_no_update_delete` is cloned from the parent by PostgreSQL itself. Returns how many partitions it made.
- **Upkeep.** The next upkeep migration is one line: `select pharmacy.create_ledger_partitions(date '2030-04-01', 12);` (or more). It must run **before April 2030**. The warning without a job (ADR-029 P15) is the app's `LedgerPartitionCheck` (WARN when fewer than 6 months remain, from October 2029) and a QA test (fails when fewer than 12 months remain at build time, from April 2029). The catalogue query both use:

```sql
select max(pg_catalog.to_date(substr(c.relname, 15, 4) || substr(c.relname, 20, 2), 'YYYYMM')) as last_month_start,
       count(*) as months
  from pg_catalog.pg_inherits i
  join pg_catalog.pg_class c on c.oid = i.inhrelid
 where i.inhparent = 'pharmacy.stock_ledger'::regclass
   and c.relname ~ '^stock_ledger_y[0-9]{4}m(0[1-9]|1[0-2])$';
```
  (The name is `stock_ledger_yYYYYmMM`: `stock_ledger_y` is 14 characters, so `YYYY` is at 15 to 18, `m` at 19 and `MM` at 20 to 21. `sahaj_app` can read `pg_inherits` and `pg_class`; no function is needed.)
- Retention: no partition is dropped until the human sets legal periods (OQ-PHI-19). When one is, a partition is detached and dropped by `sahaj_migrator` in a migration; the deny triggers do not stop `DROP TABLE` by the owner (by design: it is the only way a ledger month ever leaves).
- Volume: about 9 million lines a month at full use (100 hospitals x about 3,000 lines a day); about 9 million rows per partition, indexes per partition. See section 9.

## 6. Lock order for the java-developer (ADR-029 P5, with table names)

Every transaction that changes stock or decides an approval takes locks in this order, and only the ones it needs. Never go backwards.

0. **`client_request` insert** (first statement, when the call carries a `clientKey`): `insert ... on conflict do nothing`, then read by `(tenant_id, client_key)` if nothing was inserted. It takes no lock on any other table. A concurrent request with the same key waits on this transaction's unique entry and then replays, so two taps post once. (Step 0 is mine; ADR-029 lists steps 1 to 8.)
1. **`store` rows** whose `has_stock` flips from false to true (ascending id). The store check of ADR-028 R5-2 stays store first. (SAH-78 flips it at approval of opening stock; posting sets nothing on `store`.)
2. **`approval_request`** `FOR UPDATE`, when an approval decision drives the action.
3. **The document header** `FOR UPDATE`, checked against `version`: for opening stock the `opening_stock_import` row; for an adjustment waiting for approval the `stock_adjustment` row. Read the header's status and `posted_at` only after the lock.
4. **`document_counter`** through `pharmacy.next_document_no(type)`, when a number is taken (the adjustment at save; the INSERT ... ON CONFLICT takes the row lock).
5. **`product` rows** whose `has_stock` flips (ascending id).
6. **`batch` rows** to create or top up, ascending `(product_id, batch_key, expiry_date)`: `insert ... on conflict (tenant_id, unit_id, product_id, batch_key, expiry_date) do nothing`, then `select ... for update`. Compare `mrp` after the lock; a difference is 409 `batch-mrp-mismatch`.
7. **`stock_balance` rows:** first insert the missing destination rows in the same order with `on conflict (tenant_id, store_id, batch_id, state) do nothing`; then lock **every** balance row of each involved `(store_id, product_id)` with one `select ... where tenant_id = ? and (store_id, product_id) in (...) order by store_id, product_id, batch_id, state for update` (served by `ix_stock_balance_store_product`). FEFO is computed in memory from the locked rows. The expiry sweep of a **read** uses `for update skip locked` on `ix_stock_balance_sweep` and never waits.
8. **Inserts and updates last:** `stock_ledger` lines (with `balance_after` computed from the locked row), the `stock_balance` update, the document lines and status (the header is already locked in step 3), `approval_request` and `approval_decision`, `document_event`, audit.

Notes:
- Inside a step with many rows (an opening-stock file of 5,000 lines) sort the whole set by that step's key before locking.
- The expiry quarantine inside a movement runs **after step 7** (rows are locked) and before the pick. It writes ledger lines with `actor_kind = 'SYSTEM'`, `txn_type = 'EXPIRY_QUARANTINE'`, `reason_key = 'damage.expired'` and no document (`doc_type` and `doc_id` null).
- A timeout or deadlock (SQLSTATE `55P03`, `57014`, `40P01`) is 503 `database-busy` with nothing saved.
- Do not send `occurred_at` or `decided_at`; the database sets them.

## 7. Notes for java-developer

### 7.1 Names to map (Spring JDBC, hand-written SQL; no JPA)
- Tables as in section 3, all in schema `pharmacy`. `version bigint` is the optimistic version on `batch`, `stock_balance`, `approval_request`, `stock_adjustment`. The balance update is `set qty = qty + :delta, updated_at = now(), updated_by = :actor, version = version + 1 where tenant_id = ? and id = ?` under the lock; the check `qty >= 0` is the backstop.
- **`stock_ledger` insert** carries: `unit_id`, `movement_id`, `txn_type`, `store_id`, `state`, `product_id`, `batch_id`, `qty_in` xor `qty_out` (leave the other at its default 0), `balance_after`, `actor_kind`, `actor_membership_id` (null for SYSTEM). `tenant_id` defaults from the bound tenant. `doc_type` and `doc_id` together or both null. `second_signer_membership_id` differs from the actor. `admission_id` exactly for `WARD_CONSUMPTION_PATIENT`.
- `batch.batch_key` is **generated**: never insert it. The conflict target of the upsert is `on conflict (tenant_id, unit_id, product_id, batch_key, expiry_date)`, naming `batch_key` as a column.
- `stock_adjustment.difference` is **generated**: never insert it. Insert `doc_seq` from `next_document_no('STOCK_ADJUSTMENT')` and `doc_no` rendered from the series; set `value_paise` rounded half up.
- Order for an adjustment that needs approval: insert the adjustment as `WAITING_APPROVAL` with `approval_request_id` null; call `ApprovalEngine.submit` (the request has `subject_id` = the adjustment id); then update the adjustment's `approval_request_id` (allowed by the guard). Level 0: insert the adjustment as `POSTED` with `posted_at` set and no request.
- `approval_decision.raised_by` is a copy of the request's `raised_by`; the trigger refuses another value. `decided_by` must differ from it (check).
- Final approval: one update of the request to `APPROVED` with `current_level = null` (the check ties status and level). Level 1 approved and level 2 applies: `current_level = 2`, `level_entered_at = now()`.
- Posting opening stock: after the lines and balances, one update of the import: `set posted_at = now(), posted_by = :membership, updated_at = now(), updated_by = :membership, version = version + 1 where tenant_id = ? and id = ? and status = 'APPROVED' and posted_at is null`. Zero rows means already posted: answer 409 `already-posted` with the stored `posted_at`.
- `batch.expiry_date` is a `date` meaning the last valid day (IST): expired when `expiry_date < (now() at time zone 'Asia/Kolkata')::date`.
- **Never log** batch numbers, quantities, names or notes (ADR-028 D9): ids and counts only.

## 10. Rollout and backward compatibility

- **Order of apply:** `1300` to `1390` in one Flyway run. `1330` (ledger parent) has no partition until `1340` (same run); an insert in between cannot happen because both are in one start-up. Each file is its own transaction; a failure in `1340` leaves `1330` applied and a re-run applies `1340`.

## 12. Deviations from ADR-029, additions, and open questions

**Deviations from ADR-029 (each is additive and reversible by a forward migration):**
1. **`next_document_no(text)` is replaced (D6).** ADR-029 "Data needed" D6 says "the counter function is unchanged". Its list of document types is written inside the function, so without the replacement the five new types would fail with "unknown document type". Same signature, privileges and behaviour.
2. **Added columns not in the ADR list:** `approval_request.level_entered_at` (needed to escalate level 2 from the time it was reached, ADR-029 P6 says "or the time the request reached level 2"); `approval_request.unit_id`, `approval_request_level.unit_id`, `approval_decision.unit_id`, `batch.unit_id` and others (the "Data needed" convention gives every table `unit_id`); `stock_adjustment.doc_seq`, `doc_no`, `approval_request_id`, `posted_at`, `unit_id` (the number is stored as issued text; the request link lets the screen read the approval); `stock_adjustment.difference` as a generated column.
3. **`approval_request.max_rate_rise_percent` is `numeric(9,2)`,** not the `numeric(5,2)` convention: a rate can more than double, and `numeric(5,2)` would overflow at 1,000%.
4. **`stock_ledger.doc_type` and `doc_id` may be null together** (the expiry quarantine has no document); `doc_type` is a pattern, not a list; `doc_no` is 1 to 40 characters.

7. **No `document_series` rows are inserted for the five new types**; the defaults are served by the application (lazy, like SAH-78). ADR-029 P9 says "defaults until saved".
8. **`store.ipd_ward_id` is in WP-D (D7)** because ADR-029 "Data needed" lists D7 under WP-D, although its only operation is WP-G.
9. **Lock-order step 0** (`client_request` first) is added; steps 1 to 8 are ADR-029's.

## 17. Deviations, additions, risks and open points for WP-E to WP-H

**Deviations from ADR-029 "Data needed" and from the task (each additive and reversible by a forward migration):**
1. **Vendor credit columns are in `V2026_12_17_1290`, not in WP-E.** Contract 0.2.1 puts them on the SAH-78 vendor shapes, so the SAH-78 vendor code of the next run needs them (section 10.5 of the SAH-78 note).
2. **Removed-line flag instead of delete.** Every draft line table (`purchase_order_line`, `goods_receipt_line`, `debit_note_line`, `indent_line`) has `removed boolean`; a removed line stays removed; partial uniques carry `where not removed`. The ADR did not say how a draft whose lines are edited drops a line when no table has a delete grant.
3. **Guard triggers on every document table** (status moves, final states, frozen identity, lines only while the parent is a draft) in the style of WP-D, so a defect in the service cannot rewrite a finished document. The allowed-move lists are written from ADR-029 P10 and P12 and the contract status enums, and are deliberately permissive where the text is silent (for example an APPROVED PO may go straight to PARTLY_RECEIVED or RECEIVED; an indent may move among APPROVED, PARTLY_DISPATCHED, DISPATCHED and RECEIVED). **If the java-developer needs a move the trigger refuses, that is a request to me for a forward migration, not a reason to remove the trigger.**
4. **Columns not named in the ADR list:** `doc_seq`, `doc_no`, `approval_request_id`, `version`, `created_*`/`updated_*` on every header; `goods_receipt_line` saved computations (`taxable_paise`, `gst_paise`, `net_rate`, `reference_rate`, `rate_basis`, `rate_percent`, `short_qty`, `landed_rate`) so a posted receipt keeps what the screen showed; `vendor_payable_entry.open_after_paise` (backs "no negative payable"); `debit_note` picking and hand-over columns; `debit_note_credit.applied_paise`, `unapplied_credit_paise`, `difference_paise`; `indent.cancel_reason_key`, `cancel_note`, `raised_at`; `indent_line.closed_qty` and the replacement columns; `dispatch.dispatch_seq`, `reference`, the receipt columns and notes; `shortage.approval_request_id`, `settled_*`; `stock_audit.closed_at`, `scope`; `stock_audit_line.posted_at`, `variance_note`, `recount_requested`.

## 18. Round 4 hardening (DEC-080; one file, `V2026_12_17_1720__pharmacy_round_4_hardening.sql`)

All items are additive. No table or column is added; no row is read or changed on a database built from scratch. One function is replaced (`next_document_no`); every other function is new. Nothing in this section changes what the previous app version does, except the refusals listed (each is a fixed rule the service already keeps). Every new trigger function has `set search_path = pg_catalog`, is SECURITY INVOKER, and has execute revoked from public and `sahaj_app`.

### 18.1 L11 · `next_document_no(text)` reads the unit row `FOR SHARE`
- **Body:** the body of `1710` with one change: `select u.id into v_unit from pharmacy.unit u where u.tenant_id = v_tenant for share`. Signature, `grant execute ... to sahaj_app` (revoked from public), `last_issued_at` on insert and on update, and the ten types are as in `1710`. Files that came before: `1220` (first body), `1280` (`last_issued_at`), `1380` (ten types), `1710` (union). The function comment names them.
- **Lock effect.** The series save holds the unit row `FOR UPDATE` and then checks "a number of this financial year was issued". An issue now takes the same row `FOR SHARE` first. So (a) a save waits for an issue in flight to commit or roll back and then sees the number; (b) an issue waits for a save in flight and then runs on the new series; (c) two issues do not wait for each other at the unit row (SHARE with SHARE) and still queue on the counter row as before. Cost: one row-level lock on a one-row-per-tenant table; no table lock.
- **Rule for the callers (java-developer).** A transaction that has issued a number holds the unit row `FOR SHARE` until it ends. It must not later ask for the same row `FOR UPDATE` (an upgrade can deadlock with a series save that is waiting). ADR-029 P5 takes the unit lock first, so a posting that locks the unit `FOR UPDATE` must do it before `next_document_no`. The SAH-79 posting reads the series after `next_document_no` in the same transaction (DEC-080).
- `sahaj_app` can take the lock: it has select and update on `pharmacy.unit` and the update policy. A test connection as the migrator is not enough.

### 18.2 L14 · ledger trigger: a Schedule X movement needs a second signer
- **Trigger** `trg_stock_ledger_schedule_x`, BEFORE INSERT, FOR EACH ROW, on the parent `pharmacy.stock_ledger`, `when (new.actor_kind = 'USER' and new.second_signer_membership_id is null)`; function `pharmacy.guard_stock_ledger_schedule_x()`. A row trigger on a partitioned parent is cloned by PostgreSQL to every existing and future partition (the same way as `trg_stock_ledger_no_update_delete` in `1330`; `create_ledger_partitions` in `1340` needs no change).
- **Message:** `schedule X movement needs a second signer`, SQLSTATE 23514.
- **Schedule lookup:** by `product_id` and `tenant_id` of the line, read as the caller (row level security). An OWN product has `schedule` on its row; an ADOPTED product has it null (`ck_product_kind_fields`) and the schedule lives on the global `pharmacy.catalogue_product` (select granted to `sahaj_app`). The function uses `coalesce(p.schedule, c.schedule)`. A line whose product is not found passes (the foreign key on the batch refuses it anyway).
- **Person-driven transaction types used.** ADR-029 P7 did not yet carry the architect's list when this file was written (it describes the verbs only), so the list is derived from P7 and the contract (`pharmacy.yaml` 0.3.2) and is **provisional**. Included (16): `GRN`, `STOCK_ADJUSTMENT`, `STOCK_AUDIT_ADJUSTMENT`, `INDENT_DISPATCH`, `INDENT_RECEIPT_ACCEPTED`, `INDENT_RECEIPT_REJECTED`, `RETURN_ACCEPTED`, `STORE_RETURN`, `DAMAGE_QUARANTINE`, `DAMAGE_SEND_TO_CS`, `VENDOR_RETURN`, `TRANSFER_DISPATCH`, `TRANSFER_RECEIPT_ACCEPTED`, `TRANSFER_RECEIPT_REJECTED`, `WARD_CONSUMPTION`, `WARD_CONSUMPTION_PATIENT`. Not included on purpose: `OPENING_STOCK` (ADR-029 A-8: no signature at posting), `EXPIRY_QUARANTINE` (system), `VENDOR_RETURN_HOLD` and `VENDOR_RETURN_RELEASE`, `DAMAGE_RELEASE`, `SHORTAGE_FOUND`, `SHORTAGE_WRITE_OFF` and `WRITE_OFF` (set off by an approval, a cancel or a finding; the actor may be an owner, who cannot sign for Schedule X). The SAH-80 types (`COUNTER_SALE` and others) are not in the ledger check list yet. **If the architect's final list differs, a forward migration replaces `guard_stock_ledger_schedule_x()` (one array) and the guardrail table lists it.** The tech lead should note that the list as written means a Schedule X dispatch, receipt, return, adjustment or consumption by a person always needs the signer on every ledger line of that movement (both lines of a two-line move).
- Existing tests insert ledger rows with `USER` and no signer; none uses a Schedule X product, so they are not affected.

### 18.3 I11a · an approval request cannot become APPROVED without its decisions
- **Trigger** `trg_approval_request_guard_approve`, BEFORE UPDATE, `when (old.status = 'PENDING' and new.status = 'APPROVED')`; function `pharmacy.guard_approval_request_approve()`. `guard_approval_request_update` (1360) is not replaced and still runs.
- **Rule:** every `approval_request_level` row of the request with `applies = true` must have an `approval_decision` row with the same level and `decision = 'APPROVED'`. **Message:** `approval request needs an approved decision for each level that applies`, 23514.
- **Why no lock is needed:** both tables are insert-only (grants and deny triggers), so a row seen here cannot disappear. A decision from another open transaction is not seen, which fails safe (refused; retry after its commit). The service already locks the request.
- **Deliberate gap:** a request with no level rows passes (vacuous), so the existing direct update in `PharmacyWpDRulesIT:351` (a request made by `Sah79Support.approvalRequest`, which writes no level rows) still passes. The service always writes the level rows at submit. A request inserted directly with status APPROVED is not covered (an INSERT cannot have level rows yet); `ck_approval_request_level_pending` already ties the status to `current_level`.

### 18.4 I11b · the rule-set pointer only moves forward
- **Trigger** `trg_approval_rule_set_guard_forward`, BEFORE UPDATE, `when (new.current_version_id is distinct from old.current_version_id)`; function `pharmacy.guard_approval_rule_set_forward()`.
- **Rule:** the new version must be a version of the same tenant and unit with a `version_no` higher than the old one. **Message:** `approval rule set can only move to a newer version`, 23514. Versions are insert-only, so no lock. An update that leaves the pointer alone (version counter, bookkeeping) is not touched.

### 18.5 m-3 and n-1 · `ck_vendor_payable_settled`
- Replaced with `SETTLED_BY_CREDIT` exactly when `credited_paise = amount_paise`, and `OPEN` only when `credited_paise < amount_paise or amount_paise = 0`. Pattern of `1230`: `drop constraint if exists`, `add constraint ... not valid`, then `validate constraint` inside a `do` block that turns a `check_violation` into a WARNING (the constraint then stays NOT VALID and still checks every new or changed row). The table is empty on a fresh database. The constraint name is unchanged, so the tests that match it still match. The service must set SETTLED_BY_CREDIT in the same update that brings `credited_paise` to `amount_paise` (it already must, because `guard_vendor_payable_update` and the old check both ruled it).

### 18.6 m-4 · indent moves are forward only after APPROVED
- **Trigger** `trg_indent_guard_forward`, BEFORE UPDATE, `when (old.status in ('APPROVED','PARTLY_DISPATCHED','DISPATCHED','RECEIVED') and new.status is distinct from old.status)`; function `pharmacy.guard_indent_forward()`. `guard_indent_write` (1500) is not replaced: both must accept, so the 1500 rules (final states, identity, moves before APPROVED) are unchanged.
- **Allowed:** APPROVED to PARTLY_DISPATCHED, DISPATCHED or CANCELLED; PARTLY_DISPATCHED to DISPATCHED, RECEIVED or CLOSED; DISPATCHED to RECEIVED or CLOSED; RECEIVED to CLOSED. **Message** (the same as 1500): `indent cannot go from <a> to <b>`, 23514.
- **Contract against design note (they disagree; the contract wins).** The contract has no indent state table. What it says: dispatch is allowed only from APPROVED or PARTLY_DISPATCHED (`pharmacyDispatchIndent`) and gives PARTLY_DISPATCHED (back-order open) or DISPATCHED; cancel is allowed only from WAITING_APPROVAL or APPROVED with nothing dispatched (`pharmacyCancelIndent`), so **no cancel from PARTLY_DISPATCHED** (the review's wish for one is not in the contract; the 1500 guard already refuses it and stays that way); the return acceptance "may become RECEIVED or CLOSED". Section 14.1 allowed any of the four to any of the four, including RECEIVED back to PARTLY_DISPATCHED for a back-order dispatched after a receipt. That cannot happen under the contract, because a RECEIVED indent cannot be dispatched. Section 14.1 is marked superseded.
- **Open point for the architect** (also in the handoff): the contract says the RECEIVED status carries a chip "back-order open", yet allows a dispatch only from APPROVED or PARTLY_DISPATCHED. A back-order after a receipt therefore needs either "the status stays PARTLY_DISPATCHED while a back-order is open" or "dispatch also accepts RECEIVED with a back-order". In the second case the database must allow RECEIVED to PARTLY_DISPATCHED again (one forward migration, one line). Until the architect decides, the database follows the contract text.

### 18.7 m-5 · a store with stock cannot be switched off

- **The SAH-78 switch-off tests** (the `has_stock` rule, `StoreServiceTest`, `OpenImportAndResendTest`, `PharmacyHardeningImportIT`) are not affected: the service rule fires first, and a store without balance rows passes the trigger.

## 20. Round 5 hardening (DEC-082; `V2026_12_17_1740__pharmacy_round_5_hardening.sql`)

### 20.1 Short-supply-only debit note (java deviation 1)
- **Rule.** A debit note with **no live `STOCK_RETURN` line** (every live line is `SHORT_SUPPLY`; "live" means `removed = false`) may go `CREATED` or `PICKED` to `CREDIT_NOTE_RECEIVED`, and may take a `debit_note_credit` insert in those two states. A note with goods (at least one live `STOCK_RETURN` line) still needs `HANDED_OVER` first, in both places.
- **Three places refused it, not two.** (1) the status guard `guard_debit_note_write()`, (2) `guard_debit_note_credit_insert()`, and (3) the check `ck_debit_note_handed_over_status` (1420: `status not in ('HANDED_OVER','CREDIT_NOTE_RECEIVED') or handed_over_at is not null`), which would refuse a `CREDIT_NOTE_RECEIVED` row with no hand-over time. A short-supply-only note has no goods, no representative and no hand-over time, and `ck_debit_note_handed_over` ties those columns together, so the hand-over data cannot be invented. The check is now `status <> 'HANDED_OVER' or handed_over_at is not null`. It is weaker than before, so every existing row passes (added NOT VALID, then validated in the same file; the validate cannot fail). ### 20.3 L16 · `ck_stock_ledger_system_types`
- **Check** on the ledger parent: `actor_kind = 'USER' or txn_type = 'EXPIRY_QUARANTINE'`. ### 20.4 m-7 · which paths are serialised against a store switch-off
Section 18.7 and the comment in `1720` (lines 268 to 272) say "the posting service locks the store row (shared) before it writes a balance". That is wrong: **`StockPosting` takes no store lock.** The applied file is not edited. The correct statement is in section 4 of `1740` and in the catalogue comment on `pharmacy.guard_store_inactive_stock()` (replaced with `comment on function`). Section 18.7's "Race" paragraph is superseded by this one.
- **Serialised:** the write services take the store row `FOR UPDATE`, re-read its status, and then call `StockPosting`. A switch-off takes the same row `FOR UPDATE`. They cannot interleave.
- **Not serialised, by design:** the approval handlers (`onApproved`: purchase order, receipt, debit note, adjustment), which post when the last level approves, and the read sweep that quarantines expired stock. The approval request is locked first (ADR-029 P5); they take no store lock.
- **Residual:** a switch-off that races an approval-driven posting or the sweep can commit an `INACTIVE` store that then holds stock. The trigger `trg_store_guard_inactive_stock` reads a snapshot, and the balance insert takes only a key-share lock on the store (it does not conflict with the status update). Stock is not lost (balances and ledger are intact) and the store can be switched on again; the service rule `has_stock` refuses the usual switch-off first. Closing it needs a store `FOR SHARE` ahead of the request lock (a lock-order change for the architect), not a database change.

### 21.1 D-5 · `approval_request.rule_version_id` is nullable
- **Decision (tech lead, SAH-78 handoff 19 Nov 13:15 and 13:55).** Before an owner saves a rule set, the engine applies the served Standard default (versionNo 0). That default has **no row** in `pharmacy.approval_rule_version`, so the request cannot name a version. `rule_version_id = null` means "the Standard default (version 0)". A saved rule set still stores its version id as before.
- **Foreign key kept.** `fk_approval_request_rule_version (tenant_id, rule_version_id)` is a plain (MATCH SIMPLE) composite key: when any referencing column is null the check is skipped. `tenant_id` is never null, `rule_version_id` null skips it, so a null version needs no rule row. A non-null id must still exist for the same tenant.
- **Guard trigger checked.** `guard_approval_request_update()` (1360, created once, line 100) tests `new.rule_version_id is distinct from old.rule_version_id`. `is distinct from` treats null = null as equal and null against a value as a change: a null version stays null on every update, and a version can never be added or removed after insert ("approval request identity cannot change", 23514).
- **Everything else that reads the column.** Searched every migration: `rule_version_id` appears only in `1360` (the column, the foreign key, the guard). No view, function, check or index uses it. `guard_approval_request_approve` (1720), the decision guard and the `approval_request_level` copy do not read it. So nothing else is replaced. The index list is unchanged (no index on the column).
- **Messages.** None new. A non-null id that does not exist still fails `fk_approval_request_rule_version` (SQLSTATE 23503). A null id no longer fails the old `null value in column "rule_version_id"` (23502).
- **For the java-developer.** Map the column as nullable (`UUID`, no primitive; a null-safe read). Read "version 0 / Standard" from `rule_version_id is null`. The `approval_request_level` rows are still written (the copy of the default's levels), so the inbox "Rule" text works the same.
