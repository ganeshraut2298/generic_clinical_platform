## Rules kept
Additive and forward-only. No `V2026_12_08_*` file and no merged migration was edited. Nothing is dropped, renamed or rewritten. The only changes to existing tables are new columns (all nullable or with a constant default), one relaxed NOT NULL (`ipd.deposit.mode`), new checks that every existing row satisfies, extended column grants, and seed updates to the global `opd.medicine` rows. Global table files never mention the clinic column (validate rule). Every new clinic table: `tenant_id uuid not null default platform.current_tenant()` with FK to `platform.tenant`, `ENABLE` + `FORCE` row level security, policy for `sahaj_app` on `platform.current_tenant()`, first index column `tenant_id`, composite keys `(tenant_id, id)` for every reference inside the module and to `patient.patient`, no foreign key across modules, money `bigint` paise, no hard delete (no DELETE grant on any new table), `revoke all` then minimal grants.

## Clinic tables, opd
**`opd.emr_record` (existing, partitioned) + 3 columns** (catalog-only change, applies to every partition): `print_language` null in (EN, MR, HI); `paper_size` null in (A4, A5); `form_refs jsonb not null default '[]'` (array, <= 16 KB). `grant update (print_language, paper_size, form_refs)` added. No new index (read with the record). RLS, partitions and other grants unchanged.

**`opd.emr_form`** (ADR-022 item 5 plus idempotency): `id`, `tenant_id`, `form_key` `^f_[a-z2-7]{10}$`, `name` 1-80, `starter_key` null FK `emr_form_starter`, `status` ACTIVE/RETIRED, `live_version_no >= 0` (0 = never published), `draft_version_no >= 1`, `draft_state` NONE/DRAFT/WAITING_APPROVAL/SENT_BACK, `draft_definition jsonb` null (object, numeric `schemaVersion`, array `fields`, <= 256 KB), `sent_back_reason` null 1-300, `submitted_at/by` null, **`idempotency_key`, `request_hash`** null, `revision`, created/updated stamps.
- Keys: PK `id`; unique `(tenant_id, form_key)`, `(tenant_id, id)`, `(tenant_id, idempotency_key)`; unique index `(tenant_id, lower(name))` (H15; also serves the forms list in name order, at most 100 rows).
- State checks: `draft_version_no = live_version_no + 1`; `(draft_state = 'NONE') = (draft_definition is null)`; a form is never empty (`live_version_no >= 1 or draft_definition is not null`); `sent_back_reason` set iff SENT_BACK; `submitted_at/by` together and set when WAITING_APPROVAL; idempotency key and hash together.
- Grants: select, insert; update only `name, status, live_version_no, draft_version_no, draft_state, draft_definition, sent_back_reason, submitted_at, submitted_by, revision, updated_at, updated_by`. No delete (retire is a status). Policy: one `for all` policy.

**`opd.emr_form_version`**: `id`, `tenant_id`, `form_id`, `version_no >= 1`, `definition jsonb` (<= 256 KB, same shape check), `approved_by/at` null together, `published_at`, `published_by`. Unique `(tenant_id, form_id, version_no)` and `(tenant_id, id)`; composite FK `(tenant_id, form_id)` to `emr_form`. **Immutable**: select and insert policies only, grants select/insert, trigger on UPDATE/DELETE/TRUNCATE. Kept for ever.

**`opd.treatment_course_counter`**: `tenant_id` PK, `last_no >= 0`. One row per clinic; upsert-increment under the row lock gives TC-n without gaps from concurrency (gaps from rollbacks allowed). Added to the ADR list (the ADR allowed a counter row or `max+1` under a lock; the counter is simpler and cannot race).

**`opd.treatment_course`**: `id`, `tenant_id`, `course_no >= 1`, `patient_id` (composite FK `patient.patient`), `kind` (DENTAL, ANC, CHEMO, SURGERY, REHAB), `unit` (SITTING, VISIT, CYCLE, STEP, SESSION; **the pair is a check**: DENTAL-SITTING, ANC-VISIT, CHEMO-CYCLE, SURGERY-STEP, REHAB-SESSION), `name` 1-120, `note` null 1-300, `doctor_membership_id` (no FK), `started_on`, `origin_record_id` + `origin_record_created_at` (null together; no FK because `emr_record` is partitioned), `status` ACTIVE (check allows ACTIVE only; widen later by migration), `idempotency_key` + **`request_hash`** (null together), `revision`, stamps.
- Keys: PK `id`; unique `(tenant_id, course_no)`, `(tenant_id, id)`, `(tenant_id, idempotency_key)`. Index `ix_treatment_course_tenant_patient (tenant_id, patient_id, created_at desc)` serves `GET /emr/courses?patientId=`.
- Grants: select, insert; update only `status, revision, updated_at, updated_by` (the course has no edit endpoint; its revision moves with its sittings).

**`opd.treatment_course_sitting`**: `id`, `tenant_id`, `course_id` (composite FK), `sitting_no >= 1`, `encounter_kind` (OPD, DAY_CARE, IPD), `add_option_key` `^[A-Z][A-Z0-9_]{1,39}$` (the fixed option list is in code), `planned_date` null, `items text[]` (0-20 texts of 1-200, by function `opd.treatment_sitting_items_valid`), `charge_paise` 0..10,000,000,000, `note` null 1-300, `opd_visit_id` null (composite FK `opd.visit (tenant_id, id)`), `ipd_admission_id` null (no FK), `admission_requested`, `done_at` null, `idempotency_key` + **`request_hash`** (null together), stamps. Status PLANNED/TODAY/DONE is computed on read.
- Checks that encode ADR-022 D12: `admission_requested = (encounter_kind in ('DAY_CARE','IPD'))`; a visit only on an OPD sitting; an admission only on a DAY_CARE or IPD sitting.
- Keys: unique `(tenant_id, course_id, sitting_no)` (also the in-order read of a course), `(tenant_id, id)`, `(tenant_id, idempotency_key)`; partial unique `(tenant_id, opd_visit_id)` and `(tenant_id, ipd_admission_id)` where not null.
- Grants: select, insert; update `encounter_kind, add_option_key, planned_date, items, charge_paise, note, opd_visit_id, ipd_admission_id, admission_requested, done_at, updated_at, updated_by`. No delete; a sitting number is never reused.

## Clinic tables, billing
**`billing.receipt_counter`**: `tenant_id` PK, `last_no bigint >= 0`, `updated_at`. Grants select, insert, update. Upsert-increment under the row lock, in the payment transaction.

**`billing.course_payment`** (append-only; select/insert grants and policies; `platform.deny_audit_mutation` trigger on UPDATE/DELETE/TRUNCATE, as `billing.payment`): `id`, `tenant_id`, `course_id` (no FK), `patient_id` (composite FK `patient.patient`), `receipt_no bigint >= 1`, `type` (VISIT_PAYMENT, FULL_BALANCE, PART_PAYMENT, ADVANCE, IPD_DEPOSIT), `mode` (CASH, UPI, CARD), `amount_paise` 100..10,000,000,000 and a multiple of 100, `against_sitting_id` null (required when IPD_DEPOSIT), `against_label` 1-80, `use_credit`, `idempotency_key` not null `^[A-Za-z0-9_-]{8,64}$`, `request_hash` not null, `recorded_by`, `recorded_at`.
- Keys: unique `(tenant_id, receipt_no)`, `(tenant_id, idempotency_key)`. Indexes: `(tenant_id, course_id, recorded_at)` (account, ledger, earmarked deposits), `(tenant_id, recorded_at)` (day closing expected cash, revenue by mode, H3).

**`billing.course_credit_transfer`** (append-only, same protections): `id`, `tenant_id`, `course_id`, `sitting_id`, `admission_id` (all opaque), `amount_paise` 100..100,000,000 and a multiple of 100, `transferred_by`, `transferred_at`. Unique `(tenant_id, admission_id)` and `(tenant_id, sitting_id)`; index `(tenant_id, course_id)`.

**`billing.bill_item` (existing) + `source_kind`** null in (`EMR`), **`source_key`** null 1-40; both null or both set; partial unique `(tenant_id, bill_id, source_key)` where `source_key is not null`. `bill_item` already grants select, insert, update, delete (SAH-10), so the qty update and the removal of an EMR line need no grant change. Old and counter lines stay null/null and the EMR sync never touches them.

Partial unique `(tenant_id, treatment_course_sitting_id)` where not null; index `(tenant_id, treatment_course_id)` where not null. `grant insert (the two columns)`; update unchanged (set at admission only).

## Tenant scope and RLS
All new clinic tables (`emr_form`, `emr_form_version`, `treatment_course_counter`, `treatment_course`, `treatment_course_sitting`, `receipt_counter`, `course_payment`, `course_credit_transfer`): `ENABLE` + `FORCE`, policy `to sahaj_app` on `platform.current_tenant()`; append-only/immutable ones have a select policy and an insert policy and no update/delete policy. Existing tables keep their policies. The two new global tables have no clinic column and no RLS (the validate rule is satisfied because their files never contain the clinic column name).

## Backward compatibility (previous app version against the new schema)
Yes. Every new column on an existing table is nullable or has a constant default, so old inserts and updates work: `opd.medicine` (read only), `opd.emr_record` (column list inserts; `form_refs` defaults `'[]'`), `billing.bill_item` (old inserts leave both source columns null), `ipd.admission` (insert grant is column-level, old column list still valid), `ipd.deposit` (old insert gives `source = 'DESK'` and a mode, which the new check accepts). The only behaviour change old code can see: a COURSE deposit has `mode = null`, which an old reader of `ipd.deposit` would not expect; that row can only be written by the new version, so the old version never sees one unless it is run against data written by the new one (a rollback after use). Flyway and the new column privileges are the only dependencies.

## Deviations from the ADR "Data needed" list and open points (each is small; none changes a contract field)
1. **Added `idempotency_key` + `request_hash` to `emr_form`, `treatment_course`, `treatment_course_sitting`** (null together). The contract requires `Idempotency-Key` with `409 idempotency-conflict` on `POST /emr/forms`, `POST /emr/courses` and `POST .../sittings`; the conflict needs the hash. The ADR listed the key only for course and sitting, and not for forms.
2. **Added `opd.treatment_course_counter`** (the ADR allowed counter row or `max+1` under a lock).
3. **Payment maximum:** the ADR text says "<= ₹1,00,00,000"; `billing.yaml` says `maximum: 10000000000` paise (₹10 crore). The column check follows the contract (10,000,000,000). Architect: fix the ADR text or the contract; the DB bound is only a backstop.
4. **Carry to IPD is capped at ₹10,00,000 by the database** (`course_credit_transfer.amount_paise <= 100,000,000`), because the merged `ipd.deposit` has `ck_deposit_amount <= 100,000,000` and the carried deposit is inserted in the same transaction. If a course holds more earmarked credit, the application must carry at most ₹10,00,000 (the rest stays on the course), or the human decides to widen `ck_deposit_amount` (a widening migration, precedent `ck_visit_type`). I did not drop that constraint (rule: stop on anything that drops).
5. **Check `admission_requested = (encounter_kind in ('DAY_CARE','IPD'))`** is stricter than the ADR prose (it follows D12: DAY_CARE and IPD options set it true, OPD false). The application must set it when it switches the kind before a link.
6. **The FormBuilder palette has 24 types** (it also has "Pain scale 0-10", `pain`); ADR-022 D11 lists 23 (`EmrFormFieldType` has no pain scale). No starter uses it, so the seed is unaffected; the definition is not type-checked in SQL. Architect to confirm whether PAIN_SCALE is added.
7. **Starter settings:** the mockup stores department and part per template and the other form settings are the builder's current ones; the seed stores the template's department list, part ASSESSMENT and the builder's initial visit types, fill roles, language (English + Marathi) and approval (on). The Morse form's only use is the place IPD_WARD (no department); GCS and MLC also use the place EMERGENCY.
8. **`Metformin 500 mg SR`** is not in the medicine master; no default seeded (see above).
9. `treatment_course.status` allows ACTIVE only (no other state is defined in phase 3).
10. Java must treat `ipd.deposit.mode` as nullable (COURSE rows) in every deposit read, DTO and the IPD bill ("From treatment course TC-n").

## Correction V2026_12_13_1010 (DEC-051 Q1, QA triage M3): starter score rules use `kind`
- **Reason.** The seed `V2026_12_10_1020` wrote the two score rules of the `diabetic_foot` starter as `{"type": "NUMBER_BELOW"|"CHOSEN_COUNT_BELOW", "fieldKey", "threshold", "points"}`. The strict form model (`EmrFormModel.ScoreRule(kind, fieldKey, threshold, points)`) and `docs/api/opd.yaml` (`required: [kind, fieldKey, threshold, points]`) name the key `kind`, so using or reading that starter failed (500 on the form screens, 3 QA tests). Human answer in DEC-051 Q1: forward migration.
- **Change.** `V2026_12_13_1010__opd_emr_form_starter_score_rule_kind.sql` renames the nested key `type` to `kind` inside `definition.fields[].score.rules[]` of the row `starter_key = 'diabetic_foot'` only (the only starter with rules; `gcs` and `morse` have `"rules": []`). Field `type` (SCORE, NUMBER, ...) and every other key are not touched. `jsonb` functions rebuild the array in the same order. Idempotent (a rule that already has `kind` is skipped, the `where` finds nothing on a second run). Seed data only: no clinic or patient row is touched.
- **Immutable trigger.** `opd.emr_form_starter` refuses UPDATE for every role (`trg_emr_form_starter_immutable`). As in `V2026_11_24_1000` (seed correction on a guarded table), the migration disables that one trigger, updates, enables it again, all in the one Flyway transaction (rollback leaves it enabled). A final `do` block fails the migration if any starter rule still lacks `kind` or the trigger is not enabled. The `no_truncate` trigger is not touched. The starter stays immutable for the application and for hand edits.
- **Not rewritten.** A clinic form (`opd.emr_form`, `emr_form_version`) already copied from the old starter keeps the old key (clinic data, versions are immutable). No such rows are expected outside test data; if any exist in a real environment, the owner must decide how to correct them.
- **Backward compatibility.** Data only, no schema change. Old app code that read `type` would break, but the Java model already requires `kind`.
